# Урок 13. Layouts і поля: з чого складається форма задачі та issue

*Після уроку ти розумієш, що таке layout у Zoho Projects, з яких секцій і полів він складається,
як прив'язується до проєкту і чим приватний layout відрізняється від публічного. Для QA це
фундамент: статуси задач, кастомні поля, Blueprint і workflow rules живуть на конкретному layout,
і налаштування на «чужому» layout у проєкті мовчки не спрацьовує.*

---

## 13.1. Що таке layout і навіщо він

**Layout** — це дизайн форми. Він визначає, які поля бачить людина, коли створює чи редагує задачу
або issue, у якому порядку, в яких секціях, які поля обов'язкові й що в них стоїть за
замовчуванням. Одна компанія веде різні процеси: розробку, онбординг співробітників, розбір
інцидентів. Кожному потрібні свої поля. Layout дає кожному типу роботи свою форму замість однієї
величезної, де половина полів завжди порожня.

Як це влаштовано в Zoho Projects:

```
Портал
└── модуль: Projects · Task · Issues · Time Log · Phase · User
    └── layouts модуля: Standard Layout, кастомні, приватні копії
        └── проєкти, прив'язані до layout (у кожного проєкту — один task layout)
            └── задачі проєкту: поля і статуси беруться з layout його проєкту
```

З цієї схеми випливають три речі, на яких тримається весь урок:

1. **Поле створюється в порталі, а видно його там, де воно стоїть у layout.** Одне кастомне поле
   може стояти в кількох layouts, а може — в жодному.
2. **Статуси задач живуть у layout** — у полі **Status**. Не «в проєкті» і не «в порталі». Два
   проєкти на різних layouts мають різні набори статусів.
3. **Автоматизація задач прив'язана до layout.** Workflow rule для задач обирає layout (правила
   за датою взагалі не можна запускати на "All Layouts"), Blueprint будується на конкретному
   layout. Правило, зібране на одному layout, не бачить задач проєкту, що працює на іншому.

Де це в інтерфейсі: **Setup → Customization → Layouts**. Угорі — вкладки модулів **Projects**,
**Task**, **Issues**, **Time Log**, **Phase**, **User**; праворуч — кнопка **Create Layout**. На
цій же сторінці — перемикач **Make private layouts as a default for all the new projects** (про
нього — у розділі про приватні layouts). Сусідні пункти меню **Customization**: **Modules and
Tabs**, **Fields**, **Layout Rules**, **Task Templates**, **Invitation Templates**.

У цьому уроці — layouts задач та issues. Layouts проєктів, фаз, time logs і користувачів
влаштовані за тим самим принципом.

### Standard Layout і плани

Кожен портал починає зі **Standard Layout**. Його можна редагувати скільки завгодно, але не можна
видалити чи пересунути в списку. Зміни в Standard Layout отримують усі проєкти, прив'язані до
нього.

Що на якому плані Zoho Projects (за довідкою Zoho):

| дія | план |
|---|---|
| редагувати Standard Layout, переставляти дефолтні поля | усі плани |
| створювати нові layouts (клонувати) | Premium і Enterprise |
| створювати й редагувати кастомні поля | Enterprise |

У тріалі Zoho One кастомні поля і Blueprint створюються, тож функції рівня Enterprise тобі
доступні. Якщо на клієнтському порталі не бачиш кнопки чи типу поля — перевір по черзі план,
права користувача і налаштування порталу. Тільки після цього це може бути дефект.

### Чим layout не є

- **Не custom view.** View вирішує, *які записи* показати в списку; форму він не змінює.
- **Не Blueprint.** Blueprint керує *переходами* між статусами. Самі статуси та їхні типи задає
  layout.
- **Не доступ до проєкту.** Хто бачить проєкт, вирішує Project Access (Public / Private).
  Приватний layout обмежує інше: хто може користуватись самим layout і його автоматизацією.

Поверх layout працюють ще **layout rules** — правила, що змінюють форму залежно від уже введених
значень. Це окремий механізм; тут ми будуємо те, на чому він стоїть.

## 13.2. Секції

**Секція** — логічна група полів усередині layout. Вона робить довгу форму читабельною: секція
«Schedule Reviews» з полями «First Review», «Second Review», «Third Review» читається краще, ніж
ті самі три дати, розкидані між пріоритетом і описом.

Правила секцій:

- у кожному layout є дефолтна секція (у layout задач довідка називає її **Task Information** — у
  ній стоїть поле **Status**);
- нову секцію додаєш, перетягнувши компонент **Add Section** (частина довідки називає його
  **Add New Section**) з лівої панелі редактора в основну;
- нові секції отримують імена `Untitled Section 1`, `Untitled Section 2`… — у тріалі (27.09.2026,
  перевірено на двох різних layouts) перша ж додана секція вже має номер `1`, а не голе
  `Untitled Section`; перейменовуєш, клікнувши заголовок секції — відкривається панель **Section
  Information** з полем **Section Name**;
- порожню секцію зберегти не можна — у ній має бути хоча б одне поле;
- іконка видалення секції з'являється лише тоді, коли з неї прибрані всі кастомні поля.

Око QA: поле, додане без окремої секції з нормальною назвою, легко опиняється в
`Untitled Section 1`. Таку назву бачитиме кожен, хто створює задачу. Перейменуй секцію до того, як
форму побачать люди.

## 13.3. Дефолтні поля задачі і поле Status

Дефолтні поля є в кожному task layout:

| поле | Editable | Removable |
|---|---|---|
| Owner | No | No |
| Status | Yes | No |
| Start Date | No | No |
| Due Date | No | No |
| Duration | No | No |
| Priority | No | No |
| Completion Percentage | No | No |
| Work Hours | Yes | Yes |
| Completed on | No | No |

Як читати таблицю:

- **Editable** — чи можна змінювати *властивості* поля в layout (наприклад, список статусів), а не
  значення в задачі. Значення Priority у задачі ти змінюєш завжди; назву і набір значень самого
  поля Priority змінити не можна.
- **Removable** — чи можна прибрати поле з layout.
- Переставляти дефолтні поля можна всі, на будь-якому плані.

Подивись на **Work Hours**: Yes / Yes. Фраза «дефолтні поля не редагуються і не видаляються, крім
Status» неповна — Work Hours теж виняток. Звіряй правило з таблицею, а не з підсумковим реченням
над нею.

Інші знайомі поля задачі теж стандартні. Наприклад, **Billing Type** (чи оплачується робота) —
стандартне поле задачі, а не тип кастомного поля. У тріалі (26.09.2026) серед стандартних полів
задачі також є **Associated Team**, **Tags**, **Rate Per Hour**, **Reminder**, **Recurrence**, а
коли в порталі увімкнений Project Budget — ще й поля бюджету (**Budgeted Hours**, **Cost Budget**,
**Revenue Budget** тощо). Таблиця вище — не весь список, а тільки поля, важливі для цього уроку.

### Поле Status: статуси живуть у layout

Статуси задач налаштовуються тут: **Setup → Customization → Layouts → Task → твій layout → поле
Status**.

Покроково:

1. Відкрий layout у редакторі (клікни його в списку).
2. Наведи курсор на поле **Status** і клікни іконку-олівець **Edit** (посилання «Customize» з
   іконкою шестерні тут не показується, у тріалі 26.09.2026) — відкриється бічна панель **Status**
   із вкладками **Properties** / **Permissions** / **Rules**.
3. На вкладці **Properties**: **+ Add Status** — з'явиться рядок для нового статусу. Впиши назву,
   обери тип і колір.
4. Окремої кнопки збереження нема: редактор автозберігає зміни (позначка «Task Configuration Auto
   saving...»), тож **Apply changes** чи **Save Layout** тут не натискаєш.

Типів статусу два — **Open** і **Closed**. Їх не видалити, і кожен новий статус належить до
одного з них. Тип читає система, назву — людина:

- задача в статусі типу Closed вважається завершеною: після оновлення сторінки вона зникає з view
  `All Open`, у `All Tasks` показується закресленою і рахується у відсотку виконання;
- статус із «готовою» назвою, але типу Open, система вважає незавершеним. Проєкт із шаблону
  `Software Development` приносить статус `UAT Done` саме такого типу.

У тріалі стандартний набір статусів задач такий: `Open`, `In Progress`, `In Review`,
`To be Tested`, `On Hold`, `Delayed`, `Closed`, `Cancelled`.

**Set Default Status** — статус, у якому народжується кожна нова задача. Цей елемент стоїть одразу
під **+ Add Status**. У тріалі дефолт одного разу опинився на `Closed` під час редагування статусів
(випадковий клік чи зсув при додаванні статусів — причину не встановлено), і кожна нова задача
народжувалась закритою: відсоток проєкту поїхав, а форма створення нічого не попередила. Після
будь-якої правки статусів створи пробну задачу й подивись, у якому статусі вона з'явилась.

Статуси належать layout. Статус, доданий у layout одного проєкту, в іншому проєкті з'явиться,
тільки якщо той працює на тому самому layout.

## 13.4. Кастомні поля

Кастомне поле — твоє поле для даних, яких нема серед стандартних: тип ризику, відділ, рівень
ескалації. Обмеження:

- створювати й редагувати — тільки на плані Enterprise;
- до 300 кастомних полів задач на портал; за довідкою, поля не дублюються: поле, що вже є в
  порталі, не створюють удруге, а беруть з **Available Fields**;
- частина типів підтримує позначку **PII** і шифрування (**Encrypt Field**) — про це в розділі
  про безпеку.

Типи полів (назви — як у довідці Zoho; у палітрі **New Fields** підписи коротші, наприклад
`Single-Line`, `Multi-Line`, `Pick List`):

| тип | що зберігає | примітка |
|---|---|---|
| Single Line Text | один рядок тексту | PII / Encrypt |
| Multi-Line Text | кілька рядків | PII / Encrypt |
| Pick List | одне значення зі списку | значення задаєш сам |
| Multi-Select Pick List | кілька значень зі списку | |
| User Pick List | одного користувача | наприклад, рецензент |
| Multi User Pick List | кількох користувачів | |
| Date, Date & Time | дату; дату з часом | |
| Number | число, до 19 цифр | PII / Encrypt |
| Decimal | дробове число, до 14 цифр перед комою | PII / Encrypt |
| Currency, Percentage | суму; відсоток | Currency — PII / Encrypt |
| Phone, Email, URL | телефон; адресу; посилання | PII / Encrypt |
| Long URL | посилання до 1000 символів | для URL, довших за 250 символів |
| Checkbox | так / ні | |
| Formula Field | значення, обчислене з інших полів | |
| Lookup Field | значення поля з іншого модуля | див. нижче |
| Connect Module | зв'язок із записом іншого модуля | див. нижче |
| Summary | агрегат із дочірніх записів | див. нижче |

Три спеціальні типи з кінця палітри:

- **Lookup Field** показує в задачі значення поля з модуля Projects — наприклад, дату завершення
  проєкту біля кожної задачі. Не більше 5 lookup-полів на модуль задач; створене поле не
  редагується; воно рахується в загальний ліміт кастомних полів.
- **Connect Module** зв'язує запис із записом іншого модуля (фази, задачі, issues, кастомні
  модулі) і за бажання показує в цільовому записі список пов'язаних (**Enable Related List**).
  Одне поле — один цільовий модуль; запис не можна зв'язати сам із собою.
- **Summary** рахує агрегат по дочірніх записах: Sum, Average, Min, Max, Count, Record Count,
  Unique Count. Буває тільки в layouts проєктів, фаз і задач (у задачі можна, зокрема, згорнути
  дані підзадач: усе дерево або лише прямі підзадачі). До 5 на модуль; редагувати не можна —
  тільки видалити і створити заново.

Formula, Lookup і Summary мають спільну рису, важливу для QA: їхнє значення **не вводить людина**.
Тестуєш їх перерахунком: змінив джерело — перевір результат.

### Покроково: додати кастомне поле

1. **Setup → Customization → Layouts → Task**, клікни layout — відкриється редактор.
2. Перетягни тип поля з панелі **New Fields** у потрібну секцію — на порожню, ще не заповнену
   секцію перетягуй, цілячи в саму секцію (на її заголовок чи в межі її рамки), а не в порожнє
   тло редактора: у тріалі (27.09.2026) поле, кинуте повз наявну секцію, не приєднується до неї, а
   створює свою нову `Untitled Section N` із цим одним полем — тоді простіше перейменувати саме її,
   ніж намагатись перенести поле.
3. Одразу відкривається панель властивостей поля: назву, для списків — значення, за потреби —
   значення за замовчуванням і обов'язковість (mandatory).
4. У тріалі (27.09.2026) кнопок **Add to Layout** і **Save Layout** для цього кроку нема: редактор
   зберігає поле в layout відразу після того, як ти вписав назву чи властивість і клікнув поза
   полем вводу (той самий автозбереж, що й для статусів, підрозділ 13.3). Кнопка **Cancel** тут не
   з'являється — щоб прибрати щойно додане поле, познач його і натисни **Remove this Field** у
   тій самій панелі (дані ще ніде не встигли з'явитись, тож прибирати нема чого).

**Що побачиш:** поле в секції редактора одразу зі своїм новим підписом, а через кілька секунд —
у формі **Add Task** кожного проєкту, що працює на цьому layout.

### New Fields і Available Fields

- **New Fields** — типи для створення нового поля.
- **Available Fields** — поля, які вже є в порталі, але не стоять у цьому layout. Перетягуєш поле
  з цієї панелі (у ній є пошук) — і воно в layout. Так одне поле працює в кількох layouts без
  дублів.

Назва поля спільна для всіх layouts: перейменуєш в одному — зміниться всюди. Так само спільні
значення pick list: змінене значення, як попереджає продукт, з'явиться в усіх layouts і задачах із
цим полем. **Інші властивості — свої в кожному layout.** Поле може бути обов'язковим в одному
layout і необов'язковим в іншому, з різними значеннями за замовчуванням. Для QA це окремий ризик:
«те саме поле» в різних проєктах поводиться по-різному.

### Прибрати з layout ≠ видалити з порталу

| дія | де | що з даними |
|---|---|---|
| прибрати поле з layout | редактор: наведи на поле → хрестик → підтверди → **Save Layout** | дані зберігаються; поле йде в **Available Fields** і повертається звідти |
| видалити поле з порталу | **Setup → Customization → Fields**: наведи на поле → кошик → підтверди | дані поля втрачені назавжди |

Два винятки з «прибрати безпечно»: поле типу **Formula**, прибране з layout, продукт не дає
повернути з **Available Fields**; а поле, яке використовує layout rule, не прибереш і не видалиш, поки
воно стоїть у правилі.

Поле, пов'язане з понад 1000 задач, видалити не вийде. На сторінці **Setup → Customization →
Fields** видно всі поля модуля: де вони стоять і які не стоять у жодному layout; є пошук.

### Значення pick list

Змінити значення: у редакторі наведи на поле → **Edit Properties** → наведи на значення → зміни →
**Done** → **Apply changes** → **Save Layout**. Видалити можна тільки невикористане значення:

- значення, що використовується в іншому layout, не видалиться;
- значення, що стоїть у задачах, спершу треба перемапити на інше значення, і лише потім
  видалити.

### Скільки полів ще можна створити

Посилання **Remaining Fields** у лівій панелі редактора, під компонентом секції, показує, скільки
полів кожного типу вже створено і скільки лишилось.

## 13.5. Створити, змінити, видалити layout

### Покроково: створити layout

1. **Setup → Customization → Layouts**, вкладка **Task**.
2. **Create Layout** праворуч угорі.
3. Обери базовий layout (поле на кшталт **Clone from existing layout**) — новий стане його копією.
   Найчастіше це `Standard Layout`: чистий старт без полів і статусів з інших процесів.
4. Впиши **Layout Name**.
5. **Create**.

**Що побачиш:** новий layout у списку вкладки **Task**; проєктів під ним поки нема. Клікни його —
відкриється редактор з секціями, полями і статусами базового layout.

### Змінити layout

У редакторі перетягуєш поля і секції, змінюєш порядок, властивості полів (обов'язковість,
значення за замовчуванням), список статусів. Назву layout змінюєш прямо в редакторі. Кожну сесію
змін закінчуй **Save Layout**.

### Видалити layout

1. **Setup → Customization → Layouts → Task**.
2. Наведи курсор на layout → іконка видалення → **Delete** → підтверди. Діалог попереджає: разом із
   layout видаляється вся прив'язана до нього автоматизація задач (Blueprint, Workflow Rules, Email
   Alerts, Codex Scripts).

Standard Layout не видаляється. Кастомний видаляється, тільки коли до нього не прив'язано жодного
проєкту, зокрема архівного чи в кошику: спершу переведи проєкти на інший layout.

### Що легко відкотити, а що — ні

| дія | відкат |
|---|---|
| додати поле чи секцію, змінити порядок | легко: прибрав — і все |
| прибрати поле з layout | легко: поле в **Available Fields**, дані на місці |
| перейменувати поле | легко, але назва зміниться в усіх layouts одразу |
| додати статус | легко; після цього перевір **Set Default Status** |
| видалити значення pick list, що стояло в задачах | важко: задачі вже переведені на інше значення |
| видалити кастомне поле з порталу | неможливо: дані втрачено |
| змінити Standard Layout | зачіпає всі проєкти, прив'язані до нього |
| видалити layout | важко: разом із layout зникає його автоматизація задач; новий layout, прив'язки і правила доведеться збирати заново |

## 13.6. Прив'язка layout до проєкту

У кожного проєкту один task layout. Прив'язати його можна з двох боків.

**З боку проєкту** — у полі **Task Layout** форми нового проєкту або в деталях наявного проєкту.
Опція приватної копії, за довідкою, є в обох місцях: знімай її, якщо проєкт має стати саме на
обраний layout.

**З боку layout:**

1. **Setup → Customization → Layouts → Task**.
2. Наведи курсор на layout і натисни іконку плюс біля назви → **Associate Projects**.
3. Обери проєкти (до 5 за раз) або шаблони проєктів.
4. Підтверди → **Associate**.

**Що побачиш:** назви прив'язаних проєктів під layout у списку. Це найнадійніший спосіб з'ясувати,
на якому layout працює проєкт.

Що відбувається при прив'язці:

- нова прив'язка **замінює** попередню — проєкт іде зі старого layout;
- поля старого layout, яких нема в новому, зникають з проєкту, але **дані в них зберігаються**:
  повернеш layout — повернуться і значення;
- якщо в новому layout нема статусів, у яких стоять задачі проєкту, то при зміні layout у деталях
  проєкту Zoho попросить зіставити їх зі статусами нового layout (**Map Status & Associate
  Project**). При прив'язці з боку layout діалог каже інше: поточний layout проєкту буде
  перезаписано, а дані кастомних статусів синхронізуються. Що саме стається зі статусами на цьому
  шляху, перевір;
- автоматизація старого layout (workflow rules, Blueprint), очікувано, на задачі проєкту більше не
  діє: вона прив'язана до layout, а не до проєкту. Перевір це окремим тестом.

Шаблон проєкту теж прив'язується до layout. Тому проєкт, створений із шаблону, отримує layout
шаблону разом з його статусами — так у проєкт приходять незвичні статуси на кшталт `UAT Done`.

Не плутай з layouts **проєктів** (вкладка **Projects**): за довідкою Zoho, коли проєкт переходить
на інший project layout, дані полів, яких нема в новому layout, **втрачаються**. Для task layouts
дані зберігаються. Однакова дія — різні наслідки в сусідніх модулях.

## 13.7. Приватні layouts

**Приватний layout** доступний тільки користувачам проєктів, прив'язаних до нього. Разом із ним
приватною стає його автоматизація задач: Blueprint, Workflow Rules, Email Templates, Email Alerts,
Webhooks і Custom Functions на цьому layout бачать лише учасники цих проєктів.

### Перемикач «приватна копія за замовчуванням»

На сторінці **Setup → Customization → Layouts** є перемикач **Make private layouts as a default for
all the new projects**. Коли він увімкнений, у формі нового проєкту у випадайці **Task Layout** уже
позначено **Create a private copy of this layout**:

- галочка стоїть — проєкт отримує **власну копію** обраного layout, названу за проєктом;
- галочку знято — проєкт прив'язується до самого обраного (публічного) layout.

У цьому тріал-порталі в кожного проєкту своя приватна копія task layout і своя копія issue layout —
так поводиться портал з увімкненим перемикачем (його стан перевір сам). Standard Layout тут
фактично шаблон, з якого роблять копії.

Не дивуйся, якщо той самий layout підписаний по-різному. У тріалі приватна копія проєкту
`QA Training Project – …` у списку **Layouts** мала коротку назву з літер назви проєкту (`QT`), а в
редакторах Workflow Rules і Task Blueprint показувалась повною назвою проєкту. Шукай layout
проєкту за назвою проєкту під layout у списку.

### Покроково: зробити наявний layout приватним

Можна тільки для layout, до якого прив'язаний рівно один проєкт; архівні проєкти і проєкти в
кошику теж рахуються.

1. **Setup → Customization → Layouts → Task**.
2. Наведи курсор на layout → **Make as Private Layout**.
3. Онови сторінку.

**Що побачиш:** layout перемістився в кінець списку — там стоять приватні.

### Покроково: зробити приватний layout публічним

Приватний layout стає публічним, щойно до нього прив'язують ще один проєкт. У тріалі (27.09.2026)
це не один безперервний майстер, а дві окремі дії:

1. У кінці списку, на приватному layout, наведи курсор → іконка **•••** → **Associate Project**.
2. Перша спроба на приватному layout відкриває не форму вибору проєкту, а попередження **Make as
   Public**: «Projects cannot be associated to a Private layout. Would you like to convert this
   layout to public and proceed?» з кнопками **Convert to Public** / **Cancel**. Натисни
   **Convert to Public** — layout одразу стає публічним, але жодного нового проєкту ще не додано.
3. Повтори **•••** → **Associate Project** (тепер уже на публічному layout) — відкриється форма
   **Associate Projects with Layout**. Впиши назву потрібного проєкту: пошук пропонує тільки ті
   проєкти, яких на цьому layout ще нема (проєкт, що вже на ньому, пошук не покаже — це нормально,
   не помилка). Обери проєкт → **Save**.

**Що побачиш:** рядок layout показує обидва проєкти (другий і далі — за лічильником на кшталт
`+1`); layout публічний.

### Що це означає для QA

- Правило, зібране на `Standard Layout`, у проєкті з приватною копією **не спрацює**: у проєкту
  інший layout. Перед тестом будь-якої автоматизації дивись, на якому layout проєкт.
- Статуси і поля, додані в копію одного проєкту, не з'являються в інших проєктах.
- Копія — окремий layout: зміни секцій, полів і статусів Standard Layout отримують лише проєкти,
  прив'язані до нього самого, а не до копій. Спільне для порталу — назви полів і значення pick
  list — змінюється всюди.
- Колега, що не бере участі в проєкті, може не бачити його приватного layout і правил на ньому.
  «У мене такого правила нема» може бути правдою.

## 13.8. Layouts для issues

Той самий принцип діє для форми issue: **Setup → Customization → Layouts → Issues**. Є Standard
Layout; кастомні layouts клонуються з нього (**Create Layout** → базовий layout → **Layout Name** →
**Create**), прив'язуються до проєктів і шаблонів, бувають приватними. У тріалі в кожного проєкту
своя приватна копія issue layout. Standard Layout і layout, до якого прив'язані проєкти, видалити
не можна.

Дефолтні поля Standard Layout для issues у тріалі: Reporter, Created Time, Associated Team,
Assignee, Tags, Last Closed Time, Last Modified Time, Due Date, Status, Severity, Release Phase,
Affected Phase, Module, Classification, Reproducible, Flag, Rate Per Hour, Cost Per Hour.

Чого там нема — і це важливо:

- **Priority** — у issues нема пріоритету; його роль грає **Severity** зі шкалою `None`,
  `Show stopper`, `Critical`, `Major`, `Minor`;
- **Type** — тип проблеми описують **Classification** і **Module**;
- milestones — замість них **Release Phase** і **Affected Phase**.

Дефолтні поля issue не редагуються і не видаляються, тільки переставляються. За довідкою, Module,
Severity, Reproducible і Classification можна перейменувати, а дефолтна секція в тріалі (27.09.2026)
називається **Issues Information** (множина, а не «Issue information» з довідки).

### Кастомне поле issue

Додаєш так само, і так само без окремих кнопок: тип із **New Fields**, властивості одразу у
відкритій панелі — редактор зберігає значення на льоту, без **Add to Layout** чи **Save Layout**
(підрозділ 13.4 вище). Серед властивостей поля issue в тріалі (27.09.2026) є:

- **Accessible in Web to Issues Form** — один прапорець, а не трійка «Project Users / Client
  Users / All Users». Знятий за замовчуванням; коли позначений, поле можна винести на публічну
  форму (**Setup → Issue Tracker → Web To Issues Form**, для обраного проєкту). Задокументованого
  окремого рівня «видно тільки учасникам проєкту» немає — поле або в межах порталу (прапорець
  знятий), або ще й на публічній формі (прапорець позначений);
- **Add to resolution** — ще один прапорець поруч (у тріалі не перевірялось, для чого саме він
  використовується — найімовірніше, позначає поле як частину підсумку рішення issue);
- значення за замовчуванням і **Mandatory**.

Раніший опис доступу як трьох рівнів (Project Users / Client Users / All Users) у цьому порталі не
підтвердився — керуй очікуваннями клієнта за фактичним чекбоксом, а не за назвою з довідки.

Порядок кастомних полів змінюєш перетягуванням і фіксуєш кнопкою, яку довідка називає **Save Field
Order**. Базові типи
ті самі, що в задачах: текст, списки, користувачі, дати, числа, валюта, відсоток, контакти,
чекбокс.

### Статуси issue і їхній workflow

У полі **Status** issue layout (у довідці і в мапінгу імпорту воно зветься `Status & Workflow`) є
**Set Default Status**, **+Add Status**, ті самі типи Open і Closed — і те, чого нема в задачах:
**workflow статусів**. Для кожного статусу задаєш наступні дозволені статуси, наприклад
`Open → In progress → Closed`. У layout має лишатися хоча б один статус типу Open і один типу
Closed; дефолтний статус не видаляється. Зверни увагу на регістр: у тріалі статус issue —
`In progress`, з малої літери. У критеріях і при імпорті регістр важить.

| | layout задач | layout issues |
|---|---|---|
| статуси | у полі Status, типи Open / Closed | те саме + дозволені наступні статуси |
| жорсткий порядок переходів | Blueprint | workflow статусів у layout |
| пріоритет | Priority | нема; є Severity |
| доступ до кастомного поля | довідка такої властивості не описує | Project Users / Client Users / All Users |
| дефолтні поля | Status і Work Hours можна налаштовувати | тільки переставляти; 4 поля можна перейменувати |

## 13.9. Безпека і приватність даних

Інструменти:

1. **Encrypt Field** — значення шифрується на бекенді. Доступно для текстових і числових полів,
   Phone, Email, URL, Long URL і Currency.
2. **PII** — позначка, що поле містить персональні дані (ім'я, телефон, e-mail). Потрібна для
   вимог захисту даних: організація знає, де в неї персональні дані.
3. **Доступ до поля issue** — Project Users, Client Users або All Users (публічна форма).
4. **Приватні layouts** — обмежують, хто взагалі користується формою та її автоматизацією.

Око QA:

- поле з доступом **Project Users** не повинен бачити клієнтський користувач;
- на **Web To Issues Form** мають потрапляти тільки поля з доступом **All Users**;
- для зашифрованого поля перевір, де воно ще працює. Продукт попереджає, що в критеріях custom view
  для зашифрованих полів доступні лише `Is` і `Is not`; правила, пошук і експорт перевір у тріалі,
  перш ніж обіцяти щось клієнту;
- кількість зашифрованих полів обмежена (повідомлення продукту: «Only 10 fields can be
  encrypted.») — ще одна межа для тесту.

## 13.10. Найкращі практики — і чому саме вони

| практика | навіщо |
|---|---|
| групуй складні форми секціями | людина заповнює форму блоками, а не шукає поле серед двадцяти |
| використовуй layout rules для логіки форми | форма показує тільки те, що потрібно в цій ситуації |
| тримай одну конвенцію назв кастомних полів | назва спільна для всіх layouts і видна в критеріях, звітах, шаблонах листів |
| регулярно переглядай **Available Fields** | зайве поле з'їдає ліміт і плутає: `Severity` і `Risk Severity` в одному порталі |
| приватні layouts — для чутливих процесів і закритих команд | форму і її автоматизацію бачать лише учасники |
| не видаляй кастомні поля без певності | видалення з порталу знищує дані; прибрати з layout — безпечно |

## 13.11. Як це тестувати

**Що може зламатися:**

- проєкт працює не на тому layout, на якому налаштована автоматизація чи поля;
- поле обов'язкове в одному layout і необов'язкове в іншому, а всі думають, що «поле одне»;
- **Set Default Status** стоїть на статусі типу Closed — задачі народжуються закритими;
- статус з «готовою» назвою має тип Open — відсоток виконання бреше;
- перейменування поля чи значення зачіпає всі layouts, критерії і звіти;
- перехід проєкту на інший layout ховає поля (дані лишаються) і вимагає зіставити статуси;
- приватна копія розійшлася з «оригіналом»: у кожного проєкту свої статуси і поля;
- поле з доступом Project Users видно клієнту; на публічній формі зайве поле.

**Позитивні, негативні, граничні перевірки:**

- **позитивні:** поле з'являється у формі **Add Task** проєкту на цьому layout; значення
  зберігається; значення за замовчуванням підставляється;
- **негативні:** поля нема в проєкті на іншому layout; обов'язкове поле не дає зберегти порожню
  задачу; невикористане поле не видно у формі;
- **граничні:** Number — 19 і 20 цифр; Decimal — 14 цифр перед комою; Long URL — понад 250 і біля
  1000 символів; порожнє значення в полі з дефолтом;
- **переходи:** прибрати поле і повернути; перевести проєкт на інший layout і назад; змінити
  статус за замовчуванням.

**Як доводити:** скриншот редактора layout (секції, поля, властивості), скриншот списку layouts з
проєктами під кожним, скриншот форми **Add Task** і картки задачі до і після зміни. Для перевірок
зі збереженням даних — одна й та сама задача до і після.

Приклад тест-кейсу у форматі, який використовує документ:

- **Title:** Поле, прибране з layout, повертається разом з даними
- **Precondition:** layout `QA Fields Sandbox` прив'язаний до проєкту `Layout Sandbox Project`; у
  задачі `Sandbox task 1` поле `Build Number` = `1.4.2`.
- **Steps:**
   1. У редакторі `QA Fields Sandbox` прибери `Build Number` (хрестик → підтверди → **Save
      Layout**).
   2. Відкрий `Sandbox task 1` і форму **Add Task** цього проєкту.
   3. Відкрий у редакторі **Available Fields**.
   4. Перетягни `Build Number` назад → **Add to Layout** → **Save Layout**.
   5. Відкрий `Sandbox task 1`.
- **Expected Result:** після кроку 2 поля нема ні в задачі, ні у формі; після кроку 3 поле є в
  **Available Fields**; після кроку 5 у задачі `Build Number` = `1.4.2`.
- **Actual Result:** *[що сталося насправді]*
- **Pass/Fail:** *[ ]*
- **Notes/Attachments:** скриншоти після кроків 2, 3 і 5.

## 13.12. Типові помилки

**1. Налаштував на Standard Layout, а проєкт живе на приватній копії.** Поле не з'являється,
правило не спрацьовує. Спершу подивись, під яким layout стоїть проєкт.

**2. Видалив поле з порталу замість прибрати з layout.** Дані поля втрачено. Щоб сховати поле з
форми, достатньо хрестика в редакторі.

**3. Не перевірив Set Default Status після правки статусів.** Нові задачі народжуються в
несподіваному статусі, аж до `Closed`.

**4. Додав статус «не в той» layout.** Статус з'явився в одному проєкті, а в сусідньому його нема:
у кожного проєкту своя копія.

**5. Вважав, що властивості поля однакові всюди.** Назва спільна, а обов'язковість і значення за
замовчуванням — свої в кожному layout.

**6. Створював поле, що вже існує.** Поля не дублюються; візьми наявне з **Available Fields** —
і дані в ньому будуть одні на всі layouts.

**7. Лишив `Untitled Section 1`.** Технічна назва секції потрапляє до всіх, хто створює задачі.

**8. Назвав багом відмову видалити layout.** Layout з прив'язаними проєктами не видаляється за
задумом: спершу переведи проєкти.

**9. Змінив Standard Layout «для одного проєкту».** Зміна дісталась усім проєктам, прив'язаним до
нього.

**10. Шукав Priority чи Type в issues.** Їх нема: є Severity, Classification і Module.

### Симптом → причина

| симптом | найімовірніша причина |
|---|---|
| нове поле є в редакторі, але нема у формі **Add Task** проєкту | проєкт на іншому layout (приватна копія) або не натиснуто **Save Layout** |
| workflow rule чи Blueprint не спрацьовує в одному проєкті, а в іншому працює | правило на layout, до якого прив'язаний лише другий проєкт |
| кнопки **Create Layout** нема або вона неактивна | план порталу нижче за Premium або недостатньо прав |
| нові задачі народжуються в `Closed` | **Set Default Status** стоїть на статусі типу Closed |
| задача зі статусом `Done` рахується незавершеною | у статусу тип Open |
| статус є в одному проєкті, а в іншому нема | у проєктів різні layouts (кожен на своїй копії) |
| після зміни layout проєкту зникли поля | нового layout нема цих полів; дані збережені, повернуться з полями |
| Zoho просить зіставити статуси при прив'язці | у новому layout нема статусів, у яких стоять задачі |
| layout не видаляється | до нього прив'язані проєкти, зокрема архівні чи в кошику |
| значення pick list не видаляється | воно використовується в іншому layout або стоїть у задачах |
| поле не видаляється з порталу | воно пов'язане з понад 1000 задач |
| **Make as Private Layout** нема біля layout | до layout прив'язано більше одного проєкту (архівні й ті, що в кошику, теж рахуються) |
| прибране поле формули не знаходиться в **Available Fields** | поле Formula після прибирання з layout повернути не можна |
| іконки видалення секції нема | у секції ще є кастомні поля |
| не вдається зберегти секцію | секція порожня |
| перейменував поле в одному проєкті — змінилось у всіх | назва поля спільна для всіх layouts |
| поле обов'язкове в одному проєкті і необов'язкове в іншому | властивості поля свої в кожному layout |
| кастомного поля issue нема на **Web To Issues Form** | у поля доступ не **All Users** |

## 13.13. Що варто запам'ятати

1. Layout — форма: поля, секції, обов'язковість, значення за замовчуванням, а для задач ще й
   статуси.
2. У кожного проєкту один task layout; що в ньому, те і бачать задачі проєкту.
3. Автоматизація задач прив'язана до layout: правило на чужому layout у проєкті мовчить.
4. У тріалі кожен проєкт має приватну копію layout; перевіряй, на якій копії налаштовуєш.
5. Дефолтні поля задачі тільки переставляються; виняток — Status (статуси) і Work Hours.
6. Тип статусу (Open / Closed) читає система; **Set Default Status** перевіряй після кожної
   правки.
7. Назва поля спільна для всіх layouts, інші властивості — свої в кожному.
8. Прибрати поле з layout безпечно (крім Formula); видалити з порталу — назавжди.
9. Перехід проєкту на інший task layout ховає поля, але зберігає дані і вимагає зіставити статуси.
10. У issues нема Priority і Type; є Severity (`None`…`Minor`), Classification, Module, Release /
    Affected Phase.
11. Поле issue має доступ Project Users / Client Users / All Users; на публічну форму йдуть лише
    поля All Users.

**13.14.**
1. **Setup → Customization → Layouts → Task** → **+** біля `Standard Layout` → **Associate
   Projects** → обидва sandbox-проєкти → **Associate**; якщо Zoho просить зіставити статус
   `Blocked` — обери `Open` (**Map Status & Associate Project**).
2. Під `QA Fields Sandbox` порожньо → наведи курсор → іконка видалення → **Delete** → підтверди.
3. **Setup → Customization → Fields** → по черзі п'ять полів → кошик → підтверди.

13.12. Зіставлення статусу `Blocked` → `Open` теж лишиться в задачі.

- [ ] пояснюєш, що таке layout у Zoho Projects і як він пов'язаний із проєктом, задачами і
  автоматизацією;
- [ ] за хвилину знаходиш, на якому task layout і issue layout працює будь-який проєкт;
- [ ] розрізняєш Standard Layout, кастомний і приватний layout і знаєш, що з кожним можна робити;
- [ ] пояснюєш таблицю дефолтних полів задачі, зокрема винятки Status і Work Hours;
- [ ] налаштовуєш статуси в layout і після кожної правки перевіряєш **Set Default Status**;
- [ ] пояснюєш, чому тип статусу важливіший за назву;
- [ ] без підглядання створюєш секцію і кастомні поля різних типів;
- [ ] розрізняєш New Fields і Available Fields, «прибрати з layout» і «видалити з порталу»;
- [ ] знаєш, що назва поля спільна для всіх layouts, а інші властивості — свої в кожному;

  копією;
