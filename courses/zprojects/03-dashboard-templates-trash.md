# Урок 3. Дашборд, Gantt, пошта, кошик і шаблони проєктів

*Після цього уроку ти читаєш дашборд проєкту й розумієш, звідки беруться його числа, налаштовуєш
віджети, знаєш два види Gantt, розумієш, як Projects приймає роботу поштою, проводиш проєкт через
архів, кошик і відновлення, а також створюєш проєкт із шаблону й бачиш, що саме він копіює. Для QA
це уроки недовіри: відсоток, графік і «відновлено» треба перевіряти, а не приймати на віру.*

---

## 3.1. Дашборд проєкту

У кожного проєкту є вкладка **Dashboard** — набір віджетів із показниками проєкту. Документ
називає головне, що там видно: прогрес проєкту, план проти факту, підсумок залогованого часу,
показники команди (Top 5 Go-getters, Top 5 Issues Fixers тощо), прострочене й найближче. Дашборд
можна налаштовувати: переставляти віджети, змінювати склад, керувати тим, хто що бачить.

### Віджети за замовчуванням

У тріалі на дашборді нового проєкту 17 віджетів: Task Status, Overdue Work Items, Team
Status, Issues Status, Project Tags Cloud, Weekly Digest, Top 5 Go-getters, Top 5 Issues Fixers,
Phase Status, Time Logs Summary, Upcoming Events, Upcoming Work Items, Today's Work Items, Task
Progression Chart, Planned Vs Actual, а також віджети із задачами й issues членів команди (Tasks /
Issues for My Team members). Що показують ті, які описує довідка Zoho:

| група | віджет | що показує |
|---|---|---|
| прогрес | **Task Status**, **Issues Status**, **Phase Status** | скільки задач, issues, фаз відкрито і скільки закрито |
| команда | **Team Status** | для кожного учасника — прострочені й відкриті роботи та що в нього на сьогодні |
| | **Top 5 Go-getters** | п'ятеро з найбільшою кількістю закритих задач |
| | **Top 5 Issues Fixers** | п'ятеро з найбільшою кількістю закритих issues |
| звіти й графіки | **Task Progression Chart** | скільки задач на якому відсотку виконання |
| | **Weekly Digest** | стан задач, списків задач, фаз і bugs за тиждень (тиждень вибирається) |
| | **Time Logs Summary** | billable і non-billable години, залоговані командою |
| робота на черзі | **Today's Work Items** | що заплановано на сьогодні |
| | **Overdue Work Items** | незавершене з минулим строком |
| | **Upcoming Events** | події цього тижня |

Решту (Planned Vs Actual, Upcoming Work Items, Project Tags Cloud, віджети команди) довідка окремо
не описує — їхній зміст дізнаєшся, відкривши. «Planned vs Actual» довідка згадує лише як частину
віджета Budget Status.

Назви в довідці й у продукті де-не-де розходяться: довідка пише «Timesheet Summary», «Issue
Status», «Task Progress Chart», а в продукті — **Time Logs Summary**, **Issues Status**, **Task
Progression Chart**. Довідка описує й віджет **Budget Status** для проєкту з бюджетом; у тріальному
проєкті з Budget Type = None його серед віджетів не було.

### Звідки береться відсоток проєкту

Документ пише: прогрес проєкту рахується «за виконанням задач, за вагою або за відсотком
виконання». Це три методи налаштування порталу **Setup → Portal Configuration → Project & Budget →
Project Completion Percentage** (довідка Zoho):

| метод | як рахує |
|---|---|
| за кількістю задач та issues | частка закритих задач та issues серед усіх; «закритість» визначає **тип статусу** (Open чи Closed) |
| за відсотком виконання задач і кількістю закритих issues | середнє відсотків виконання задач; issues рахуються закритими чи ні |
| за вагою | кожна задача й issue має вагу з числового поля layout; відсоток — зважений |

Загальна формула з довідки:

```
Project % = (Σ(Task Completion% × Task Weightage) + Σ(100% × Closed Issue Weightage))
            / (Σ Task Weightage + Σ Issue Weightage)
```

Звідси висновок: коли в проєкті 5 задач і статусу `Done` дали
**тип Closed**, одна задача в `Done` піднімає проєкт з 0% до 20%. Той самий `Done` з типом Open
виглядав би виконаним, а рахувався б відкритим. **Дашборд показує не назву статусу, а його тип.**

### Як налаштовувати дашборд

**Видалити віджет**: наведи курсор на віджет → **•••** (More Actions) → **Delete** → у вікні
`Do you want to delete this widget?` постав прапорець
`I understand that once deleted, this action cannot be undone.` (без нього кнопка **Delete**
неактивна) → **Delete**. **Видалений віджет не відновлюється**: його можна хіба що додати заново
як новий (див. нижче), без старих налаштувань — вибирай свідомо.

**Додати віджет**: **Add Widget** угорі праворуч. Спершу вибираєш тип —

- **Chart** — графік на кшталт звіту;
- **Numbers (KPI)** — одне число, яке видно з першого погляду;
- **Embedded** — вбудований вміст за посиланням (у довідці — Embed URL);

далі відкривається **Widgets Gallery**: кнопка **Create Widget** (власний віджет: назва,
налаштування звіту — Report Settings, Criteria тощо) і готові зразки за модулями (для Numbers
(KPI) — Task Widgets: **Total Tasks**, **Open Tasks**, **Completed Tasks**…; Issues Widgets; Phase
Widgets), кожен з кнопкою **Use this**. У тріалі **Use this** одразу додає віджет (повідомлення
`Widget Created.`) у кінець дашборда, а назву й налаштування потім міняють через **••• → Edit**.
У галереї типу **Chart**, крім звітів за модулями (Task Status Report, Issues Status Report, Phase
Status Report…), є група **System Widgets**: Weekly Digest, Team Status, Overdue Work Items, Today's
Work Items, Upcoming Work Items, Upcoming Events, Top 5 Go-getters, Top 5 Issues Fixers, Tasks for
My Team members, Issues for My Team members, Project Tags List, Project Tags Cloud, Timeline. Отже,
видалений системний віджет можна додати заново як новий.

**Змінити розташування і розмір**: у кожного віджета є ручка для перетягування і маркери розміру
по краях — віджети переставляються перетягуванням, розмір змінюється перетягуванням країв.
Перетягування одного віджета на місце іншого міняє їх місцями
(інші віджети на дашборді не зсуваються), і новий порядок лишається після повного перезавантаження
сторінки — це налаштування дашборда, а не тимчасовий стан сесії. У меню **•••** власного віджета є
**Edit**, **Clone** і **Delete**, у стандартного — лише **Delete**.

**Власні дашборди** (довідка Zoho): випадний список дашбордів над віджетами (**Project Dashboard**)
→ **+ Create Custom Dashboard** → назва, тип, рівень доступу → **Save**. Такий дашборд можна
поділити з людьми з правами **Full Access** (перегляд, зміни, поширення), **Editor** (зміна
віджетів без видалення й поширення) або **Viewer** (лише перегляд), клонувати, експортувати в PDF,
видалити (назавжди). Це і є
«налаштування видимості для різних ролей» з документа. Ще одне правило видимості: щоб бачити
віджет, людині потрібен дозвіл на перегляд відповідного модуля.

## 3.2. Gantt

Документ: Gantt показує графік і залежності; у компанії ним користуються передусім у проєктах
розробки, де результати плануються спринтами або йдуть водоспадом, одне за одним. Можливості за
документом: планування перетягуванням, порівняння з базовим планом (Baseline, лише Enterprise),
фільтри за власниками, датами, статусом, експорт у PDF і друк. На Gantt потрапляють лише проєкти з
датами початку й кінця.

У Projects **два** Gantt, і їх корисно не плутати:

| | Gantt проєктів | Gantt задач |
|---|---|---|
| де | **Projects** → перемикач виду → Gantt | проєкт → **Tasks** → перемикач виду → Gantt (або **Overview → Tasks** для всіх проєктів) |
| рядки | проєкти | списки задач і задачі |
| що видно | смуга проєкту, найраніша й найпізніша задачі, прострочене, відсоток | смуги задач, залежності, прогрес, власник, статус |
| хто не потрапляє | проєкти без Start Date або End Date | задачі без дат (Unscheduled) |

Що вміє Gantt задач (довідка Zoho):

- перетягни смугу задачі на інші дати — графік зміниться; потягни кінець смуги — задача
  подовжиться;
- залежність малюється лінією між кінцями двох смуг (типи залежностей і лаг — окрема тема);
- масштаб: Years, Quarters, Months, Weeks, Days, плюс кнопки **Zoom In** і **Zoom Out**;
- **скасування**: на смузі інструментів справа (smart bar: **Undo**, **Show Options**, **Baseline**,
  **Critical path**, **Timeline**, **Unscheduled Tasks**) кнопка **Undo** скасовує зміни дат,
  тривалості й залежностей — до п'яти останніх дій, поки ти не оновив сторінку й не пішов на
  інший екран;
- **Baseline** — знімок графіку для порівняння з поточним: план Enterprise, до 15 знімків на
  проєкт, у знімок потрапляють лише відкриті задачі з датами;
- критичний шлях, легенда кольорів, експорт у PDF (до 2 500 задач).

У тріалі кнопка **Baseline** на Gantt задач є: доки знімок не створено, панель пише
`No Baseline found. Create and compare the baseline from here..` і пропонує **Set Baseline**.
За довідкою функція належить до плану Enterprise.

## 3.3. Керування проєктом поштою

Документ: Projects дає створювати й оновлювати задачі, issues і статуси листами, завантажувати
документи і коментувати задачі чи події. Адреса (email alias) для кожного об'єкта — у його деталях;
пишеш лист у потрібному форматі — дія записується сама.

**Де адреси проєкту**. Відкрий проєкт →
**•••** біля назви (Other actions) → **Email Alias** (або правий клік по рядку проєкту в списку →
**Email Alias**). Там окремі адреси: **To Add Status**, **To Add Task**, **To Add Issues**, **To
Upload Document**, **To Add Forum** — вигляду `<портал>_<ID проєкту>@tasks.zohoprojects.eu`
(для статусу — без `tasks.`), біля кожної значок копіювання; клік по самому полю відкриває
поштовий клієнт. Своя адреса є й у коментарів проєкту (у панелі деталей — «To add Project Comment
via email»). За довідкою, свої адреси мають і список задач (на його сторінці деталей — «To add
Task via email to this Task list») і коментарі задачі чи issue («To add Task Comment via email» /
«To add Issue Comment via email»).

Далі — правила й синтаксис листів, як їх описує довідка Zoho.

**Умови.** Лист має йти з адреси, зареєстрованої в Zoho, і ти маєш бути учасником проєкту
(для не-учасників — лише в Enterprise з окремим налаштуванням пошти).

**Синтаксис задачі в темі листа:**

- на початку теми — пріоритет: `!` — Low, `!!` — Medium, `!!!` — High;
- дати у квадратних дужках: спершу початок, потім кінець, у форматі **mm-dd-yyyy**, наприклад
  `[11-29-2026][11-30-2026]`, або словами: `Today`, `Tomorrow`, `Next Monday` тощо;
- люди в **CC** стають виконавцями;
- вкладення (до 20 MB) потрапляють у документи задачі.

Приклад теми: `!!! Prepare regression checklist [10-05-2026][10-09-2026]`.

**Для форуму**: `[announcement]` або `[sticky]` на початку теми.

Для QA пошта — ще одна точка входу з власним парсером, і вона ламається інакше, ніж форма.
Найнебезпечніше місце — формат дат: портал показує дати як dd-MM-yyyy, а пошта чекає mm-dd-yyyy.
Лист із `[10-03-2026]` означає 3 жовтня, а не 10 березня, — і жодної помилки не буде.

## 3.4. Архів, кошик і остаточне видалення

У проєкту три «кінцеві» дії, і вони дуже різні:

| дія | де | що відбувається | як повернути |
|---|---|---|---|
| **Move to Archive** | меню рядка в списку проєктів | проєкт переходить на вкладку **Archived Projects** (у тріалі зі статусом Completed); дані на місці | меню рядка на вкладці **Archived Projects** → **Move to Active** |
| **Trash** | меню рядка в списку проєктів (у довідці — Trash Project) | проєкт іде в **Recycle Bin**, зникає зі списків | **Restore** у кошику протягом строку зберігання |
| видалити остаточно (**Delete Permanently**; стаття довідки про Recycle Bin називає кнопку просто **Delete**) | **Setup → Data Administration → Recycle Bin**, меню **•••** рядка | видалення назавжди | ніяк |

### Recycle Bin

Кошик — **Setup → Data Administration → Recycle Bin**. Туди потрапляють видалені проєкти, фази,
списки задач, задачі, issues, записи часу, шаблони проєктів. Колонки: **Name**, **Entity** (тип
об'єкта), **Project**, **Trashed By** (хто видалив), **Trashed Time**; угорі — кнопка **Empty
Recycle Bin**, у рядка — меню **•••** з **Restore** і **Delete Permanently**.

Правила (довідка Zoho):

- записи зберігаються **60 днів**, потім видаляються назавжди;
- **Portal Owner і адміністратори** можуть відновлювати й видаляти будь-що, зокрема видалене
  іншими, і лише вони очищають кошик повністю (**Empty Recycle Bin**); іншим користувачам потрібні
  дозволи профілю — на все, лише на своє або ні на що;
- відновлювати можна до 100 записів за раз;
- відновлення дочірнього об'єкта відновлює й батьківські (задача повертає свій список і фазу) —
  **крім проєкту**: поки проєкт у кошику, нічого з його вмісту окремо не відновиш — спершу
  відновлюють проєкт;
- якщо дочірній об'єкт пішов у кошик раніше за батьківський, відновлення батька дитину не
  повертає (так пише сама сторінка кошика в тріалі);
- і **Delete Permanently**, і **Empty Recycle Bin** просять поставити прапорець-підтвердження
  (`I understand that once deleted, the records cannot be recovered.` /
  `I understand the impact`) — без нього кнопка видалення неактивна;
- коли в кошик іде задача чи issue, їхні записи часу виключаються з підсумків і повертаються разом
  із ними при відновленні.

Наслідки в інших застосунках (довідка Zoho): задача, пов'язана з CRM, потрапляє і в кошик CRM;
задача, пов'язана з Zoho Desk чи Zoho Sprints, там лишається активною, а оновлення з них
застосуються лише після відновлення; записи часу, пов'язані з Zoho Books, прибираються з Books і
повертаються при відновленні.

Уважно з датами: частина статей довідки (про Kanban і Gantt задач, про Gantt проєктів) досі пише
«30 днів». Стаття про Recycle Bin уточнює: 60 днів для всього, що видалено після 25 листопада 2025
року, — і сам кошик у тріалі пише 60. Коли документація суперечить сама собі, джерело істини —
продукт, а суперечність варто зафіксувати.

## 3.5. Шаблони проєктів

Шаблон — готова структура проєкту: фази, списки задач, задачі. Документ пояснює, навіщо він
компанії: схожі впровадження (налаштування CRM, конфігурація Desk) повторюються, і шаблон
стандартизує їх.

### Два види шаблонів

| | готові шаблони Zoho | шаблони порталу |
|---|---|---|
| де | **New Project** → Template Gallery → **Predefined Project Templates** | **Projects → Project Templates** (і вкладка **Project Templates** у галереї) |
| хто створює | Zoho | ти: **New Project Template** або **Create Template** з меню проєкту |
| редагування | лише використання | можна змінювати, клонувати, видаляти |

Створення шаблону порталу (довідка Zoho): **Projects → Project Templates → New Project Template**
→ Project Layout → **Project Template Name** → **Choose from Projects** (з якого проєкту взяти
структуру) → за потреби **Add closed tasks as open tasks in the project template** → опис → **Add
Project Template**. За довідкою, у плані Premium можна мати до 20 шаблонів, в Enterprise — до 30.

### Що відбувається при створенні проєкту з шаблону

За довідкою: фази, списки задач, задачі й інша інформація шаблону копіюються в новий проєкт, а
дати зсуваються від **Start Date** нового проєкту. Приклад із довідки: у шаблоні задача A стартує
через 2 дні після початку і триває 5 днів; новий проєкт стартує 15-го — задача A буде з 17-го по
22-ге. Задачі в новому проєкті — нові, тому в них немає історії змін (Activity Stream).

Що робить готовий шаблон **Software Development**:

- **Use Template** у галереї створює проєкт одразу, без форми: з назвою шаблону
  (`Software Development`), стартом сьогодні, приватний; назву потім міняють у панелі деталей
  проєкту. Поле **Template** на формі нового проєкту пропонує лише шаблони порталу (у тріалі їх
  немає — `No matches found`);
- копіює 3 фази (Grooming or Planning stage, Development stage, QA or Testing phase) і 38
  задач у кількох списках; дати фаз і задач перераховує від старту проєкту (фази охоплюють
  приблизно пів року від старту);
- **усі задачі призначає на того, хто створив проєкт**;
- статуси копіює як є: 3 задачі одразу `Closed`, 4 — у статусі `UAT Done` з типом **Open**;
  тому новий проєкт, у якому ще ніхто нічого не зробив, показує 7% виконання, а перша фаза — 21%;
- статус `UAT Done` приїжджає разом із приватною копією layout, яку отримує новий проєкт;
- **End Date проєкту лишається рівною Start Date**, хоча фази розписані на півроку вперед;
- префікс задач генерується з назви (`SD1`; другий проєкт з таким шаблоном отримує `SD2`).

## 3.9. Як це тестувати

### Дашборд

- **Числа проти джерела.** Кожне число віджета звіряй з тим, що бачиш у списку: Task Status — з
  кількістю задач, Top 5 Go-getters — з тим, хто скільки закрив.
- **Тип статусу.** Зміни статус задачі на статус з типом Closed — відсоток проєкту й Task Status
  мають змінитися; на статус з назвою «Done», але типом Open, — відсоток не зміниться.
- **Графік читай критично.** У тріалі Weekly Digest для проєкту з 5 задачами показував стовпчик
  висотою 10: у ньому складені Created (5), Completed (1) і Still Open (4), а Completed + Still Open
  — це ті самі створені задачі. Можливо, так задумано (три серії на одному стовпчику), але вісь
  «Number of Items» підштовхує читати це як кількість. Такі речі записують як спостереження щодо
  зручності, а не як дефект.
- **Права.** Користувач без дозволу на модуль не бачить віджет цього модуля.
- **Незворотність.** Видалений віджет не відновлюється — перевір, чи є попередження перед
  видаленням (у тріалі є: вікно з обов'язковим прапорцем `I understand that once deleted, this
  action cannot be undone.`).

### Кошик і відновлення

- відновлений проєкт повертається з вмістом: задачі, статуси, документи, записи часу;
- ID проєкту й задач після відновлення ті самі;
- поки проєкт у кошику, його задачі не відновлюються окремо;
- користувач без дозволів на відновлення не може відновити чужий об'єкт;
- наслідки в інших застосунках, якщо є інтеграції (CRM, Books, Desk).

### Шаблони

- дати фаз і задач зсунуті від Start Date нового проєкту;
- **End Date** проєкту охоплює графік;
- які статуси прийшли разом із шаблоном і чи є серед них закриті;
- на кого призначено задачі;
- який layout отримав проєкт і що до нього прив'язано;
- опція **Add closed tasks as open tasks in the project template** справді відкриває закриті
  задачі.

### Пошта

Кожне правило синтаксису — окремий тест: `!`, `!!`, `!!!` і тема без маркера; дати в mm-dd-yyyy,
словами і в «портальному» dd-MM-yyyy; CC з учасником і з не-учасником; вкладення до 20 MB і
більше; лист з незареєстрованої адреси.

## 3.10. Типові помилки

**1. Шукати віджети Timesheet Summary і Budget Status.** У тріалі є **Time Logs Summary**, а
віджета Budget Status у проєкті без бюджету серед стандартних не було.

**2. Шукати стандартний віджет одразу після Add Widget.** Спершу треба вибрати тип (Chart, Numbers
(KPI), Embedded); системні віджети — у галереї **Chart**, група **System Widgets**.

**3. Видалити віджет «на хвилинку».** Видалені віджети не відновлюються; системний можна лише
додати заново, без колишніх налаштувань.

**4. Вірити відсотку, не знаючи методу.** Відсоток залежить від налаштування Project Completion
Percentage і від типів статусів.

**5. Шукати вкладку Trash чи Recycle Bin у списку проєктів.** Кошик — у **Setup → Data
Administration → Recycle Bin**.

**6. Плутати архів і кошик.** Архів — проєкт на місці, кошик — видалення з відкладеним кінцем.

**7. Натиснути Delete Permanently замість Restore.** Звідти не повертаються.

**8. Лишити назву, яку підставив шаблон.** **Use Template** називає проєкт іменем шаблону, а
завдання вимагає `Template-Based QA Project` — перейменуй у панелі деталей.

**9. Написати «призначив задачу на себе», коли це зробив шаблон.** Звіт описує те, що сталося, а
не те, що просило завдання.

**10. Писати дати в листі у форматі порталу.** Пошта чекає mm-dd-yyyy.

### Симптом → причина

| симптом | найімовірніша причина |
|---|---|
| немає віджета Timesheet Summary | він називається **Time Logs Summary** |
| немає віджета Budget Status | у проєкті без бюджету (Budget Type = None) його серед стандартних не було; довідка пов'язує його з бюджетом проєкту |
| **Add Widget** пропонує лише Chart, Numbers (KPI), Embedded | це перший крок; далі — Widgets Gallery з готовими зразками, системні віджети — у Chart → System Widgets |
| кнопка **Delete** у вікні видалення віджета неактивна | не поставлено прапорець `I understand that once deleted, this action cannot be undone.` |
| доданого віджета не видно | він додається в кінець дашборда — прокрути донизу |
| у меню стандартного віджета немає **Edit** | Edit і Clone є лише у власних віджетів |
| видалений віджет не повернути | видалені віджети не відновлюються; системний додай заново: **Add Widget → Chart → System Widgets → Use this** |
| відсоток проєкту стрибнув після зміни статусу | новий статус має тип Closed |
| задача в «Done», а відсоток не росте | у статусу `Done` тип Open |
| Weekly Digest показує вдвічі більше задач | стовпчик складає Created, Completed і Still Open |
| проєкту немає на Gantt проєктів | немає Start Date або End Date |
| задача не малюється на Gantt | у неї немає дат (Unscheduled) |
| кнопка undo на Gantt сіра | скасовувати нічого або сторінку вже оновлено |
| видаленого проєкту немає ніде в Projects | він у **Setup → Data Administration → Recycle Bin** |
| у кошику не знайти кнопку **Restore** | вона в меню **•••** рядка (там же Delete Permanently) |
| після **Use Template** одразу з'явився проєкт з назвою шаблону | так працює галерея: форми немає, назву міняють у панелі деталей |
| поле **Template** на формі проєкту пише `No matches found` | воно пропонує лише шаблони порталу, а готові шаблони Zoho беруться з галереї |
| задачу з видаленого проєкту не відновити | спершу відновлюють проєкт |
| немає кнопки Empty Recycle Bin чи Restore для чужого | ти не адміністратор або профіль не має дозволу |
| новий проєкт з шаблону одразу показує кілька відсотків | шаблон приніс задачі в закритих статусах |
| End Date проєкту з шаблону = Start Date | так поводиться тріал: рамки проєкту не перераховуються |
| задачі з шаблону вже призначені на тебе | готові шаблони призначають задачі на того, хто створив проєкт |
| під гридом задач `Total Count : #######` | дефект відображення лічильника в тріалі; рахуй за лічильниками груп у виді All Tasks |
| лічильник групи менший, ніж задач у списку шаблону | вид All Open не рахує закриті задачі; перемкнись на All Tasks |
| задача з листа отримала не ті дати | дати в темі сприйнято як mm-dd-yyyy |

# Розв'язки

**3.1.** У тріалі — 17 віджетів:

| група | віджети |
|---|---|
| прогрес | Task Status, Issues Status, Phase Status |
| команда | Team Status, Top 5 Go-getters, Top 5 Issues Fixers, Tasks / Issues for My Team members |
| звіти й графіки | Task Progression Chart, Weekly Digest, Time Logs Summary, Planned Vs Actual |
| робота на черзі | Today's Work Items, Overdue Work Items, Upcoming Events, Upcoming Work Items |
| інше | Project Tags Cloud |

Порожні в навчальному проєкті зазвичай ті, що залежать від даних, яких ще немає: Issues Status і
Top 5 Issues Fixers (немає issues), Phase Status (немає фаз), Time Logs Summary (немає записів
часу), Upcoming Events (немає подій), Project Tags Cloud (немає тегів). Порожній віджет — не
дефект, якщо даних справді немає.

**3.2.**

- а) 1 закрита з 5 → **20%**.
- б) Жодної закритої за типом → **0%**, хоча задача «виглядає виконаною».
- в) Закриті: 1 задача + 1 issue = 2 з 6 → **33%**.

Висновок: назва статусу для відсотка не важить нічого, тип — усе.

**3.3.** Кінцевий стан: на дашборді щонайменше на один стандартний віджет менше (наприклад, без
Project Tags Cloud), є твій віджет (наприклад, Numbers (KPI) `Total Tasks` з **Use this** у
Widgets Gallery, з числом, що збігається з кількістю задач на вкладці Tasks), порядок віджетів
змінено (Task Status і KPI у першому ряду; новий віджет спершу стоїть у кінці дашборда).
Скриншоти: «до» — стандартний дашборд; «після» — змінений. Якщо віджетів багато, кілька кадрів з
підписами — нормально.

**3.4.** Зразок абзацу (англійською, мовою документа):

> For a QA role the most useful widgets answer two questions: what can be tested now, and what is
> stuck. Task Status shows how the work is spread across statuses, and Overdue Work Items shows
> what has slipped. These numbers are only as good as the status setup behind them: the project
> percentage follows the status type, not its name, so a "Done" status with the Open type makes
> finished work look unfinished. I removed Project Tags Cloud because this project uses no tags,
> and added a Numbers (KPI) widget with the total number of tasks, which I checked against the
> task list.

Оцінюй свій абзац так: 3–5 речень; названо конкретні віджети; є «чому» для QA; є хоча б одна
перевірка числа проти джерела.

**3.5.** Кінцевий стан: `Sample Deletion Project` — серед Active Projects з тим самим ID, що й до
видалення, всередині `Marker task` у своєму статусі. Скриншот №1 — Recycle Bin із рядком проєкту
(Entity `Projects`, Trashed By — ти). Скриншот №2 — відновлений проєкт з вкладкою Tasks, де видно
маркер. Кошик після відновлення не містить цього проєкту.

**3.6.**

- **Move to Archive** — проєкт переходить на вкладку Archived Projects (статус `Completed`); дані
  на місці; повертається однією дією — **Move to Active** у меню рядка.
- **Trash** — проєкт іде в Recycle Bin, зникає зі списків; відновлюється протягом 60 днів, далі
  зникає сам.
- **Delete Permanently** — з кошика, назавжди.

Відновити проєкт, який видалив інший, можуть Portal Owner і адміністратори; іншим потрібен дозвіл
профілю на відновлення всього (з дозволом «лише своє» — тільки те, що видалили самі). Записи часу
видаленої задачі виключаються з підсумків і повертаються при її відновленні. Задача, пов'язана з
CRM, потрапляє і в кошик Projects, і в кошик CRM.

**3.7.** **Use Template** створює проєкт одразу з назвою `Software Development` — перейменуй його
в панелі деталей. Кінцевий стан: проєкт `Template-Based QA Project` зі структурою Software
Development:
фази з датами від сьогодні (3 фази), списки задач з задачами (38 задач),
усі задачі призначено на тебе шаблоном. Списки задач є — додавати не треба; у звіті так і
пишеш: «список задач є; задачі вже призначені на мене шаблоном». Скриншоти: вкладка Phases з
фазами й датами; вкладка Tasks зі списками й задачами. До звіту корисно додати числа (кількість
фаз, задач за лічильниками груп).

**3.8.** 7% — бо шаблон скопіював статуси задач: частина задач у проєкті одразу закрита, а
відсоток за методом «за кількістю» рахує закриті за типом статусу. Це властивість шаблону (і
метод підрахунку), а не зламаний підрахунок; у звіті — спостереження з рекомендацією: створювати
шаблони порталу з опцією **Add closed tasks as open tasks in the project template** або
перевіряти статуси після створення.

End Date = Start Date при фазах на півроку — а це вже розрив у самому продукті: дати фаз і задач
перераховано, рамки проєкту — ні. Проєкт не суворий, тож нічого не блокує, але звіти й Gantt
проєктів показують проєкт, що «закінчився» задовго до останньої фази. Це варто оформити як
дефект з кроками відтворення.

**3.9.**

(а) Приклади (дати в mm-dd-yyyy):

- `!!! Prepare regression checklist [10-05-2026][10-09-2026]`
- `! Review test data`
- `!! Update smoke suite [Tomorrow]`

(б) Пошта читає дати як mm-dd-yyyy: `03-10-2026` — це 10 березня, `05-10-2026` — 10 травня. Задача
отримає період з 10 березня по 10 травня 2026 — і ніхто не побачить помилки, поки не гляне на
дати. Пріоритет — Medium (`!!`).

(в) Наприклад: тема без маркера пріоритету (який пріоритет за замовчуванням?); `!!!!` (чотири
знаки); дата в dd-MM-yyyy, що існує і як mm-dd-yyyy; дата, якої не існує в mm-dd-yyyy (`13-01-2026`);
кінець раніше за початок; CC з людиною, яка не є учасником проєкту; вкладення понад 20 MB; лист з
адреси, не зареєстрованої в Zoho.

**3.10.** Очікуваний результат: перетягуєш смугу задачі на кілька днів вперед — у деталях
задачі Start Date і Due Date змінюються, Duration лишається той самий (наприклад, був 3 дні по буднях, лишається
3 дні, хоч календарна відстань зростає — новий діапазон зачепив вихідні). В Activity Stream одразу
з'являється запис під сьогоднішньою датою: «`<user>` has updated Start Date from `<стара дата>` to
`<нова дата>`. Hence, End Date changed from `<стара>` to `<нова>`» — з точним автором і обома
значеннями. Кнопка **Undo** на smart bar (іконка ліворуч від **Show Options**) одразу, без
перезавантаження сторінки, повертає смугу на попереднє місце. Після перезавантаження сторінки та
сама кнопка отримує атрибут `disabled` — скасувати вже не можна, що збігається з довідкою: undo
працює для останніх п'яти дій, поки не оновив сторінку й не пішов на інший екран. Для QA висновок:
«скасування» на Gantt — не страховка, а зручність у межах одного сеансу.

**3.11.** Приклад набору:

| # | Title | Expected Result |
|---|---|---|
| 1 | Trashed project appears in the Recycle Bin | listed with Entity Projects and Trashed By |
| 2 | Restored project keeps its ID and content | same ID; tasks, statuses, documents are back |
| 3 | Restored task brings back its task list | the task list is restored with the task |
| 4 | Task of a trashed project cannot be restored alone | the project must be restored first |
| 5 | Time logs of a trashed task leave the totals | totals drop on trash and return on restore |
| 6 | User with "restore own" permission cannot restore another user's item | restore not available for that item |
| 7 | Restore of more than 100 records at once | the limit is enforced with a clear message |
| 8 | Recycle Bin states the retention period | the screen shows 60 days |

Повністю — наприклад, кейс 2 (зразок у розділі 3.9). Оцінюй набір так: є хоча б одна перевірка
прав, одна перевірка вмісту, одна на межу і одна на порядок відновлення.
