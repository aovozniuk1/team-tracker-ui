# Урок 7. Pages і Forums: знання та обговорення в проєкті

*Після уроку ти додаєш у проєкт модулі Pages і Forums, будуєш маленьку базу знань з ієрархією
сторінок, публікуєш пост на форумі з правильними опціями й прив'язуєш його до задачі, а ще точно
знаєш, хто бачить проєкт і його вміст. Для QA-команди це місце для правил (як описувати баг, що
перевіряти перед релізом) і для рішень, які не мають загубитися в чаті.*

---

## 7.1. Модулі проєкту: звідки беруться вкладки

Кожна вкладка проєкту — це **модуль**: **Tasks**, **Issues**, **Phases**, **Documents**, **Pages**,
**Forums** тощо. Набір модулів у кожного проєкту свій.

**При створенні проєкту** модулі вибирають у блоці **Customize tabs for this project** форми
проєкту. У тріалі там були: Dashboard, Tasks, Users, Reports, Documents, Phases, Time Logs, Finance,
Expense Claims, Bugs (це модуль Issues під іншою назвою), Feed, Forums, Pages, Timesheet.

**В уже існуючий проєкт** модуль додають з рядка вкладок: **•••** (More Tabs) → **Add Module/Web
Tab** → у розділі активних модулів (у тріалі: Finance, Expense Claims, Forums, Pages) клік по
потрібному. У тріалі так додали **Pages** до існуючого проєкту: з'явилось повідомлення «Module
Added.», а в модулі одразу була сторінка `HomePage`. **Forums** лежить у тому самому меню.

Частина модулів показується не в рядку вкладок, а під **•••** (More Tabs) — у тріалі там були,
наприклад, Issues, Feed, Timesheet, а також Forums і Pages, якщо їх увімкнено. Тому «вкладки немає»
спершу перевіряють там.

Щоб не плутати сусідні інструменти:

| Інструмент | Для чого | Приклад |
|---|---|---|
| **Pages** | структуровані живі тексти, що їх оновлюють | правила оформлення багів, чек-лист релізу |
| **Forums** | обговорення з відповідями, анонси, питання | «Який інструмент для API-тестів беремо?» |
| **Documents** | файли | специфікація від клієнта у PDF |
| коментар у задачі | розмова про одну конкретну задачу | «Відтворив на Safari, лог у вкладенні» |
| чат (Zoho Cliq) | швидке спілкування | «Хто зараз на стейджі?» |

У зведеній таблиці документа про Pages сказано прямо: компанія цей модуль не використовує. Знати
його все одно треба: він є в клієнтських порталах, а завдання документа на нього є.

## 7.2. Pages — база знань проєкту

**Pages** — легка вікі всередині проєкту. Документ наводить приклади: HR — інструкції для нових
співробітників; розробка — технічні стандарти, чек-листи, інструкції з налаштування; продажі —
документація продукту й правила угод. Для QA — правила репортингу, чек-листи, опис тестових
середовищ.

Що вміє модуль (документ і довідка Zoho):

- створювати сторінки або імпортувати їх з файлу (**Import Page**: doc, docx, sxw, html, odt, rtf,
  wpd; імпорту з Google Docs у тріалі немає);
- будувати ієрархію «батьківська сторінка → підсторінки»;
- коментарі й вкладення на сторінці;
- **Site Map** — візуальна карта всіх сторінок, де видно й змінюють ієрархію.

На вкладці **Pages** у тріалі були: кнопка **Create new page**, пошук **Quick Search**, навігація
**Navigate Pages** і **Site Map**.

Як це працює (так описує довідка Zoho):

| Дія | Де |
|---|---|
| нова сторінка | **Create new page** → **Page Name**, **Page Type**, розташування: у корені (**Put page in Root Level**) або під іншою сторінкою (**Put page under another Page** → **Choose Parent Page**) → **Create** |
| підсторінка існуючої | відкрий сторінку → **Page Options** → **Add Sub Page** |
| коментар | на сторінці поле **Post a comment** → однойменна кнопка |
| вкладення | **Add Attachments** (файл з комп'ютера або з Google Docs) |
| карта сторінок | **Site Map** (у правому нижньому куті) → **Expand All** / **Collapse All**; сторінки можна перетягувати |

**Хто що може.** За довідкою всі користувачі порталу мають дозвіл на всі операції в Pages. Тобто
тонких ролей «читає / редагує» тут немає: будь-хто з доступом до проєкту може змінити чи видалити
сторінку. Для бази знань це ризик, і QA варто перевірити, чи це правда у твоєму порталі.

### Покроково: база знань «QA Handbook»

Це завдання документа **Create and Organize Knowledge Base Pages**.

1. Відкрий будь-який проєкт → вкладка **Pages**. Якщо її немає ні в рядку вкладок, ні під **•••**:
   **•••** → **Add Module/Web Tab** → **Pages**.
   **Що побачиш:** «Module Added.», вкладку **Pages** і сторінку `HomePage`.
2. **Create new page** → **Page Name** `QA Handbook`, розташування — у корені → **Create**. Якщо
   форма просить **Page Type**, обери тип для звичайної текстової сторінки.
3. Створи дві підсторінки під `QA Handbook`: `Bug Reporting Guidelines` і `Testing Checklist` — через
   **Create new page** з батьківською сторінкою `QA Handbook` або з відкритої `QA Handbook` через
   **Page Options** → **Add Sub Page**.
4. Додай у кожну сторінку 3–5 рядків змісту. Приклад:

   ```
   QA Handbook
   The QA team's working rules for this project.
   Start with Bug Reporting Guidelines before filing your first bug.
   Use Testing Checklist before every release.

   Bug Reporting Guidelines
   Title: what is broken and where, in one line.
   Steps: numbered, starting from a known state.
   Expected vs Actual: one line each, no opinions.
   Evidence: screenshot or video, plus environment and browser.

   Testing Checklist
   Smoke: login, main navigation, create and save one record.
   Regression: the flows touched by the release.
   Negative: empty and invalid input on every changed form.
   Sign-off: all Critical and Show stopper issues are closed.
   ```

5. На одній зі сторінок (наприклад, `Bug Reporting Guidelines`) залиш коментар (`Reviewed, format
   approved for the team.`) і прикріпи зразковий файл через **Add Attachments** (наприклад, шаблон
   баг-репорту).
   **Що побачиш:** коментар під сторінкою і файл у вкладеннях.
6. Відкрий **Site Map** → **Expand All**.
   **Що побачиш:** `QA Handbook` з двома підсторінками під нею; поряд `HomePage`.
7. Зроби скриншот розгорнутої **Site Map** і напиши коротку нотатку (2–3 речення) про зміст.

Сторінки редагуються й видаляються будь-коли; неправильно вкладену сторінку перетягни в **Site Map**
на своє місце.

## 7.3. Forums — асинхронні обговорення

**Forums** — обговорення з темами й відповідями всередині проєкту. На відміну від чату, пост
живе довго, його видно всім учасникам, до нього повертаються й посилаються. Документ називає
приклади: поділитися ідеями й висновками з проєкту, оголосити важливі етапи чи реліз, поставити й
розібрати технічне питання.

### Форма нового поста

Кнопка — **New Forum Post**. У тріалі форма мала такі поля (зірочка — обов'язкове):

| Поле | Що це |
|---|---|
| **Title** * | заголовок теми |
| **Description** * | текст поста |
| **Tags** | мітки для пошуку й фільтрів |
| вкладення | до 10 файлів |
| **Category** * | категорія форуму, до якої належить пост |
| **Flag** * | `Internal` або `External` |
| **Q&A**, **Sticky Post**, **Announcement** | прапорці-опції поста |
| **Send notification about the topic** | кому надіслати лист про новий пост |

Кнопки: **Publish**, **Cancel**, **Preview**. Обов'язкових полів чотири: **Title**, **Description**,
**Category** і **Flag** — без будь-якого з них пост не опублікується.

### Опції поста

| Опція | Що робить |
|---|---|
| **Sticky Post** | пост закріплено нагорі форуму |
| **Announcement** | лист про пост отримують усі користувачі проєкту, крім клієнтських |
| **Q&A** | пост-питання, під яким обговорюють і відповідають |

Опції — прапорці, а не один вибір: пост може бути і закріпленим, і анонсом.

**Flag** визначає коло читачів: `Internal` — лише користувачі проєкту, `External` — ще й клієнтські
користувачі (довідка). З анонсами він пов'язаний так: підказка продукту до **Announcement** каже
«All project users except client users will receive an email notification. This will override
their email notification setting.», а для поста `External` у продукті є повідомлення «External
forums cannot be marked as announcements.». Стара FAQ довідки ще
радить знімати **Announcement**, щоб не слати листів клієнтам. Тож хто саме отримав анонс, доводь
тестом з другим користувачем, а не міркуваннями.

Чи прийде людині лист про звичайний пост, залежить ще й від її особистих налаштувань e-mail-сповіщень:
стара FAQ довідки називає там пункт «When a message is posted in a forum», а серед текстів продукту є
схожий «When a forum is posted or a comment is posted in any forum.» — шукай пункт на кшталт цих.
Тож «лист прийшов / не прийшов» спершу звіряють з цим налаштуванням; анонс, за підказкою продукту,
його перекриває.

### Категорії, теги, підписка

**Category** обов'язкова, тож категорія має існувати до першого поста. За довідкою категорії додають
на вкладці **Forums** через іконку-меню в правому верхньому куті → **Add Category**; редагують і
видаляють при наведенні на категорію. Пост можна перенести в іншу категорію (меню поста → **Move**).

Документ згадує ще «tag, follow, or comment via email»: теги ставлять посту (при створенні або
пізніше), **Follow** підписує на оновлення теми, а коментар можна надіслати листом (довідка:
**Post a comment via email**). Відповіді пишуть у секції коментарів відкритого поста; на окремий
коментар можна відповісти кнопкою **Reply** (довідка). Порожня вкладка **Forums** у тріалі
пропонувала ще **Add Forum via email** — створити пост листом.

### Прив'язка поста до задачі

Документ каже «Associate forums directly with tasks», але не каже, з якого боку. Відповідь: **з
задачі**. У самого поста дії «прив'язати» в тріалі не було.

- сторінка задачі → секція **Forums** → **Associate Forums** → обери категорію → познач пости →
  **Associate Forums**;
- після прив'язки задача показує `Forums (1)` і кнопку **Associate More**, а в списку форуму біля
  поста з'являється лічильник пов'язаних задач (тріал).

Секцію **Forums** на сторінці задачі, найімовірніше, видно лише в проєкті з модулем Forums: у тріалі
в проєкті без цього модуля серед секцій задачі її не було, а в проєкті з ним — була. Документ
прив'язує пост до задачі того самого проєкту.

### Покроково: пост «QA Tools Suggestion» і задача

Це завдання документа **Create a Forum Post and Associate It with a Task**.

1. Відкрий проєкт → вкладка **Forums**. Якщо її немає: **•••** → **Add Module/Web Tab** → **Forums**.
2. Перевір **Category** у формі нового поста, перш ніж створювати нову: у тріалі
   порожній проєкт уже мав одну готову категорію з назвою проєкту, і форма підставляла її сама —
   окремий крок «створити категорію» не знадобився. Категорій справді немає лише не показала жодна —
   тоді додай її: іконка-меню в правому верхньому куті вкладки **Forums** → **Add Category** (шлях з
   довідки; якщо пункт зветься інакше, шукай додавання категорії в цьому ж меню).
3. **New Forum Post** і заповни:

   | Поле | Значення |
   |---|---|
   | **Title** | `QA Tools Suggestion` |
   | **Description** | 3–5 рядків про один інструмент (приклад нижче) |
   | **Category** | будь-яка наявна (у тріалі — та, що з назвою проєкту) |
   | **Flag** | `Internal` |
   | опції | постав **Q&A**; зніми **Sticky Post**, якщо форма поставила її сама (у тріалі вона
     виявилась увімкненою за замовчуванням); **Announcement** не став |
   | вкладення | 1 зразковий файл (необов'язково, якщо завантаження файлів вимкнене) |

   ```
   Suggestion: use Playwright for automated UI regression of our CRM screens.
   Why: it waits for elements automatically, runs in Chromium, Firefox and WebKit,
   and can record a trace for failed runs.
   First step: automate the five most-used flows and run them before each release.
   Question: which flows would you pick first?
   ```

4. **Publish**.
   **Що побачиш:** пост у списку форуму з позначкою Q&A; відкритий пост показує заголовок, опис,
   флаг і вкладення.
5. Відкрий пост і додай коментар у секції коментарів (наприклад, `First candidates: login, create
   deal, convert lead.`); за довідкою коментар зберігає кнопка **Submit**.
6. Відкрий будь-яку задачу цього проєкту (немає задач — створи `Evaluate QA tooling options`).
7. На сторінці задачі → секція **Forums** → **Associate Forums** → категорія `QA` → познач `QA Tools
   Suggestion` → **Associate Forums**.
   **Що побачиш:** `Forums (1)` з твоїм постом і кнопка **Associate More**.
8. Скриншоти: відкритий пост; задача з прив'язаним постом. Нотатка 1–2 речення: що з чим пов'язано.

Пост редагується й видаляється з його меню; прив'язку знімають на сторінці задачі.

## 7.4. Public і Private: хто бачить проєкт

Доступ до проєкту задає поле **Project Access** у формі проєкту — `Private` або `Public`.

| | Private | Public |
|---|---|---|
| учасники проєкту | повний доступ за своїми ролями | повний доступ за своїми ролями |
| інші користувачі порталу | проєкту не бачать | бачать, стежать (**Follow**) і коментують, але не можуть додавати, змінювати чи видаляти роботу |
| де шукати | у своїх проєктах | ще й на вкладці **Public Projects** сторінки **Projects** |

Рядок про інших користувачів — за довідкою Zoho; вона ж додає, що адміністратор має всі права навіть
у публічному проєкті, де він не учасник. Документ формулює коротше: private — лише доданим
користувачам, public — усім користувачам порталу, лише на читання.

**Змінити доступ існуючого проєкту** документ дозволяє адміністраторам через налаштування Project
Access. Довідка описує шлях: **Projects** → наведи курсор на проєкт → **Access Project** → **Open
Details** біля назви → іконка в правій панелі → розділ **Project Access** → `Public`. У тріалі в
панелі деталей проєкту поля доступу немає, тож приватність доводять непрямо: вкладка **Public
Projects** показує «No projects found». Якщо поле не знайдеш і ти — перевір результат так само.

### Дві різні осі видимості

Не плутай два механізми:

| Механізм | Кого стосується | Де задається |
|---|---|---|
| **Project Access** (Private / Public) | користувачі порталу, які не є учасниками проєкту | форма проєкту |
| **Flag** (Internal / External) | клієнтські користувачі проєкту | кожен пост, issue, список задач, фаза |

Приклад: публічний проєкт з постом `Internal` — будь-який користувач порталу побачить проєкт, але
клієнт, доданий у проєкт, цей пост не побачить. Приватний проєкт з постом `External` — клієнт
проєкту пост побачить, а колега з іншого відділу не побачить нічого.

Є й сіра зона: довідка форуму описує `Internal` як «only for project users». Чи побачить неучасник
публічного проєкту пост `Internal` — з документації однозначно не випливає. Такі місця QA не
домислює, а перевіряє.

А тепер поєднай з Pages: у публічному проєкті неучасник має лише читання, а довідка Pages каже, що
всі користувачі порталу мають усі права на сторінки. Що переможе — перевіряють тестом, а не
міркуваннями.

## 7.5. Як це тестувати

**Що довести в кожному завданні:**

| Завдання | Що має бути видно | Доказ |
|---|---|---|
| Pages | `QA Handbook` у корені, дві підсторінки під ним, зміст, коментар і вкладення на одній сторінці | скриншот **Site Map** після **Expand All** + нотатка |
| Forums | пост з Title, Category, Flag, опцією Q&A, описом, коментарем; прив'язка з боку задачі | скриншот поста, скриншот задачі з `Forums (1)` + нотатка |

**Позитивні, негативні й граничні випадки:**

- Pages: підсторінка під підсторінкою (скільки рівнів?); перенесення сторінки перетягуванням у
  **Site Map**; видалення батьківської сторінки — що стається з дітьми; сторінка з однаковою назвою
  поруч; пошук **Quick Search** за словом зі змісту;
- Forums: **Publish** без кожного з обов'язкових полів по черзі; 11-те вкладення; пост одночасно
  **Sticky Post** і **Announcement**; **Announcement** разом з `External`; два закріплені пости —
  який вище; **Announcement** — хто отримав лист, зокрема користувач з вимкненими сповіщеннями
  форуму; `External` — чи бачить його клієнтський користувач; прив'язка одного поста до двох задач і
  двох постів до однієї задачі; видалення поста, прив'язаного до задачі, — що показує задача;
- доступ: неучасник порталу відкриває публічний проєкт — чи може коментувати пост, чи може змінити
  сторінку в Pages; приватний проєкт — чи з'являється він у **Public Projects**.

Частину перевірок не зробити з одним користувачем: листи, видимість для неучасника й для
клієнтського користувача. Для них потрібен другий користувач порталу (і клієнтський користувач для
`External`). Такі кейси пиши одразу, а виконуй, коли з'явиться друга людина.

## 7.6. Типові помилки

**1. Шукати вкладку лише в рядку вкладок.** Сховані модулі — під **•••**; відсутні — додаються
через **Add Module/Web Tab**.

**2. Перестворювати проєкт заради Pages чи Forums.** Модуль додається в існуючий проєкт.

**3. Створити підсторінку в корені.** При створенні вибери батьківську сторінку або виправ
перетягуванням у **Site Map**.

**4. Робити скриншот нерозгорнутої Site Map.** Результат завдання — дерево після **Expand All**.

**5. Лишити порожньою Category чи Flag.** Обидва поля обов'язкові разом з Title і Description.

**6. Ставити Announcement «про всяк випадок».** За підказкою продукту це лист усім користувачам
проєкту, крім клієнтських, — навіть тим, хто вимкнув сповіщення форуму.

**7. Шукати кнопку прив'язки в самому пості.** Прив'язують зі сторінки задачі, секція **Forums**.

**8. Плутати Project Access і Flag.** Перше — про неучасників порталу, друге — про клієнтських
користувачів.

**9. Вірити, що Pages захищені ролями.** За довідкою будь-який користувач порталу може все; перевір.

### Симптом → причина

| симптом | найімовірніша причина |
|---|---|
| немає вкладки **Pages** чи **Forums** | модуль сховано під **•••** або не додано: **•••** → **Add Module/Web Tab** |
| після додавання **Pages** уже є сторінка `HomePage` | вона створюється разом з модулем |
| підсторінка опинилась на верхньому рівні | при створенні лишилось розташування в корені |
| на **Site Map** видно не всі сторінки | не натиснуто **Expand All** |
| **Publish** не публікує пост | не заповнене одне з полів **Title**, **Description**, **Category**, **Flag** |
| у списку **Category** порожньо | категорій ще немає — **Add Category** в меню вкладки **Forums** |
| у пості немає дії «прив'язати до задачі» | прив'язують зі сторінки задачі, секція **Forums** |
| на сторінці задачі немає секції **Forums** | у проєкті не ввімкнено модуль Forums |
| лист про пост отримали всі учасники | стояла опція **Announcement** |
| **Announcement** не ставиться | у поста **Flag** = `External`: «External forums cannot be marked as announcements.» |
| клієнт не бачить пост | у поста **Flag** = `Internal` |
| колега з іншого відділу не бачить проєкт | проєкт `Private`, а колега не учасник |
| проєкт видно у **Public Projects** | у нього **Project Access** = `Public` |

## 7.7. Що варто запам'ятати

1. Вкладки проєкту — модулі; Pages і Forums додаються в існуючий проєкт через **•••** → **Add
   Module/Web Tab**.
2. Pages — вікі проєкту: ієрархія, коментарі, вкладення, **Site Map** з **Expand All**.
3. За довідкою в Pages усі користувачі порталу мають усі права — ролей «лише читання» немає.
4. Пост форуму вимагає **Title**, **Description**, **Category** і **Flag**.
5. **Q&A**, **Sticky Post**, **Announcement** — окремі прапорці; Announcement розсилає лист
   користувачам проєкту, крім клієнтських, і з `External` не поєднується.
6. **Flag** `Internal` — лише користувачі проєкту, `External` — ще й клієнти.
7. Пост прив'язують до задачі зі сторінки задачі; видно з обох боків.
8. **Project Access** Private/Public — про користувачів порталу поза проєктом; Flag — про клієнтів.
9. Публічний проєкт неучасник бачить і коментує, але не змінює роботу; адміністратор може все.
10. Листи й видимість для інших людей з одним користувачем не перевірити — такі кейси чекають
    другого користувача.

# Задачі

**7.1.** Підготуй проєкт до завдань. Візьми існуючий проєкт і перевір, чи є в ньому вкладки
**Pages** і **Forums** (не забудь про **•••**). Якщо немає — додай обидва модулі через **Add
Module/Web Tab**. Запиши, що з'явилось разом з модулем Pages.

**7.2.** Виконай завдання документа **Create and Organize Knowledge Base Pages**. Відкрий будь-який
проєкт, перейди на вкладку **Pages** (якщо її немає: **•••** → **Add Module/Web Tab** → **Pages**).
Створи батьківську сторінку `QA Handbook` і дві підсторінки під нею: `Bug Reporting Guidelines` і
`Testing Checklist`. Додай у кожну сторінку короткий зміст (3–5 рядків). На одній зі сторінок додай
1 коментар і прикріпи 1 зразковий файл. Відкрий **Site Map** і натисни **Expand All**. Результат:
скриншот розгорнутої Site Map і коротка нотатка (2–3 речення) про те, який зміст ти додав.

**7.3.** Виконай завдання документа **Create a Forum Post and Associate It with a Task**. Відкрий
будь-який проєкт, перейди на вкладку **Forums** (якщо її немає: **•••** → **Add Module/Web Tab** →
**Forums**). Створи пост: Title `QA Tools Suggestion`; Category — будь-яка (обов'язкова); опції —
постав Q&A; короткий опис (3–5 рядків) з однією пропозицією QA-інструмента; прикріпи 1 зразковий
файл (необов'язково, якщо завантаження файлів вимкнене). Опублікуй пост і додай до нього 1
коментар. Відкрий будь-яку задачу того самого проєкту, у деталях задачі відкрий секцію **Forums**,
натисни **Associate Forums** і прив'яжи свій пост. Результат: скриншот поста, скриншот задачі з
прив'язаним постом і нотатка (1–2 речення) про те, що з чим пов'язано.

**7.4.** *(обери інструмент)* Для кожної ситуації обери Pages, пост форуму (з якими опціями), коментар
у задачі чи **Documents**: а) правила оформлення баг-репортів, які оновлюються раз на квартал; б)
«Завтра о 10:00 стейдж недоступний — оновлення»; в) «Чи тестуємо ми Safari на iOS 16?»; г)
«Відтворив баг на Firefox, HAR у вкладенні»; д) договір з клієнтом у PDF; е) щомісячна нагадувалка
«перевір, що чек-лист релізу актуальний», яка має висіти нагорі.

**7.5.** *(передбач)* Проєкт `Mobile App`, у ньому учасники Олена (користувач порталу) і клієнт
Марк (клієнтський користувач). Сергій — користувач порталу, не учасник. Хто побачить пост у кожному
випадку: а) проєкт Private, пост `Internal`; б) проєкт Private, пост `External`; в) проєкт Public,
пост `Internal`; г) проєкт Public, пост `External`? Хто з них може змінити сторінку в Pages у
випадку в)?

**7.6.** *(знайди помилку)* Колега пише: «Заповнив Title і Description, поставив Q&A, тисну Publish —
нічого не публікується. Потім усе ж опублікував, але не знайшов у пості, як прив'язати його до
задачі. А ще весь відділ отримав лист про мій пост». Поясни кожну з трьох проблем і що робити.

**7.7.** *(спроєктуй тести)* Склади тест-кейси для опцій поста форуму: **Sticky Post**,
**Announcement**, **Q&A**, **Flag**. Щонайменше шість назв з очікуваним результатом; два розпиши
повністю у форматі документа. Познач, які кейси потребують другого користувача.

**7.8.** *(поясни)* Чим відрізняються **Project Access** і **Flag**? Наведи приклад, коли проєкт
публічний, а клієнт усе одно не бачить пост, і приклад, коли проєкт приватний, а клієнт пост бачить.

# Розв'язки

**7.1.** Якщо вкладок немає ні в рядку, ні під **•••**: **•••** → **Add Module/Web Tab** → **Pages**,
потім так само **Forums**. Разом з модулем Pages з'являється повідомлення «Module Added.» і сторінка
`HomePage`. Проєкт перестворювати не потрібно.

**7.2.** Кінцевий стан у **Site Map** після **Expand All**:

```
HomePage
QA Handbook
   Bug Reporting Guidelines
   Testing Checklist
```

У кожній сторінці 3–5 рядків (як у прикладі розбору); на `Bug Reporting Guidelines` — коментар і
вкладення. Приклад нотатки:

> I created the QA Handbook with two subpages. Bug Reporting Guidelines describes how to write a bug
> (title, steps, expected vs actual, evidence), and Testing Checklist lists the smoke, regression,
> negative and sign-off checks before a release. One page has a review comment and an attached bug
> report template.

**7.3.** Кінцевий стан: пост `QA Tools Suggestion` з **Category** (наприклад, `QA`), **Flag**
`Internal`, опцією **Q&A**, описом з 3–5 рядків, вкладенням (якщо завантаження ввімкнене) і одним
коментарем. На сторінці задачі секція **Forums** показує `Forums (1)` з цим постом. Приклад нотатки:

> The forum post "QA Tools Suggestion" (Q&A, Internal) is associated with the task "Evaluate QA
> tooling options" from the task's Forums section, so the discussion is one click away from the
> work it informs.

**7.4.** а) **Pages** — живий структурований текст, який оновлюють. б) пост форуму з
**Announcement** і флагом `Internal` (усім учасникам команди потрібен лист; анонс з `External`
продукт не приймає). в) пост форуму з **Q&A** —
питання, на яке чекаємо відповіді й обговорення. г) коментар у задачі чи issue, до якого він
стосується, з вкладенням. д) **Documents** — це файл. е) пост форуму зі **Sticky Post**, щоб висів
нагорі (або сторінка в Pages з посиланням у закріпленому пості).

**7.5.** а) Олена — так; Марк — ні (`Internal`); Сергій — ні (проєкт приватний, він не учасник).
б) Олена — так; Марк — так (`External`); Сергій — ні. в) Олена — так; Марк — ні (`Internal`); Сергій
проєкт бачить (Public), а чи бачить він пост `Internal` — сіра зона: довідка описує `Internal` як
«only for project users». г) Олена і Марк — так; Сергій — так, як неучасник публічного проєкту
(читання й коментарі). Pages у випадку в): Олена — так; Марк — залежить від доступу клієнтських
користувачів до модуля — перевір це окремо; Сергій — суперечність: публічний проєкт дає
неучаснику лише читання, а довідка Pages каже, що всі користувачі порталу можуть усе. Відповіді «сіра
зона» тут правильні: це тести, які треба провести, а не питання, на які є відповідь заздалегідь.

**7.6.** 1) Не заповнені обов'язкові поля **Category** і **Flag** — пост вимагає чотири поля.
2) Прив'язки в пості немає: відкрий задачу → секція **Forums** → **Associate Forums**. 3) Стояла
опція **Announcement** — вона розсилає лист; для звичайного питання її не ставлять.

**7.7.** Приклад набору:

1. **Sticky Post**: пост стоїть нагорі списку незалежно від дати.
2. Два **Sticky Post**: обидва нагорі; порядок між ними — зафіксуй фактичний.
3. **Announcement**: лист отримали всі користувачі проєкту, крім клієнтських, навіть з вимкненими
   сповіщеннями форуму (потрібні другий і клієнтський користувачі).
4. Без **Announcement** і без вибраних отримувачів: лист не надсилається тим, у кого вимкнено
   особисте сповіщення про пости форуму (другий користувач).
5. **Q&A**: пост позначено як питання, під ним можна відповідати в коментарях.
6. **Flag** `External`: пост бачить клієнтський користувач (потрібен клієнтський користувач).
7. **Flag** `Internal`: клієнтський користувач поста не бачить (потрібен клієнтський користувач).
8. **Sticky Post** + **Announcement** разом: обидва ефекти працюють.
9. **Announcement** + **Flag** `External`: пост з такими опціями не зберігається, продукт пояснює
   чому (очікуване повідомлення — «External forums cannot be marked as announcements.»).

Повний приклад — у розділі 7.5 «Як це тестувати». Ще один:

```
Title: A sticky post stays above newer posts
Precondition:
- The Forums module is on; a category exists.
- Post P1 is published with Sticky Post ticked.
Steps:
1. Publish post P2 without Sticky Post.
2. Open the Forums tab and sort by Recent Forums.
Expected Result:
- P1 is shown above P2 although P2 is newer.
Actual Result: [...]
Pass/Fail: [...]
Notes/Attachments: screenshot of the list.
```

**7.8.** **Project Access** вирішує, чи бачать проєкт користувачі порталу, які не є його
учасниками. **Flag** вирішує, чи бачать конкретний пост (issue, список задач, фазу) клієнтські
користувачі проєкту. Публічний проєкт, пост `Internal`: будь-хто в порталі бачить проєкт, але клієнт
цього поста не побачить. Приватний проєкт, пост `External`: сторонні користувачі порталу не бачать
нічого, а клієнт — учасник проєкту — пост бачить.
