# Урок 6. Issues: баг-трекер усередині проєкту

*Після уроку ти заводиш issues з правильною severity, будуєш представлення без пасток на датах,
зв'язуєш issues із задачами й між собою, логуєш на них час, ставиш нагадування й імпортуєш issues з
Excel. Для QA Issue Tracker — щоденний робочий інструмент: від того, як заведено баг і як
відфільтровано список, залежить, чи побачить розробник критичне вчасно.*

---

## 6.1. Issue і задача: дві різні сутності

**Issue Tracker** вбудований у кожен проєкт Zoho Projects. **Issue** — це запис про проблему:
дефект, невідповідність вимозі, збій. **Задача** — це робота. Zoho тримає їх окремо, бо зв'язок між
ними не «один до одного»: один баг може потребувати кількох задач (виправити, перевірити, оновити
документацію), а одна задача може закрити кілька багів. Тому issue і задачу **асоціюють**, а не
зливають в одне.

Де живуть issues:

- у проєкті — вкладка **Issues** (якщо її не видно в рядку вкладок, вона під **•••**, More Tabs);
- у списку модулів **Customize tabs for this project** у формі проєкту той самий модуль називається
  **Bugs** — це не інший модуль, а інша назва;
- у лівій панелі, у розділі Overview, пункт **Issues** — issues з усіх проєктів разом.

ID issue будується з префікса задач і issues проєкту: задачі мають вигляд `QT1-T20`, issues —
`QT1-I2` (літера `I` — issue). За ID issue шукають і згадують у коментарях.

### Поля issue

У тріалі стандартний layout issues (**Setup → Customization → Layouts → Issues → Standard Layout**)
мав такі поля:

| Група | Поля |
|---|---|
| хто і коли | **Reporter**, **Created Time**, **Last Modified Time**, **Last Closed Time** |
| хто виправляє | **Assignee**, **Associated Team** |
| що й наскільки погано | **Severity**, **Classification**, **Module**, **Reproducible** |
| коли | **Due Date**, **Release Phase**, **Affected Phase** |
| процес | **Status** |
| видимість | **Flag** |
| гроші | **Rate Per Hour**, **Cost Per Hour** |
| інше | **Tags** |

**Поля Priority і поля Type в issue немає.** Якщо інструкція для issue згадує priority, найближче
поле в продукті — **Severity**, а терміновість додатково задають дедлайном; якщо type — це
**Classification** або **Module**.

Значення, які варто знати напам'ять:

| Поле | Значення |
|---|---|
| **Severity** | `None`, `Show stopper`, `Critical`, `Major`, `Minor` — ні `Medium`, ні `High` немає |
| **Status** (стандартні) | `Open`, `In progress`, `To be tested`, `Closed`, `Reopen` |
| **Classification** | `None`, `Security`, `Crash/Hang`, `Data loss`, `Performance`, `UI/Usabililty`, `Other bug`, `Feature(New)`, `Enhancement` |
| **Reproducible** | `None`, `Always`, `Sometimes`, `Rarely`, `Unable`, `Never tried`, `Not applicable` |
| **Flag** | `Internal` — лише користувачі порталу; `External` — бачать і клієнтські користувачі |

Зверни увагу на регістр: у порталі статус пишеться `In progress`, з малої `p`. У фільтрах і при
імпорті це має значення. Статуси `Closed` і `Reopen`, а також списки Classification і Reproducible в
тріалі не записували; вище вони подані так, як їх пише інтерфейс продукту, — з малої літери в другому
слові і навіть з помилкою в `UI/Usabililty`. Довідка пише ці значення інакше (`Data Loss`, `Other
Bug`, `UI/Usability`, `Never Tried`, `Not Applicable`), тож звір зі своїм порталом.

**Release Phase** — фаза, у якій issue виправлено, **Affected Phase** — фаза, у якій його знайдено.
Кожен проєкт у тріалі має приватну копію layout issues.

### Severity — це не пріоритет

**Severity** відповідає на питання «наскільки погано»: `Show stopper` — робота неможлива, `Minor`
— дрібниця. **Пріоритет** відповідає на питання «наскільки терміново виправляти», і це рішення
бізнесу: опечатка на головній сторінці перед релізом може бути терміновішою за рідкісний збій в
адмінці. У Zoho Projects окремого пріоритету для issue немає, тож терміновість виражають дедлайном
(**Due Date**), представленнями і правилами обслуговування. Для QA важливо не підміняти одне іншим:
severity ставить той, хто знайшов і описав баг, за наслідками.

## 6.2. Як issue з'являється і що з ним роблять

**Вручну.** У проєкті на вкладці **Issues** є кнопка **Submit Issue** (так описує довідка Zoho): у
формі — назва, **Assignee** та інші поля layout, збереження — **Add**. У List view є ще рядок
**Submit Issue** для швидкого створення: вводиш лише назву й Enter, решту полів заповнюєш на
сторінці issue. Глобальний пункт **Issues** у лівій панелі теж дає створити issue — там спершу
обирають проєкт.

**Поштою.** Документ описує роботу з проєктом через e-mail-адреси (alias): адресу елемента показує
його сторінка, а лист на неї створює запис чи коментар. Для issues у тріалі цей шлях не
перевірявся.

**Через інтеграції.** У **Setup → Issue Tracker** є **Web To Issues Form** — форма на сайті, яка
створює issues. Репозиторії коду (GitHub, GitLab, Bitbucket, Gitea) можна під'єднати так, що
коміт з ID issue у повідомленні оновлює цей issue (довідка).

Документ згадує ще повторювані issues (recurrence). Повторення довідка описує для задач; серед
полів стандартного layout issues у тріалі його не було. Не знайдеш — це не твоя помилка.

**Сторінка issue.** Поля в блоці інформації зберігаються одразу після зміни. Нижче — вкладки
(так їх було видно в тріалі): **Comments** · **Attachments** · **Log Hours** · **Link Issues** ·
**Resolution** · **Tasks** · **Status Timeline** · **Activity Stream**. У коментарях працюють
@-згадки, скриншоти й вкладення; **Resolution** — опис того, як issue вирішено; **Status
Timeline** — історія статусів, найкращий доказ «хто, коли і куди перевів». Через меню **•••**
issue клонують, переносять в інший проєкт (не можна, якщо на ньому є виставлений у рахунок час),
підписуються на нього (**Follow**).

## 6.3. Представлення: List, Kanban і custom views

**List view** — таблиця: колонки додаються, ховаються й переставляються (правий клік по заголовку
колонки дає **Apply Filter**, **Insert Column Before**, **Insert Column After**, **Hide Column**),
поля редагуються прямо в рядку, кілька issues можна змінити масово — виконавця, severity, статус,
дедлайн, теги, асоціації.

**Kanban** — картки в колонках. Колонки будуються за **Status**, **Severity**, **Module**,
**Classification** або **Reproducible**. Перетягування картки між статусами змінює статус — але
лише якщо workflow статусів дозволяє такий перехід.

**Predefined views** (довідка): `All Issues`, `All Open`, `All Closed`, `My Open`, `My Closed`,
`Unassigned`, `Overdue & Open`, `Created Today`, `Issues I Follow`, `Escalated Issues`, `Assigned
Via Pick List`, `Issues Associated to Team`.

### Custom view

Custom view — збережений фільтр з назвою. Створюють його зі списку представлень: **All Issues ▾**
(назва поточного представлення) → **+ Create Custom View**. Далі:

| Крок | Що робиш |
|---|---|
| критерії | рядок = поле + оператор + значення; рядки з'єднуються AND або OR; можна групувати |
| назва | **Custom View Name**, за бажанням опис |
| доступ | лише ти, усі користувачі або вибрані користувачі |
| accessibility | чи показувати представлення в глобальних **Issues** і в інших проєктах |
| **Save** | представлення з'являється в розділі Custom Views списку |

**Favorite** ставлять не у формі, а в списку представлень: наведи курсор на представлення й
натисни зірочку. Улюблені збираються в окремому розділі списку.

### Три пастки критеріїв

**1. Оператор Is на даті.** **Due Date** в issue — це дата **і час**. Критерій `Due Date Is
<дата>` збігається лише з однією хвилиною (`00:00` цього дня), тож у тріалі таке представлення
повернуло порожньо — при тому, що issues з таким дедлайном були. Для діапазону бери **Between**
(або **Less Than** для верхньої межі без нижньої).

**2. Верхня межа діапазону.** Якщо верхня межа — `00:00` сьомого дня, issue з дедлайном сьомого дня
о `17:00` у діапазон не потрапить. Перевір, який час стоїть на межі, і зроби контрольний issue
саме на цю межу. І пам'ятай: фільтр з конкретними датами статичний — завтра він уже не «наступні 7
днів».

**3. Кілька значень одного поля.** «Status = Open або In progress» — це один рядок з двома
значеннями (у тріалі їх вводили як «чіпси» в одному рядку: `Status Is Open, In progress`). Два
рядки `Status Is Open` AND `Status Is In progress` дадуть порожній результат: один issue не може
мати два статуси одночасно.

### Покроково: представлення «Urgent Issues»

Це завдання документа **Build a Custom Issue View**. Спершу підготуй дані, на яких фільтр можна
**довести**, а не просто побудувати. Нехай сьогодні — день D:

| Issue | Status | Severity | Due Date | Має бути у view? |
|---|---|---|---|---|
| `UV-1 Checkout crashes on submit` | `Open` | `Show stopper` | D+2 | так |
| `UV-2 Login returns 500` | `In progress` | `Critical` | D+6 | так |
| `UV-3 Typo in footer` | `Open` | `Minor` | D+3 | ні — severity |
| `UV-4 Payment timeout` | `To be tested` | `Critical` | D+1 | ні — статус |
| `UV-5 Export fails` | `Open` | `Critical` | D+10 | ні — дата |
| `UV-6 Boundary check` | `Open` | `Critical` | D+7, `17:00` | так — межа діапазону |

1. **Issues** → список представлень (**All Issues ▾**) → **+ Create Custom View**.
2. Критерії, з'єднані AND:
   - **Status** — **Is** — `Open`, `In progress` (один рядок, два значення);
   - **Severity** — **Is** — `Show stopper`, `Critical`;
   - **Due Date** — **Between** — від сьогодні `00:00` до кінця сьомого дня від сьогодні.
3. **Custom View Name**: `Urgent Issues`. Доступ — поки лише тобі. **Save**.
   **Що побачиш:** відкрилось представлення `Urgent Issues`: `UV-1`, `UV-2`, `UV-6`. Якщо `UV-6`
   немає — верхня межа стоїть на `00:00` сьомого дня; відредагуй її.
4. У списку представлень наведи курсор на `Urgent Issues` і натисни зірочку.
   **Що побачиш:** зірочка заповнена, представлення є в Favorite Views.
5. Скриншоти: представлення з результатом; критерії у формі редагування представлення (іконка
   редагування біля назви або меню біля представлення в списку).

Представлення безпечно редагувати й видаляти — воно не змінює жодного issue.

## 6.4. Зв'язки: issue ↔ задача і issue ↔ issue

### Issue і задача

Асоціацію створюють з будь-якого боку, а видно її з обох:

- **зі сторінки issue:** вкладка **Tasks** → **Associate Tasks** → знайди задачу за назвою → обери →
  **Associate Tasks**. Там же можна одразу створити нову задачу, ввівши її назву (довідка);
- **зі сторінки задачі:** вкладка **Issues** (у тріалі, 27.09.2026, вона стоїть просто в рядку
  вкладок задачі — Comments, Subtasks, Log Hours, Documents, Dependency, Status Timeline, **Issues**
  — а не під **•••**; лічильник виду `Issues (1)` з'являється одразу після прив'язки) →
  **Add Issues** створює новий issue, **Associate Issues** прив'язує наявний;
- **масово зі списку:** дія **Associate Tasks** для виділених issues.

Одна асоціація — дві сторони. Друга дія «навпаки» не потрібна, її треба лише **перевірити**. Якщо
закрити задачу, до якої прив'язані відкриті issues, Zoho попередить про них — це вмикається й
вимикається в налаштуваннях задач (**Associate Tasks with Issues**, довідка).

### Issue і issue: Link Issues

Між issues ставлять **зв'язки з типом**. У тріалі набір типів (**Setup → Issue Tracker → Link
Issues**, окремо для кожного проєкту) був такий:

| Тип | Зворотний тип | Що означає (за довідкою) |
|---|---|---|
| `blocks` | `is blocked by` | A blocks B: B не закрити, доки не закрито A |
| `depends on` | `is a prerequisite of` | A depends on B: A не закрити, доки не закрито B |
| `is related to` | — | просто пов'язані, закриття не обмежує |
| `is duplicate of` | — | дублікати однієї проблеми; закриття одного не закриває інші |
| `is clone of` | `is cloned from` | B створено клонуванням A; зв'язок ставить сама дія **Clone**; **за замовчуванням вимкнений** |

`is clone of` — не звичайний тип для ручного зв'язування. Підказка продукту каже прямо: цей зв'язок
утворюється автоматично, коли issue клонують, і вручну ним issues не зв'язують. Увімкнений тип
означає, що issue, створений через **Clone**, автоматично зв'язується з оригіналом. Вмикають його в
**Setup → Issue Tracker → Link Issues**: угорі **Select Project** — обери свій проєкт, потім
(довідка) увімкни тип у колонці **Actions**. Там же можна додати власний тип: **Add Link Type** →
**Link Name** і **Reverse Link Name**; стандартні типи не редагуються й не видаляються.

Як зв'язати: сторінка issue → вкладка **Link Issues** → обери тип → знайди issue за назвою чи ID →
**Link Issues**. Пов'язані issues позначаються символом у списку. Обмеження з довідки: зв'язок має
один тип (не буває одночасно `blocks` і `depends on`), і зв'язати можна не більше 10 issues — обидва
варто перевірити на практиці.

Навіщо це QA: `blocks` і `depends on` — не просто мітки, вони **забороняють закриття**. Перевіряти
треба саме цю заборону, а не наявність стрілки.

### Покроково: баг і задача на виправлення

Це завдання документа **Create and Link Issues to Tasks**.

1. **Issues** → **Submit Issue**: назва `Bug: Submit Button Not Working`, **Assignee** — ти,
   **Severity** = `Major`, **Due Date** — завтра (наприклад, `17:00`). **Flag** залиш `Internal` →
   **Add**.
   **Що побачиш:** issue зі статусом `Open` і ID виду `<префікс>-I<номер>`.
2. **Tasks** → створи задачу `Fix Submit Button Bug`, власник — ти.
3. Відкрий issue → вкладка **Tasks** → **Associate Tasks** → почни вводити назву
   `Fix Submit Button Bug`. У тріалі (27.09.2026) сам клік на знайдений рядок одразу створює
   зв'язок — окремої кнопки-підтвердження після вибору із списку не було: рядок задачі з'явився в
   таблиці й лічильник вкладки одразу став `Tasks (1)`.
   **Що побачиш:** вкладка показує `Tasks (1)` і задачу в списку.
4. Відкрий задачу `Fix Submit Button Bug` → вкладка **Issues** — у тріалі вона в тому самому рядку
   вкладок, що й Comments/Subtasks/Dependency, не під **•••**.
   **Що побачиш:** `Issues (1)` і твій issue — без жодної другої дії.
5. Скриншоти: вкладка **Tasks** на issue і секція **Issues** на задачі. Це «link from both views».

Відкотити: навести курсор на пов'язаний запис → **Dissociate**.

## 6.5. Час на issue

Облік часу на issue влаштований так само, як на задачі: таймер і ручні записи, **Billable** чи
**Non Billable**. Таймер є в заголовку сторінки issue (іконка годинника) і в рядку List view;
запустити його може лише виконавець issue. Після зупинки — форма з типом оплати й примітками
(довідка), збереження **Update**. Записи лежать на вкладці **Log Hours** issue: з періодом «з — до»,
позначкою оплати й підсумком.

Документ пояснює, навіщо це: облік зусиль підтримки, рахунки клієнту, контроль SLA. Для QA це ще й
чесна метрика: скільки коштує один баг від відтворення до перевірки.

## 6.6. Нагадування і сповіщення

### Нагадування на issue

Поле **Reminder** на сторінці issue зберігає **одну** конфігурацію нагадування. Варіанти (за
довідкою):

| Режим | Налаштування |
|---|---|
| **Based on Due Date** | **Reminder Type**: `Daily` (щодня), `On Due Date` (у день дедлайну), `Day(s) before Due Date` (за N днів); час; кого сповістити |
| **Specific Date** | конкретна дата й час; кого сповістити |

У тріалі (26.09.2026) написання пункту в списку саме `Day(s) before Due Date`; а після збереження
**On Due Date** поле **Reminder** показує напис «On the Same Day at HH:MM».

Кнопка — **Set Reminder**. Коли нагадування вже є, поле пропонує **Update reminder** і **Remove
Reminder** — кнопки «додати ще одне» немає. Нове налаштування **замінює** попереднє; у тріалі це
підтвердило повідомлення «Reminder Updated Successfully». Отримувач за замовчуванням — виконавець
(`Assignee`). «Manual reminders (one-time or recurring)» з документа — це `Daily` (повторюване) і
решта режимів (одноразові).

Довідка перелічує випадки, коли нагадування **не поставити**: issue вже прострочений; дедлайну
немає; дата нагадування раніше за сьогодні або дорівнює сьогоднішній; дедлайн — сьогодні; issue
нікому не призначений; issue перенесли в інший проєкт. Це готовий список негативних тестів — і в
тріалі (26.09.2026) підтвердився: на issue з дедлайном на завтра **Days(s) before Due Date = 1**
(за будь-якої години, включно з 23:00) двічі дало помилку «The reminder date should fall after the
current date» — дата нагадування («завтра мінус 1 день» = сьогодні) дорівнює сьогоднішній, тож
продукт її відхиляє. **On Due Date** на тому самому issue зберігається без проблем.

### Сповіщення про події

Автоматичні листи про події налаштовуються в **Setup → Issue Tracker → Notifications** — окремо для
проєкту: для кожної події (створено, призначено, закрито, перевідкрито тощо) — чи надсилати,
кому (**Assignee**, **Reporter**, власник проєкту, **Followers**, інші користувачі) і за яким
шаблоном листа (довідка). **Notification Helper** відповідає на питання «чи отримає цей користувач
лист про цю подію на цьому issue».

Важливо для тестування з одним користувачем: **Zoho не надсилає сповіщення про зміни, які ти зробив
сам** (довідка). Лист «issue призначено тобі» не прийде, якщо ти сам собі його призначив. Для
перевірки сповіщень потрібен другий користувач.

### Від ручного до автоматичного

Нагадування й сповіщення — ручний і напівручний рівень. Далі Zoho Projects автоматизує роботу
правилами: для issues — Business Rules і SLA (у **Setup → Issue Tracker**), для задач — Blueprints,
Workflow Rules, Macro Rules, Email Templates, Email Alerts і Webhooks. Усі вони змінюють поля,
статуси й надсилають листи без участі людини — тобто додають шляхів, якими запис може змінитись.
Коли тестуєш issue, пам'ятай: поле могла змінити не людина, а правило. Історію змін шукай на вкладці
**Activity Stream**.

### Покроково: таймер і нагадування на issue

Це завдання документа **Track Issue Timers and Reminders**. Візьми issue, призначений тобі, з
дедлайном щонайменше через 2–3 дні (наприклад, D+3 `17:00`) — так обидва нагадування точно в
майбутньому. Випадок «нагадування на сьогодні» перевір окремо як граничний.

1. Відкрий issue → у заголовку натисни іконку таймера. Зачекай хвилину-дві → зупини → обери тип
   оплати → **Update**.
   **Що побачиш:** на вкладці **Log Hours** запис з періодом «з — до».
2. Клікни поле **Reminder** → **Based on Due Date** → **Reminder Type** = `On Due Date`, час `09:00`,
   сповістити — виконавця → **Set Reminder**. (Варіант: **Specific Date** = дата дедлайну.)
   **Що побачиш:** у полі **Reminder** — нагадування в день дедлайну. Скриншот №1.
3. Клікни поле **Reminder** ще раз: у формі поточного нагадування лиши **Based on Due Date** і зміни
   **Reminder Type** на `Day(s) before Due Date`, `1` день, час `17:00` (той самий, що в дедлайну —
   тоді це рівно 24 години) → **Update reminder**.
   **Що побачиш:** повідомлення «Reminder Updated Successfully»; у полі — нагадування за 1 день,
   попереднього більше немає. Скриншот №2.
4. Скриншот вкладки **Log Hours** — історія таймера.

Результат: два скриншоти конфігурації нагадування (до і після заміни) і скриншот історії таймера.
У нотатці до здачі одним реченням поясни, чому другий скриншот замінив перший, а не додав друге
нагадування.

## 6.7. Імпорт і експорт

**Імпорт** переносить issues з іншого трекера чи таблиці. Формати — CSV, XLS, XLSX. Що важливо знати
до першого запуску:

| Що | Як насправді (тріал) |
|---|---|
| звідки запускати | з вкладки проєкту **Issues**: **•••** → **Import**. **Setup → Data Administration → Imports** відкриває імпорт **задач** |
| зіставлення колонок | автоматично збіглися 4 колонки з 6: `Description`, `Assignee`, `Due Date`, `Severity`. `Title` → **ISSUES NAME** і `Status` → **STATUS & WORKFLOW** довелося вибрати руками |
| формат дати | за замовчуванням `month - day - year`, хоча портал показує дати як `dd-MM-yyyy`. Не переключиш — дати поїдуть мовчки або рядок не прийметься |
| Assignee | лише e-mail користувача. Ім'я відхиляється з повідомленням «Assignee does not contain emails» |
| значення | у тріалі брали лише ті Severity і Status, що є в порталі (`Major`, а не `Medium`; `In progress`, а не `In Progress`); що майстер робить з іншими, не перевіряли |
| коли з'являться | імпорт асинхронний: екран **Import Scheduled**, лист на пошту, рядки в списку — приблизно за хвилину |

За довідкою майстер також попереджає, якщо одну колонку зіставити з кількома полями. Документ
згадує ще зіставлення колонок з кастомними полями і шаблони імпорту — у тріалі ці пункти не
перевірялись.

**Експорт** (довідка, у тріалі не перевірявся): **Issues** → **•••** → **Export Issues** → обери
custom view, формат (XLS або CSV), перенеси потрібні поля з **Available** у **Selected** →
**Export**; Zoho запропонує зашифрувати файл, посилання на завантаження з'явиться в куті екрана.
Експорт — це бекап, обмін з клієнтом і аналіз офлайн.

### Покроково: імпорт issues з Excel

Це завдання документа **Import Issues from Excel**.

1. Створи файл Excel з колонками `Title`, `Description`, `Severity`, `Status`, `Assignee`, `Due
   Date` і 3–5 рядками. Колонку дат зроби текстовою, щоб Excel не переробив дати по-своєму.
   Приклад (e-mail — той, з яким ти входиш у Zoho; дати підстав свої, на найближчі тижні):

   | Title | Description | Severity | Status | Assignee | Due Date |
   |---|---|---|---|---|---|
   | `Import: checkout total rounds down` | `Total shows 19.99 instead of 20.00 after discount` | `Critical` | `Open` | `you@example.com` | `15-10-2026` |
   | `Import: photo upload fails on Safari` | `Upload spinner never ends` | `Major` | `In progress` | `you@example.com` | `17-10-2026` |
   | `Import: date picker week starts on Sunday` | `EU locale expects Monday` | `Minor` | `Open` | `you@example.com` | `22-10-2026` |
   | `Import: CSV export misses header row` | `First data row is used as header` | `Major` | `To be tested` | `you@example.com` | `19-10-2026` |

   Збережи як `.xlsx` або `.xls`.
2. Проєкт → **Issues** → **•••** → **Import Issues** (у тріалі, 27.09.2026, саме так підписаний
   пункт меню, поруч із **Export Issues**, **Issues Settings**, **Changesets**, **Help**) — відкриє
   сторінку **Import Issues** з двома кроками: **1** формат (перемикач **XLS/XLSX** / **CSV**,
   XLS/XLSX обраний за замовчуванням) і **2** **Select File** — поле «Drop or attach the file here»
   з приміткою «File size cannot exceed 20 MB». Клік по цьому полю відкриває системний діалог
   вибору файлу операційної системи — його автоматизацією не провести, тому завантаження файлу і
   кроки після нього (зіставлення полів, формат дати, сам **Import**) виконуй руками. Обери формат →
   завантаж файл → **Continue**.
3. Зіставлення: перевір кожен рядок. Постав руками `Title` → **ISSUES NAME** і `Status` → **STATUS &
   WORKFLOW**, якщо вони не зіставились самі.
4. Формат дати: обери той, яким записані дати у файлі — для прикладу вище `day - month - year`.
   **Що побачиш:** попередження, якщо одну колонку випадково віддано двом полям.
5. **Import**.
   **Що побачиш:** екран **Import Scheduled**; через хвилину-дві — нові issues у списку з наступними
   ID; на пошту прийде лист.
6. Відкрий два-три імпортовані issues і звір кожне поле з файлом: назва, severity, статус,
   виконавець, **дата саме така, як у файлі**. Скриншоти: підтвердження імпорту і список
   імпортованих issues. Збережи файл — він теж частина здачі.

Якщо імпорт пішов не так, зайві issues доведеться видаляти (видалені issues йдуть у **Setup → Data
Administration → Recycle Bin**). Тому спершу — пробний файл на 1–2 рядки.

## 6.8. Issues на команду (Enterprise)

У тарифі Enterprise issue можна віддати **команді**, а не лише людині. Для цього в layout є поле
**Associated Team** (у стандартному layout тріалу воно є). Команди створюють у **Users → Teams →
Add Team** (довідка). Правила з довідки, які варто знати тестувальнику:

- issue отримує **одну** команду, а виконавців — кількох людей з цієї команди;
- якщо issue вже був призначений людям не з обраної команди, вибір команди **прибирає їх** з
  виконавців — тихий побічний ефект, який варто перевірити окремим кейсом;
- команду можна використати в сповіщеннях, Business Rules, SLA, вебхуках, шаблонах листів і
  custom views (наприклад, `Issues Associated to Team`).

Документ говорить і про команди як спостерігачів; довідка описує лише поле **Associated Team** і
вибір виконавців з команди.

## 6.9. Як це тестувати

**Що довести в кожному завданні:**

| Завдання | Що має бути видно | Доказ |
|---|---|---|
| issue ↔ задача | одна асоціація, видна з обох боків; severity `Major`, дедлайн завтра, виконавець — ти | скриншоти **Tasks** на issue і **Issues** на задачі |
| custom view | лише issues, що відповідають усім трьом умовам; контрольні issues відсіяні; межа діапазону | скриншот результату + скриншот критеріїв |
| таймер і нагадування | запис таймера; нагадування до і після заміни | три скриншоти |
| імпорт | усі рядки імпортовані, поля збігаються з файлом, дати не переставлені | підтвердження, список, файл |

**Негативні й граничні випадки:**

- створення: issue без назви; дедлайн у минулому; severity `None`; зміна **Flag** на `External` —
  хто тепер бачить issue;
- представлення: `Due Date Is` проти `Between`; issue рівно на межі діапазону; статус з іншим
  регістром; два AND-рядки на одному полі; представлення, поширене на всіх, — що бачить інший
  користувач;
- зв'язки: закрити задачу з відкритим пов'язаним issue (чи буде попередження); закрити issue B,
  коли A `blocks` B і A відкритий; `is duplicate of` — закрити один, перевірити інший; зв'язати 11-й
  issue; клонувати issue при вимкненому і при ввімкненому `is clone of` — чи з'явився зв'язок з
  оригіналом; чи є `is clone of` серед типів при ручному зв'язуванні;
- нагадування: друге нагадування; нагадування без дедлайну; без виконавця; на прострочений issue;
  «за 1 день» при дедлайні завтра;
- імпорт: `Medium` у Severity; невідомий e-mail; дата в іншому форматі; порожня назва; статус, якого
  немає в порталі. Для кожного рядка з'ясуй: відхилено рядок, увесь файл чи значення тихо
  підмінено. Тиха підміна — найгірший результат і найцінніша знахідка.

**Приклад тест-кейсу у форматі документа:**

```
Title: "Urgent Issues" view includes an issue due at the end of day 7
Precondition:
- Issue UV-6 exists: Status Open, Severity Critical, Due Date = today + 7 days, 17:00.
- The view Urgent Issues has Due Date Between today 00:00 and the end of day 7.
Steps:
1. Open Issues > Urgent Issues.
2. Search the list for UV-6.
3. Open the view criteria and read the upper bound of Due Date.
Expected Result:
- UV-6 is listed.
- The upper bound includes the whole day 7.
Actual Result: [...]
Pass/Fail: [...]
Notes/Attachments: screenshot of the list and of the criteria.
```

**Чек-лист у форматі документа:**

| Checklist Item | Completed (Y/N) | Notes |
|---|---|---|
| Issue has Severity Major, Assignee = me, Due Date = tomorrow | | |
| Task and issue show each other (Tasks (1) / Issues (1)) | | |
| Urgent Issues uses Is (multi-value) for Status and Severity, Between for Due Date | | |
| Control issues are excluded; the boundary issue is included | | |
| Urgent Issues is a favorite | | |
| Timer entry is saved in Log Hours | | |
| Reminder replaced, not added; both states captured | | |
| All imported rows are present; dates match the file | | |

## 6.10. Типові помилки

**1. Шукати Medium чи High у Severity.** Шкала: `None`, `Show stopper`, `Critical`, `Major`,
`Minor`.

**2. Шукати Priority чи Type в issue.** Їх немає: терміновість — дедлайн, тип — Classification чи
Module.

**3. Фільтрувати дату оператором Is.** Is на даті з часом — одна хвилина. Для діапазону — Between.

**4. Два AND-рядки на одному полі.** Кілька значень поля — один рядок.

**5. Писати `In Progress`.** У порталі `In progress`.

**6. Зв'язувати issue і задачу двічі.** Асоціація одна й видна з обох боків — друга сторона
перевіряється, а не створюється.

**7. Чекати друге нагадування.** Нагадування одне; нове замінює старе.

**8. Тестувати сповіщення сам на собі.** Про власні зміни Zoho листів не надсилає.

**9. Запускати імпорт issues з Setup.** Там імпорт задач. Issues — з вкладки **Issues** → **•••**.

**10. Писати ім'я замість e-mail в Assignee.** Імпорт приймає лише e-mail.

**11. Пропустити формат дати в майстрі.** За замовчуванням `month - day - year`; перевір результат на
кількох рядках.

**12. Вважати `blocks` просто міткою.** Він забороняє закриття — перевіряти треба заборону.

### Симптом → причина

| симптом | найімовірніша причина |
|---|---|
| немає вкладки **Issues** у проєкті | вона під **•••** (More Tabs); у формі проєкту модуль зветься **Bugs** |
| у Severity немає `Medium` / `High` | шкала `None` / `Show stopper` / `Critical` / `Major` / `Minor` |
| у формі issue немає Priority чи Type | їх немає в стандартному layout issues |
| custom view з `Due Date Is <дата>` порожній | Is на даті з часом збігається лише з `00:00` цього дня |
| view не показує issue з дедлайном на останній день діапазону | верхня межа Between — `00:00` останнього дня |
| view порожній, хоча статуси збігаються | два AND-рядки на одному полі або `In Progress` замість `In progress` |
| зірочки Favorite немає у формі представлення | Favorite ставлять у списку представлень |
| у списку типів при ручному зв'язуванні немає `is clone of` | цей зв'язок ставить лише дія **Clone** |
| клонований issue не пов'язаний з оригіналом | тип `is clone of` вимкнений: **Setup → Issue Tracker → Link Issues**, обери проєкт, увімкни |
| issue не закривається | він `is blocked by` чи `depends on` відкритого issue |
| на задачі не видно пов'язаного issue | шукай вкладку **Issues** в самому рядку вкладок задачі (не в **•••**) і перевір лічильник поруч |
| немає іконки таймера на issue | issue не призначений тобі |
| друге нагадування замінило перше | на issue зберігається одне нагадування |
| нагадування не ставиться | немає дедлайну чи виконавця, issue прострочений або дата нагадування сьогодні чи раніше |
| лист про призначення не прийшов | зміну зробив ти сам — про власні зміни Zoho не пише; або подія вимкнена в **Notifications** |
| **Setup → Data Administration → Imports** відкрив Import Tasks | issues імпортують з вкладки **Issues** → **•••** → **Import** |
| «Assignee does not contain emails» | в Assignee ім'я замість e-mail |
| назва чи статус не імпортувались | `Title` → **ISSUES NAME** і `Status` → **STATUS & WORKFLOW** треба зіставити руками |
| день і місяць переставились | у майстрі лишився формат `month - day - year` |
| після **Import** список не змінився | імпорт асинхронний: екран **Import Scheduled**, зачекай і онови список |
| після вибору команди зникли виконавці | вибір команди прибирає виконавців не з цієї команди |
| картка Kanban не переходить у колонку | workflow статусів не дозволяє такий перехід |

## 6.11. Що варто запам'ятати

1. Issue — проблема, задача — робота; їх асоціюють, і асоціацію видно з обох боків.
2. Severity: `None`, `Show stopper`, `Critical`, `Major`, `Minor`. Priority і Type в issue немає.
3. Статус у порталі — `In progress`, з малої `p`; регістр важливий у фільтрах і імпорті.
4. Due Date — дата з часом: `Is` ловить одну хвилину, для діапазону — `Between`, і перевір межу.
5. Кілька значень поля — один рядок критерію; Favorite — зірочка в списку представлень.
6. `blocks` і `depends on` забороняють закриття; `is clone of` за замовчуванням вимкнений і
   ставиться лише клонуванням.
7. Таймер на issue запускає лише виконавець; записи — на вкладці **Log Hours**.
8. Нагадування на issue одне: нове замінює старе.
9. Про власні зміни Zoho не надсилає сповіщень — для тестів потрібен другий користувач.
10. Імпорт issues — з вкладки **Issues**; Assignee — e-mail; назву й статус зіставляй руками; формат
    дати за замовчуванням `month - day - year`.
11. Імпорт асинхронний, а зайві issues потім доведеться видаляти — спершу пробний файл.
12. Команди на issue — Enterprise; вибір команди може прибрати виконавців.

# Задачі

**6.1.** Виконай завдання документа **Create and Link Issues to Tasks**. Створи issue з назвою `Bug:
Submit Button Not Working`. Признач його собі, severity `Major` (шкала: None, Show stopper, Critical,
Major, Minor), дедлайн — завтра. Створи пов'язану задачу `Fix Submit Button Bug`. Зв'яжи issue із

**6.2.** Виконай завдання документа **Build a Custom Issue View**. Створи custom view для issues з
критеріями: Status = Open або In Progress (у порталі — `In progress`); Severity = Show stopper або
Critical; Due Date між сьогодні і 7 днями від сьогодні (оператор Between; оператор Is збігається
з точною датою й часом). Збережи представлення з назвою `Urgent Issues` і познач як улюблене.
Результат: скриншот представлення і його критеріїв фільтра. Перед цим створи контрольні issues, на

# Розв'язки

**6.1.** Кінцевий стан: issue `Bug: Submit Button Not Working`, `Open`, **Assignee** — ти, **Severity**
`Major`, **Due Date** — завтра; задача `Fix Submit Button Bug`, власник — ти; одна асоціація. На
issue вкладка **Tasks** показує `Tasks (1)`, на задачі секція **Issues** — `Issues (1)`. Асоціацію
створено один раз (з issue через **Associate Tasks** або з задачі через **Associate Issues**) —
друга сторона лише перевіряється. Приклад нотатки до здачі:

> The issue and the task are associated once, from the issue's Tasks tab. The association is shown
> on both records: Tasks (1) on the issue and Issues (1) on the task.

**6.2.** Критерії, з'єднані AND:

```
Status    Is       Open, In progress
Severity  Is       Show stopper, Critical
Due Date  Between  <today 00:00>  and  <end of day today+7>
```

Назва `Urgent Issues`, зірочка в списку представлень заповнена. На контрольних даних з розбору в
результаті `UV-1`, `UV-2`, `UV-6`; `UV-3`, `UV-4`, `UV-5` відсіяні. Якщо `UV-6` не видно — підняти
верхню межу до кінця сьомого дня. Приклад нотатки: «Between is used because Is on a date-time
field matches a single minute. The view is static: its dates must be updated to stay "the next 7
days".»

**6.3.** Очікуване: запис таймера на **Log Hours** з періодом; скриншот №1 — нагадування `On Due
Date` (або **Specific Date** на дату дедлайну); скриншот №2 — після **Update reminder**:
`Day(s) before Due Date` = 1 з часом дедлайну, повідомлення «Reminder Updated Successfully», першого
нагадування більше немає. Нотатка: «An issue keeps one reminder; Update reminder replaced the
due-date reminder with a 1-day-before reminder, so both states were captured one after another.»

**6.4.** Файл — як у прикладі розбору, з твоїм e-mail. У майстрі: `Title` → **ISSUES NAME**,
`Status` → **STATUS & WORKFLOW** (руками), решта — автоматично; формат дати `day - month - year` для
дат виду `15-10-2026`. Після **Import** — **Import Scheduled**, за хвилину-дві issues у списку.
Перевірка: у кожного імпортованого issue назва, severity, статус, виконавець і дата збігаються з
файлом.

**6.5.** Точно потрапить **A**: усі три умови. B: `Major` — ні. C: статус `Reopen` не входить у
список — ні. D: дедлайн D+7 `17:00` пізніше за верхню межу D+7 `00:00` — ні, хоча за змістом «7
днів» мав би бути; це і є пастка верхньої межі. **E**: `00:00` дня D — рівно нижня межа; потрапить,
якщо Between включає межі. Це перевіряють контрольним issue саме на межі й записують результат як
факт.

**6.6.** Помилки: `In Progress` замість `In progress`; два AND-рядки на **Status** (один issue не
може мати два статуси); `High` — такої severity немає; `Due Date Is` ловить одну хвилину. Правильно:

```
Status    Is       Open, In progress
Severity  Is       Show stopper, Critical
Due Date  Between  <today 00:00>  and  <end of day today+7>
```

**6.7.** а) `Show stopper` (або `Critical`, якщо є обхідний шлях) — втрата замовлень; дедлайн —
сьогодні. б) `Minor` за наслідками, але терміновий: дедлайн до релізу, окреме представлення «до
релізу». в) `Major` — функція збоїть, є обхідний шлях; дедлайн звичайний. г) `Minor`; дедлайн без
поспіху. Терміновість виражають **Due Date**, представленнями (як `Urgent Issues`) і правилами
обслуговування; severity лишається чесною оцінкою наслідків.

**6.8.** а) Закрити B не вийде, доки відкритий A (A blocks B). б) Спершу A закривається, потім B —
теж. в) Закрити C не вийде, доки відкритий D (C depends on D). г) F закриється, E лишиться
відкритим — дублікати не закриваються разом. Так описує довідка; точні повідомлення при відмові
запиши з продукту.

**6.9.** Для кожного рядка три реакції: відхилено рядок (з повідомленням), відхилено файл, значення
тихо підмінено (наприклад, `Medium` → `None`, невідомий e-mail → без виконавця, дата → інша дата).
Дефект або щонайменше знахідка — тиха підміна без повідомлення: дані в системі відрізняються від
файлу, і ніхто про це не знає. Відхилення рядка з зрозумілим повідомленням — коректна поведінка. У
тріалі такий файл готували, але не імпортували, тож фактичний результат — твій.

**6.10.** Перелік назв (очікуване — «нагадування не зберігається» з повідомленням):

1. issue без дедлайну;
2. прострочений issue;
3. дата нагадування раніше за сьогодні (**Specific Date** у минулому);
4. дата нагадування — сьогодні;
5. дедлайн — сьогодні;
6. issue без виконавця;
7. позитивний: `Day(s) before Due Date` = 1 при дедлайні через 3 дні — зберігається;
8. заміна: друге налаштування замінює перше.

Усі виконуються одним користувачем, крім перевірки, чи прийшов лист іншому отримувачу. Пункт 4
підтверджено в тріалі (26.09.2026): `Day(s) before Due Date` = 1 при дедлайні завтра дає ту саму дату,
що й сьогодні, і продукт її відхиляє — розбіжності з довідкою тут нема. Серед текстів продукту для
нагадувань issue є «Set the due date to enable the reminder» і «The reminder date should fall after
the current date» — другий текст саме на цей випадок. Приклад повного кейсу:

```
Title: Reminder cannot be set on an issue without a due date
Precondition:
- Issue R-1 exists, is assigned to me and has no Due Date.
Steps:
1. Open R-1 and click the Reminder field.
2. Choose Based on Due Date > On Due Date, time 09:00, notify the assignee.
3. Click Set Reminder.
Expected Result:
- The reminder is not saved; the product explains why (due date is missing).
Actual Result: [...]
Pass/Fail: [...]
Notes/Attachments: screenshot of the message.
```

**6.11.** Zoho не надсилає сповіщень про зміни, які зробив сам користувач. Якщо ти сам собі
призначив issue, листа не буде — і це правильна поведінка, а не баг. Потрібен другий користувач
порталу: він призначає issue тобі (або ти — йому, і лист перевіряє він). Також без другого
користувача не перевірити: що бачить інший користувач у поширеному представленні; що бачить
клієнтський користувач при **Flag** `External`; сповіщення на **Reporter**; видимість за командами.
