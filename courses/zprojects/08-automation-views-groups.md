# Урок 8. Автоматизація, custom views і групи проєктів

*Після уроку ти налаштовуєш workflow-правило з подією, умовою й дією і доводиш, що воно спрацювало
саме через свою умову, а не випадково; будуєш збережені представлення для задач і проєктів;
групуєш проєкти й знаєш, що саме змінює префікс групи. Для QA автоматизація — це невидимий
«користувач», який змінює дані без людини, а представлення й групи — інструменти, якими ти бачиш
рівно те, що треба перевірити.*

---

## 8.1. Workflow rules: подія → умова → дія

**Workflow rule** — правило, яке Zoho виконує сам: коли стається подія і виконується умова, система
робить дію. Людина лише один раз налаштовує правило, далі воно працює мовчки на кожному записі.

З чого складається правило:

| Частина | Що це | Приклад |
|---|---|---|
| модуль | над чим працює правило | проєкти, задачі, записи часу, фази, користувачі |
| layout | на які записи поширюється: усі layouts (**All Layouts**) або вибрані | layout задач одного проєкту |
| execution condition | коли запускається: на дію користувача (**Based on User action**) чи за датою (**Based on Date & Time**) | задачу створено; за 3 дні до дедлайну |
| умови | **Condition 1**, **Condition 2**… — у кожній набір критеріїв | `Task Name` містить `QA` |
| дії | що зробити, коли умова збіглась | **Update Field** → власник = я |

Правила живуть у **Setup → Automation → Workflow Rules**; у тріалі там вкладки **Projects**, **Task**,
**Time Logs**, **Phases**, **Users** — по одній на модуль.

### Як Zoho виконує правило

- **Умови перевіряються по черзі, і за замовчуванням спрацьовує лише перша, що збіглась.** Її дії
  виконуються, решта умов цього правила вже не перевіряються (довідка). Порядок умов — це логіка, а
  не косметика. Виняток дає прапорець умови **Execute Next Condition**: за підказкою продукту з ним
  наступна умова перевіряється, навіть коли поточна збіглась — підтвердь це прогоном на своєму порталі.
- **Правила перевіряються в порядку списку.** Прапорець **Execute the next workflow rule** передає
  запис наступному правилу списку. За довідкою ланцюжок зупиняється в кінці списку або на правилі,
  де прапорець не відмічено. Порядок змінюють перетягуванням і зберігають кнопкою **Save Order**
  (довідка).
- **Правило має перемикач активності.** Неактивне правило не робить нічого; вимкнути правило — це
  найбезпечніший спосіб «відкотити» автоматизацію.
- **Ліміт:** до 20 правил на один layout (довідка; продукт пише те саме: «Only 20 workflows can be
  created per layout»).
- **Правила за датою** не можна застосувати до всіх layouts. У тріалі редактор відповідав: «Select a
  different layout as the Date and time based workflows cannot be applied to All Layouts.»

Дії правила для задач у тріалі: **Update Field** (серед полів — Priority, Owner, Start Date, Due Date,
Duration, Status, Followers, Associated Team, Completion Percentage, Billing Type, Reminder, Color),
**Associate Webhook**, **Associate Custom Function**, **Associate Email Alert**.

**Стандартні правила.** На вкладці **Task** у тріалі вже лежали чотири правила, усі **неактивні**:
`Notify Owner…`, `Notify Follower…`, `Remind Task Owners on the Due Date`, `Assign Task to Project
Owner by Default`. Останнє, судячи з назви, ставить новим задачам власника проєкту — якщо його
ввімкнути, будь-яка твоя перевірка «правило поставило власника» перестає щось доводити. Перш ніж
тестувати своє правило, подивись, що ще активне на тому самому модулі й layout.

**Правило і шаблони проєктів.** Довідка попереджає: для задач у проєктах, створених з шаблону
проєкту, правила з подією створення не спрацьовують. Тестуй у проєкті, створеному з нуля.

### Три інструменти, які легко сплутати

| Інструмент | Як запускається | Що робить |
|---|---|---|
| **Workflow rule** | сам, на подію чи за датою | змінює поля, надсилає листи, викликає вебхуки й функції |
| **Blueprint** | людина натискає перехід | веде задачу по статусах і перевіряє умови кожного переходу |
| **Macro rule** | людина запускає вручну | масово змінює поля багатьох задач за раз |

### Правила для проєктів

Документ описує **Project Automation** — workflow rules над самими проєктами.

**Де:** на сторінці **Projects** кнопка **Automation** відкриває панель правил проєктів; те саме —
**Setup → Automation → Workflow Rules** → вкладка **Projects**. Кнопка **Automation** всередині
проєкту на вкладці **Tasks** — це вже правила **задач**, не проєктів.

**Що всередині (тріал):** панель уже містить стандартні правила, що оновлюють статус проєкту при
архівуванні й розархівуванні. **New Workflow Rule** пропонує дію користувача або дату й час; події
для проєкту — **Created**, **Updated**, **Comment is added**, **Archived**, **UnArchived**,
**Trashed**; є прапорець **Execute the next workflow rule**. Далі — умови й дії, як описано вище, і
**Save Rule**. Документ підсумовує: правила можна редагувати, переставляти, вимикати й видаляти.

Приклади з документа і куди вони насправді належать:

| Приклад | Де реалізувати |
|---|---|
| призначати команду за власником проєкту | правило **проєктів**: подія створення чи оновлення, умова на власника, **Update Field** |
| оновлювати дедлайни, коли змінюється статус задачі | правило **задач**: подія — оновлення статусу задачі |
| лист, коли завантажено документ | довідка описує подію **Document is attached** і для правил задач, і для правил проєктів; у тріалі в списку подій проєкту її не було — шукай її в правилах задач і перевір у своєму порталі |

**Масштаб дії.** У тріалі layout проєктів один на всіх (`Standard Layout`), тож правило проєктів без
звужувальної умови спрацює на **кожному** проєкті порталу. У продукті для цього є й попередження
перед збереженням: для **All Layouts** — «This workflow rule will apply to all the projects since it
is associated with All Layouts. Do you want to save this rule?», для layout, спільного для кількох
проєктів, — таке саме питання з назвою layout. Для вправ додавай умову, яка ловить лише тестові
проєкти, і вимикай правило після перевірки. За довідкою правила проєктів доступні в тарифі
Enterprise; у тріалі вони є.

### Покроково: правило «Auto Assign QA Tasks»

Це завдання документа **Set Up a Workflow Rule Using Automation**.

1. **Підготовка.** **Setup → Automation → Workflow Rules** → вкладка **Task**. Переконайся, що не
   активне жодне правило, яке саме ставить власника задачам (зокрема `Assign Task to Project Owner
   by Default`). Візьми проєкт, створений з нуля, а не з шаблону.
2. Відкрий проєкт → **Tasks** → **Automation** → **New Workflow Rule**. (Або **Setup → Automation →
   Workflow Rules** → **Task** → **New Workflow Rule** — тоді обери layout свого проєкту.) У тріалі
   редактор, відкритий з проєкту, уже був прив'язаний до layout цього проєкту.
3. **Rule Name**: `Auto Assign QA Tasks`.
4. **Based on User action**, подія — створення задачі: **is Created** (рядок читається як «When a
   Task is Created»; довідка називає подію Created). Якщо далі редактор показує **Next** — натисни
   (так описує довідка).
5. **Condition 1** → **Add Criteria**: поле назви задачі (**Task Name**), оператор **Contains**,
   значення `QA` → **Done**.
6. **Add Action** → **Update Field** → **Owner** → ти.
7. **Execute the next workflow rule** не відмічай. **Save Rule**. Переконайся, що перемикач правила
   увімкнений.
   **Що побачиш:** `Auto Assign QA Tasks` у списку правил, активне.
8. Створи задачу з назвою рівно `QA - Login form check`. **Owner** лиши порожнім: якщо форма
   підставила тебе сама, прибери — інакше доказу немає.
   **Що побачиш:** після збереження власник задачі — ти (за потреби онови сторінку).
9. Контроль: створи `Login form check` без власника.
   **Що побачиш:** задача лишилась без власника — правило спрацьовує лише на свою умову.
10. Скриншоти: правило (подія, критерій, дія); задача `QA - Login form check` після спрацювання
    (поле **Owner**, за можливості й історія задачі в **Activity Stream** — продукт позначає там
    оновлення, зроблені умовою workflow-правила). Одне речення: спрацювало чи ні.

Щоб прибрати ефект, правило вимикають перемикачем — задачі, яким воно вже поставило власника,
лишаться з власником.

## 8.2. Custom views: збережені фільтри

**Custom view** — це збережений запит: критерії + назва + хто бачить + де показується. Представлення
не копіює й не змінює даних; видалити чи переробити його безпечно.

### Представлення списку проєктів

Документ описує custom views на сторінці **Projects**. У тріалі список представлень там мав розділи
**Favorite Views**, **Predefined Views** (`All Projects`, `Recently accessed projects`, `Completed
Projects`, `View by Group`, `View by Owner`, `View by Customer`), **Custom Views** і пункт **+ Create
Custom View**.

- **Критерії** з'єднують операторами AND (мають виконатися всі) і OR (достатньо одного); критерії
  можна групувати.
- **Видимість** у формі (тріал): «Show this Custom view only to me», «Show this Custom view to all»,
  «Share this custom view with select users» — це і є private, public і shared з документа.
- **Favorite** у формі немає: зірочку ставлять у списку представлень, навівши курсор на
  представлення.

Приклади документа — лише strict-проєкти, проєкти, що закінчуються цього місяця, бюджет понад поріг
— вимагають даних. Фільтр за бюджетом нічого не покаже, поки в порталі не ввімкнено бюджет (**Setup
→ Portal Configuration → Project & Budget → Budget Settings → Enable Project Budget**) і в проєктів
немає бюджету. Порожній результат не означає, що фільтр працює: доводять його на даних, які мають і
потрапити, і випасти.

### Представлення задач

Для задач усе те саме, плюс кілька деталей (довідка):

| Налаштування | Що дає |
|---|---|
| **Share Custom View** | для всіх користувачів проєкту або для вибраних |
| **Accessibility** | показувати в **Overview → Tasks** і в інших проєктах (усіх або вибраних); не вибрано нічого — представлення є лише в цьому проєкті |
| меню представлення | **Edit**, **Copy Link**, **Delete**, **Clone**, **Set as Default** |
| обмеження | до 20 критеріїв; у шаблонах проєктів custom views не задаються |

Твої представлення з'являються в списку в розділі **My Custom Views**, поширені тобі — у розділі
**Shared Custom Views** (довідка). Ще одна деталь з довідки: у відфільтрованому списку Zoho може
показати й батьківську задачу, яка під фільтр не підпадає, щоб не рвати дерево підзадач. Це не баг
фільтра.

**«Owner = Me» — не те саме, що «Owner = <твоє ім'я>».** Якщо в критерії стоїть конкретний користувач,
поширене представлення покаже всім **твої** задачі. Якщо в критерії поточний користувач, кожен
побачить **свої**. Для особистого представлення різниці немає, для поширеного — принципова.

### Покроково: представлення «My QA Tasks»

Це завдання документа **Create a Custom Task View**.

1. Відкрий проєкт → **Tasks** → список представлень (кнопка з назвою поточного представлення,
   наприклад `All Open`) → **+ Create Custom View**.
2. Назва: `My QA Tasks`.
3. Критерії, з'єднані AND:
   - поле власника (**Owner**) — поточний користувач («я»). Якщо в значеннях немає окремого пункту
     для поточного користувача, обери себе зі списку користувачів і запам'ятай різницю вище;
   - поле назви (**Task Name**) — **Contains** — `QA`.
4. Доступ — лише тобі. **Save**.
5. У списку представлень наведи курсор на `My QA Tasks` → зірочка (Favorite).
6. Створи дві задачі: `QA - Homepage checks` і `QA - Checkout validation`, власник — ти. (Якщо
   правило `Auto Assign QA Tasks` активне, воно саме поставить тебе власником — ще одне
   підтвердження, що воно працює.)
7. Контроль: `Homepage copy review` з власником — ти (немає `QA` у назві) і `QA - Unowned check`
   без власника. Для другої: якщо правило поставило тебе власником, прибери власника вручну —
   правило реагує лише на створення.
8. Обери `My QA Tasks`.
   **Що побачиш:** `QA - Homepage checks`, `QA - Checkout validation` (і `QA - Login form check`, якщо
   вона в цьому проєкті й твоя); контрольних задач немає.
9. Скриншот представлення з відфільтрованими задачами і нотатка 1–2 речення: коли це представлення
   корисне.

## 8.3. Групи проєктів і префікс

**Project Group** — категорія для проєктів: за клієнтом, відділом чи напрямом (приклади документа:
Zoho Clients, Internal; Marketing, Development, QA). Групу видно в списку проєктів (є готове
представлення `View by Group`), групи можна переставляти й видаляти. **Група не впливає на права
доступу** — це мітка для навігації, а не межа видимості.

**Де:** **Projects** → вкладка **Project Groups** (поряд з **Active Projects**, **Project Templates**,
**Public Projects**, **Archived Projects**) → **New Group** → назва групи (і префікс, якщо його
ввімкнено) → **Create Group**.

### Префікс групи

Кожен проєкт має ID, наприклад `TE-2`. `TE-` — префікс проєктів порталу (**Setup → Portal
Configuration → Project & Budget**, розділ Prefix & ID). **Префікс групи замінює цей префікс в ID
проєкту**:

| До | Після приєднання до групи з префіксом `QAINT` |
|---|---|
| ID `TE-2` | ID `QAINT-2` — номер той самий |
| назва `temp` | назва `temp` — **не змінюється** |
| ID задач і issues проєкту (вигляду `QT1-T5`, `QT1-I2`) | без змін — у них свій префікс (Task & Issues Prefix) |

Правила префікса:

- поле префікса з'являється у формі групи лише після ввімкнення **Project Group Prefix** у **Setup →
  Portal Configuration → Project & Budget** (у довідці — вкладка Project & Project Groups); до того
  поля просто немає;
- до 10 символів («Project Group Prefix must not exceed 10 characters.»); символи — за повідомленням
  продукту лише літери й цифри («Project Group Prefix can only contain alphabets and numbers.»),
  довідка допускає ще дефіс — дефіс перевір тестом;
- префікс, який уже має інша група, продукт не забороняє, а перепитує: «Project Group Prefix already
  exists. Are you sure you want to duplicate it?»;
- проєкти без групи лежать у групі за замовчуванням з префіксом порталу — у тріалі вкладка показувала
  `TE- Ungrouped Projects` поруч з `QAINT- Internal QA Projects`;
- проєкт, перенесений в іншу групу, отримує префікс нової групи (довідка);
- у полі **Project Group** проєкту група показується разом з префіксом: `QAINT-Internal QA
  Projects`.

**Як додати проєкт у групу:** проєкт → меню **•••** біля назви → **Edit Project** → поле **Project
Group**; новий проєкт — поле **Project Group** у формі створення (там же **Add new group**). Щоб
прибрати проєкт з групи, за довідкою його перетягують у **Ungrouped Projects**. Якщо видалити групу,
її проєкти не видаляються — продукт попереджає: «The projects will be moved to Ungrouped Projects
section. This cannot be undone.»

**Чому це важливо QA.** ID проєкту міняється. Усе, що посилалось на старий ID — листи, тікети,
документи, інтеграції (у компанії проєкти створюються автоматично з CRM), — тепер вказує на ID, якого
більше немає. Перевір, чи знаходить пошук проєкт за старим ID.

### Покроково: група «Internal QA Projects»

Це завдання документа **Create and Assign a Project Group**.

1. **Setup → Portal Configuration → Project & Budget** → увімкни **Project Group Prefix**. Це
   налаштування всього порталу.
2. **Projects** → **Project Groups**. Якщо групи `Internal QA Projects` ще немає → **New Group** →
   назва групи `Internal QA Projects`, **Group Prefix** `QAINT` → **Create Group**. Якщо група вже є
   (з попередніх спроб), не плоди дубль: відкрий її редагування й перевір префікс.
   **Що побачиш:** група в списку з префіксом `QAINT`.
3. Візьми існуючий проєкт або створи простий тестовий. Запиши його ID **до** зміни (наприклад,
   `TE-2`).
4. Проєкт → **•••** → **Edit Project** → **Project Group** = `Internal QA Projects`.
   **Що побачиш:** поле показує `QAINT-Internal QA Projects`; ID проєкту став `QAINT-<номер>`, номер
   не змінився, назва не змінилась.
5. **Projects** → **Project Groups** → відкрий `Internal QA Projects`.
   **Що побачиш:** проєкт у списку групи.
6. Скриншот групи з проєктом (і, для повноти, заголовок проєкту з новим ID). Нотатка 1–2 речення: як
   групи допомагають організувати роботу.

Відкотити: поверни проєкт до проєктів без групи (за довідкою — перетягуванням у **Ungrouped
Projects**); ID має знову отримати префікс порталу — перевір це як окремий кейс. Перемикач **Project
Group Prefix** зачіпає весь портал — вимикати його, коли групи вже мають префікси, без потреби не
варто.

## 8.4. Зведена таблиця документа

## 8.5. Як це тестувати

**Що довести в кожному завданні:**

| Завдання | Що має бути видно | Доказ |
|---|---|---|
| workflow rule | назва, подія створення, критерій `Task Name` містить `QA`, дія **Update Field** → **Owner**; правило активне; тестова задача отримала власника, контрольна — ні | скриншот правила, скриншот задачі, речення-висновок |
| custom view | лише твої задачі з `QA` у назві; контрольні задачі відсіяні; Favorite | скриншот представлення + нотатка |
| project group | група з префіксом `QAINT`, проєкт у групі, ID змінився, назва — ні | скриншот групи з проєктом + нотатка |

**Позитивні, негативні й граничні випадки:**

- правило: `qa - lowercase` (чи чутливе «містить» до регістру); `QA` всередині слова (`AQA tools`);
  перейменування наявної задачі на `QA …` (подія створення не має спрацювати); задача з власником,
  заданим у формі (правило перезапише?); вимкнене правило; той самий тест у проєкті з шаблону; два
  правила з однаковою умовою і різними діями — з і без **Execute the next workflow rule**; правило з
  двома умовами, коли запис підходить під обидві, — з і без **Execute Next Condition**;
- представлення: задача з `QA` і чужим власником; твоя задача без `QA`; підзадача з `QA` під
  батьком без `QA`; поширене представлення — що бачить інший користувач; представлення в іншому
  проєкті з увімкненою **Accessibility**;
- групи: префікс з 10 і з 11 символів; префікс з пробілом чи спецсимволом; префікс з дефісом
  (довідка й повідомлення продукту розходяться); префікс, який уже має інша група; перенесення
  проєкту між групами; видалення групи з проєктами; пошук за старим ID; ID задач після зміни групи.

**Приклад тест-кейсу у форматі документа:**

```
Title: Auto Assign QA Tasks sets the owner only when the task name contains "QA"
Precondition:
- The rule Auto Assign QA Tasks is active: Created, Task Name contains QA,
  Update Field Owner = me.
- No other active rule sets the task owner; the project was not created from a template.
Steps:
1. Create task "QA - Login form check" with an empty Owner.
2. Create task "Login form check" with an empty Owner.
3. Open both tasks.
Expected Result:
- "QA - Login form check" has Owner = me.
- "Login form check" has no owner.
Actual Result: [...]
Pass/Fail: [...]
Notes/Attachments: screenshots of the rule and of both tasks.
```

**Чек-лист у форматі документа:**

| Checklist Item | Completed (Y/N) | Notes |
|---|---|---|
| No other active rule sets the task owner | | |
| Rule Auto Assign QA Tasks: Created, Task Name contains QA, Owner = me, active | | |
| Test task got the owner; control task did not | | |
| My QA Tasks: Owner = me AND Task Name contains QA | | |
| Control tasks are not in My QA Tasks; the view is a favorite | | |
| Project Group Prefix is on | | |
| Internal QA Projects has prefix QAINT and lists the project | | |
| Project ID changed (TE-n → QAINT-n); the name did not | | |

## 8.6. Типові помилки

**1. Тестувати правило, коли поруч активне інше, що робить те саме.** Тоді результат нічого не
доводить. Спершу подивись список правил модуля.

**2. Створювати тестову задачу з уже заповненим власником.** Правило нічого не змінить видимо —
доказу немає.

**3. Обрати подію оновлення замість створення.** Правило на оновлення не спрацює при створенні — зате
спрацює на кожну правку задачі, що підходить під умову.

**4. Тестувати у проєкті з шаблону.** За довідкою там правила на створення задачі не спрацьовують.

**5. Сподіватись, що спрацюють усі умови правила.** Спрацьовує лише перша, що збіглась, якщо на
ній не відмічено **Execute Next Condition**.

**6. Шукати правила проєктів у Tasks → Automation.** Там правила задач. Правила проєктів — кнопка
**Automation** на сторінці **Projects** або вкладка **Projects** у Setup.

**7. Створити правило проєктів без звужувальної умови.** Воно спрацює на кожному проєкті порталу.

**8. Шукати Favorite у формі представлення.** Зірочка — у списку представлень.

**9. Вважати порожній результат представлення успіхом.** Доведи фільтр даними, що мають потрапити
й випасти.

**10. Шукати поле префікса в групі до ввімкнення Project Group Prefix.** Його немає, доки перемикач
вимкнений.

**11. Чекати, що префікс групи з'явиться в назві проєкту.** Він замінює префікс в ID; назва та сама.

### Симптом → причина

| симптом | найімовірніша причина |
|---|---|
| правило не спрацювало на новій задачі | правило неактивне, подія не «створення», інший layout, умова не збіглась або проєкт створено з шаблону |
| власник стоїть, хоча правило вимкнене | форма підставила власника або активне інше правило (`Assign Task to Project Owner by Default`) |
| правило спрацювало в усіх проєктах | воно на **All Layouts**, а для проєктів layout один на всіх |
| друга умова правила не виконалась | запис уже збігся з першою, а **Execute Next Condition** на ній не відмічено — далі не перевіряється |
| наступне правило не спрацювало | не відмічено **Execute the next workflow rule** або інший порядок у списку |
| правило за датою не зберігається | обрано **All Layouts** — для дати потрібен конкретний layout |
| у **Tasks → Automation** немає правил проєктів | вони на сторінці **Projects** → **Automation** або у Setup на вкладці **Projects** |
| задача з `QA` не в `My QA Tasks` | власник — не ти, або задача в іншому проєкті без **Accessibility** |
| у представленні видно задачу без `QA` | це батьківська задача, показана заради ієрархії, або критерій з'єднано через OR |
| поширене представлення показує колегам твої задачі | у критерії конкретний користувач, а не поточний |
| у формі групи немає поля префікса | вимкнено **Project Group Prefix** |
| префікс не приймається | понад 10 символів («Project Group Prefix must not exceed 10 characters.») або недопустимі символи («Project Group Prefix can only contain alphabets and numbers.») |
| назва проєкту не змінилась | так і має бути: префікс змінює ID |
| ID задач не змінились | у задач і issues свій префікс |
| після видалення групи проєкти «зникли» з неї | вони перейшли в **Ungrouped Projects** |

## 8.7. Що варто запам'ятати

1. Workflow rule = модуль + layout + подія чи дата + умови + дії; живе в **Setup → Automation →
   Workflow Rules**.
2. Спрацьовує перша умова, що збіглась (далі — лише з **Execute Next Condition**); ланцюжок правил —
   через **Execute the next workflow rule**.
3. Правила за датою не працюють на **All Layouts**.
4. Перед тестом правила перевір сусідні активні правила модуля.
5. Правила проєктів — кнопка **Automation** на сторінці **Projects**; у **Tasks → Automation** —
   правила задач.
6. Правило проєктів без звужувальної умови зачепить усі проєкти порталу.
7. Custom view — збережений запит; не змінює даних; Favorite — зірочка в списку.
8. Фільтр доводять даними, що мають потрапити й випасти.
9. Конкретний користувач у критерії й поточний користувач — різні речі для поширеного представлення.
10. Префікс групи вмикається перемикачем **Project Group Prefix** і замінює префікс в ID проєкту;
    назва й ID задач не змінюються.
11. Групи — для навігації, не для доступу.

# Задачі

**8.1.** Виконай завдання документа **Set Up a Workflow Rule Using Automation**. Відкрий будь-який
проєкт. Перейди в **Setup → Automation → Workflow Rules** → вкладка **Task** (або в проєкті **Tasks
→ Automation**). Створи правило `Auto Assign QA Tasks`: подія — задачу створено; критерій (усі
умови) — Task Name містить `QA`; дія — **Update Field** → власник задачі = ти. Збережи й активуй
правило. Створи тестову задачу з назвою рівно `QA - Login form check` і переконайся, що власник
автоматично став ти. Результат: скриншот правила (подія, критерій, дія), скриншот тестової задачі
після спрацювання і одне речення, чи спрацювало.

**8.2.** Виконай завдання документа **Create a Custom Task View**. Відкрий будь-який проєкт →
**Tasks** → список представлень → **+ Create Custom View**. Назва `My QA Tasks`. Критерії (усі умови):
Owner = я; Task Name містить `QA`. Збережи представлення і познач його як улюблене (якщо доступно).
Створи щонайменше 2 задачі для перевірки: `QA - Homepage checks` і `QA - Checkout validation`. Обери
своє представлення і зроби скриншот відфільтрованого результату. Результат: скриншот представлення з
відфільтрованими задачами і нотатка (1–2 речення), коли це представлення корисне.

**8.3.** Виконай завдання документа **Create and Assign a Project Group**. Перейди на вкладку
**Projects** → **Project Groups**. Створи групу: Group Name `Internal QA Projects`, Group Prefix
`QAINT` (спершу ввімкни **Project Group Prefix**). Додай у групу один проєкт (існуючий або новий
простий тестовий). Відкрий групу і переконайся, що проєкт там є. Перевір ID проєкту: префікс групи
замінює префікс порталу (наприклад, `TE-2` стає `QAINT-2`), назва проєкту не змінюється. Результат:
скриншот групи з проєктом і нотатка (1–2 речення), як групи проєктів покращують організацію.

**8.4.** *(передбач)* Правило задач на подію створення: **Condition 1** — `Task Name` містить `Bug`
→ Priority = High; **Condition 2** — `Task Name` містить `QA` → Owner = Олена. Прапорці **Execute
Next Condition** і **Execute the next workflow rule** не відмічено; наступне в списку правило на ту
саму подію додає тебе у **Followers** усім новим задачам. Що станеться з задачами: а) `QA - Bug in
login`; б) `QA - Smoke`; в) `Release notes`? Що зміниться в а), якщо на **Condition 1** відмітити
**Execute Next Condition**?

**8.5.** *(знайди помилку)* Колега налаштував `Auto Assign QA Tasks`, але «воно не працює». Що
перевіриш і в якому порядку? Його конфігурація: подія **Updated**; критерій `Task Name` містить
`QA`; дія **Update Field** → **Owner** = він; правило активне. Тестова задача `QA - Login form check`
створена в проєкті `Template-Based QA Project` з власником, якого форма підставила сама.

**8.6.** *(поясни)* Чим правило проєктів відрізняється від правила задач: де кожне налаштовується,
на що реагує, на які записи поширюється? Розклади три приклади з розділу документа про Automation
(команда за власником, дедлайни за статусом задачі, лист про завантажений документ) по цих двох
видах правил.

**8.7.** *(спроєктуй тести)* Склади щонайменше вісім тест-кейсів на групи проєктів і префікс:
позитивні, негативні, граничні. Один розпиши повністю у форматі документа.

**8.8.** *(спроєктуй представлення)* Опиши критерії для двох custom views списку проєктів з прикладів
документа: а) проєкти, що закінчуються цього місяця; б) проєкти з бюджетом понад 10 000. Що має бути
ввімкнено в порталі й заповнено в проєктах, щоб б) хоч щось показало? Які дані ти створиш, щоб
довести кожен фільтр?

**8.9.** *(досліди, необов'язково)* Створи правило проєктів з умовою, яка ловить лише тестові
проєкти (наприклад, назва містить `WF-TEST`), і подивись, які поля пропонує **Update Field** для
проєктів. Чи є серед них група проєкту? Якщо так — налаштуй правило, яке кладе новий проєкт
`WF-TEST 1` у групу `Internal QA Projects`, створи проєкт і перевір його ID. Після перевірки вимкни
правило.

# Розв'язки

**8.1.** Кінцева конфігурація:

| Частина | Значення |
|---|---|
| Rule Name | `Auto Assign QA Tasks` |
| Layout | layout твого проєкту (правило створене з **Tasks → Automation**) |
| Execution condition | **Based on User action**, подія створення задачі |
| Condition 1 | `Task Name` містить `QA` |
| Action | **Update Field** → **Owner** = ти |
| Execute the next workflow rule | не відмічено |
| Стан | активне |

Очікуване: `QA - Login form check`, створена без власника, після збереження має власника — тебе;
контрольна `Login form check` лишилась без власника. Речення до здачі: «The rule worked: "QA - Login
form check" was created without an owner and got me as the owner automatically, while the control
task without "QA" stayed unassigned.»

**8.2.** Критерії:

```
Owner      Is         <current user (me)>
AND
Task Name  Contains   QA
```

Представлення `My QA Tasks` у Favorite. Результат: `QA - Homepage checks`, `QA - Checkout
validation` (і інші твої задачі з `QA` у назві); `Homepage copy review` і `QA - Unowned check` відсіяні.
Приклад нотатки: «My QA Tasks shows only the QA tasks assigned to me, so I can plan my testing day
from one list without the rest of the project's work.»

**8.3.** Кінцевий стан: **Project Group Prefix** увімкнено; група `Internal QA Projects` з префіксом
`QAINT`; проєкт у групі; ID змінився з `TE-<n>` на `QAINT-<n>`, номер і назва ті самі; у полі **Project
Group** — `QAINT-Internal QA Projects`. Приклад нотатки: «Project groups sort projects by client or
area; with a group prefix the project ID itself shows the group (TE-2 became QAINT-2), so internal QA
projects are recognisable in any list, while access stays unchanged.»

**8.4.** а) `QA - Bug in login` збігається з обома умовами, але спрацьовує лише перша: Priority =
High, власник не змінюється. **Execute the next workflow rule** не відмічено — наступне правило
(Followers) за довідкою не виконується. б) `QA - Smoke`: перша умова не збіглась, друга — так: Owner
= Олена; Followers — ні (прапорець не відмічено). в) `Release notes`: жодна умова не збіглась,
правило нічого не робить. Чи дійде запис до наступного правила, коли в цьому правилі не збіглась
жодна умова, довідка не уточнює — це кейс для перевірки, а не для віри. З **Execute Next Condition**
на **Condition 1** задача а) за підказкою продукту пройде й другу умову: Priority = High і Owner =
Олена — підтверди це прогоном на своєму порталі.

**8.5.** По черзі: 1) подія **Updated** — на створення правило не реагує; потрібна подія створення.
2) Проєкт створено з шаблону — за довідкою правила на створення там не спрацьовують; тестувати в
проєкті з нуля. 3) Власника підставила форма — навіть працююче правило не показало б зміни; створювати
тестову задачу без власника. 4) Чи немає інших активних правил, що чіпають власника. 5) Чи правило на
тому layout, де живе задача. 6) Регістр і точність назви: `QA` у назві є. Після виправлень — позитивна
й контрольна задачі.

**8.6.** Правило проєктів — сторінка **Projects** → **Automation** або **Setup → Automation →
Workflow Rules** → **Projects**; реагує на події проєкту (створено, оновлено, коментар, архівовано,
розархівовано, у кошику); поширюється на проєкти вибраних layouts проєктів — у тріалі layout один на
всі проєкти. Правило задач — **Tasks → Automation** або вкладка **Task** у Setup; реагує на події задач;
поширюється на задачі проєктів з вибраними layouts задач (у тріалі в кожного проєкту свій). Команда
за власником проєкту — правило проєктів. Дедлайни за статусом задачі — правило задач. Лист про
документ — залежить від того, чи є в списку подій подія на вкладення: довідка описує **Document is
attached** і для задач, і для проєктів, але в списку подій проєкту в тріалі її не було. Відповідь
фіксують за фактичним списком подій свого порталу.

**8.7.** Приклад набору:

1. Групу створено з префіксом `QAINT` — префікс видно в списку груп.
2. Проєкт додано в групу — ID `TE-n` → `QAINT-n`, номер той самий.
3. Назва проєкту після додавання не змінилась.
4. ID задач і issues проєкту не змінились.
5. Префікс рівно з 10 символів — зберігається.

11. Видалення групи — проєкти не видаляються, переходять в **Ungrouped Projects**; ID — очікувано з
    префіксом порталу (перевір).
12. Пошук проєкту за старим ID — зафіксуй фактичну поведінку.
13. Перемикач **Project Group Prefix** вимкнено — поля префікса у формі групи немає.
