# Урок 4. Задачі, статуси і Kanban

*Після цього уроку ти знаєш, з чого складається задача в Zoho Projects, створюєш її вісьмома
шляхами і розумієш, чим ці шляхи відрізняються, орієнтуєшся на сторінці деталей задачі, налаштовуєш
статуси в layout і пояснюєш різницю між назвою статусу і його типом, а також працюєш із Kanban. Для
QA це базова механіка: кожна точка входу — окремий шлях у коді, а тип статусу тихо керує звітами.*

---

## 4.1. Задача: одиниця роботи

Документ: задачі в Zoho Projects — окремі одиниці роботи, які групують, планують, призначають,
відстежують і включають у звіти. Вони підтримують складні конфігурації: підзадачі, залежності,
облік оплачуваного часу, оновлення статусів.

Де задача живе:

```
Project
  Phase                 (необов'язково)
    Task List           група задач (у тріалі є список General)
      Task              ID на кшталт QT1-T1: префікс задач проєкту + номер
        Subtask         теж повноцінна задача зі своїм ID
```

**Список задач** (task list) — група пов'язаних задач. За довідкою Zoho, у списку може бути до 5000
задач, і в нього є позначка **Internal** (бачать лише користувачі порталу) або **External**
(бачать і клієнти порталу). Список можна прив'язати до фази. У тріалі задачі, створені без вибору
списку, опинялись у списку **General**.

Де задачі видно:

- у проєкті — вкладка **Tasks** з трьома видами: **List**, **Gantt**, **Kanban**;
- по всьому порталу — ліве меню **Overview → Tasks**.

### Поля задачі

Документ ділить поля так:

| група | поля (за документом) |
|---|---|
| базові | назва, опис, пріоритет, власник, строк |
| розширені | тип білінгу (billable / non-billable), відсоток виконання, залежності |
| кастомні | поля під проєкт — для класифікації чи автоматизації |
| вкладення й коментарі | для документування й спільної роботи |

Точні поля layout задачі (довідка Zoho):

| поле | що важливо знати |
|---|---|
| **Owner** | власник (виконавець); їх може бути кілька |
| **Status** | поточний статус; список статусів задає layout |
| **Start Date**, **Due Date** | дати; задача без дат — «незапланована» (Unscheduled) |
| **Duration** | тривалість: у днях (без вихідних і свят), годинах (без неробочого часу), календарних днях (cdays) чи годинах годинника (chours); не більше 10 років |
| **Priority** | **None**, **Low**, **Medium**, **High** |
| **Completion Percentage** | відсоток виконання |
| **Work Hours** | оцінка трудомісткості |
| **Completed on** | коли задачу завершено |
| **Tags**, **Reminder**, **Recurrence** | мітки, нагадування, повторення |
| **Billing Type** | None, Billable, Non-Billable; лише коли в порталі ввімкнено бюджет |
| **Associated Team** | команда, відповідальна за задачу |

Кастомні поля додаються в layout; якщо кастомне поле обов'язкове, задача без нього не
збережеться.

## 4.2. Способи створити задачу

Документ перелічує вісім точок входу. Як кожна працює (довідка Zoho):

| точка входу | де | що вводиш одразу |
|---|---|---|
| **Add Task** | проєкт → **Tasks** → кнопка **Add Task** угорі праворуч | повна форма: назва, опис, список задач, власник, дати, пріоритет (поля статусу немає); **Add** або **Add More** |
| **List view** | **Tasks** → вид List → рядок **Add Task** унизу групи списку | лише назву + Enter; решта — на сторінці деталей |
| **Gantt** | **Tasks** → вид Gantt → рядок **Add Task** у групі списку в табличній частині | лише назву + Enter (у тріалі); кнопка **Add Task** угорі відкриває повну форму |
| **Kanban** | **Tasks** → вид Kanban → **+** (Create New Tasks) у заголовку колонки | лише назву + Enter; решта — на сторінці деталей |
| сторінка списку задач | List або Gantt → наведи на заголовок списку → значок **View Details** → **Tasks** → **Add Task** | задачу одразу в цьому списку |
| **Task Templates** | **Setup → Customization → Task Templates** → **Create a Task List Template** → **Add Task** | шаблон списку з задачами; у проєкт — за довідкою, через **Add Task List → Clone from Task Template** (у тріалі шаблонів задач немає, а на формі **Add Task List** видно посилання **Clone from a Project or Project Template**) |
| пошта | адреса списку задач («To add Task via email to this Task list») | тема листа: `!`/`!!`/`!!!` + назва + дати в mm-dd-yyyy |
| Workload Report | проєкт → **Reports** → **Workload Report** → клік по графіку людини в потрібному періоді | форма задачі: назва, опис, список, дані задачі |

Документ формулює суть кожної: Add Task — повна форма; List — структуровані задачі з фільтрами;
Gantt — створення й зв'язування задач перетягуванням; Kanban — візуальні задачі в колонках; сторінка
списку — задачі в контексті списку; шаблони — готові структури для нових проєктів; пошта —
створення листом на адресу проєкту; Workload — створення й коригування задач з аналізу
навантаження.

Список задач створюється так: **Tasks** → стрілка поруч з **Add Task** → **Add Task List** → назва
→ за бажанням **Related Phase** → якщо фази немає, позначка **Internal** або **External** → **Add**.

**Для QA головне:** це вісім різних шляхів у продукті. Вони можуть по-різному підставляти значення
за замовчуванням, по-різному перевіряти обов'язкові поля і по-різному запускати автоматизацію. У
тріалі задачі з рядків швидкого додавання в List, Kanban і Gantt лягають в той список, у
групі якого їх додали, — без власника, без дат і з пріоритетом None: рядок бере лише назву. Іноді
в проєкті трапляється другий список General з позначкою (External), і задачі з List і Gantt лягають
туди; варіант External → General є у випадному списку **Task List** на формі нової задачі. Після
створення будь-яким шляхом перевіряй, куди й з якими значеннями лягла задача.

## 4.3. Сторінка деталей задачі

Документ: це центральне місце керування життям задачі — редагування всіх даних (власник, строк,
тривалість, пріоритет, список), фоловери, облік годин вручну чи таймером, пов'язані файли й issues,
чат у Zoho Cliq, історія статусів, залежності (блокує / чекає).

Як це виглядає (довідка Zoho):

- відкривається значком **View Details** біля назви задачі (у рядку списку чи на картці Kanban);
  клік по самій назві на картці Kanban вмикає перейменування на місці;
- **зміни зберігаються автоматично** — кнопки «Зберегти» немає, тож помилкову зміну виправляєш
  вручну (у тріалі пріоритет, змінений у панелі деталей, лишився після перезавантаження);
- угорі — випадний список статусу; фоловерів додають окремою кнопкою; опис — через **+**;
- меню задачі (**•••**, Other actions): **Copy Link**, **Color**, **Follow**, **Move**, **Clone**,
  **Trash**, **Associate Blueprint**, **Execute Macro Rule**;
- розділи внизу:

| розділ | для чого |
|---|---|
| Comments | коментарі зі скриншотами й позначками; тут і адреса «To add Task Comment via email» |
| Subtasks | підзадачі |
| Log Hours | записи часу; таймер: старт, пауза, стоп, потім Billable або Non-billable |
| Documents | вкладення |
| Forums | пов'язані дописи форуму |
| Dependency | залежності; статус «чекає» чи «блокує» інші задачі |
| Status Timeline | історія статусів задачі в часі |
| Issues | пов'язані issues (**Associate Issues**) |
| Activity Stream | хто, що й коли змінив |

- значок чату праворуч починає обговорення в Zoho Cliq (працює, лише коли чат Cliq увімкнено).

Два розділи — головні інструменти QA: **Activity Stream** (хто й коли змінив поле — людина чи
правило) і **Status Timeline** (доказ, що статус справді проходив певні стани).

## 4.4. Статуси: де живуть і як ними керувати

### Статус належить layout

У проєкті немає вкладки Settings, де «налаштовують статуси». Статуси — це значення поля **Status**
у **task layout** проєкту. Шлях: **Setup → Customization → Layouts → вкладка Task → твій layout →
поле Status**.

Нагадування: у тріалі кожен проєкт отримує **приватну копію** layout. Тому «твій layout» — не
Standard Layout, а копія, під якою в списку layouts указано твій проєкт. Статус, доданий у копію
одного проєкту, в іншому проєкті не з'явиться: у тріалі статуси `To Do` і `Done`, додані для
першого проєкту, у Kanban другого проєкту не показувались — той мав свою копію зі стандартними
статусами.

### Стандартні статуси

У Standard Layout — вісім статусів: **Open, In Progress, In Review, To be Tested, On Hold, Delayed,
Closed, Cancelled**.

### Назва і тип

Кожен статус має **тип**: **Open** або **Closed**. Це два базові типи, їх не можна видалити; будь-який
новий статус належить до одного з них.

- **Назву** читає людина: вона на картці, у колонці Kanban, у фільтрі.
- **Тип** читає система: від нього залежить, чи вважається задача завершеною.

Що керується типом (приклад на статусах `Done` і `Closed` з типом Closed):

- у виді **All Open** задача в статусі закритого типу зникає зі списку (після перезавантаження), а
  лічильник групи її вже не рахує;
- у виді **All Tasks** вона є і показується перекресленою;
- відсоток виконання проєкту рахує її виконаною: одна така задача з п'яти дала 20%.

Статус `Done` з типом **Open** виглядав би виконаним, а для звітів лишався б відкритим. Та сама
пастка є в готовому шаблоні Software Development: статус `UAT Done` там має тип Open.

### Як додати статус

Кроки:

1. Шестерня → **Customization → Layouts** → вкладка **Task**.
2. Відкрий layout свого проєкту.
3. Наведи курсор на поле **Status** (секція Task Information) → значок олівця **Edit**. Праворуч
   відкривається панель **Status** (вкладки Properties, Permissions, Rules): рядок на кожен
   статус — ручка для перетягування, колір, назва, перемикач **Open | Closed**, кошик.
4. **+ Add Status** → новий рядок з типом Open → назва → за потреби клік по перемикачу (стане
   Closed) і колір.
5. Кнопок збереження немає: редактор layout зберігає зміни сам (біля назви layout на мить
   з'являється `Auto saving...`).

Колір статусу, за довідкою, можна змінити і з Kanban, згрупованого за статусом (у колонки є значок
зміни кольору). Довідка згадує ще кнопку **Create** в кінці колонок Kanban для створення статусу;
основний шлях — через layout.

### Статус за замовчуванням: найтихіша пастка

У тій самій панелі статусів є **Set Default Status** — він визначає, з яким статусом
**народжується кожна нова задача** проєкту. Керування стоїть одразу під **+ Add Status**. Пастка тут
у тому, що після редагування статусів статус за замовчуванням може непомітно з'їхати на `Closed` —
і тоді нові задачі з усіх точок входу народжуються закритими, без жодного попередження від форми, а
відсоток проєкту і Weekly Digest їдуть слідом. Поверни `Set Default Status = Open` — і нова задача
знову народжується `Open`.

Правило: після будь-якої правки статусів відкрий панель ще раз і перевір, який статус стоїть за
замовчуванням; потім створи пробну задачу і подивись, з яким статусом вона з'явилась.

## 4.5. Kanban

Документ: Kanban — дуже наочний спосіб керувати задачами в колонках за **Status**, **Task List**,
**Priority** або **Percentage** (відсоток виконання). Можливості: перетягування задач; швидкі дії —
клонувати, перемістити, редагувати на місці; фільтри за користувачем, списком, власними видами;
згортання й розгортання підзадач у картках; Kanban проєкту і глобальний Kanban. Для сервісних
команд Kanban — основний робочий вид завдяки гнучкості й видимості в реальному часі. Для компанії це
так і є: більшість проєктів ведуться за Kanban.

Як це влаштовано (довідка Zoho):

- **де:** проєкт → **Tasks** → вид **Kanban**; для всіх проєктів — **Overview → Tasks** → Kanban;
- **групування:** випадний список угорі ліворуч, що показує поточне групування: **Status**, **Task
  List**, **Priority** або **Percentage**; колонки — значення вибраного поля. При групуванні за
  статусом колонки — це статуси layout проєкту (нові — в кінці; дошка прокручується вбік). Кнопка
  **Show Option** поруч лише вмикає й вимикає частини картки: Task prefix, Task list, Image Preview,
  Bottom Tray;
- **картка** показує ID задачі, назву, виконавців, дату завершення, пріоритет, таймер, коментарі;
- **перетягування між колонками змінює поле**: статус, список, пріоритет чи відсоток. У тріалі
  після перетягування з'являється повідомлення `Task updated`;
- **порядок усередині колонки** при групуванні за статусом змінює лише Kanban-вид; інші види не
  змінюються;
- **швидкі дії:** правий клік по картці → **View Details**, **Copy Link**, **Color**, **Move** (в
  інший список чи проєкт), **Clone** (кількість копій), **Trash**; назву можна редагувати на місці
  (клік по назві); дату — у нижній смузі картки;
- **масові зміни:** познач картки (прапорець на картці) → **Move**, **Trash**, **Associate Issues**,
  **Owner**, **Status**, **Tags**, **Start Date**, **Due Date**, **Priority**, **Associated Team**,
  **Billing Type**; кнопки остаточного видалення серед них у тріалі немає;
- **фільтри:** готові види (All Tasks, All Open, All Closed, All Overdue & Open, Unassigned,
  Unscheduled Tasks, Closed Task Lists), «мої» види (My Open, My Closed, My Overdue & Open, Today's
  Tasks, Tasks I Follow, Tasks Created By Me, Task Associated to Team, Assigned Via Pick List) і
  власні види;
- **підзадачі:** опція **Collapse Subtasks**; вимкни її, щоб бачити підзадачі.

Для QA перетягування — окремий шлях запису: поле змінюється без відкриття форми. Все, що має
спрацьовувати при зміні статусу (правила, обмеження, процеси), треба перевіряти й через
перетягування.

## 4.6. Покроково: Assignment 2 — Add Tasks and Set Up a Kanban View

**Мета завдання:** зрозуміти створення задач, керування статусами і Kanban.

Вимоги: у проєкті `QA Training Project – <твоє ім'я>` щонайменше 5 задач у різних статусах, як-от
To Do, In Progress, Review, Done; кожна з пріоритетом; Kanban проєкту; щонайменше одна задача
перетягнута між статусами. Deliverable: скриншоти списку задач і Kanban-дошки.

### Частина 1. Статуси

Статуси з документа — приклади («such as»), а в layout уже є вісім. Розумне рішення:

| статус з документа | що робиш | тип |
|---|---|---|
| To Do | додаєш | Open |
| In Progress | є готовий | Open |
| Review | не створюєш: є **In Review** з тим самим змістом | Open |
| Done | додаєш | Closed |

Другий майже однаковий статус (Review поруч з In Review) робить список неоднозначним для всіх, хто
ним користується. Своє рішення запиши в здачу одним рядком: «Review → використано наявний In
Review». Якщо рецензент наполягатиме на точній назві — додати `Review` з типом Open можна за
хвилину.

**Крок 1.** Шестерня → **Customization → Layouts** → вкладка **Task**. Знайди layout, під яким
указано твій навчальний проєкт, і відкрий його.

**Крок 2.** Наведи на поле **Status** → значок олівця **Edit**.

**Що побачиш:** панель зі списком статусів layout (вісім стандартних, якщо його ще не змінювали),
**+ Add Status** і **Set Default Status**. Подивись, який тип стоїть на перемикачі **Open | Closed**
у кожного статусу, і запиши (у тріалі Closed і Cancelled — тип Closed, решта — Open).

**Крок 3.** **+ Add Status** → `To Do`, тип **Open**, будь-який колір.

**Крок 4.** **+ Add Status** → `Done`, клік по перемикачу — тип **Closed**.

**Крок 5.** Перевір **Set Default Status**: має лишитися `Open` (або той, що був). Не клікай поруч
навмання — керування стоїть одразу під **+ Add Status**.

**Крок 6.** Нічого натискати не треба: редактор зберігає зміни сам (`Auto saving...` біля назви
layout).

**Крок 7.** Перезавантаж сторінку й відкрий **Status** ще раз: `To Do` і `Done` на місці з
правильними типами, статус за замовчуванням не змінився.

Що відкотити легко: назву, тип чи колір статусу змінюють у тому ж редакторі (довідка описує
створення й редагування статусів). Що відкотити важко: задачі, які встигли народитися в
неправильному статусі за замовчуванням, доведеться виправляти вручну.

### Частина 2. П'ять задач

**Крок 8.** Проєкт → **Tasks** → вид **List** → **Add Task**.

**Крок 9.** Створи п'ять задач (у формі: **Task Name**, **Owner** — ти, **Priority**; між задачами —

## 4.9. Типові помилки

**1. Шукати статуси у вкладці Settings проєкту.** Її немає; статуси — у task layout: **Setup →
Customization → Layouts → Task → твій layout → Status**.

**2. Додати статус у Standard Layout.** Проєкт працює на своїй приватній копії — статус там не
з'явиться.

**3. Створити `Review` поруч з `In Review`.** Два статуси з одним змістом плутають усіх.

**4. Дати статусу `Done` тип Open.** Задача виглядатиме завершеною, а звіти рахуватимуть її
відкритою.

**5. Випадково змінити Set Default Status.** Усі нові задачі народжуватимуться в цьому статусі.

**6. Чекати, що Kanban чи рядок List спитає всі поля.** Там вводиш лише назву — решту доповнюєш на
сторінці деталей.

**7. Писати `!!` у назві задачі у формі.** Синтаксис `!`/`!!`/`!!!` довідка описує лише для теми
листа; у формі пріоритет — поле **Priority**.

**8. Вирішити, що задача «зникла».** Вид All Open ховає задачі закритого типу; перемкнись на All
Tasks.

**9. Не перевірити список задач.** У тріалі задачі без вибраного списку опинялись у General, а
завдання вимагає конкретний список.

**10. Здати відео, де не видно заповнених полів.** Покажи наприкінці список з колонками.

### Симптом → причина

| симптом | найімовірніша причина |
|---|---|
| нові задачі народжуються `Closed` | **Set Default Status** стоїть на закритому статусі |
| задача зникла зі списку після перезавантаження | вид All Open, а статус задачі має тип Closed |
| задача в списку перекреслена | її статус має тип Closed |
| у Kanban немає колонок `To Do`/`Done` | статуси додано в інший layout (Standard чи копію іншого проєкту) |
| доданого статусу немає у випадному списку задачі | правили не той layout (у своєму редактор зберігає зміни сам) |
| колонки Kanban — списки задач, а не статуси | у випадному списку групування вибрано Task List |
| у формі нової задачі немає поля Status | так і є: задача народжується в статусі за замовчуванням, статус міняють після створення |
| клік по назві картки Kanban не відкриває задачу | це перейменування на місці; деталі — значок **View Details** |
| у меню задачі чи в масових діях немає Delete | прибирання тут — **Trash** (у кошик) |
| задача з Gantt чи Kanban без власника і з пріоритетом None | швидке додавання бере лише назву; решта — на сторінці деталей |
| з'явився другий список `General` з позначкою (External) | іноді трапляється в тріалі: туди лягають задачі з List і Gantt; причина непостійна — перевір список кожної задачі |
| у рядку задачі немає кнопки таймера | у задачі немає власника |
| під гридом задач `Total Count : #######` | дефект відображення лічильника в тріалі; на задачі не впливає |
| не виходить видалити задачу | за довідкою, задачі видаляють лише Portal Owner, Admin, Manager і власники задачі |
| не знайти, де створити список задач | стрілка поруч з кнопкою **Add Task** → **Add Task List** |
| порядок карток у колонці змінився лише в Kanban | так задумано: порядок усередині статусу діє лише на Kanban-вид |

## 4.10. Що варто запам'ятати

1. Задача живе в списку задач (у тріалі без вибору — у General), список — у проєкті, за бажанням —
   у фазі.
2. Пріоритети задачі: None, Low, Medium, High. `!`/`!!`/`!!!` — лише для теми листа.
3. Вісім точок входу — вісім шляхів у продукті; швидкі рядки в List, Kanban і Gantt беруть лише
   назву.
4. Сторінка деталей зберігає зміни сама; Activity Stream і Status Timeline — твої докази.
5. Статуси — значення поля Status у task layout проєкту (у тріалі — приватна копія).
6. Стандартні статуси: Open, In Progress, In Review, To be Tested, On Hold, Delayed, Closed,
   Cancelled.
7. Тип статусу (Open / Closed) керує видами, перекресленням і відсотком; назва — лише для людей.
8. **Set Default Status** визначає статус кожної нової задачі — перевіряй після кожної правки.
9. Kanban групує за Status, Task List, Priority, Percentage; перетягування змінює поле.
10. Перетягування в Kanban — окремий шлях запису; усе, що стосується статусу, перевіряй і через
    нього.

# Розв'язки

**4.1.** Для layout, який ще не змінювали, — вісім стандартних статусів: Open, In Progress, In
Review, To be Tested, On Hold, Delayed, Closed, Cancelled. У тріалі перші шість мають
тип Open, а `Closed` і `Cancelled` — тип Closed. Статус за замовчуванням має бути `Open`; якщо там
закритий статус — виправ, інакше нові задачі народжуватимуться закритими.

**4.2.** Назву бачать люди (картки, колонки, фільтри), тип — система (чи вважати задачу
завершеною).

- а) Тип Closed: у All Open задачі немає (після перезавантаження), у All Tasks вона є і
  перекреслена. Тип Open: вона є в обох видах і не перекреслена.
- б) Тип Closed: задача рахується виконаною — одна з п'яти дає 20% за методом «за кількістю». Тип
  Open: не рахується — проєкт лишається на 0%, хоча «Done» написано.

**4.3.** Кінцевий стан layout: є `To Do` (Open) і `Done` (Closed); `Review` не створено — у здачі
рядок «Review → In Review (наявний статус з тим самим змістом)»; **Set Default Status** = `Open`;
після перезавантаження обидва нові статуси на місці з тими самими типами. Додатковий доказ —
створи пробну задачу й переконайся, що вона з'явилась в `Open`, потім прибери її в кошик
(**Trash**) або використай у 4.4.

**4.4.** Очікуваний результат: п'ять задач, наприклад:

| Task Name | Status | Priority |
|---|---|---|
| Prepare test data | To Do | Low |
| Write smoke checklist | In Progress | Medium |
| Review acceptance criteria | In Review | High |
| Verify login flow | To be Tested | Medium |
| Close onboarding checklist | Done | Low |

Статуси ставиш уже після створення, у списку (у формі поля статусу немає). Скриншот знімай у виді
**All Tasks**: у All Open задача в `Done` після перезавантаження зникне, і на скриншоті буде чотири
статуси замість п'яти.

**4.5.** Kanban → випадний список групування угорі ліворуч → **Status**; перетягування, наприклад,
`Review acceptance criteria` з In Review у To be Tested → повідомлення `Task updated`. Скриншот
дошки після перетягування (краще пара до/після). Доказ збереження: після перезавантаження картка в
новій колонці; у задачі **Status Timeline** / **Activity Stream** показують зміну статусу; у List
view колонка Status показує новий статус.

**4.6.** Кінцевий стан: чотири задачі в списку `View Tests`:

| задача | точка входу | Owner | Priority | дати | Description |
|---|---|---|---|---|---|
| Views – Add Task button | кнопка Add Task | ти | High | є | є |
| Views – List view | рядок Add Task у List | ти | Medium | є | є |
| Views – Kanban | + у колонці Kanban | ти | Low | є | є |
| Views – Gantt | Add Task у Gantt | ти | будь-який | є | є |

Відео: одна задача за одною, кожна з видимою точкою входу; в кінці — список з колонками власника,
пріоритету, дат і списку. Жодна задача не закрита (якщо закрита — дивись статус за замовчуванням).

**4.7.** Очікувана картина:

| точка входу | одразу | доповнював на сторінці деталей | що підставилось само |
|---|---|---|---|
| Add Task | усе, крім статусу | нічого | статус — за замовчуванням; те, що не заповнив, — значення за замовчуванням layout |
| List (рядок) | назва | власник, пріоритет, дати, опис | список — той, у групі якого додав; статус — за замовчуванням |
| Kanban (+) | назва | власник, пріоритет, дати, опис | список — колонка (при групуванні за списками); статус — за замовчуванням |
| Gantt (рядок у групі) | назва | власник, пріоритет, дати, опис | у тріалі: список — той, у групі якого додав; без власника, пріоритет None |

Ризики для клієнта: задачі без власника (ніхто не отримає сповіщень, таймер недоступний, правила
на власника не спрацюють); пріоритет None (правила й фільтри за пріоритетом їх пропустять);
задачі не в тому списку (не той доступ Internal/External, не та фаза); обов'язкові кастомні поля,
які швидке додавання може обійти, — це треба перевірити окремо.

**4.8.**

- а) Проєкт працює на своїй приватній копії layout; статус треба додавати туди. Не баг.
- б) Навпаки, небезпечніше: задача виглядатиме завершеною, а звіти рахуватимуть її відкритою.
  Зникнення з All Open — правильна поведінка для закритого типу.
- в) Задача в статусі закритого типу; вид All Open її ховає. У All Tasks вона є. Дані на місці.
- г) Спершу перевір **Set Default Status** у layout проєкту — у тріалі саме він «з'їжджає» на
  Closed. Це налаштування, а не збій сервера.
- д) Синтаксис `!!!` працює лише в темі листа. У формі він стане частиною назви; пріоритет
  задається полем **Priority**.

**4.9.**

- а) Пріоритет задачі змінився з Low на High (поле групування = поле, яке змінює перетягування).
- б) Ні: за довідкою, порядок усередині статусу змінює лише Kanban-вид; інші види не змінюються.
- в) Очікувано — дві нові задачі з тими ж даними (назва, поля) і новими ID. Прибери їх: у List
  view познач копії → **Trash** (вони підуть у **Setup → Data Administration → Recycle Bin**, звідки
  їх можна відновити). Довідка згадує в масових діях Kanban і **Delete** (остаточне видалення), але
  в тріалі серед масових дій є лише **Trash**. Якщо твій результат відрізняється від очікуваного —
  запиши фактичне; це і є мета дослідження.

**4.10.** Приклад набору:

| # | Title | Expected Result |
|---|---|---|
| 1 | New status appears only in its own layout | status visible in this project, not in a project with another layout |
| 2 | Closed-type status hides the task from All Open | task not listed in All Open, struck through in All Tasks |
| 3 | Default status is applied to new tasks from every entry point | tasks from Add Task, List, Kanban, Gantt are born in the default status |
| 4 | Kanban drag updates the status and persists | new status after reload, recorded in Status Timeline |

| 7 | Due Date earlier than Start Date is refused | error shown, task not saved with this range |
| 8 | Duration above 10 years is refused | error shown |

Повністю — наприклад, 2 і 4 (зразки в розділі 4.8). Оцінюй свій набір так: є негативні (7, 8), є
перевірка точок входу (3), є перевірка збереження після перезавантаження (4).

**4.11.** Тема листа (дати в mm-dd-yyyy): `!! Views – Email [10-05-2026][10-09-2026]`.

(`[05-10-2026]`), задача отримає 10 травня — помилки не буде. Адреса списку — на сторінці деталей
