# Урок 5. Підзадачі, залежності, roll-up і облік часу

*Після уроку ти розкладаєш задачу на дерево підзадач, зв'язуєш задачі залежностями з лагом, вмикаєш
roll-up і пояснюєш, звідки взявся кожен відсоток на екрані, а ще логуєш час таймером і вручну. Для
QA це чотири механізми, які мовчки перераховують дати, відсотки й години: запис збережено, помилки
немає, а цифра не та. Тут вчимося бачити, хто саме цю цифру порахував.*

---

## 5.1. Ієрархія задач: від проєкту до підзадачі

Робота в Zoho Projects лежить у вкладених контейнерах:

```
Project                    проєкт
  Phase                    фаза (раніше називалась Milestone)
    Task List              список задач; може належати фазі, а може й ні
      Task                 задача
        Subtask            підзадача
          Subtask          ... і так до 6 рівнів вкладеності
```

**Підзадача — це повноцінна задача**, у якої просто є батько. Вона має свій ID (він продовжує
загальну нумерацію задач проєкту: якщо остання задача була `T11`, підзадачі отримають `T12`,
`T13`…), свого власника, пріоритет, тривалість, відсоток виконання, дати початку й кінця. Документ
називає саме ці незалежні властивості: Assigned user, Priority and duration, Completion percentage,
Start and end dates.

Навіщо це потрібно. Велика робота на кшталт «підготувати тестовий набір» не має одного виконавця
й одного дедлайну. Розкладена на підзадачі, вона отримує виконавця й дати на кожен шматок, а
батьківська задача стає зведенням, яке можна рахувати автоматично (roll-up, розділ 5.3).

Ліміт: до **6 рівнів** вкладеності. Підзадачі є в усіх тарифах Zoho Projects.

Де створюють підзадачі:

| Де | Як |
|---|---|
| сторінка задачі | секція **Subtasks** → **Add Subtask** → відкриється форма нової задачі; поле **Task Name** — багаторядкове, звичайний Enter додає рядок, зберігає кнопка **Add** (або **Ctrl+Enter**) |
| List view | правий клік по задачі → **Add Subtask**; або перетягни задачу на іншу — вона стане її підзадачею |
| Gantt | правий клік по задачі → **Create Subtask** |
| Kanban | картки показують підзадачі; перемикач **Collapse Subtasks** згортає й розгортає їх; нову підзадачу надійно додати через сторінку задачі (довідка згадує й додавання підзадач у Kanban, згрупованому за Task List) |

Перетягування працює в обидва боки: задача, кинута на іншу, стає підзадачею; підзадача, витягнута
за межі батька, стає звичайною задачею. Так документ описує «Convert existing tasks into subtasks or
vice versa» і «Organize hierarchies via drag-and-drop».

Правила, які Zoho застосовує до ієрархії (так описує довідка Zoho) — кожне з них готовий тест-кейс:

- закриту задачу не можна зробити підзадачею, і до закритої задачі не можна додати підзадачу;
- закриття батьківської задачі закриває всі її підзадачі;
- щоб перевідкрити підзадачу, спершу перевідкрий батька;
- у відфільтрованому списку Zoho може показати й батька, який під фільтр не підпадає, — щоб не
  рвати дерево.

**Пастка статусу за замовчуванням.** Нова задача отримує статус, заданий у layout задач проєкту:
**Setup → Customization → Layouts → Task →** layout проєкту **→** поле **Status →** **Set Default
Status**. Якщо там опинився статус закритого типу, кожна нова задача народжується закритою
(закресленою), а до закритої задачі підзадачу не додати. У тріалі так можуть народитися одинадцять
задач поспіль — з усіх точок створення, без жодного попередження у формі (у продукті є й перевірка
«Default status should be Open»). Перед вправами створи одну пробну задачу і подивись на її статус.

Чим ієрархія **не є**: це не порядок виконання. Те, що `Write API Tests` лежить під `Write Test
Cases`, нічого не каже про те, що за чим іде. Порядок задають залежності.

### Покроково: дерево «Prepare Test Suite»

Це завдання документа **Build a Task Hierarchy with Subtasks**.

1. Відкрий проєкт → вкладка **Tasks** → перемкни вигляд на **List**. Створи задачу `Prepare Test
   Suite` (кнопка **Add Task** або рядок **Add Task** у списку).
   **Що побачиш:** задача в списку, назва не закреслена. Закреслена — див. пастку вище.
2. Відкрий `Prepare Test Suite` → секція **Subtasks** → **Add Subtask**. Відкриється форма **Add
   Subtask** — це повноцінна форма нової задачі: впиши в поле **Task Name** `Define Test Scenarios` і
   збережи кнопкою **Add** (або **Ctrl+Enter**; звичайний Enter у цьому полі лише додає рядок, бо
   Task Name тут багаторядкове). Так само додай `Write Test Cases`, `Review Test Data`, `Assign Test
   Cases`.
   **Що побачиш:** чотири рядки в секції **Subtasks**; у List view вони стоять з відступом під
   батьком, а біля батька з'явилась стрілка згортання.
3. Відкрий `Write Test Cases` → **Subtasks** → **Add Subtask** → `Write API Tests` → **Add**
   (**Ctrl+Enter**).
   **Що побачиш:** у List view третій рівень відступу: `Prepare Test Suite` → `Write Test Cases` →
   `Write API Tests`.
4. У List view розгорни всі рівні і зроби скриншот усього дерева — це результат завдання.

Усе тут легко відкотити: зайву підзадачу видаляють або витягують з-під батька перетягуванням.

## 5.2. Залежності: порядок робіт, який перераховує дати

Залежність зв'язує дві задачі: **попередник** (Predecessor) і **наступник** (Successor). На
діаграмі Gantt це стрілка, але для Zoho це передусім **правило перерахунку дат**: при жорсткому
зв'язку зсунув попередника — поїхав наступник. Бувають залежності всередині проєкту і між
проєктами.

### Чотири типи

| Тип | Правило | Приклад |
|---|---|---|
| **FS** — Finish-to-Start | наступник не починається, доки попередник не закінчився; тип за замовчуванням | `Testing` після `Development` |
| **SS** — Start-to-Start | наступник не починається, доки не почався попередник | підготовка тестових даних стартує разом з розробкою |
| **FF** — Finish-to-Finish | наступник не закінчується раніше, ніж закінчився попередник | документація фіналізується разом з розробкою |
| **SF** — Start-to-Finish | наступник не може завершитись, доки не почався попередник; рідкісний тип | підтримку старої системи не закрити, доки не стартував запуск нової |

Документ формулює SF інакше («task B must start before A finishes»); зараз довідка Zoho описує SF
так, як у таблиці: наступник можна завершити, лише коли попередник починається. Орієнтуйся на
довідку. SS документ спрощує до «B starts at the same time as A» — насправді це нижня межа: B не
раніше за A.

### Лаг і випередження

**Lag** — пауза між попередником і наступником: «B починається через 2 дні після кінця A». Від'ємний
лаг називають **lead** (випередження): B стартує раніше, ніж закінчилась A.

Одиниці лагу (довідка): дні (без вихідних і свят), години (без неробочих годин), календарні дні
(з вихідними) і «годинникові» години (з неробочим часом). Лаг у годинах продукт не прийме, якщо
тривалість задач у порталі задана в днях («Dependency lag cannot be in hours because the Task
Duration is configured in Days.»). Звичайні «дні» рахуються за робочим календарем проєкту — поле
**Business Hours** у формі проєкту. У тріалі це було видно наочно:
`Design` закінчувалась у п'ятницю, а `Development` стала на понеділок; лаг 2 дні після середи дав
старт `Testing` у понеділок.

### Жорсткий і м'який зв'язок

| Link type | Що робить |
|---|---|
| **Hard Link** | дати наступника підпорядковані попереднику: затримка попередника автоматично зсуває наступника |
| **Soft Link** | стрілка є, але дати наступника не рухаються самі |

Тип залежності за замовчуванням (**Default Dependency Type**), тип зв'язку за замовчуванням
(**Dependency Link Type**) і три перемикачі поведінки задаються на двох рівнях (довідка):
**Org Level Task Dependency** — для всього порталу, у **Setup → Portal Configuration → Task &
Timesheet → Task Settings**; **Project Level Task Dependency** — для одного проєкту, у **Setup →
Project Configuration → Task Settings** (проєкт обирають у випадному списку), і він перекриває
портальний. У тріалі саме там, на рівні проєкту, **Dependency Link Type** стояло на `Hard Link`.
Перемикачі:
**Moving up Due Dates** (попередник зсунувся раніше — наступник теж), **Extend Due Dates**
(попередник подовжився — наступник поїхав), **Completing / Reopening a Predecessor Task**
(попередника закрили раніше, пізніше чи перевідкрили — графік наступника оновлюється). Серед
значень **Default Dependency Type** є ще `Automatic`: тип визначається за датами задач, а лаг з ним
не поставиш («Lag cannot be set for 'Automatic'.»). Зміна типу зв'язку за замовчуванням діє лише на
нові залежності, наявні лишаються як були. Для окремої залежності тип зв'язку можна змінити на
сторінці задачі або в Gantt.

### Blocking і Waiting for

Документ говорить про blocking tasks (задача не дає іншим стартувати) і waiting tasks (задача чекає
на інші). У продукті це **статус залежності** на сторінці задачі: **Waiting for** або **Blocking**;
наведи курсор — побачиш список пов'язаних задач. За довідкою статус вмикається в портальних Task
Settings (**Setup → Portal Configuration → Task & Timesheet → Task Settings → Dependency
Status**), а задачі можна відфільтрувати за ним (Blocking tasks, Waiting for tasks, Independent
tasks) і зберегти результат як custom view.

### Де ставлять залежності

| Де | Як (за довідкою Zoho) |
|---|---|
| Gantt | протягни лінію між кінцями двох смуг задач; клік по залежній задачі відкриває тип і **Lag** |
| сторінка задачі | секція **Dependency** → **Add Predecessor** або **Add Successor** → знайди задачу; там же тип, тип зв'язку і **Lag** |
| List view | колонки **Predecessors** / **Successors** → **+Add**; звідти не більше 5 залежностей, решта — зі сторінки задачі |
| Kanban | через сторінку задачі, секція **Dependency** |

Прибрати залежність: секція **Dependency** → меню біля попередника чи наступника → **Unlink** →
**Remove**. У Gantt є ще й кнопка скасування останніх п'яти дій із датами й залежностями — поки ти не
пішов з екрана.

Обмеження, які варто пам'ятати:

- закриті й видалені задачі та задачі з архівних проєктів не можна зробити залежними;
- залежності всередині проєкту — у тарифах Premium, Enterprise, Ultimate; між проєктами — Enterprise
  і Ultimate (задачу іншого проєкту шукають за її ID);
- залежність можна поставити й між задачами без дат, але вони опиняться в секції Unscheduled Tasks
  Gantt, і стрілки на смугах не буде — для скриншота задачам потрібні дати;
- у проєкті з roll-up не можна зв'язати підзадачу з її батьком, а задачу із залежністю не можна
  перетворити на підзадачу.

### Покроково: Design → Development → Testing

Це завдання документа **Create Task Dependencies**. Візьми проєкт, який не є strict: у strict-проєкті
дати задач мусять уміститися в дати проєкту, а ланцюжок з лагом легко вилазить за межі.

1. У **Tasks** створи три задачі з датами й власником (собою):

   | Задача | Назва | Дати |
   |---|---|---|
   | A | `Design` | 3 робочі дні, наприклад пн–ср наступного тижня |
   | B | `Development` | 3 робочі дні, навмисно перекрий їх з A (наприклад, вт–чт) |
   | C | `Testing` | 3 робочі дні, теж з перекриттям з B |

   Перекриття потрібне, щоб побачити роботу Hard Link: після зв'язування дати мають поїхати.
2. Відкрий `Development` → вкладка **Dependency** на сторінці задачі → **Add Predecessor** →
   знайди `Design`. Перевір тип і тип зв'язку: має бути `FS` і `Hard Link` (обидва підставляються
   за замовчуванням, окремо міняти не довелось).
   **Що побачиш:** `Development` більше не перекривається з `Design` — з Hard Link вона стала після
   кінця `Design`. У тріалі цей зсув стається не в ту саму мить, коли зберігається рядок
   залежності: перше читання сторінки одразу після збереження ще показує старі дати
   (перекриття), а повторне відкриття тієї самої задачі за кілька секунд — уже зсунуті. Перевіряй
   результат, перевідкривши задачу, а не за станом одразу після збереження.
3. Відкрий `Testing` → **Dependency** → **Add Predecessor** → `Development`, тип `FS`.
   **Що побачиш:** рядок попередника на кшталт
   `Predecessor <ID задачі Development> · FS · Hard Link`; `Testing` стала після `Development`
   (з тією самою поправкою на невелику затримку перерахунку, що й вище).
4. У тому ж рядку заповни **Lag**: `2` (дні). Перечитай рядок після збереження: лаг може зберегтися
   коректно з першого разу й пережити перезавантаження сторінки, а може зберегтися й порожнім, і це
   видно лише перечитавши — тому перевірку через перечитування варто робити завжди, навіть коли з
   першого погляду все зберіглось.
   **Що побачиш:** `Testing` зсунулась ще на два робочі дні (з урахуванням тієї самої затримки
   перерахунку), тривалість лишилась 3 дні.
5. Перемкнись на **Gantt**: дві стрілки `Design → Development → Testing`, між `Development` і
   `Testing` видно проміжок. Зроби скриншот — це результат завдання.

Те саме можна зробити в Gantt, протягнувши лінію від кінця смуги `Design` до початку смуги
`Development`. Відкотити легко: **Unlink → Remove**, а в Gantt — кнопка скасування дії.

## 5.3. Roll-up: як дані підзадач піднімаються вгору

Без roll-up батьківська задача — окремий запис: у неї свої дати, свій відсоток, свої години, які
ніяк не пов'язані з підзадачами. З roll-up батько стає **зведенням** дітей, а значення
піднімаються далі — у фазу й проєкт. Що саме і куди піднімається (довідка Zoho):

| Що | Звідки → куди |
|---|---|
| дата початку, дата кінця, % виконання, бюджет (якщо ввімкнений) | підзадачі → задачі → фази → проєкт |
| робочі години (**Work Hours**) і залоговані години | лише підзадачі → задачі |

Так покриваються три пункти документа: % Completion Tracking, Work vs. Logged Hours і Schedule
Management (дати фази й проєкту підлаштовуються під дати підзадач).

**Як вмикається.** Roll-up вмикається для одного проєкту: у формі проєкту є галочка **Roll-up**.
Довідка каже, що ввімкнути її при редагуванні можна лише для нових проєктів; у тріалі на панелі
вже існуючого проєкту цієї опції немає. Тому для вправи створюють новий проєкт. Функція
доступна в тарифах Premium і Enterprise; у тріалі Zoho One галочка у формі є.

**Незворотність.** Вимкнути roll-up після ввімкнення не можна (довідка пояснює: ручні значення
поверх автоматичних дали б суперечливі звіти). Тому roll-up вмикають на окремому навчальному
проєкті, а не на робочому.

Roll-up не ввімкнеться, якщо (довідка): є залежність між підзадачею і її батьком; у батьківської
задачі вже є робочі чи залоговані години (продукт згадує ще й таймери); задачі проєкту імпортовані
масово.

Що змінюється в поведінці:

- дати батька = найраніший старт і найпізніший кінець підзадач;
- у батьківську задачу не можна залогувати час: години сумуються з підзадач (у журналі часу вона
  позначена як недоступна для записів);
- у strict-проєкті дати самого проєкту не змінюються, а дати підзадач мусять уміщатися в них.

### Три різні відсотки на одному екрані

Відсоток **батьківської задачі** — це просте середнє відсотків підзадач. Відсоток **списку задач,
фази й проєкту** рахує портальний метод **Project Completion Percentage** (**Setup → Portal
Configuration → Project & Budget**; у довідці — вкладка Project & Project Groups). Методів три:

| Метод | Як рахує |
|---|---|
| за кількістю задач і issues | частка закритих (за типом статусу Open / Closed) |
| за відсотком виконання задач і кількістю закритих issues | середнє відсотків задач; можна обрати, рахувати за кореневими задачами чи за підзадачами |
| за полем ваги | кожна задача й issue важить стільки, скільки записано в обраному числовому полі |

У тріалі з налаштуваннями за замовчуванням одна батьківська задача з трьома підзадачами на 25 / 50 /
100 % дала:

| Рівень | Значення | Звідки |
|---|---|---|
| батьківська задача | **58 %** | середнє: (25 + 50 + 100) / 3 |
| список задач | **33 %** | закрита 1 з 3 |
| фаза | **25 %** | закрита 1 з 4 — батька теж пораховано |

Менеджер дивиться на фазу, інженер — на задачу, і вони бачать різний прогрес однієї роботи. Це не
баг, а три визначення — але в звіті чи передачі клієнту про це треба сказати.

Ще два спостереження з тріалу. Підзадача, якій поставили 100 %, закрилась (стала закресленою) — а
закриті задачі потрапляють у рахунок списку й фази. І **години без дат не сумуються**: **Work
Hours** на підзадачі без дат зберігаються як ставка «на день» (`04:00 / day`), тривалості немає,
загальна сума 0 — батько показував `00:00`. Щойно підзадачам дали дати, ставки стали сумами, і батько
показав `16:00`.

### Покроково: проєкт з roll-up

Це завдання документа **Configure Roll-Up for a Task List**.

1. **Projects** → **New Project** → **Blank project**. Назва `QA Rollup Project`, власник — ти,
   постав галочку **Roll-up**, збережи проєкт.
   **Що побачиш:** одразу після галочки — діалог «Task Roll-up cannot be disabled in the future. Do you
   want to continue?»; підтверди його. Новий проєкт створюється з увімкненим roll-up; галочку вже не
   зняти — тому проєкт окремий.
2. Вкладка **Phases** → **Add Phase** → назва `Release 1`, дати на найближчі два тижні, власник — ти →
   **Add**.
3. **Tasks** → стрілка поруч з **Add Task** → **Add Task List** → назва `Rollup List`, **Related
   Phase** = `Release 1` → **Add**.
4. У `Rollup List` створи задачу `Release Regression`, а в ній три підзадачі: `Smoke Suite`, `API
   Suite`, `UI Suite`.
5. Кожній підзадачі дай дату (один робочий день), **Work Hours** і відсоток:

   | Підзадача | Work Hours | Completion Percentage |
   |---|---|---|
   | `Smoke Suite` | 4 | 25 |
   | `API Suite` | 8 | 50 |
   | `UI Suite` | 4 | 100 |

   Відсоток зручно вводити прямо в колонці **Completion %** у List view.
   **Що побачиш:** `UI Suite` після 100 % стала закресленою; у `Release Regression` — `58 %`, `16:00`,
   дати батька зійшлися з датами підзадач.
6. За бажанням залогуй на `Smoke Suite` годину (колонка **Timelog Total** → форма **New Time Log** →
   **Add**) — у батька в **Timelog Total** з'явиться та сама година. У самого батька цю колонку
   заповнити не вийде.
7. Зроби скриншоти: List view з колонками **Completion %** і **Work Hours** (рівень задачі й списку);
   вкладка **Phases** з відсотком `Release 1` (рівень фази); сторінка `Release Regression` з
   піднятими датами й годинами. Під скриншотами коротко напиши, чому числа різні.

Про години на рівні фази довідка пише неоднозначно: у переліку — лише «підзадачі → задачі», а у
вступі — що дані roll-up можна підняти й до фаз. Що саме показує твоя фаза, зафіксуй як факт, а не
як припущення.

## 5.4. Таймер і журнал часу

**Запис часу** (time log) — це «хто, на якій задачі чи issue, якого дня, скільки годин, оплачувано
чи ні, з якою приміткою». Запис з таймера має ще й період «з — до», який ставить система; у ручному
записі в тріалі періоду не було (довідка згадує, що час початку й кінця можна вказати й руками).
Із записів складаються модуль **Time Logs**, табелі, бюджет і рахунки клієнту: **Billable** години
йдуть у рахунок, **Non Billable** — ні. Тому кожна помилка тут — це гроші.

### Таймер

Таймер запускають, ставлять на паузу, продовжують і зупиняють. Запис з'являється в момент зупинки.

- **Хто може запустити:** лише виконавець задачі чи issue. Іконка таймера видна на задачах,
  призначених тобі; у тріалі її не було на задачах без власника.
- **Де:** колонка з годинником у рядку List view (**Start Timer**), заголовок сторінки задачі, а
  також загальний віджет таймерів у верхній панелі — з нього керують усіма своїми таймерами.
  Поки таймер іде, час видно в заголовку задачі й у назві вкладки браузера.
- **Зупинка:** з'являється форма (довідка) — **Billable** чи **Non Billable**, **Notes**, **Cost Per
  Hour** → **Update** зберігає запис, **Remove** видаляє таймер без запису.
- **Один таймер на портал.** Спроба запустити другий у тріалі дала повідомлення «Multiple timers are
  not allowed in this portal. Pause or stop the current timer to start a new one.». Зупинка першого
  з цього діалогу одразу запустила другий. За це відповідає налаштування **Allow Multiple Timers**
  (**Setup → Portal Configuration → Task & Timesheet** → вкладка **Time Log Settings**).
- **Округлення:** у тріалі 8 хв 12 с роботи таймера стали записом `00:09`.

### Ручний запис

Три місця, куди Zoho дає вписати час руками (довідка): у List view клік по колонці **Timelog
Total** задачі → форма **New Time Log** → **Add**; вкладка проєкту **Time Logs** → **Add Time Log**
(поля: задача чи issue, **Date**, користувач, години **Daily Log**, **Billing Type**, **Notes**, а
за певного налаштування затвердження часу — ще **Approver**) → **Add**; а також секція **Log Hours**
на сторінці задачі.

### Налаштування, які змінюють правила

Коли час «не логується», перш ніж шукати баг, перевір **Time Log Settings** (довідка): дозвіл
логувати закриті задачі й issues (**Allow Log Hours for Closed Tasks and Issues** — у тріалі таймер
запустився на закритій задачі), денні й тижневі ліміти (**Daily Log Hour Limit**, **Weekly Log Hour
Limit**), обмеження за робочими годинами задачі й за її датами, перекриття записів (**Time Log
Overlap**: Allow / Warn but allow / Restrict), дозвіл логувати минуле й майбутнє (**Log Past
Time**, **Log Future Time**), режим **Time Log Configuration** (лише таймер, лише ручні записи чи
обидва). І нагадування: у проєкті з roll-up батьківську задачу не залогуєш.

### Покроково: таймер і ручний запис

Це завдання документа **Use the Task Timer and Log Hours**. Візьми задачу, призначену тобі, без
підзадач (у проєкті з roll-up — не батьківську).

1. List view → у рядку задачі натисни іконку таймера (**Start Timer**).
   **Що побачиш:** таймер іде в рядку, у заголовку задачі й у назві вкладки браузера.
2. Зачекай щонайменше 2 хвилини. Зупини таймер.
3. У формі зупинки обери **Billable**, додай примітку (`timer run for assignment`) → **Update**.
   **Що побачиш:** у секції **Log Hours** задачі запис з періодом «з — до» і позначкою Billable.
4. Додай ручний запис для тієї ж задачі: колонка **Timelog Total** → **New Time Log** (або **Time
   Logs** → **Add Time Log** з вибором цієї задачі): сьогоднішня дата, `01:00`, **Billing Type** =
   `Non Billable`, примітка `manual entry` → **Add**.
   **Що побачиш:** у **Log Hours** два записи; у ручного періоду «з — до» немає, якщо ти його не
   вказав. Внизу підсумок; у тріалі він виглядав як
   `Billable 00:09 h · Non Billable 01:00 h · Total Count: 2`.
5. Зроби скриншот секції **Log Hours** — у ній і історія таймера, і зведення. За бажанням додай
   скриншот вкладки **Time Logs** з колонкою типу оплати.

Записи потім редагують і видаляють на сторінці запису у **Time Logs** — нічого незворотного тут
немає, якщо в порталі не ввімкнене затвердження часу.

## 5.5. Як це тестувати

**Що довести в кожному завданні:**

| Завдання | Що має бути видно | Доказ |
|---|---|---|
| ієрархія | 4 підзадачі першого рівня, 1 другого, назви точно як у документі | скриншот List view з розгорнутим деревом |
| залежності | тип FS в обох зв'язках, лаг 2 дні саме на B → C, дати зсунулись | скриншот Gantt + секція **Dependency** задачі `Testing` |
| roll-up | батько = середнє %, сума годин, дати дітей; відсоток списку й фази | скриншоти List view, **Phases**, сторінки батька |
| таймер | запис таймера Billable ≥ 2 хв, ручний Non Billable, підсумок | скриншот **Log Hours** |

**Негативні й граничні випадки:**

- ієрархія: сьомий рівень підзадачі; підзадача під закритою задачею; закриття батька — чи закрились
  діти; перевідкриття підзадачі при закритому батькові; перетягування задачі із залежністю під
  іншу в roll-up проєкті;
- залежності: цикл (A залежить від C, коли C вже залежить від A через B); закрита задача як
  попередник; лаг у днях через вихідні проти лагу в календарних днях; від'ємний лаг; Soft Link
  проти Hard Link при зсуві попередника; перенесення попередника раніше з вимкненим і ввімкненим
  **Moving up Due Dates**; лаг при типі `Automatic`;
- roll-up: передбач і перевір середнє проти зваженого за годинами (58 % чи 56 %); години без дат;
  додавання четвертої підзадачі й видалення однієї; спроба залогувати час у батька; спроба ввімкнути
  roll-up на проєкті, де в батька вже є години;
- таймер: зупинка раніше ніж через хвилину (як округлиться?); другий таймер; таймер на закритій
  задачі; перезавантаження сторінки під час роботи таймера; ручний запис, що перекривається з
  записом таймера; сума Billable і Non Billable у підсумку.

Результат, який не збігся з очікуванням, спершу звір з налаштуваннями (Task Settings, Time Log
Settings, Project Completion Percentage, статус за замовчуванням у layout) — і лише потім пиши баг.
Багато «дивних» цифр тут — задокументована поведінка.

**Приклад тест-кейсу у форматі документа:**

```
Title: FS dependency with a 2-day lag moves the successor by working days
Precondition:
- The project is not strict; Business Hours = Standard Business Hours.
- Dependency Link Type = Hard Link.
- Development (Mon-Wed) and Testing (3 days) exist, are open and assigned.
Steps:
1. Open Testing > Dependency > Add Predecessor > Development.
2. Check that the type is FS and the link is Hard Link.
3. Set Lag = 2 (days) and re-open the Dependency section.
4. Switch to the Gantt view.
Expected Result:
- The lag is saved as 2 days.
- Testing starts on Monday (Thu and Fri are the lag, the weekend is skipped).
- Testing keeps its 3-day duration.
- The Gantt shows an arrow Development > Testing with a visible gap.
Actual Result: [what really happened]
Pass/Fail: [Pass / Fail with details]
Notes/Attachments: Dependency section and Gantt screenshots.
```

| Checklist Item | Completed (Y/N) | Notes |

## 5.6. Типові помилки

**1. Працювати в проєкті, де нові задачі народжуються закритими.** До закритої задачі не додати
підзадачу, закриту задачу не зробити попередником, а відсотки одразу 100. Спершу перевір статус
пробної задачі.

**2. Плутати ієрархію з порядком.** Підзадача не «йде після» батька чи сестер. Порядок — тільки
залежністю.

**3. Ставити залежності задачам без дат і чекати стрілок.** Такі задачі сидять у Unscheduled Tasks;
на Gantt стрілок немає.

**4. Не перечитати лаг.** Залежність збереглась, а лаг — ні. Відкрий секцію **Dependency** ще раз.

**5. Рахувати лаг календарними днями.** «2 дні» — це робочі дні за календарем проєкту; після середи
наступник стартує в понеділок.

**6. Вмикати roll-up на робочому проєкті.** Вимкнути його не можна. Тільки окремий проєкт.

**7. Шукати галочку Roll-up на панелі старого проєкту.** Вона у формі створення; редагування
доступне лише для нових проєктів.

**8. Вводити Work Hours підзадачам без дат.** Це ставка на день, сума 0, у батька `00:00`.

**9. Чекати однакових відсотків у задачі, списку й фазі.** Задача — середнє підзадач, список і фаза
— портальний метод. Числа різні за визначенням.

**10. Шукати таймер на чужій або непризначеній задачі.** Таймер запускає лише виконавець.

**11. Забути вибрати Billable при зупинці таймера.** Тип оплати потім доведеться правити вручну, а
підсумок уже неправильний.

### Симптом → причина

| симптом | найімовірніша причина |
|---|---|
| нова задача одразу закреслена | статус за замовчуванням у layout задач — закритого типу |
| немає **Add Subtask** або підзадача не додається | батьківська задача закрита |
| підзадачу не вдається перевідкрити | закритий батько — спершу перевідкрий його |
| закрив батька — закрились і всі підзадачі | так працює ієрархія, це задокументовано |
| задачу не знайти в пошуку при **Add Predecessor** | вона закрита, видалена або з архівного проєкту; для іншого проєкту — шукай за ID і перевір тариф |
| стрілка є, а дати наступника не змінились | зв'язок Soft Link або задачі не перекривались |
| лаг 2 дні дав чотири календарні дні | лаг у робочих днях, вихідні пропущено |
| на Gantt немає стрілки між задачами | у задач немає дат — вони в Unscheduled Tasks |
| у формі старого проєкту немає **Roll-up** | вмикається при створенні; редагування — лише для нових проєктів |
| roll-up не вмикається | залежність між підзадачею й батьком, у батька є години або задачі імпортовані масово |
| у батька `00:00` годин, хоча в підзадач є **Work Hours** | у підзадач немає дат — години збережені як ставка на день |
| батько 58 %, список 33 %, фаза 25 % | батько — середнє підзадач, список і фаза — метод Project Completion Percentage |
| підзадача зі 100 % стала закресленою | 100 % закриває задачу |
| у батьківську задачу не залогувати час | проєкт з roll-up: години батька — сума підзадач |
| немає іконки таймера | задача не призначена тобі |
| «Multiple timers are not allowed in this portal…» | вже йде інший таймер; вимкнено **Allow Multiple Timers** |
| 8 хвилин таймера стали `00:09` | так записав тріал: 8 хв 12 с (період `09:05 – 09:14`) → `00:09`; правило округлення довідка не описує — перевір на своїх прогонах |
| лаг не зберігається | тип залежності `Automatic`: «Lag cannot be set for 'Automatic'.» — зміни тип на `FS` |
| ручний запис без періоду «з — до» | так і має бути: період автоматично ставить лише таймер |
| час не логується зовсім | обмеження в **Time Log Settings**: ліміти, дати задачі, перекриття, закриті задачі |

## 5.7. Що варто запам'ятати

1. Підзадача — повноцінна задача з власним ID, власником, датами й відсотком; рівнів — до 6.
2. Закриту задачу не зробиш підзадачею і не додаси до неї підзадач; закриття батька закриває дітей.
3. Ієрархія — не порядок. Порядок — залежності FS, SS, FF, SF.
4. Залежність з Hard Link перераховує дати; Soft Link — лише малює стрілку.
5. Лаг рахується в робочих днях за календарем проєкту; від'ємний лаг — lead.
6. Roll-up вмикають на проєкт при створенні, і вимкнути його вже не можна.
7. Дати й відсоток піднімаються до фази й проєкту, години — лише з підзадач у задачу.
8. Відсоток батька — середнє підзадач; список, фаза й проєкт рахуються портальним методом.
9. Години без дат — ставка на день, а не сума.
10. Таймер запускає лише виконавець; чи можна кілька таймерів одночасно, вирішує **Allow Multiple
   Timers**.
11. Billable або Non Billable вибирають при зупинці таймера чи в ручному записі — це гроші клієнта.

# Задачі

**5.1.** Побудуй ієрархію з завдання документа **Build a Task Hierarchy with Subtasks**. У будь-якому
своєму проєкті створи батьківську задачу `Prepare Test Suite`. Під нею — чотири підзадачі: `Define
Test Scenarios`, `Write Test Cases`, `Review Test Data`, `Assign Test Cases`. Під `Write Test Cases`
додай підзадачу другого рівня `Write API Tests`. Результат: скриншот усього дерева з List view.
Перед початком переконайся, що нові задачі в проєкті створюються відкритими.

**5.2.** Виконай завдання документа **Create Task Dependencies**. Створи три задачі з датами: A
`Design`, B `Development`, C `Testing`. Постав залежності: B залежить від A (Finish-to-Start), C
залежить від B (Finish-to-Start). Додай лаг 2 дні на залежність B → C. Результат: скриншот Gantt, на
якому видно стрілки залежностей.

**5.3.** Виконай завдання документа **Configure Roll-Up for a Task List**. Увімкни roll-up в
існуючому проєкті або створи новий (roll-up не вимикається, тому краще окремий новий проєкт). Створи
1 список задач, 1 фазу і головну задачу з 3 підзадачами. Дай підзадачам різні
відсотки виконання і подивись, як відсоток збирається в батьківській задачі. Результат: скриншот, що
показує roll-up відсотка й годин на рівні списку задач і фази, з короткою приміткою, чому числа на
різних рівнях різні.

**5.4.** Виконай завдання документа **Use the Task Timer and Log Hours**. Відкрий задачу, запусти
таймер, дай йому попрацювати щонайменше 2 хвилини, зупини й залогуй час як Billable. Потім вручну
додай ще один запис часу для тієї ж задачі як non-billable (`Non Billable`). Результат: скриншот
історії таймера і зведення записів часу.

**5.5.** *(передбач)* Батьківська задача в проєкті з roll-up має три підзадачі: 25 % і 4 год, 50 % і
8 год, 100 % і 4 год; у всіх є дати. Портальний метод відсотків — за замовчуванням (за кількістю
закритих). Що покажуть батько (відсоток і години), список задач, де лежать лише ці чотири задачі, і
фаза? Скільки був би відсоток батька, якби Zoho зважував за годинами?

**5.6.** *(передбач)* `Design` триває пн–ср, `Development` — 3 робочі дні, зв'язок FS, Hard Link, лаг
0. Вихідні — субота й неділя. Коли почнеться й закінчиться `Development`? Що зміниться, якщо: а) лаг
2 дні; б) `Design` закінчується в п'ятницю — порівняй лаг 2 дні і лаг 2 календарні дні; в) зв'язок
Soft Link, лаг 0, а `Design` подовжили до п'ятниці?

**5.7.** *(знайди помилку)* Колега пише: «Створив `Prepare Test Suite`, а кнопка додавання підзадачі не
працює. І ще: усі мої нові задачі чомусь закреслені, відсоток проєкту росте сам». Що сталось, де це
перевірити і як виправити, щоб нові задачі знову народжувались відкритими?

**5.8.** *(знайди помилку)* Інша колега: «Увімкнула roll-up у нашому клієнтському проєкті, щоб
подивитись, як воно працює. Тепер не можу залогувати години в батьківські задачі, а вимкнути roll-up
не виходить». Поясни, чому так, і сформулюй правило для команди на майбутнє.

**5.9.** *(спроєктуй тести)* Склади щонайменше вісім тест-кейсів на залежності й лаг: позитивні,
негативні, граничні. Два з них розпиши повністю у форматі документа (Title, Precondition, Steps,
Expected Result, Actual Result, Pass/Fail, Notes/Attachments), решту — однорядковими назвами з
очікуваним результатом.

**5.10.** *(поясни)* Чим відрізняються: а) підзадача і задача-наступник у залежності; б) Hard Link і
Soft Link; в) запис таймера і ручний запис часу — що кожен з них доводить як свідчення роботи?

**5.11.** *(досліди)* Знайди у своєму порталі **Time Log Settings** і подивись значення **Allow Log

таймер на закритій задачі; б) запустити другий таймер, не зупинивши перший. Перевір і запиши

# Розв'язки

**5.1.** Порядок дій — як у покроковому розборі розділу 5.1. Кінцевий вигляд у List view:

```
Prepare Test Suite
   Define Test Scenarios
   Write Test Cases
      Write API Tests
   Review Test Data
   Assign Test Cases
```

Підзадачі мають свої ID у загальній нумерації проєкту. Власники й дати завдання не вимагає. Якщо нова
задача виявилась закресленою — дивись розв'язок 5.7 і почни після виправлення.

**5.2.** Конфігурація після виконання:

| Задача | Predecessor | Тип | Link | Lag |
|---|---|---|---|---|
| `Design` | — | — | — | — |
| `Development` | `Design` | FS | Hard Link | — |
| `Testing` | `Development` | FS | Hard Link | 2 дні |

Очікуване: `Development` починається на першому робочому дні після кінця `Design`; `Testing` —
через два робочі дні після кінця `Development`; тривалості збереглись. На Gantt дві стрілки, між
`Development` і `Testing` видно проміжок. Якщо дати не поїхали — перевір тип зв'язку (Soft Link) і
чи перекривались задачі.

**5.3.** Конфігурація: новий проєкт `QA Rollup Project` з галочкою **Roll-up**; фаза `Release 1`;
список `Rollup List` з **Related Phase** = `Release 1`; батько `Release Regression`; підзадачі з
датами, **Work Hours** 4 / 8 / 4 і відсотками 25 / 50 / 100. Очікуване при налаштуваннях за
замовчуванням: батько 58 % і `16:00`, дати батька = дати підзадач; `UI Suite` закрита; список 33 %
(закрита 1 з 3); фаза 25 % (закрита 1 з 4). Приклад примітки до скриншотів:

> The parent task shows 58% because roll-up averages the subtask percentages (25, 50, 100). The task
> list (33%) and the phase (25%) use the portal's Project Completion Percentage method, which counts
> closed tasks; only UI Suite is closed at 100%. Hours roll up from subtasks to the parent (4 + 8 + 4
> = 16 h).

Допиши до примітки, що показує щодо годин вкладка **Phases**: довідка обіцяє підйом годин лише з
підзадач у задачу, а рівень фази для годин перевір і зафіксуй сам. Якщо твій портал налаштований
інакше, числа списку й фази будуть іншими — тоді в примітці вкажи метод, який стоїть у **Project
Completion Percentage**.

**5.4.** Очікуване в секції **Log Hours** задачі: запис таймера з періодом «з — до», тривалістю від
`00:02` і позначкою Billable; ручний запис `01:00` Non Billable без періоду; підсумок з окремими
сумами Billable і Non Billable та кількістю записів 2. Якщо іконки таймера немає — признач задачу
собі. Якщо з'являється повідомлення про кілька таймерів — зупини той, що йде.

**5.5.** Батько: (25 + 50 + 100) / 3 ≈ **58 %**, години 4 + 8 + 4 = **16 год**. Підзадача зі 100 %
закрита, тому за методом «за кількістю закритих» список покаже частку закритих, а фаза — теж, але зі
своїм знаменником: у тріалі це було 33 % (1 з 3) і 25 % (1 з 4, батька пораховано). Зважений за
годинами варіант дав би (25·4 + 50·8 + 100·4) / 16 = 900 / 16 ≈ **56 %** — Zoho цього не робить,
він бере просте середнє.

**5.6.** Базово `Development` — чт, пт, пн: старт на першому робочому дні після середи, три робочі
дні з пропуском вихідних. а) Лаг 2 дні: чт і пт — пауза, `Development` — пн, вт, ср (саме так у
тріалі поїхала `Testing`). б) `Design` закінчується в пт. Лаг 2 дні рахується робочими днями: пауза
пн і вт, `Development` — ср, чт, пт. Лаг 2 календарні дні «з'їдає» вихідні: пауза сб і нд,
`Development` — пн, вт, ср. в) Soft Link: `Design` тепер закінчується в пт, але дати `Development` самі
не змінюються (чт, пт, пн) — задачі перекриваються в чт і пт, і це видно на Gantt; з Hard Link
`Development` поїхала б на пн–ср. Відповіді б) і в) — прогноз за визначеннями довідки. Якщо результат інший, звір тип зв'язку і перемикач
**Extend Due Dates**.

**5.7.** Статус за замовчуванням у layout задач проєкту став статусом закритого типу. Тому кожна нова
задача народжується закритою (закреслена, 100 %), відсоток проєкту росте, а до закритої задачі не
додати підзадачу. Де перевірити: **Setup → Customization → Layouts → Task →** layout проєкту **→**
поле **Status** → **Set Default Status**. Виправлення: встанови статус відкритого типу (наприклад,
`Open`), збережи, створи пробну задачу й переконайся, що вона не закреслена. Уже створені закриті
задачі перевідкрий вручну.

**5.8.** Roll-up після ввімкнення вимкнути не можна — так задумано: години й відсотки батька
рахуються з підзадач, і ручні значення поверх автоматичних зіпсували б звіти. Тому в батьківські
задачі не можна логувати час — лише в підзадачі. Правило для команди: roll-up вмикають лише на
новому проєкті, свідомо, з домовленістю, що час логують тільки в підзадачі; експерименти — на
окремому навчальному проєкті.

**5.9.** Приклад набору (назва → очікуване):

1. FS без лагу: наступник стартує на наступний робочий день після кінця попередника.
2. FS з лагом 2 дні через вихідні: пауза не включає суботу й неділю.
3. Лаг 2 календарні дні через вихідні: пауза включає вихідні.
4. Від'ємний лаг (lead) −1 день: наступник починається на робочий день раніше, ніж без лагу, і
   перекривається з попередником.
5. Hard Link, попередника подовжили на 2 дні: наступник зсунувся на 2 робочі дні.
6. Soft Link, попередника подовжили: дати наступника не змінились, задачі перекриваються.
7. Цикл A → B → C → A: Zoho не дає зберегти останню залежність (зафіксуй точне повідомлення).
8. Закрита задача як попередник: її не можна обрати.
9. Попередник перенесли раніше при вимкненому **Moving up Due Dates**: наступник лишився на місці;
   при ввімкненому — зсунувся раніше на той самий інтервал.

Пункт 2 повністю розписаний у розділі 5.5 «Як це тестувати». Пункт 6, наприклад, так:

```
Title: Soft link keeps the successor's dates when the predecessor is extended
Precondition:
- Design (Mon-Wed) and Development (Thu-Mon) exist, are open and assigned.
- Development depends on Design: FS, Soft Link, no lag.
Steps:
1. Open Design and move its due date from Wed to Fri.
2. Open Development and read its dates.
3. Open the Gantt view.
Expected Result:
- Development keeps Thu-Mon.
- The Gantt shows the two bars overlapping, the arrow is still there.
Actual Result: [...]
Pass/Fail: [...]
Notes/Attachments: dates before and after, Gantt screenshot.
```

Очікування для решти пунктів узято з визначень довідки. Для пункту 7
«зберегти не можна» — очікування до коректного планувальника. Точне повідомлення запиши як факт
після прогону, заздалегідь його не вигадуй. Дозволить Zoho цикл — це знахідка.

**5.10.** а) Підзадача — частина роботи батька: вона визначає, **з чого** складається задача (і з
roll-up — її дати, відсоток, години). Наступник у залежності — окрема робота, яка визначає, **коли**
можна починати чи закінчувати іншу. Підзадача може не мати жодних залежностей, а наступник може
лежати в іншому списку чи навіть проєкті. б) Hard Link підпорядковує дати наступника попереднику і
зсуває їх сам; Soft Link лише фіксує зв'язок і малює стрілку. в) Запис таймера отримує період «з —
до» від системи, тобто показує, коли саме йшла робота; ручний запис — це заява людини про дату й
кількість годин (навіть якщо вона вписала час початку й кінця). Для перевірки обліку часу ти
тестуєш обидва шляхи окремо.

**5.11.** Відповідь залежить від налаштувань твого порталу — у цьому й сенс задачі. Орієнтир з
тріалу: таймер запустився на закритій задачі, а другий таймер не запустився з повідомленням
«Multiple timers are not allowed in this portal. Pause or stop the current timer to start a new
one.». Якщо твій результат інший — поруч має стояти значення налаштування, яке його пояснює.
