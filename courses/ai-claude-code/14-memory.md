# Урок 14. Пам'ять: CLAUDE.md і auto memory

*Кожна нова сесія Claude Code починається з чистого аркуша: учорашню розмову він не пам'ятає. Щоб
не пояснювати щоразу одне й те саме — як у тебе оформлюють тест-кейси, які дані можна брати, що
ніколи не робити, — є два механізми: файли `CLAUDE.md`, які пишеш ти, і auto memory, яку веде сам
Claude. Після уроку ти створюєш і перевіряєш `CLAUDE.md`, знаєш, де він може лежати і хто його
бачить, переглядаєш і чистиш auto memory і розумієш, чому жоден із цих файлів не є «залізним»
правилом.*

## Коротко

*Картка уроку: прочитай її перед уроком і повернись до неї після.*

**Одним реченням.** `CLAUDE.md` — твої постійні інструкції для Claude, auto memory — його власні
нотатки; обидва підвантажуються на початку кожної сесії, але це підказки, а не закон.

**Навіщо.** Щоб не повторювати ті самі пояснення й виправлення в кожній сесії і щоб Claude
однаково працював у тебе і в колег.

**Де.** Файл `CLAUDE.md` у папці проєкту (або `~/.claude/CLAUDE.md` для всіх проєктів); команди
`/init`, `/memory`, `/context`; нотатки auto memory — у `~/.claude/projects/<project>/memory/`.

**Модель**

- **`CLAUDE.md`** — Markdown-файл з інструкціями, який пишеш ти; Claude читає його на старті сесії.
- **`CLAUDE.local.md`** — те саме, але тільки для тебе в цьому проєкті; не потрапляє в git.
- **`.claude/rules/`** — інструкції, розкладені по файлах; частину можна прив'язати до певних папок.
- **Auto memory** — нотатки, які Claude записує сам: твої вподобання, виправлення, контекст роботи.
- **`MEMORY.md`** — зміст (індекс) auto memory; на старті читаються перші 200 рядків або 25KB.

**Запам'ятай**

1. Пиши в `CLAUDE.md` тільки те, чого Claude не знайде сам у файлах проєкту.
2. Конкретно й коротко: ціль — до 200 рядків на файл; «Use 2-space indentation», а не «пиши гарно».
3. `/context` → **Memory files** показує, які файли справді завантажились.
4. «Запам'ятай …» → auto memory; «додай у CLAUDE.md …» → у файл проєкту.
5. Правило без винятків (наприклад, «ніколи не читати `.env`») — не в `CLAUDE.md`, а в дозволи
   (урок 9) або хук (урок 17).

**Пастки** (симптом → причина)

- Claude ігнорує правило з `CLAUDE.md` → файл не завантажився, правило розмите або суперечить іншому.
- Колеги не бачать твоїх правил → ти писав у `CLAUDE.local.md` або `~/.claude/CLAUDE.md`.
- `AGENTS.md` «перестав читатися» → у проєкті з'явився `CLAUDE.md` або `CLAUDE.local.md`.

**Як перевірити**

- У папці-практиці є `CLAUDE.md` з твоїми правилами; у новій сесії `/context` показує його під
  **Memory files**, а новий тест-кейс від Claude оформлений за цими правилами без нагадувань.

## 14.1. Чому Claude «забуває»

З уроків 4 і 6 ти знаєш: модель не має пам'яті між викликами. У межах сесії Claude Code щоразу
надсилає їй усю історію розмови, а нова сесія — це новий, порожній контекст. Документація каже
прямо: "Each Claude Code session begins with a fresh context window." — кожна сесія починається
зі свіжого контекстного вікна.

Аналогія: Claude — дуже здібний працівник на погодинній основі, який щоранку приходить без
спогадів про вчорашній день. Якщо в нього на столі лежить записка «у нас так заведено: …», він її
прочитає й працюватиме за нею. Якщо записки немає — почне з нуля.

Таких «записок» дві:

| | `CLAUDE.md` | Auto memory |
|---|---|---|
| хто пише | ти | Claude |
| що містить | інструкції й правила | те, чого навчився: вподобання, виправлення, контекст |
| охоплення | проєкт, ти особисто або вся організація | один репозиторій (проєкт) на цьому комп'ютері |
| коли завантажується | у кожній сесії | у кожній сесії (перші 200 рядків або 25KB `MEMORY.md`) |
| для чого | стандарти, порядок роботи, будова проєкту | твої вподобання, твої виправлення, факти, яких немає у файлах |

Найважливіше речення розділу: "Claude treats them as context, not enforced configuration." Тобто
обидва механізми — **контекст**, а не налаштування, яке Claude Code примусово виконує. Claude
читає інструкції і зазвичай їх дотримується, але гарантії немає. Пам'ятаєш з уроку 9: правила
дозволів виконує сам Claude Code, а не модель. Тут навпаки — `CLAUDE.md` читає модель і вирішує
сама.

⏸ **Зупинись і перевір себе.** Ти написав у `CLAUDE.md`: «Ніколи не видаляй файли з папки
`evidence`». Чи гарантує це, що Claude їх не видалить?

> **Відповідь.** Ні. `CLAUDE.md` — контекст, а не примусове правило: Claude майже завжди
> дотримається, але може й ні. Для «ніколи» потрібен механізм, який виконує сам Claude Code:
> правило заборони в дозволах (урок 9) або хук (урок 17).

## 14.2. Що таке `CLAUDE.md` і що в нього писати

`CLAUDE.md` — звичайний текстовий файл у форматі Markdown (урок 2: розширення `.md`). Його ім'я
пишеться саме так, великими літерами. Claude Code сам знаходить такі файли й додає їхній вміст у
контекст на початку сесії. Технічно це додаткове повідомлення після системних інструкцій, тому
воно впливає на поведінку, але не має сили закону.

### Коли щось додавати

Документація радить дописувати `CLAUDE.md`, коли:

- Claude робить ту саму помилку вдруге;
- під час рев'ю виявилось щось, що Claude мав би знати про цей проєкт;
- ти друкуєш у чат те саме виправлення чи пояснення, що й минулої сесії;
- новій людині в команді потрібен був би той самий контекст, щоб почати працювати.

### Що туди писати, а що ні

Claude починає кожне завдання з читання файлів і дуже добре сам розбирається, як влаштований
проєкт. Тож перед кожним рядком задай собі два питання з документації:

1. Чи може Claude дізнатися це, прочитавши файли проєкту?
2. Чи піде він справді це шукати?

Якщо обидві відповіді «так» — рядок зайвий.

| писати | не писати |
|---|---|
| точні команди перевірки: як запустити тести, лінтер | опис папок, який видно з `ls` |
| місця, де проєкт вводить в оману («стара папка `legacy/` ще жива, але не копіюй її стиль») | загальні поради на кшталт «пиши якісно» |
| рішення, яких немає у файлах: домовленості команди, як проходить реліз | довгі покрокові процедури — їм місце у скілі (урок 16) |
| те, що ти вже двічі виправляв | паролі, ключі, токени — ніколи (урок 11) |

### Приклад

*Приклад для папки з тест-кейсами (вигаданий, але типовий):*

```
# QA notes

## Тест-кейси
- ID у форматі TC-<МОДУЛЬ>-<номер>, наприклад TC-LOGIN-001
- Поля: Назва, Передумови, Кроки (нумеровані), Очікуваний результат
- Мова — українська; назви кнопок і полів — англійською, як в інтерфейсі

## Тестові дані
- E-mail тільки на домені example.com, наприклад qa1@example.com
- Справжніх паролів не пиши; пиши «пароль тестового користувача»

## Перевірка
- Після змін у test-data/ запускай: python check_data.py
```

Тут немає «будь уважним»: кожен рядок можна перевірити — ID або має потрібний формат, або ні.

⏸ **Зупинись і перевір себе.** Який із двох рядків варто лишити в `CLAUDE.md`:
«У проєкті є папка `tests`» чи «Один тест запускається так: `pytest tests/test_login.py`»?

> **Відповідь.** Другий. Папку `tests` Claude побачить сам. А точна команда для запуску одного
> тесту — це те, що допомагає йому перевіряти свою роботу, і шукати її щоразу довше, ніж прочитати
> один рядок.

## 14.3. Де лежать файли `CLAUDE.md` і хто їх бачить

`CLAUDE.md` може лежати в кількох місцях, і від місця залежить, на кого він діє:

| рівень | де лежить | для чого | хто бачить |
|---|---|---|---|
| **керована політика** (managed policy) | Windows: `Program Files\ClaudeCode\CLAUDE.md` на системному диску; macOS: `/Library/Application Support/ClaudeCode/CLAUDE.md`; Linux і WSL: `/etc/claude-code/CLAUDE.md` | правила компанії, які розгортає IT | усі користувачі в організації |
| **користувацький** (user) | `~/.claude/CLAUDE.md` | твої особисті вподобання для всіх проєктів | тільки ти, усі проєкти |
| **проєктний** (project) | `./CLAUDE.md` або `./.claude/CLAUDE.md` | команди, домовленості, будова проєкту | команда, через git |
| **локальний** (local) | `./CLAUDE.local.md` (додай у `.gitignore`) | твої тестові URL, улюблені тестові дані | тільки ти, цей проєкт |

`./` означає «у корені проєкту» — у робочій папці (урок 2). `.gitignore` — список файлів, які git
не зберігає (урок 10); саме тому `CLAUDE.local.md` лишається тільки в тебе.

### Як вони завантажуються

- Claude Code читає `CLAUDE.md` і `CLAUDE.local.md` з робочої папки **і з усіх папок вище неї**.
  Запустиш Claude у `Documents/ai-course/qa-notes` — він підхопить і `qa-notes/CLAUDE.md`, і
  `ai-course/CLAUDE.md`, якщо такий є.
- Файли **не заміняють** один одного — вони складаються докупи. Спершу ширші (вище в дереві),
  потім ближчі до робочої папки; у кожній папці `CLAUDE.local.md` йде після `CLAUDE.md`.
- `CLAUDE.md` у **підпапках** робочої папки на старті не читаються. Кожен із них завантажується,
  щойно Claude прочитає, створить або змінить якийсь файл у цій підпапці. Коли це стається, у
  терміналі з'являється рядок `Loaded` зі шляхом до файлу.

Що буде, якщо два файли кажуть різне? Документація: "if two instructions contradict each other,
Claude may pick one arbitrarily." — Claude може обрати будь-яку з двох. Тому суперечності
прибирають, а не сподіваються, що «ближчий файл переможе».

⏸ **Зупинись і перевір себе.** У `~/.claude/CLAUDE.md` написано «відповідай англійською», а в
`CLAUDE.md` проєкту — «відповідай українською». Якою мовою відповість Claude?

> **Відповідь.** Передбачити не можна: обидва файли потрапляють у контекст, і Claude може обрати
> будь-яке з двох правил. Виправлення — прибрати суперечність: наприклад, у загальному файлі
> написати «за замовчуванням англійською, якщо проєкт не каже інакше» або прибрати рядок зовсім.

## 14.4. Як писати інструкції, щоб вони працювали

Документація дає три правила.

**Конкретно.** Пиши так, щоб виконання можна було перевірити:

| розмито | конкретно |
|---|---|
| «Format code properly» | «Use 2-space indentation» |
| «Test your changes» | «Run `npm test` before committing» |
| «Keep files organized» | «API handlers live in `src/api/handlers/`» |

**Коротко.** "target under 200 lines per CLAUDE.md file. Longer files consume more context and
reduce adherence." — до 200 рядків на файл: довші з'їдають контекст і гірше виконуються. Кожен
рядок `CLAUDE.md` трохи відбирає увагу Claude в **кожному** завданні, навіть там, де він не
потрібен. Якщо файл задовгий, Claude Code показує попередження на старті й у `/status`.

**Структуровано й без суперечностей.** Групуй правила під заголовками й списками — так їх легше
виконувати, ніж суцільний текст. Час від часу перечитуй усі свої файли й прибирай застаріле.

### Чому не допомагає КАПС

Стара звичка — писати «ВАЖЛИВО!!!» або «НІКОЛИ» великими літерами, коли Claude щось пропускає.
Документація тепер прямо радить від цього відмовитись: сучасні моделі виконують звичайно
сформульований рядок, а надмірний наголос змушує їх застосовувати правило там, де не треба. Якщо
рядок губиться — файл задовгий. Якщо правило не може мати винятків — йому місце в хуку чи в
правилі заборони.

### Імпорти: `@шлях`

`CLAUDE.md` може підтягувати інші файли: "CLAUDE.md files can import additional files using
@path/to/import syntax." Наприклад:

```
Огляд проєкту — у @README.md.
Правила оформлення баг-репортів — у @docs/bug-format.md
```

Відносний шлях рахується від файлу, в якому стоїть імпорт. Важливо: імпорт допомагає
впорядкувати текст, але **не економить контекст** — імпортований файл завантажується разом із
`CLAUDE.md`. Щоб згадати шлях без імпорту, візьми його в зворотні лапки: `` `@README.md` ``.

### Помічники

- `/doctor` пропонує скоротити `CLAUDE.md`: прибрати те, що Claude і так знайде у файлах.
- `/doctor prompt-audit` шукає застарілі, суперечливі інструкції й посилання на файли, яких уже
  немає, і показує звіт; у файлах нічого не змінює, поки ти не попросиш (потрібна версія 2.1.283+).

⏸ **Зупинись і перевір себе.** Твій `CLAUDE.md` розрісся до 400 рядків. Ти виносиш половину в
`docs/rules.md` і пишеш у `CLAUDE.md` рядок `@docs/rules.md`. Чи стане контексту менше?

> **Відповідь.** Ні. Імпортований файл завантажується разом із `CLAUDE.md`, тож Claude отримає ті
> самі 400 рядків. Зменшити можна, лише прибравши зайве або перенісши частину правил туди, де вони
> вантажаться тільки за потреби: у правила з `paths` (розділ 14.6) чи скіл (урок 16).

## 14.5. Створюємо й перевіряємо `CLAUDE.md` на практиці

Для практики уроків 14–16 знадобиться маленька папка-проєкт. Створи її (урок 2):

```
> cd ~/Documents/ai-course
> mkdir qa-notes
> cd qa-notes
> claude
```

Попроси Claude дати тобі матеріал для роботи:

```
Створи файл login-tests.md з трьома короткими тест-кейсами для форми входу (поля Email і Password).
```

### Три способи створити `CLAUDE.md`

| спосіб | що робиш | коли зручно |
|---|---|---|
| `/init` | Claude аналізує проєкт і сам пише стартовий `CLAUDE.md` | новий проєкт, немає з чого почати |
| попросити | «додай у CLAUDE.md: …» | треба дописати одне-два правила |
| вручну | `/memory` → обрати файл проєкту → він відкриється в редакторі | хочеш повністю контролювати текст |

Про `/init` документація каже: "Claude analyzes your codebase and creates a file with build
commands, test instructions, and project conventions it discovers." Якщо `CLAUDE.md` уже існує,
`/init` не перезаписує його, а пропонує покращення. Після `/init` основна робота — **викреслювати**:
усе, що Claude знайде сам, можна прибрати, а дописати те, чого він не знає.

`/memory` показує список файлів пам'яті (особистий, проєктний тощо), навіть тих, яких ще немає.
Обираєш рядок — файл відкривається у твоєму текстовому редакторі, а якщо його не було, спершу
створюється. Якщо замість вікна редактора термінал перетворився на редактор (наприклад, Vim),
вийти без змін можна так: `Esc`, потім набрати `:q!` і `Enter`.

### Як перевірити, що файл підхопився

1. Вийди з Claude Code (`exit`) і запусти його знову в тій самій папці: `CLAUDE.md` читається на
   старті сесії.
2. Набери `/context`. Під заголовком **Memory files** має бути твій `CLAUDE.md`. Якщо його там
   немає — Claude його не бачить, і ніякі правила в ньому не працюють.
3. Дай завдання, де правила мають проявитися, і не нагадуй про них:

```
Напиши тест-кейс для відновлення пароля.
```

4. Порівняй результат із правилами: формат ID, поля, мова, e-mail на example.com.

Не виконалось одне правило — переформулюй його конкретніше; жодне — спершу перевір `/context`.

⏸ **Зупинись і перевір себе.** Ти щойно попросив «додай у CLAUDE.md правило про формат ID», Claude
відповів, що додав. Чому для перевірки краще почати нову сесію, а не питати в цій самій?

> **Відповідь.** У цій сесії правило й так є в історії розмови, тож Claude виконає його, навіть
> якщо файл не завантажується. Нова сесія показує чесний результат: працює тільки те, що справді
> лежить у файлі й підхоплюється на старті. Плюс `/context` у новій сесії показує, чи файл серед
> **Memory files**.

## 14.6. Особисте й часткове: `CLAUDE.local.md`, `~/.claude/CLAUDE.md`, `.claude/rules/`

### Особисте

- **`~/.claude/CLAUDE.md`** — для звичок, однакових у всіх твоїх проєктах: «пояснюй команди
  терміналу одним реченням», «відповідай українською». Бачиш тільки ти.
- **`CLAUDE.local.md`** у корені проєкту — для того, що стосується тільки тебе й тільки цього
  проєкту: адреса твого тестового стенда, твій тестовий користувач. Додай рядок `CLAUDE.local.md`
  у `.gitignore`, щоб файл не потрапив у спільний репозиторій.

Пам'ятай з уроку 11: це звичайні текстові файли. Паролів і ключів у них не пишуть, навіть у
«локальних».

### Правила по файлах: `.claude/rules/`

Коли інструкцій багато, їх можна розкласти по темах у папку `.claude/rules/`:

```
qa-notes/
├── CLAUDE.md
└── .claude/
    └── rules/
        ├── test-cases.md
        └── bug-reports.md
```

Кожен `.md` файл у цій папці — окреме правило. Файл **без** спеціального заголовка завантажується
на старті, так само як `CLAUDE.md`.

Найкорисніше — правило з **`paths`**: воно завантажується лише тоді, коли Claude працює з
файлами, що підходять під шаблон. Це відповідь документації на питання «що робити з довгим
`CLAUDE.md`». Шаблон пишуть у блоці між `---` на початку файлу (такий блок називають
**frontmatter**):

```
---
paths:
  - "bugs/**/*.md"
---

- Кожен баг-репорт починається з рядка Severity: low, medium або high
- Кроки відтворення — нумерований список, по одній дії в кроці
- Окремо пиши «Фактичний результат» і «Очікуваний результат»
```

Шаблони (glob) читаються так:

| шаблон | що підходить |
|---|---|
| `bugs/**/*.md` | усі `.md` файли в папці `bugs` і будь-яких її підпапках |
| `**/*.csv` | усі `.csv` файли в будь-якій папці |
| `*.md` | `.md` файли в корені проєкту |

Таке правило завантажується, коли Claude читає, створює чи змінює файл, що підходить під шаблон.
Поки ти працюєш з іншими файлами, воно не займає контекст.

⏸ **Зупинись і перевір себе.** Ти хочеш, щоб правила оформлення баг-репортів діяли лише тоді, коли
Claude працює в папці `bugs`. Назви два способи це зробити.

> **Відповідь.** 1) Файл `bugs/CLAUDE.md` — він завантажиться, щойно Claude торкнеться файлу в
> `bugs`. 2) Файл у `.claude/rules/` з `paths: - "bugs/**/*.md"` у frontmatter. Обидва не
> займають контекст, поки Claude не працює з цими файлами.

## 14.7. `AGENTS.md`: коли проєкт уже налаштований під інші інструменти

Деякі інші ШІ-інструменти для коду читають файл `AGENTS.md` з тією самою ідеєю — інструкції для
агента. Claude Code (з версії 2.1.277) теж уміє його читати, але за чітким правилом:

| у проєкті є | що читає Claude |
|---|---|
| `AGENTS.md`, і немає `CLAUDE.md` чи `CLAUDE.local.md` у робочій папці або вище | `AGENTS.md` |
| `AGENTS.md` і `CLAUDE.md` або `CLAUDE.local.md` | тільки `CLAUDE.md` |
| `CLAUDE.md`, у якому є рядок `@AGENTS.md` | `CLAUDE.md` разом з імпортованим `AGENTS.md` |

Пастка: проєкт жив на `AGENTS.md`, ти додав свій `CLAUDE.local.md` з особистими нотатками — і
Claude перестав читати `AGENTS.md`. `~/.claude/CLAUDE.md` і файли в `.claude/rules/` до цієї
перевірки не рахуються.

Найпростіший спосіб мати обидва: створити поруч `CLAUDE.md` з першим рядком `@AGENTS.md`, а нижче
дописати те, що стосується тільки Claude. Змінити поведінку можна також у `/config`, параметр
**Project instructions**.

## 14.8. Auto memory: нотатки, які Claude веде сам

### Що це

Auto memory — це пам'ять, яку Claude наповнює без твоєї участі: "Auto memory lets Claude
accumulate knowledge across sessions without you writing anything." У локальних сесіях вона
ввімкнена за замовчуванням.

Claude записує чотири види нотаток і позначає вид полем `type` у заголовку файлу:

| тип | що зберігає | приклад нотатки (вигаданий) |
|---|---|---|
| `user` | твоя роль, досвід, як тобі зручно працювати | «Новачок; пояснювати команди терміналу одним реченням» |
| `feedback` | твої виправлення і підходи, які ти підтвердив | «Хоче спершу короткий підсумок, потім деталі» |
| `project` | поточна робота, терміни, рішення, яких немає у файлах | «Реліз заморожено до кінця місяця» |
| `reference` | де шукати інформацію поза проєктом | «Баги ведуться в трекері, проєкт WEB» |

Чого Claude **не** записує: те, що можна знайти у файлах проєкту (будову папок, шляхи, виправлення
коду), і те, що вже сказано в `CLAUDE.md`. І не в кожній сесії він щось зберігає: лише те, що
знадобиться в майбутніх розмовах.

### Де лежить

```
~/.claude/projects/<project>/memory/
├── MEMORY.md            ← зміст: один рядок на нотатку
├── user_role.md         ← одна нотатка
├── feedback_testing.md  ← ще одна
└── ...
```

`<project>` — назва, утворена зі шляху до проєкту (урок 7: там само лежать сесії). Якщо проєкт —
git-репозиторій, усі його підпапки ділять одну пам'ять; поза git береться корінь проєкту. Пам'ять
**локальна**: вона живе тільки на цьому комп'ютері й не синхронізується з іншими.

Кожна нотатка — звичайний Markdown-файл: угорі короткий блок із назвою, описом і типом, нижче —
сам зміст. Точний вигляд цього блоку залежить від версії Claude Code, тож не спирайся на нього —
читай і правь зміст.

### Як працює

- На старті кожної розмови завантажуються перші 200 рядків `MEMORY.md` або перші 25KB — що
  скінчиться раніше. Решта на старті не читається, тому Claude тримає `MEMORY.md` коротким.
- Окремі файли нотаток на старті не читаються: "Claude reads them on demand" — Claude відкриває їх,
  коли потрібна інформація.
- Коли Claude записує чи читає пам'ять, ти бачиш повідомлення на кшталт «Saved 2 memories» або
  «Recalled 2 memories» (число буде своє).
- Старі сесії видаляються через 30 днів (урок 7), а файли пам'яті — ні: вони лежать, доки ти або
  Claude їх не зміните чи не видалите.

### Як керувати промптами

| ти пишеш | що відбувається |
|---|---|
| «Запам'ятай: тести API потребують локального Redis» | Claude зберігає це в auto memory |
| «Додай це в CLAUDE.md: …» | Claude дописує файл проєкту |
| «Що ти пам'ятаєш про цей проєкт?» | Claude читає `MEMORY.md` і переказує (приклад) |
| «Забудь нотатку про заморозку релізу — її скасували» | Claude змінює або видаляє нотатку (приклад) |

### Як переглянути, виправити, вимкнути

- `/memory` → пункт про папку auto memory відкриває її; усе там — звичайний Markdown, який можна
  читати, редагувати й видаляти.
- **Вимкнути для всіх проєктів:** перемикач auto memory у `/memory`. Він записує
  `autoMemoryEnabled` у твої **користувацькі** налаштування `~/.claude/settings.json`, тобто діє
  на всі проєкти, а не лише на поточний.
- **Вимкнути для одного проєкту:** у налаштуваннях цього проєкту (наприклад,
  `.claude/settings.local.json`, урок 9) додати:

```
{
  "autoMemoryEnabled": false
}
```

- **Через змінну середовища:** `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`.

⏸ **Зупинись і перевір себе.** Ти вимкнув auto memory перемикачем у `/memory`, працюючи в
`qa-notes`. Наступного дня відкриваєш інший проєкт. Пам'ять там увімкнена?

> **Відповідь.** Ні. Перемикач у `/memory` пише налаштування в `~/.claude/settings.json` — це
> користувацький рівень, він діє на всі проєкти. Щоб вимкнути пам'ять лише в одному проєкті,
> потрібен `"autoMemoryEnabled": false` у налаштуваннях саме цього проєкту.

## 14.10. Що куди класти

| що | куди |
|---|---|
| правило для всіх у проєкті, коротке, потрібне щоразу | `CLAUDE.md` проєкту |
| твоя звичка в усіх проєктах | `~/.claude/CLAUDE.md` |
| твоє, тільки цей проєкт (стенд, тестовий користувач) | `CLAUDE.local.md` |
| правило лише для частини файлів | `.claude/rules/` з `paths` або `CLAUDE.md` у підпапці |
| довга покрокова процедура («як оформити реліз-ноти») | скіл (урок 16) |
| те, що Claude помітив про тебе і роботу | auto memory — хай веде сам |
| правило без винятків («ніколи не читати `.env`») | дозволи (урок 9) або хук (урок 17) |
| разове уточнення для одного завдання | просто промпт |

Коротке правило з документації: якщо це правило для всіх у проєкті — `CLAUDE.md`; якщо це те, чого
Claude навчився про тебе чи роботу, — хай це тримає auto memory.

Джерело: [How Claude remembers your project](https://code.claude.com/docs/en/memory),
[Best practices](https://code.claude.com/docs/en/best-practices).

## 14.11. У роботі QA

- **Формат тест-кейсів.** У `CLAUDE.md` проєкту — формат ID, обов'язкові поля, мова. Кожен
  тест-кейс від Claude одразу в стандарті команди, без «перероби під наш шаблон».
- **Тестові дані.** Рядок «e-mail лише на example.com, телефони — вигадані» в `CLAUDE.md` захищає
  від справжніх персональних даних у тест-даних і баг-репортах.
- **Баг-репорти тільки там, де треба.** Правило з `paths: - "bugs/**/*.md"` описує формат
  баг-репорту і не заважає, коли ти пишеш тест-план.
- **Твій стенд.** URL тестового середовища і твій тестовий користувач (без пароля) — у
  `CLAUDE.local.md`: колегам не потрібні, у git не потрапляють.
- **Повторне виправлення.** Удруге пояснюєш Claude, що «Blocked» і «Failed» — різні статуси?
  Це сигнал записати різницю одним рядком у `CLAUDE.md`.
- **Ревізія пам'яті.** Раз на кілька тижнів відкрий `/memory`, переглянь auto memory і видали
  застарілі нотатки (старий стенд, закритий реліз).

## 14.12. Типові помилки

### Симптом → причина

| симптом | причина | що зробити |
|---|---|---|
| Claude не дотримується правила з `CLAUDE.md` | файл не завантажився | `/context` → **Memory files**; перевір назву й місце файлу |
| файл завантажився, але правило ігнорується | правило розмите або суперечить іншому файлу | переформулюй конкретно; прибери суперечність |
| пишеш «ВАЖЛИВО!!!», а Claude все одно пропускає | файл задовгий або правило мусить бути без винятків | скороти файл; для «ніколи» — дозволи чи хук |
| колеги кажуть, що в них Claude «не знає правил» | ти писав у `CLAUDE.local.md` або `~/.claude/CLAUDE.md` | спільні правила — в `CLAUDE.md` проєкту, у git |
| `CLAUDE.local.md` потрапив у репозиторій | не додав його в `.gitignore` | додай рядок `CLAUDE.local.md` у `.gitignore` |
| перевіряєш нове правило в тій самій сесії — «працює», а завтра ні | правило було в історії чату, файл не читався | перевіряй у новій сесії |
| `AGENTS.md` раптом перестав діяти | з'явився `CLAUDE.md` або `CLAUDE.local.md` | додай у `CLAUDE.md` рядок `@AGENTS.md` |
| Claude «пам'ятає» застаріле (старий стенд) | нотатка в auto memory | «забудь …» або видали нотатку через `/memory` |
| вимкнув пам'ять в одному проєкті, а вона зникла скрізь | перемикач у `/memory` пише в користувацькі налаштування | для одного проєкту — `autoMemoryEnabled` у налаштуваннях проєкту |

## 14.13. Що варто запам'ятати

1. Кожна сесія починається з чистого контексту; пам'ять між сесіями дають `CLAUDE.md` і auto memory.
2. Обидва — контекст, а не примусове правило; для «ніколи» — дозволи (урок 9) або хук (урок 17).
3. `CLAUDE.md` бувають: керовані (компанія), `~/.claude/CLAUDE.md` (ти, усі проєкти), проєктний
   (команда, git), `CLAUDE.local.md` (ти, цей проєкт).
4. Файли з робочої папки й вище вантажаться на старті й складаються докупи; з підпапок — за потреби.
5. Пиши тільки те, чого Claude не знайде сам; конкретно; до 200 рядків; без суперечностей.
6. `@шлях` імпортує файл, але не економить контекст; економлять правила з `paths` і скіли.
7. `/init` створює стартовий файл, `/memory` відкриває файли й керує auto memory, `/context`
   показує, що завантажилось.
8. Auto memory: `MEMORY.md` (перші 200 рядків або 25KB) + нотатки за потреби; локальна, редагована.
9. Перемикач у `/memory` вимикає auto memory для всіх проєктів; для одного — налаштування проєкту.
10. `AGENTS.md` читається, лише коли немає `CLAUDE.md` і `CLAUDE.local.md`; інакше — імпорт `@AGENTS.md`.

**14.9.** Напиши файл правила `.claude/rules/test-data.md`, яке діє тільки для `.csv` файлів у

**14.10.** Колега каже: «У нас у репозиторії `AGENTS.md`, я додав собі `CLAUDE.local.md` з

**14.11.** Ти вимкнув auto memory перемикачем у `/memory`, бо в одному проєкті вона заважала.

# Розв'язки

**14.1.** `CLAUDE.md` пишеш ти: це інструкції й правила (формат, команди, домовленості). Auto
memory пише Claude: це його нотатки про тебе, твої виправлення, контекст роботи. Обидва
завантажуються на старті кожної сесії: `CLAUDE.md` повністю (з робочої папки й вище), auto memory —
перші 200 рядків або 25KB `MEMORY.md`, а окремі нотатки — за потреби. Аналогія: `CLAUDE.md` —
посадова інструкція, яку дав керівник; auto memory — блокнот, куди працівник сам записує, як тобі
зручніше.

**14.2.** Одразу: `ai-course/CLAUDE.md` (папка вище робочої) і `qa-notes/CLAUDE.md` (робоча
папка) — обидва складаються докупи, спершу `ai-course`, потім `qa-notes`. `bugs/CLAUDE.md` на
старті не читається: він завантажиться, щойно Claude прочитає, створить або змінить якийсь файл у
`bugs`; у терміналі з'явиться рядок `Loaded` зі шляхом.

**14.3.** Зразок:
```
- Тест-кейс: ID TC-<МОДУЛЬ>-<номер>; поля Назва, Передумови, Кроки, Очікуваний результат
- E-mail у тестових даних тільки на example.com; паролів у файлах не пишемо
- Баг-репорт: Severity, Кроки (нумеровані), Фактичний і Очікуваний результат, Середовище
- Після змін у test-data/ запускай: python check_data.py
```
Кожен рядок тепер можна перевірити: є поле чи ні, той домен чи ні, запущено команду чи ні.

**14.4.** До `/init` під **Memory files** найчастіше порожньо або тільки `~/.claude/CLAUDE.md`,
якщо ти його вже створював. Після `/init` у папці з'являється `CLAUDE.md`. У ньому, ймовірно, буде
опис файлів і папок — це Claude знайде сам, тож викреслюй. Лишаються правила й домовленості, яких
у файлах немає. Перевір, що файл називається саме `CLAUDE.md`: `ls` має показати його в корені
`qa-notes`.

**14.5.** Найпростіше — попросити: «Додай у CLAUDE.md: ID тест-кейсу TC-<МОДУЛЬ>-<номер>; поля
Назва, Передумови, Кроки, Очікуваний результат; e-mail лише на example.com». Потім `exit`, знову
`claude`, `/context` — `CLAUDE.md` під **Memory files**. Тест-кейс для відновлення пароля має
отримати ID на кшталт `TC-PASSWORD-001`, усі чотири поля й e-mail на кшталт `qa1@example.com`.
Якщо якесь правило пропущене — уточни саме його формулювання, а не додавай «ВАЖЛИВО».

**14.6.** 1 — `CLAUDE.local.md` (тільки ти, тільки цей проєкт). 2 — `~/.claude/CLAUDE.md`.
3 — `CLAUDE.md` проєкту. 4 — дозволи (правило заборони, урок 9) або хук (урок 17): це «ніколи».
5 — скіл (урок 16): довга процедура, потрібна не щоразу. 6 — просто промпт: разове уточнення.
7 — auto memory: Claude запише це сам.

**14.7.** Після прохання з'явиться повідомлення на кшталт «Saved 1 memory» або подібне. У `/memory`
обери пункт, що відкриває папку auto memory: там `MEMORY.md` з рядком-посиланням на нову нотатку і
сам файл нотатки з текстом про префікс `qa_`. У новій сесії на «Що ти пам'ятаєш?» Claude має
згадати префікс — пам'ять пережила кінець сесії. Якщо нотатки немає, перевір, чи не вимкнена auto
memory (перемикач у `/memory`).

**14.8.** До запиту `bugs/CLAUDE.md` під **Memory files** не видно — він не завантажується на
старті. Коли Claude читає `bugs/bug-001.md`, у терміналі з'являється рядок `Loaded` зі шляхом до
`bugs/CLAUDE.md`. Переписаний баг-репорт найчастіше починається з `Severity: TBD`. Файл створено
командою в терміналі, а не руками Claude, — так документація радить перевіряти нові `CLAUDE.md` у
підпапках, щоб Claude не «знав» правило з власних дій.

**14.9.**
```
---
paths:
  - "**/*.csv"
---

- E-mail у тестових даних тільки на домені example.com, наприклад qa1@example.com
```
Файл кладеш у `qa-notes/.claude/rules/test-data.md`. Правило завантажиться, коли Claude прочитає,
створить або змінить будь-який `.csv` файл у проєкті; до того воно не займає контекст.

**14.10.** Claude читає `AGENTS.md`, лише якщо в робочій папці чи вище немає `CLAUDE.md` і
`CLAUDE.local.md`. Новий `CLAUDE.local.md` «рахується», тож Claude тепер читає тільки його.
Виправлення: 1) створити поруч `CLAUDE.md` з рядком `@AGENTS.md` (і за бажанням Claude-специфічними
правилами нижче); 2) у `/config` поставити **Project instructions** на `claude-md-and-agents-md`.

**14.11.** Перемикач у `/memory` пише `autoMemoryEnabled` у `~/.claude/settings.json` — це
налаштування для всіх твоїх проєктів. Правильно: увімкнути пам'ять назад тим самим перемикачем, а
в проблемному проєкті додати `"autoMemoryEnabled": false` у його налаштування (наприклад,
`.claude/settings.local.json`).

**14.12.** Хороший файл має 10–30 рядків: точні команди перевірки, формат артефактів, домовленості
команди, «пастки» проєкту. Типові кандидати на викреслення: опис папок, перелік технологій,
загальні поради. Рядки без винятків — «ніколи не відправляй листи реальним клієнтам», «ніколи не
читай `.env`» — не для `CLAUDE.md`, бо Claude може їх не виконати; для них потрібні правила
заборони в дозволах або хук, які виконує сам Claude Code.

**14.13.** 20 рядків загальних правил лишаються в `CLAUDE.md`. 120 рядків про баг-репорти — у
`.claude/rules/bug-reports.md` з `paths: - "bugs/**/*.md"` (або в `bugs/CLAUDE.md`), бажано ще й
скоротити. 100 рядків процедури — у скіл (урок 16), який завантажується лише на запит. 60 рядків
опису папок — видалити: Claude побачить їх сам. У `CLAUDE.md` лишиться близько 20 рядків.
