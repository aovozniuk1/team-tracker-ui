# Урок 9. Дозволи й режими

*Claude Code може змінювати файли й запускати команди на твоєму комп'ютері. Дозволи вирішують, що
він робить сам, а на що потрібне твоє «так». Після уроку ти знаєш, у якому режимі стартує сесія і
як перемкнутися в Manual, щоб бачити кожну дію, читаєш запит дозволу й обираєш правильну відповідь,
працюєш у режимі плану і пишеш постійні правила, які Claude Code застосовує незалежно від того, що
«думає» модель.*

## Коротко

*Картка уроку: прочитай її перед уроком і повернись до неї після.*

**Одним реченням.** Дозволи — це правила Claude Code про те, які дії виконуються без тебе, які
потребують твого «так», а які заборонені зовсім.

**Навіщо.** Помилкова команда чи зайва зміна файлу коштує реальних втрат; дозволи — місце, де ти
вирішуєш, скільки свободи дати Claude.

**Де.** Рядок статусу під полем вводу (`⏸ manual mode on`, `⏵⏵ auto mode on` …), `Shift+Tab` для
перемикання режимів, команда `/permissions`, файли `.claude/settings.json`,
`.claude/settings.local.json` і `~/.claude/settings.json`.

**Модель**

- **Запит дозволу** — пауза, у якій Claude Code показує точну дію і чекає твоєї відповіді.
- **Режим дозволів** — загальне налаштування «як часто питати»: Manual, acceptEdits, plan, auto та інші.
- **Класифікатор** — друга модель, яка в режимі auto перевіряє ризиковані дії замість тебе.
- **Правило** — постійний запис `allow` / `ask` / `deny` у файлі налаштувань, наприклад `Bash(npm test)`.
- **Режим плану (plan)** — Claude досліджує й пропонує план, нічого не змінюючи.

**Запам'ятай**

1. З версії v2.1.283 сесія в терміналі й VS Code стартує в режимі **auto** — запитів майже не буде.
2. Поки вчишся, перемкнись у **Manual** (`Shift+Tab` або `claude --permission-mode manual`) — і бачитимеш кожну дію.
3. Правила застосовує Claude Code, а не модель; прохання в чаті чи в `CLAUDE.md` дозволів не змінюють.
4. Порядок перевірки правил: **deny → ask → allow**; дозвіл не може зробити виняток із заборони.
5. Правила `deny` діють у кожному режимі, але не герметичні: ту саму дію можна записати інакше.

**Пастки** (симптом → причина)

- «Чому Claude нічого не питає?» → сесія в режимі auto; перемкнись `Shift+Tab` у Manual.
- `Shift+Tab` на Windows не перемикає режим → спробуй `Alt+M`.
- Написав у чаті «ніколи не роби `git push`», а він усе одно може → це прохання, а не правило; додай `deny`.
- Правило `Bash(npm test)` не спрацювало на `npm test --watch` → без `*` правило збігається лише з точною командою.

**Як перевірити**

- Ти запускаєш Claude Code, читаєш режим у рядку статусу, перемикаєшся в Manual, отримуєш запит
  дозволу на команду й пояснюєш кожен варіант відповіді, а правило `deny` на тестовий «секретний»
  файл не дає Claude його прочитати.

## 9.1. Навіщо дозволи і хто їх застосовує

З уроку 8 ти знаєш: модель лише **просить** виклик інструмента, а виконує його Claude Code. Між
проханням і виконанням стоїть перевірка дозволів. Вона відповідає на одне з трьох:

- **дозволено** — виконати одразу;
- **треба спитати** — показати тобі запит і чекати;
- **заборонено** — відмовити, і модель отримає повідомлення про відмову.

Найважливіше речення уроку — з документації: "Permission rules are enforced by Claude Code, not by
the model." — правила дозволів застосовує Claude Code, а не модель. Інструкції в промпті чи в
`CLAUDE.md` (урок 14) не змінюють того, що Claude Code дозволяє.

Аналогія. Модель — це новий працівник, а Claude Code — турнікет на вході в серверну. Можна
сказати працівнику «не заходь у серверну», і він, найімовірніше, не зайде. А можна просто не дати
йому перепустку — і тоді він не зайде, навіть якщо дуже захоче. Прохання в чаті — це перше; правило
`deny` — друге.

Офіційна документація ділить усі інструкції на два види:

| вид | хто вирішує | приклади |
|---|---|---|
| **недетерміновані** — модель читає й вирішує | Claude (модель) | твій промпт, `CLAUDE.md`, класифікатор режиму auto |
| **детерміновані** — виконуються завжди | Claude Code (оболонка) | правила `deny`, хуки (урок 17), налаштування організації |

«Детермінований» означає «завжди однаково, без варіантів». Прохання модель зазвичай виконує, але
гарантії немає. Правило — гарантія (з обмеженнями, про які в розділі 9.8).

⏸ **Зупинись і перевір себе.** Ти написав у промпті: «Ніколи не видаляй файли в папці `reports`».
Це правило дозволів?

> **Відповідь.** Ні. Це прохання до моделі — вона, найімовірніше, його виконає, але Claude Code
> цього не забезпечує. Справжнє правило — запис `deny` у файлі налаштувань, який застосовує сам
> Claude Code.

## 9.2. Що питає дозволу, а що ні

Ось офіційна таблиця погоджень для режиму **Manual** — режиму, де Claude Code питає про все, крім
читання. Останній стовпчик — скільки діє відповідь «Так, і більше не питай» (*Yes, and don't ask
again*).

| тип дії | приклад | чи питає | «don't ask again» діє |
|---|---|---|---|
| тільки читання | читання файлів, `Grep` | ні, в межах робочої папки | — |
| команди `Bash` | запуск команд терміналу | так, крім вбудованого набору команд тільки для читання | назавжди, для цього репозиторію й цієї команди |
| зміна файлів | `Edit`, `Write` | так | до кінця сесії |
| читання вебсторінки | `WebFetch` | так, крім попередньо дозволених сайтів документації | назавжди, для цього репозиторію й цього домену |
| пошук в інтернеті | `WebSearch` | так | назавжди, для цього репозиторію |

**Репозиторій** тут — твоя папка проєкту (детально про це слово в уроці 10).

Команди тільки для читання, які **ніколи** не питають дозволу в жодному режимі: `ls`, `cat`, `echo`,
`pwd`, `head`, `tail`, `grep`, `find`, `wc`, `which`, `diff`, `stat`, `du`, `cd` і команди git, які
лише читають (наприклад, `git status`).

Ще два уточнення:

- **Читання поза робочою папкою питає дозволу** навіть для `Read`, `Grep` і `Glob`.
- **`Agent` не питає дозволу на запуск** субагента, але кожна дія субагента проходить ті самі
  правила (урок 8).

⏸ **Зупинись і перевір себе.** У Manual ти дозволив Claude змінити `style.css` з варіантом «don't
ask again». Завтра ти відкрив нову сесію в тій самій папці. Чи спитає він знову про зміну файлу?

> **Відповідь.** Так. Для змін файлів відповідь «don't ask again» діє лише до кінця сесії й не
> зберігається у файл. Назавжди зберігаються такі відповіді для команд `Bash` і для `WebFetch`.

## 9.3. Як відповідати на запит дозволу

Коли Claude хоче зробити щось, що потребує погодження, він зупиняється й показує **точну дію** —
наприклад, команду `npm install axios` чи вміст файлу, який збирається записати. Запит на команду
`Bash` пропонує до чотирьох варіантів (тут для прикладу — команда `npm test`):

```
Yes
Yes, and don't ask again for: npm test *
Yes, and switch to auto mode
No
Esc to cancel · Tab to amend
```

| варіант | що означає | коли обирати |
|---|---|---|
| **Yes** | дозволити один раз | звичайна відповідь, коли дія зрозуміла |
| **Yes, and don't ask again for: …** | дозволити й зберегти правило для таких команд | безпечна команда, яку Claude запускатиме постійно (тести, збирання) |
| **Yes, and switch to auto mode** | дозволити й перейти в режим auto | коли досить перевіряти кожен крок і ти довіряєш класифікатору |
| **No** | відмовити | дія неправильна чи ризикована — і поясни Claude, що робити натомість |

Деталі, які варто знати:

- **Не кожен запит має всі чотири варіанти.** Деякі пропонують лише одноразове «так», а на запитах
  інструмента `PowerShell` немає варіанта переходу в auto.
- **«Don't ask again» для `Bash` і `WebFetch` зберігається у файл** `.claude/settings.local.json` у
  корені проєкту. Тобто ти буквально дописуєш правило `allow` — і воно діятиме в наступних сесіях.
- **`Esc` на запиті — теж відмова.** Підказка внизу (`Esc to cancel`) нагадує саме про це.
- **Після «No» скажи, як треба.** Наприклад: «не додавай бібліотек, використай вбудований `fetch`».
  Відмова без пояснення змушує Claude вгадувати іншу дорогу.

Запит на `WebFetch` має три варіанти: **Yes** (лише цей раз), **Yes, and don't ask again for
`<domain>`** (зберегти дозвіл на цей сайт) і **No, and tell Claude what to do differently**
(відмовити й пояснити, як інакше).

### Що читати уважно

Запит дозволу — це твій останній шанс зупинити помилку. Особливо уважно дивись на:

| що бачиш | чому небезпечно |
|---|---|
| `rm -rf …`, `Remove-Item -Recurse …` | видалення файлів і папок, часто без кошика |
| `git push --force` | перезаписує історію на сервері, можна знищити чужу роботу |
| зміни в базі даних | дані можуть не відновитися |
| встановлення незнайомих пакетів | чужий код на твоєму комп'ютері |
| `curl …`, переданий одразу в `bash` | завантажує й одразу запускає скрипт з інтернету |
| будь-що поза папкою проєкту | дія торкається того, що не належить до завдання |

Правило звички: **прочитай команду повністю, перш ніж натиснути Yes.** Якщо не розумієш, що вона
робить, — обери **No** і спитай: «Поясни, що зробить ця команда, простими словами».

⏸ **Зупинись і перевір себе.** Claude просить дозволу на `npm test`, і ти знаєш, що в цьому проєкті
він запускатиме тести десятки разів. Який варіант обрати і що станеться з файлами проєкту?

> **Відповідь.** Варіант `Yes, and don't ask again for: npm test *`. Claude Code збереже правило `allow`
> для цієї команди у `.claude/settings.local.json` у корені проєкту, і в наступні рази (і в
> наступних сесіях) `npm test` запускатиметься без запиту.

## 9.4. Режими дозволів

**Режим** — загальне налаштування того, як часто Claude Code питає. Офіційна таблиця:

| режим (значення в налаштуваннях) | що виконується без запиту | для чого найкраще |
|---|---|---|
| **Manual** (`default`) | лише читання | перевіряти кожну дію самому, чутлива робота |
| `acceptEdits` | читання, зміни файлів і звичайні файлові команди (`mkdir`, `touch`, `mv`, `cp` тощо) | ітерації над кодом, який ти переглядаєш |
| `plan` | читання, плюс команди, схвалені класифікатором, коли доступний режим auto | дослідити проєкт перед змінами |
| `auto` | усе, з фоновими перевірками безпеки | довгі завдання, менше запитів |
| `dontAsk` | читання файлів у робочих папках і заздалегідь дозволені інструменти; усе, що потребувало б запиту, відхиляється | закриті автоматичні запуски і скрипти |
| `bypassPermissions` | усе | лише ізольовані контейнери й віртуальні машини |

### Режим auto і класифікатор

В auto Claude Code не зупиняється на рутинних погодженнях. Документація пояснює: "a second model,
the classifier, reviews actions instead of you" — друга модель, класифікатор, перевіряє дії замість
тебе. Він зосереджений на тому, що зупинила б уважна людина, зокрема:

- `curl | bash` (завантажити й одразу запустити скрипт);
- розгортання на продакшн і міграції бази даних;
- примусовий `push` поверх чужої роботи;
- надсилання чутливих даних на зовнішні адреси;
- дії, які схожі на виконання інструкцій із прочитаного вмісту, а не твоїх (про це — урок 11).

Коли класифікатор щось блокує, ти отримуєш сповіщення, а дія з'являється в розділі **Recently
denied** команди `/permissions` — звідти її можна повторити з ручним погодженням. Після трьох
блокувань поспіль (або двадцяти загалом) auto ставить себе на паузу й знову починає питати тебе.

Головне про auto: **класифікатор — це теж модель, яка оцінює, а не жорстке правило.** Він може
помилитися. Тому все, що «ніколи», записують у правила `deny` (розділ 9.7), а не залишають на його
судження. Правила `deny` і `ask` перевіряються **до** класифікатора.

### Який режим у тебе на старті

Цитата з документації: "With Claude Code v2.1.283 or later, auto mode is the built-in starting
permission mode for interactive terminal and VS Code sessions. On earlier versions, it's the
built-in starting permission mode only on Pro, Max, and Team plans."

Тобто на свіжій версії сесія в терміналі й у VS Code **починається в auto**, і ти майже не бачитимеш
запитів. Для роботи це зручно. Для навчання — ні: ти не бачиш, що саме Claude збирається зробити.
Тому порада курсу: **поки вчишся, працюй у Manual.** Курс звірено з документацією на 30.10.2026;
перевір свою версію `claude --version` і онови `claude update`. Якщо щось виглядає інакше, ніж тут, —
офіційна документація має рацію.

⏸ **Зупинись і перевір себе.** Що станеться в режимі auto, якщо в налаштуваннях є правило
`deny` для `Read(./.env)`, а класифікатор вважає читання `.env` безпечним?

> **Відповідь.** Читання буде заблоковано. Правила `deny` і `ask` перевіряються раніше за
> класифікатор і діють у кожному режимі, включно з auto і `bypassPermissions`.

## 9.5. Як перемикати режими

### У терміналі: `Shift+Tab`

Натискай `Shift+Tab` у полі вводу. Документація описує цикл так: з auto перше натискання перемикає
в Manual (`default`), а далі цикл іде `default` → `acceptEdits` → `plan`. Після `plan` наступне
натискання повертає на початок циклу. Під полем вводу рядок статусу показує, де ти зараз:

| що в рядку статусу | режим |
|---|---|
| `⏸ manual mode on` | Manual (`default`) |
| `⏵⏵ accept edits on` | `acceptEdits` |
| `⏸ plan mode on` | `plan` |
| `⏵⏵ auto mode on` | `auto` |

Режим `dontAsk` у цей цикл не входить ніколи. **Якщо `Shift+Tab` на Windows не працює**, спробуй
`Alt+M`. Не запам'ятовуй порядок — просто натискай і дивись на рядок статусу.

### Під час запуску: прапорець

Можна одразу стартувати в потрібному режимі:

```
> claude --permission-mode manual
> claude --permission-mode plan
```

Прапорець приймає `manual`, `acceptEdits`, `plan`, `auto`, `dontAsk` і `bypassPermissions`.

### У застосунку для комп'ютера і VS Code

У застосунку Claude Desktop є перемикач режимів біля поля вводу. У VS Code — індикатор режиму.

⏸ **Зупинись і перевір себе.** Ти щойно запустив `claude` на свіжій версії і бачиш
`⏵⏵ auto mode on`. Що натиснути, щоб опинитися в Manual, і як переконатися, що вийшло?

> **Відповідь.** Один раз `Shift+Tab` (на Windows, якщо не спрацювало, — `Alt+M`). Рядок статусу має
> показати `⏸ manual mode on`.

## 9.6. Режим плану на практиці

**Режим плану** (`plan`) — Claude читає, досліджує і пропонує план, але **нічого не змінює**. Це
як попросити майстра спершу оглянути квартиру й написати кошторис, а вже потім братися за ремонт.

Як увімкнути:

- `Shift+Tab`, доки в рядку статусу не з'явиться `⏸ plan mode on`;
- або почати один промпт із `/plan`, наприклад: `/plan fix the auth bug`.

Що відбувається далі:

1. Claude читає потрібні файли і складає план: які файли зміняться, що саме, у якому порядку.
2. Ти читаєш план і **правиш його словами**: «зберігай картинки в `/uploads`, не в базі; обмеж
   розмір 2 MB». Claude оновлює план.
3. Хочеш правити план як текст — `Ctrl+G` відкриває запропонований план у твоєму текстовому
   редакторі.
4. Коли план готовий, ти обираєш, як рухатися далі: **Yes, and use auto mode** (якщо auto
   недоступний, цей варіант називається **Yes, auto-accept edits**), **Yes, manually approve edits**
   (погоджувати кожну зміну) або **No, keep planning** (планувати далі). Погодження виводить із
   режиму плану, і Claude починає змінювати файли.

**Приклад (ілюстративний).** Промпт: `/plan I want users to be able to upload a profile photo.`
Claude читає код і повертає план: які файли зміняться, де зберігаються картинки, обмеження розміру,
які тести додати. Ти відповідаєш: «Store images in /uploads, not in the database, and limit to
2 MB.» Claude оновлює план. Після погодження він реалізує саме це.

Коли варто планувати: якщо зміна торкається кількох файлів, якщо ти не впевнений, з чого почати, або
якщо помилка дорога. Коли можна пропустити: правка одного слова, однієї помилки в тексті.

⏸ **Зупинись і перевір себе.** У режимі плану Claude запропонував план, і тобі все подобається,
але ти хочеш і далі погоджувати кожну зміну файлу. Чи підходить варіант «Yes, and use auto mode»?

> **Відповідь.** Ні: він переведе сесію в auto, і зміни йтимуть без твоїх погоджень (під наглядом
> класифікатора). Обери **Yes, manually approve edits** — погодити план і переглядати кожну зміну
> окремо; після погодження переконайся в рядку статусу, що ти в Manual.

## 9.7. Постійні правила

Відповідати на запити щоразу — втомлює, а прохання в чаті — не гарантія. Для сталих рішень є
**правила** у файлах налаштувань:

| файл | для кого | коли використовувати |
|---|---|---|
| `.claude/settings.json` у папці проєкту | для проєкту, спільний (його можна закомітити, урок 10) | правила, які мають діяти для всіх, хто працює з проєктом |
| `.claude/settings.local.json` у папці проєкту | для проєкту, лише для тебе | твої особисті дозволи в цьому проєкті (сюди пише «don't ask again») |
| `~/.claude/settings.json` | для всіх твоїх проєктів | твої загальні правила |

Приклад файлу з документованим синтаксисом:

```json
{
  "permissions": {
    "allow": ["Bash(npm test)", "Bash(npm run *)", "Bash(git status)"],
    "ask": ["Bash(git push *)"],
    "deny": ["Read(./.env)", "Read(./secrets/**)"]
  }
}
```

Три списки:

- **`allow`** — виконувати без запиту;
- **`ask`** — завжди питати, навіть у режимі auto;
- **`deny`** — заборонено завжди, у кожному режимі.

### Як правило збігається з дією

Правило записується як `Інструмент(уточнення)`. Ось що означають правила з прикладу:

| правило | збігається | не збігається |
|---|---|---|
| `Bash(npm test)` | рівно `npm test` | `npm test --watch` |
| `Bash(npm run *)` | `npm run build`, `npm run test --watch` | `npm install` |
| `Bash(git push *)` | `git push`, `git push origin main` | `git pull` |
| `Read(./.env)` | читання `.env` у поточній папці | інші файли |

Зірочка `*` означає «будь-що далі». Старіший запис `Bash(git push:*)` означає те саме, що
`Bash(git push *)`; діалог дозволу, коли ти обираєш «don't ask again», записує форму з пробілом.

На Windows команди часто йдуть через інструмент `PowerShell`, і для нього правила пишуться окремо, у
своїй формі, наприклад `PowerShell(Get-ChildItem *)`. Правило `Bash(...)` команди PowerShell не
обмежує. Тому на Windows, якщо встановлено Git for Windows, правило `deny` для `Bash` (навіть
вузьке, як `Bash(git push *)`) вимикає інструмент `PowerShell` на всю сесію, якщо поруч немає
окремого правила для `PowerShell`, — щоб заборону не можна було обійти через PowerShell.

### Порядок: deny → ask → allow

Claude Code перевіряє правила в такому порядку: спершу `deny`, потім `ask`, потім `allow`. Перше
збігання вирішує. Звідси правило з документації: "An allow rule can't carve an exception out of a
deny rule." — дозвіл не може «вирізати» виняток із заборони. Якщо `deny` забороняє `Bash(git push *)`,
то `allow` для `Bash(git push origin test)` нічого не змінить.

### Як редагувати правила

- **`/permissions`** — відкриває інтерактивний редактор правил. Це рекомендований спосіб.
- **Відредагувати файл** у текстовому редакторі (Блокнот, TextEdit, VS Code). Після зміни файлу
  перезапусти Claude Code, щоб напевно працювати з новими правилами.
- **Попросити Claude**: «Дозволь `npm test` без запитів у цьому проєкті». Це спрацює лише тому, що
  Claude відредагує файл налаштувань — а така зміна сама потребує твого погодження. Правила не
  змінюються від того, що ти щось сказав у чаті.

⏸ **Зупинись і перевір себе.** У файлі є `"deny": ["Bash(git push *)"]` і
`"allow": ["Bash(git push origin main)"]`. Claude хоче виконати `git push origin main`. Що буде?

> **Відповідь.** Відмова. Спершу перевіряється `deny`, і `Bash(git push *)` збігається з
> `git push origin main`. Дозвіл не може зробити виняток із заборони.

## 9.8. Межі правил: deny не герметичний

Правила збігаються з **викликами інструментів**, а не з наміром. Документація чесно попереджає, де
межі:

- **Ту саму дію можна записати інакше.** "A push written another way, such as `git -C . push`,
  isn't matched." — `push`, записаний інакше (`git -C . push`), правило `Bash(git push *)` не
  впізнає.
- **`Read(./.env)` ловить `cat .env`**, бо Claude Code знає поширені команди читання файлів. Але не
  ловить скрипт (на Python чи Node), який сам відкриває файл.
- **Файл `.claudeignore` не діє.** Деякі люди створюють його за аналогією з `.gitignore`, але на
  те, що Claude може читати, він не впливає.

Що робити з цим новачку:

1. Записуй у `deny` те, чого точно не має бути (секрети, `push`), — це перший шар.
2. **Читай запити дозволу** (працюй у Manual на чутливих проєктах) — це другий шар.
3. Не тримай справжні секрети там, куди не хочеш пускати Claude. Справжнє обмеження на рівні
   системи — **пісочниця** (*sandbox*), про неї і про безпеку загалом — урок 11.

І про режим без обмежень: **`bypassPermissions`** пропускає запити навіть на запис у `.git` і
`.claude`. Його вмикають лише в контейнерах чи віртуальних машинах, де нічого не шкода. Правила
`deny` діють навіть у ньому.

⏸ **Зупинись і перевір себе.** У тебе є `deny` на `Bash(git push *)`. Чи можеш ти бути впевнений,
що Claude ніколи не відправить зміни на сервер?

> **Відповідь.** Ні. Правило не впізнає інакше записану команду (наприклад, `git -C . push`). Це
> сильний запобіжник, але не гарантія. Додатково читай запити дозволу, тримай у Manual чутливі
> проєкти, а для справжньої ізоляції використовуй пісочницю (урок 11).

**9.4.** У запиті видно назву файлу і вміст, який Claude збирається записати (`hi`). Після «No» з
поясненням Claude не створює `hello.txt`, а пропонує новий запит — на `greeting.txt` з тим самим
текстом. Висновок: «No» + пояснення змінює план, а не зупиняє роботу.

**9.5.** Для `Bash` зазвичай чотири рядки: **Yes**, **Yes, and don't ask again for: …**, **Yes, and
switch to auto mode**, **No** і підказка `Esc to cancel · Tab to amend`. Деякі запити пропонують лише
одноразове «так». На Windows команда часто йде через `PowerShell` — на таких запитах варіанта
переходу в auto немає. Команда — щось на кшталт `mkdir reports` (або `New-Item … reports`).

**9.6.** а) `plan` — Claude читає й пояснює, нічого не змінюючи. б) Manual — кожна дія, крім
читання, з запитом. в) `acceptEdits` або `auto` — менше запитів; у навчальному проєкті це прийнятно,
якщо ти переглядаєш результат. г) `dontAsk` — усе, що потребувало б запиту, відхиляється, сесія не
зависає. д) Не `bypassPermissions`: він лише для ізольованих контейнерів і віртуальних машин. Якщо
запити набридли — `auto` з правилами `deny`/`ask` для важливого.

**9.7.** Після `/plan` Claude читає вміст папки і пропонує план: який файл створить і що в ньому буде.
Після правки план оновлюється. При погодженні вибір варіанта визначає подальший режим: **Yes, and
use auto mode** переводить у auto (рядок статусу `⏵⏵ auto mode on`). `README.md` з'являється в
`plan-lab`; перевір `ls` (або `cat README.md`).

**9.8.** `Bash(npm run *)`: `npm run build` — так; `npm run lint --fix` — так; `npm install` — ні;
`npm test` — ні (це не `npm run`). `Bash(git push *)`: `git push` — так; `git push origin main` — так;
`git pull` — ні; `git -C . push` — **ні**: команда записана інакше, і правило її не впізнає.

**9.9.** Claude отримує відмову на `Read` для `secret.txt` і пише, що доступ заборонено правилами.
`Ctrl+O` показує спробу читання і відмову. На прохання вивести вміст командою: якщо команда — одна з
поширених команд читання файлів (як `cat secret.txt`), правило `Read` її теж заблокує; якщо Claude
спробує інший спосіб, результат може бути іншим — це наочний урок про те, що `deny` не герметичний.
Саме тому у файлі — `not-a-real-secret`.

**9.10.** `CLAUDE.md` — це прохання до моделі, а не правило: модель зазвичай його виконує, але
Claude Code цього не гарантує, скільки б знаків оклику не стояло. Треба додати правило в
`.claude/settings.json` проєкту: `"deny": ["Read(./.env)"]`. Воно діятиме в кожному режимі, і для
всіх, хто працює з проєктом.

**9.11.** Помилка: `allow` не може зробити виняток із `deny` — порядок перевірки deny → ask → allow,
тож `git push origin test-branch` усе одно заборонено. Один із робочих варіантів — не забороняти
`push` повністю, а вимагати запит, і дозволити потрібний:
```json
{
  "permissions": {
    "ask": ["Bash(git push *)"],
    "allow": ["Bash(git push origin test-branch)"]
  }
}
```
Але й тут `ask` перевіряється раніше за `allow`, тож для `test-branch` запит теж буде. Чесний
висновок: правилами не зробиш «заборонено все, крім одного». Найпростіше — залишити `ask` для всіх
`push` і погоджувати потрібний вручну.

**9.12.** Зразок:
```json
{
  "permissions": {
    "allow": ["Bash(npm test)"],
    "ask": ["Bash(git push *)"],
    "deny": ["Read(./.env)"]
  }
}
```
`allow` — `npm test` без запиту (саме ця команда; якщо треба з параметрами — `Bash(npm test *)`);
`ask` — кожен `git push` з запитом навіть в auto; `deny` — читання `.env` заборонено в кожному
режимі. Файл у `.claude/settings.json` — тому правила спільні для всіх, хто працює з цією папкою.
На Windows пам'ятай: команди можуть іти через `PowerShell`, для якого правила пишуться окремо.

**9.13.** Шар 1 — правила: `deny` для читання файлу з паролями і `ask` для команд, що відправляють
дані назовні. Слабкість: інакше записана команда чи скрипт можуть не збігтися з правилом. Шар 2 —
Manual і уважне читання кожного запиту. Слабкість: людина втомлюється й погоджує не читаючи.
Шар 3 — не тримати справжні паролі там, де працює Claude, і для ризикованих експериментів
використовувати ізоляцію (пісочницю, урок 11). Слабкість: потребує дисципліни. Разом шари
перекривають слабкості одне одного.
