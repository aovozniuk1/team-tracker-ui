# Урок 10. Відкат і страховка: checkpoints, rewind, git

*Claude іноді робитиме зміни, які тобі не сподобаються. Це нормально — важливо вміти повернутися
назад. Після уроку ти відкочуєш роботу Claude через rewind і знаєш, чого він не відкочує, розумієш
git з нуля — репозиторій, коміт, diff, гілку — і вмієш простими промптами попросити Claude зберегти
стан проєкту, показати зміни, скасувати їх або спробувати щось у безпечній гілці.*

## Коротко

*Картка уроку: прочитай її перед уроком і повернись до неї після.*

**Одним реченням.** У Claude Code є три шари відкату: чекпоінти з rewind (швидко, в межах сесії),
git (постійна історія проєкту) і резервні копії з ізоляцією (на випадок, коли все інше не врятувало).

**Навіщо.** Коли відкотитися легко, можна сміливо пробувати; коли важко — кожна помилка Claude
коштує тобі годин.

**Де.** `Esc` двічі на порожньому полі вводу або команда `/rewind` (також `/checkpoint`, `/undo`);
git — у терміналі (`git status`, `git diff`, `git log`) і через прохання до Claude.

**Модель**

- **Чекпоінт (checkpoint)** — автоматичний знімок файлів, які Claude змінив своїми інструментами; створюється з кожним твоїм промптом.
- **Rewind** — меню, яке повертає код, розмову або обидва до вибраного промпту.
- **Репозиторій** — папка проєкту, в якій git веде історію (прихована папка `.git`).
- **Коміт (commit)** — збережений знімок усього проєкту з підписом «що змінено».
- **Diff** — різниця між двома станами: які рядки додано, які прибрано.
- **Гілка (branch)** — окрема лінія історії, де можна пробувати, не чіпаючи основну.

**Запам'ятай**

1. `Esc` `Esc` на порожньому полі або `/rewind` — повернути код і/або розмову до попереднього промпту.
2. Файл, який змінювали лише команди терміналу, rewind не відновлює; зміни субагентів зазвичай теж.
3. Чекпоінти — не заміна git: офіційно це "Not a replacement for version control".
4. Перед великою зміною — коміт; після неї — читаєш diff.
5. Для експерименту — гілка або копія папки; `bypassPermissions` — ніколи на машині з цінними даними.

**Пастки** (симптом → причина)

- `Esc` двічі нічого не відкриває → у полі вводу є текст; очисти його.
- Після rewind файл лишився зміненим → його міняла команда терміналу, а не інструменти редагування Claude.
- На `git --version` термінал пише `command not found` / `is not recognized` → git не встановлено або не відкрито новий термінал після встановлення.
- Коміт не створюється, git питає `Please tell me who you are` → git ще не знає твого імені й пошти.

**Як перевірити**

- У тестовій папці ти повертаєш файл через rewind до стану до останнього промпту, створюєш
  репозиторій з першим комітом, показуєш `git diff` після зміни і повертаєш файл до останнього коміту.

## 10.1. Три шари відкату

Уяви, що ти редагуєш важливий документ. У тебе є три способи врятуватися від помилки:

1. **`Ctrl+Z` у редакторі** — швидко, але лише для недавніх дій і лише поки документ відкритий.
2. **Історія версій** (як у хмарних документах) — кожна збережена версія з датою, до будь-якої
   можна повернутися навіть через місяць.
3. **Копія на іншому диску чи в хмарі** — якщо пропаде все, вона лишиться.

У Claude Code ці три шари такі:

| шар | аналогія | що дає | межі |
|---|---|---|---|
| **чекпоінти й rewind** | `Ctrl+Z` | миттєво повертає файли, змінені Claude, і/або розмову | лише зміни інструментів редагування Claude; лише в межах сесій Claude Code |
| **git** | історія версій | постійні знімки всього проєкту, які робиш ти (або Claude на твоє прохання) | рятує лише те, що закомічено |
| **резервні копії та ізоляція** | копія на іншому диску | захист від втрати всього; безпечне місце для експериментів | треба зробити заздалегідь |

Далі розберемо кожен шар.

⏸ **Зупинись і перевір себе.** Ти попросив Claude переписати п'ять файлів, і результат не
сподобався. Який шар найшвидший, щоб повернути все як було?

> **Відповідь.** Чекпоінти й rewind: `Esc` двічі на порожньому полі (або `/rewind`), обрати промпт
> перед переписуванням і відновити код. Якщо перед цим був коміт, можна й через git, але rewind —
> швидше і без жодних команд.

## 10.2. Чекпоінти

Документація пояснює: "Claude Code automatically tracks Claude's file edits as you work" — Claude
Code автоматично відстежує зміни файлів, які робить Claude. І далі: "Every prompt you send that
starts a turn creates a new checkpoint" — кожен твій промпт, що починає хід (урок 4), створює новий
чекпоінт.

Тобто тобі нічого не треба вмикати чи зберігати. Кожного разу, коли ти надсилаєш повідомлення,
Claude Code запам'ятовує, яким був стан файлів **перед** роботою над ним. Якщо після п'яти промптів
щось пішло не так, можна повернутися до стану перед будь-яким із них.

Чекпоінти переживають і продовження сесії: якщо назвати сесію (`/rename`, урок 7) і потім
повернутися до неї через `claude --resume <назва>`, чекпоінти теж будуть на місці.

⏸ **Зупинись і перевір себе.** Ти надіслав три промпти: «створи `index.html`», «додай кнопку»,
«зроби кнопку червоною». Скільки чекпоінтів створено?

> **Відповідь.** Три — по одному на кожен промпт, що почав хід. Кожен зберігає стан файлів перед
> відповідним ходом.

## 10.3. Rewind: як повернутися

Відкрити меню відкату можна двома способами:

- натиснути **`Esc` двічі**, коли поле вводу **порожнє**;
- набрати команду **`/rewind`** (інші назви тієї самої команди — `/checkpoint` і `/undo`).

Далі ти обираєш один зі своїх попередніх промптів — точку, куди повертатися. За словами документації,
меню дає змогу "Rewind the conversation and/or code to a previous point, or summarize from a selected
message" — повернути розмову і/або код до попередньої точки або стиснути розмову від вибраного
повідомлення.

Після вибору точки меню пропонує дії:

| варіант | що робить | коли обирати |
|---|---|---|
| **Restore code and conversation** | повертає і файли, і розмову | «усе це було помилкою, почнімо цей крок заново» |
| **Restore conversation** | повертає лише розмову, файли лишаються як є | файли влаштовують, а от гілка розмови заплуталась |
| **Restore code** | повертає лише файли, розмова лишається | результат поганий, але обговорення корисне — Claude пам'ятає, що не спрацювало |
| **Summarize from here** | стискає частину розмови в короткий підсумок | розмова стала довгою й застарілою |
| **Summarize up to here** | теж стискає частину розмови, з іншого боку від вибраної точки | те саме |
| **Never mind** | закриває меню без змін | передумав |

Для відкату тобі найчастіше потрібні перші три. Варіанти зі стисканням розмови стосуються контексту
(урок 6) і для відкату файлів не потрібні.

**Приклад (ілюстративний).** Ти попросив новий дизайн шапки сайту, Claude переписав п'ять файлів, і
результат тобі не подобається. Відкриваєш rewind, обираєш промпт із проханням про дизайн, тиснеш
**Restore code and conversation** — і пишеш кращий промпт: «Залиш поточне розташування елементів;
зміни лише кольори на темно-синій і білий».

Rewind робить сміливі спроби дешевими: можна спершу попросити сміливий варіант, а якщо не
вийде — відкотитися.

⏸ **Зупинись і перевір себе.** Claude змінив файл невдало, але в розмові він уже з'ясував, чому
твоя перша ідея не працює, і тобі шкода губити це пояснення. Який варіант rewind обрати?

> **Відповідь.** **Restore code** — файли повернуться до стану перед вибраним промптом, а розмова з
> поясненням залишиться, і Claude враховуватиме його в наступній спробі.

## 10.4. Чого rewind не відкотить

Тут найважливіше уточнення уроку. Чекпоінти відстежують зміни, які Claude зробив **своїми
інструментами редагування файлів** (`Write`, `Edit` з уроку 8). Команди терміналу — інша історія.
Дослівно з документації:

> "Once Claude has edited a file with its file editing tools in your conversation, `/rewind` undoes
> changes that Bash commands make to that file afterward. A file that only Bash commands changed
> isn't tracked and stays as it is."

Простими словами:

- якщо файл **спершу** змінив Claude своїми інструментами, а **потім** його змінила команда
  терміналу — rewind відкотить і зміни від команди;
- якщо файл створювали чи змінювали **лише команди** терміналу — він не відстежується, і rewind його
  не чіпає.

Що ще rewind не відновлює:

| що | чому |
|---|---|
| зміни, зроблені **субагентами** (урок 15) | зазвичай не відстежуються |
| зміни, які зробив **ти сам** у редакторі чи інша програма | це зовнішні зміни, не дії Claude |
| символічні посилання (*symlinks*) | пропускаються |
| дуже старі точки | знімки файлів зберігаються лише для 100 останніх чекпоінтів і видаляються приблизно через 30 днів |
| усе поза файлами проєкту: дані в базі, встановлені пакети, надіслане в інтернет | rewind працює лише з файлами |

Тому документація прямо називає чекпоінти "Not a replacement for version control" — не заміною
системи контролю версій. Для цього є git.

⏸ **Зупинись і перевір себе.** Claude командою терміналу видалив папку `old-reports`, якої раніше
не торкався своїми інструментами. Чи поверне її rewind?

> **Відповідь.** Ні, не варто на це розраховувати: файли в ній змінювала лише команда терміналу, а
> такі файли не відстежуються. Повернути їх може git (якщо вони були закомічені) або резервна
> копія. Саме тому запит дозволу на видалення варто читати дуже уважно (урок 9).

## 10.5. Git з нуля: встановлення

**Git** — програма для контролю версій: вона зберігає знімки всього проєкту, які ти робиш, і
дозволяє повернутися до будь-якого з них. Це справжня страховка, і Claude дуже добре з нею працює.
Git працює локально, на твоєму комп'ютері; інтернет йому не потрібен.

Не плутай: **git** — програма, **GitHub** — онлайн-сервіс, де можна зберігати копію репозиторію
(зручно як резервна копія і для командної роботи). У цьому уроці нам потрібен лише git.

### Чи встановлено git

```
> git --version
```

Якщо бачиш рядок на кшталт `git version 2.…` — git є, переходь до розділу 10.6. Якщо бачиш
`'git' is not recognized` (Windows) або `command not found` (macOS/Linux) — встанови.

### Як встановити

| система | що зробити |
|---|---|
| **Windows** | завантаж **Git for Windows** з офіційного сайту [git-scm.com](https://git-scm.com/downloads), запусти інсталятор і проходь кроки з варіантами за замовчуванням |
| **macOS, Linux** | інструкції для своєї системи — на тій самій сторінці [git-scm.com/downloads](https://git-scm.com/downloads) |

Для Windows є додатковий плюс: Git for Windows дає Claude Code інструмент `Bash` (урок 8). Він не
обов'язковий, але рекомендований.

Після встановлення **відкрий новий термінал** (старий не знає про нову програму) і перевір
`git --version` ще раз. Якщо Claude Code був відкритий — перезапусти й його.

### Хто ти для git

Кожен коміт підписується іменем і поштою автора. Якщо git їх ще не знає, перший коміт закінчиться
повідомленням `Please tell me who you are`. Один раз на комп'ютер налаштуй:

```
> git config --global user.name "Olena"
> git config --global user.email "you@example.com"
```

Підстав своє ім'я і пошту. Пам'ятай: якщо колись викладеш репозиторій у відкритий доступ, ці ім'я
й пошту в історії комітів побачать усі.

⏸ **Зупинись і перевір себе.** Ти встановив Git for Windows, але `git --version` у тому самому
вікні PowerShell пише, що команду не знайдено. Чому?

> **Відповідь.** Термінал, відкритий до встановлення, не знає про нову програму. Закрий його,
> відкрий новий і повтори `git --version`.

## 10.6. Чотири слова git: репозиторій, коміт, diff, гілка

### Репозиторій

**Репозиторій** (*repository*, коротко «репо») — папка проєкту, в якій git веде історію. Вся історія
зберігається в прихованій папці `.git` усередині (урок 2: приховані файли видно через `ls -Force` або
`ls -a`). Зробити звичайну папку репозиторієм — команда `git init`. Видалиш `.git` — зникне вся
історія, а самі файли лишаться.

### Коміт

**Коміт** (*commit*) — знімок **усього** проєкту в певний момент, з коротким підписом, що змінено.
Як фото кімнати після прибирання з підписом «розклав книжки». Коміти утворюють історію: можна
подивитися будь-який і повернутися до нього.

Коміт робиться у два кроки:

1. `git add .` — «поклади всі змінені файли в коробку для наступного знімка»;
2. `git commit -m "Add login test cases"` — «зроби знімок і підпиши його».

Зміни, які ти зробив, але ще не закомітив, називаються **незакоміченими** (*uncommitted*). Git їх
бачить, але **ще не зберіг**. Якщо їх втратити, git не допоможе.

### Diff

**Diff** (від *difference*) — список відмінностей між двома станами. Найчастіше — між останнім
комітом і тим, що зараз у файлах. Команда `git diff` показує рядки:

```
- BUG-2 typo on checkout page
+ BUG-2 spelling error on checkout page
```

Рядок з `-` був і зник, рядок з `+` з'явився. Змінений рядок виглядає як пара: старий з `-`, новий з
`+`. Для тестувальника diff — це як порівняння «очікуваного» і «фактичного».

### Гілка

**Гілка** (*branch*) — окрема лінія історії. Основна гілка зазвичай називається `main` (або `master`
— залежить від налаштувань). Створюєш гілку `try-new-menu`, пробуєш там що завгодно, і основна гілка
не змінюється. Сподобалось — пізніше можна об'єднати; ні — просто повертаєшся на основну.

### Ще кілька слів, які ти зустрінеш

| слово | що означає | команда, яку побачиш |
|---|---|---|
| status | що змінено й не закомічено зараз | `git status` |
| log | історія комітів | `git log --oneline` |
| revert | новий коміт, який скасовує зміни попереднього (історія зберігається) | `git revert …` |
| restore / discard | викинути незакомічені зміни у файлі, повернувши його до останнього коміту | `git restore styles.css` (або старіше `git checkout -- styles.css`) |
| `.gitignore` | список файлів, які git не повинен зберігати (наприклад, `.env` із секретами) | — |

⏸ **Зупинись і перевір себе.** Ти змінив файл, але не закомітив, а потім попросив Claude «викинути
всі незакомічені зміни». Чи зможе git потім повернути твою зміну?

> **Відповідь.** Ні. Незакомічені зміни git ще не зберігав, тож після «викинути» їх немає в
> історії. Тому перед такою командою подумай, чи нічого цінного не загубиш, а цінне — спершу
> закоміть.

## 10.7. Git руками Claude: промпти

Команди git не обов'язково вчити напам'ять. Можна просити Claude звичайними словами — він сам
запустить потрібні команди, а ти в режимі Manual (урок 9) побачиш кожну до виконання. Промпти нижче —
приклади; можна писати й англійською, і українською.

| що хочеш | промпт |
|---|---|
| почати користуватися git | «Налаштуй git у цій папці й зроби перший коміт. Поясни кожен крок простими словами.» (*Set up git in this folder and make a first commit. Explain each step simply.*) |
| зберегти стан перед ризикованою зміною | «Закоміть поточний стан, перш ніж почнеш.» (*Commit the current state before you start.*) |
| побачити, що змінилося | «Покажи простими словами, що ти змінив з останнього коміту.» (*Show me what you changed since the last commit, in plain words.*) |
| скасувати останній коміт | «Скасуй останній коміт через revert.» (*Revert the last commit.*) |
| викинути незакомічені зміни у файлі | «Викинь усі незакомічені зміни у styles.css.» (*Throw away all uncommitted changes to styles.css.*) |
| безпечно поекспериментувати | «Створи нову гілку try-new-menu і працюй у ній.» (*Create a new branch called try-new-menu and work there.*) |

Що ти побачиш у запитах дозволу:

- `git status`, `git diff`, `git log` — команди тільки для читання, вони **не потребують дозволу**;
- `git init`, `git add`, `git commit`, `git switch`, `git revert`, `git restore` — змінюють стан, у
  Manual Claude спитає дозволу;
- `git reset --hard`, `git push --force`, `git clean` — читай особливо уважно: такі команди можуть
  безповоротно стерти роботу. Якщо не розумієш, що вони роблять, — **No** і «поясни простими
  словами».

⏸ **Зупинись і перевір себе.** Чому промпт «Закоміть поточний стан, перш ніж почнеш» корисний навіть
тоді, коли є rewind?

> **Відповідь.** Rewind не відкочує файлів, які змінювали лише команди терміналу, зміни субагентів і
> зміни поза сесією. Коміт — знімок усього проєкту, до якого можна повернутися незалежно від того,
> хто і як змінив файли.

## 10.8. Бекапи, ізоляція і золоте правило

Третій шар — на випадок, коли ні rewind, ні git не допоможуть (наприклад, папку видалили разом із
`.git`):

- **Резервна копія важливої роботи** — репозиторій на GitHub чи копія в хмарному сховищі.
- **Ризикований експеримент — на копії.** Скопіюй папку, створи гілку або **worktree** (окрему
  робочу копію репозиторію, урок 7) і пробуй там.
- **Ніколи не вмикай `bypassPermissions`** (урок 9) на комп'ютері з даними, які не можна втратити.

**Золоте правило уроку: коміть перед великими змінами, читай diff після них.**

Як це виглядає в одному робочому циклі:

```
> git status                      (чисто? якщо ні — закоміть)
  "Закоміть поточний стан, перш ніж почнеш."
  ... Claude працює ...
> git diff                        (що саме змінилося?)
  подобається → "Закоміть з коротким описом змін."
  не подобається → rewind або "Викинь незакомічені зміни."
```

⏸ **Зупинись і перевір себе.** Назви дві ситуації, де жоден із перших двох шарів не допоможе, а
допоможе лише резервна копія.

> **Відповідь.** 1) Папку проєкту видалено повністю разом із `.git` — немає ні файлів, ні історії.
> 2) Диск ноутбука зламався чи ноутбук загубився — історія git зберігалася на тому самому диску.
> В обох випадках рятує лише копія в іншому місці (GitHub, хмара).

## 10.11. Типові помилки

### Симптом → причина

| симптом | причина | що зробити |
|---|---|---|
| `Esc` двічі не відкриває меню | у полі вводу є текст | очисти поле й натисни ще раз або набери `/rewind` |
| після rewind файл не повернувся | файл змінювали лише команди терміналу (або субагент чи ти сам) | повернути через git або резервну копію; на майбутнє — коміт перед зміною |
| `git` не знайдено | git не встановлено або старе вікно терміналу | встанови з git-scm.com, відкрий новий термінал |
| `Please tell me who you are` | git не знає імені й пошти | `git config --global user.name …` і `user.email …` |
| «викинув незакомічені зміни», а там була потрібна робота | незакомічене git не зберігав | коміть цінне до будь-яких скасувань |
| `git diff` нічого не показує, хоча зміни були | зміни вже закомічені або файл новий і ще не доданий у git | `git status`, `git log --oneline` |
| експеримент зіпсував основну версію | працювали прямо в основній гілці | для експериментів — гілка, копія папки або worktree |
| погодив `git reset --hard`, не читаючи | звичка натискати Yes | Manual + читати команду; не розумієш — No і «поясни» |

## 10.12. Що варто запам'ятати

1. Три шари: чекпоінти з rewind, git, резервні копії з ізоляцією.
2. Кожен промпт, що починає хід, створює чекпоінт автоматично.
3. Rewind: `Esc` двічі на порожньому полі або `/rewind` (`/checkpoint`, `/undo`); варіанти
   **Restore code and conversation**, **Restore conversation**, **Restore code**, два варіанти
   стискання і **Never mind**.
4. Файл, який змінювали лише команди терміналу, rewind не відновлює; зміни субагентів зазвичай теж;
   знімки є лише для 100 останніх чекпоінтів.
5. Чекпоінти — "Not a replacement for version control".
6. Git: репозиторій (папка з `.git`), коміт (знімок + підпис), diff (`-` зникло, `+` з'явилося),
   гілка (окрема лінія для експериментів).
7. Незакомічене git не зберігає — цінне коміть до будь-яких скасувань.
8. Git можна просити словами; `git status`, `git diff`, `git log` дозволу не потребують.
9. Золоте правило: коміт перед великими змінами, diff після них.

# Розв'язки

**10.1.** Чекпоінти й rewind — миттєвий відкат змін, які Claude зробив своїми інструментами
редагування. Рятує: Claude невдало переписав файли в цій сесії. Не рятує: файл видалила команда
терміналу. Git — постійна історія знімків проєкту. Рятує: треба повернутися до стану тижневої
давності. Не рятує: незакомічені зміни, які викинули. Резервні копії й ізоляція — копія проєкту в
іншому місці й окремі місця для експериментів. Рятує: зламався диск. Не рятує: якщо копію не зробили
заздалегідь.

**10.2.** а) Так — файл створено інструментом `Write`, він відстежується. б) Так — після того як
Claude змінив файл своїм інструментом, rewind відкочує й подальші зміни командами терміналу. в) Ні —
файл, який змінювали лише команди, не відстежується. г) Ні — це зовнішня зміна, не дія Claude.
д) Зазвичай ні — зміни субагентів, як правило, не відновлюються.

**10.3.** До rewind: `APPLE`, `BANANA`, `CHERRY`. Після **Restore code** до точки «Зроби всі рядки…»:
`apple`, `banana`, `cherry`. Обирати треба саме той промпт, наслідки якого хочеш скасувати: чекпоінт
зберігає стан перед ним.

**10.4.** **Restore conversation** повертає лише розмову: Claude «не пам'ятає» прохання про `date`,
а сам рядок `date` у файлі **лишається**. **Restore code** зробив би навпаки: прибрав би рядок із
файлу, але розмова з проханням лишилася б. Після вправи прибери рядок `date` будь-яким способом
(наприклад, попроси Claude його видалити), щоб наступні задачі починалися з чистого файлу.

**10.5.** Прогноз за документацією: `shell-made.txt` лишиться, бо його створила лише команда
терміналу, а такі файли не відстежуються. Найімовірніше, меню для цього промпту взагалі не
запропонує **Restore code**: варіанти відновлення коду з'являються лише тоді, коли після вибраної
точки є відстежені зміни файлів. `ls` показує `shell-made.txt` поруч із `notes.txt`. Якщо на Windows команда йшла через `PowerShell` і файл зник — запиши це як своє
спостереження; правило в документації сформульоване для команд `Bash`, тож надійніше вважати, що
зміни командами терміналу rewind не гарантує.

**10.6.** Встановлений git виводить рядок на кшталт `git version 2.…`. Якщо команду не знайдено —
встанови Git for Windows з git-scm.com (Windows) або за інструкцією для своєї системи на тій самій
сторінці, закрий термінал, відкрий новий і повтори.

**10.7.** Типові команди: `git init` (створює прихований `.git`), `git add .` або `git add notes.txt`
(готує файли), `git commit -m "…"` (знімок). У Manual дозволу просять `git init`, `git add`,
`git commit`; `git status` і `git log` проходять без запиту. Якщо git попросив ім'я й пошту — Claude
запропонує `git config` або ти виконаєш його сам (розділ 10.5). `git log --oneline` показує один
рядок: короткий ідентифікатор коміту і підпис, наприклад `a1b2c3d Initial commit`. (Якщо в папці
лишився `shell-made.txt` із кроку 5, він теж потрапить у коміт — це нормально.)

**10.8.** `git status` показує `notes.txt` як змінений (`modified`). `git diff` показує рядок
`+date` — його додано; рядків з `-` немає, бо нічого не видаляли. Пояснення Claude має збігатися:
«додано один рядок `date` у кінець `notes.txt`». Якщо Claude описав більше, ніж у diff, — вір diff.

**10.9.** `cat notes.txt` — без `date`, `git status` — без змін (*nothing to commit, working tree
clean* або схоже). Повернути `date` через git **не можна**: зміна не була закомічена, тож у
історії її немає. (Rewind міг би, бо рядок додав Claude своїм інструментом, — але покладатися на
це як на основну страховку не варто.)

**10.10.** На основній гілці `cat notes.txt` показує рядки без `grape`. `git branch` показує дві
гілки — основну (`main` або `master`, позначена `*`) і `try-fruits`. Рядок `grape` живе лише в коміті
гілки `try-fruits`: перейдеш на неї — він з'явиться. Так гілка захищає основну версію від
експерименту.

**10.11.** а) Коміт. б) Diff (`git diff` або «покажи, що змінилося з останнього коміту»). в) Гілка
(або копія папки / worktree). г) Revert. д) Restore — викинути незакомічені зміни у файлі
(`git restore styles.css`).

**10.12.** `git log --oneline` показує на один коміт більше: зверху — коміт на кшталт
`Revert "…"`. Revert не видаляє коміт з історії, а додає **новий**, який робить протилежну зміну, тож
історія чесно показує і зміну, і її скасування. «Викинути незакомічені зміни» працює з тим, що ще не
потрапило в історію, і нічого в ній не лишає — тому таке скасування не можна повернути через git.

**10.13.** Зразок протоколу: 1) `git status` — переконатися, що все закомічено; якщо ні — «Закоміть
поточний стан». 2) «Створи гілку rename-test-data і працюй у ній». 3) `/plan` — Claude пропонує план
перейменування; перевіряю 3–4 приклади «було → стало». 4) Manual: читаю кожну команду, особливо
