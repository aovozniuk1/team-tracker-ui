# Урок 19. Перший проєкт крок за кроком: to-do сторінка

*Вісімнадцять уроків ти вивчав частини окремо: промпти, режими, інструменти, git, пам'ять, контекст.
Тут ти складеш їх в одну справжню роботу — маленьку вебсторінку зі списком справ — і пройдеш
12 кроків від порожньої папки до збереженого в git проєкту. Після уроку ти сам запускаєш повний цикл
«план → зміни → перевірка → коміт», бачиш кожну дію Claude, вмієш її відкотити і повторюєш цикл на
іншому маленькому проєкті без підказок.*

## Коротко

*Картка уроку: прочитай її перед уроком і повернись до неї після.*

**Одним реченням.** Ти будуєш to-do сторінку з трьох файлів у 12 кроків і на кожному кроці
перевіряєш, що сталося, а не віриш на слово.

**Навіщо.** Усе, що було в уроках 1–18, працює тільки разом: план без перевірки, зміни без git чи
пам'ять без контексту — це половина навички.

**Де.** Термінал у папці `Documents/ai-course/todo-app` (або застосунок Claude з вкладкою **Code**), браузер
для перевірки сторінки, другий термінал для `git`.

**Модель**

- **Plan mode** — Claude досліджує й пропонує план, але нічого не змінює (урок 9).
- **Manual mode** — Claude питає дозволу на кожну правку й команду; на старті навчання — твій режим.
- **Перевірка** — ти сам відкриваєш сторінку й проходиш свій чек-лист; «готово» від Claude — не доказ.
- **Коміт** — знімок проєкту в git, до якого завжди можна повернутись (урок 10).
- **Чекпоінт** — автоматичний знімок правок Claude перед кожним твоїм промптом; його відкочує `/rewind`.

**Запам'ятай**

1. Сесія стартує в **auto mode**; щоб бачити й погоджувати кожну правку — перейди в **Manual** (`Shift+Tab` один раз; на Windows запасний варіант — `Alt+M`).
2. До plan mode з auto — кілька натискань `Shift+Tab` або просто почни промпт із `/plan`.
3. Спершу план, потім код; спершу відтвори проблему, потім проси виправлення.
4. Перевіряєш ти: відкрий сторінку, пройди чек-лист, попроси в Claude доказ (команду і її вивід).
5. Комітиш після кожного робочого стану; `/rewind` — для швидкого відкату, git — для справжнього.

**Пастки** (симптом → причина)

- Claude створив файли й жодного разу не спитав → сесія в auto mode; дивись рядок стану.
- `git` «не знайдено» → git не встановлено; встанови його до кроку 8.
- `Author identity unknown` під час коміту → git не знає твого імені й пошти.
- Після `/rewind` колір не повернувся → зміну зробила Bash-команда у файлі, який Claude не редагував своїми інструментами.

**Як перевірити**

- У папці `todo-app` лежать `index.html`, `style.css`, `app.js` і `CLAUDE.md`; сторінка в браузері додає, відмічає й видаляє задачі та пам'ятає їх після перезапуску; `git log --oneline` показує щонайменше два коміти.

## 19.1. Що ми будуємо і що знадобиться

**To-do сторінка** — вебсторінка зі списком справ: поле вводу, кнопка «додати», у кожної задачі
галочка «зроблено» і кнопка «видалити». Задачі мають лишатися після того, як ти закрив браузер.
Для цього сторінка зберігатиме їх у **localStorage** — маленькому сховищі, яке браузер тримає для
кожної сторінки окремо (як шухляда в столі, закріплена за однією сторінкою).

Сторінка складатиметься з трьох файлів — тих самих, що ти бачив у дереві з уроку 2:

| файл | що в ньому | аналогія |
|---|---|---|
| `index.html` | структура: заголовок, поле, кнопка, список | каркас будинку |
| `style.css` | вигляд: кольори, відступи, шрифти | фарба й меблі |
| `app.js` | поведінка: що відбувається після кліку | електрика |

Нічого встановлювати для самої сторінки не треба: вона відкривається подвійним кліком у браузері.

## 19.2. Крок 1. Папка проєкту

```

```

**Що побачиш.** `pwd` покаже шлях, що закінчується на `Documents\ai-course\todo-app` (Windows) або

**Що перевірити.** Запитай щось дешеве, що не потребує дій:

```
У якій папці ти зараз працюєш і що в ній лежить?
```

Claude назве `todo-app` і скаже, що вона порожня. Так ти переконуєшся, що робоча папка правильна,

⏸ **Зупинись і перевір себе.** Чому довіру до папки варто давати лише папкам, які ти знаєш?

## 19.4. Крок 3. Спершу план

План потрібен, щоб Claude спершу пояснив, **що** він збирається зробити, а ти погодив це до того,
як з'явиться перший файл. Виправити план — один рядок тексту; виправити готовий код — значно довше.

**Як увійти в plan mode.** Два способи (урок 9):

- **`Shift+Tab` кілька разів.** З auto цикл іде так: auto → Manual → accept edits → plan. Тобто
  три натискання, і ти дивишся на рядок стану, поки не побачиш `⏸ plan mode on`.
- **Почни промпт із `/plan`.** Команда вмикає plan mode просто з поля вводу — найпростіше.

У застосунку Claude режим обирають у перемикачі режимів біля поля вводу.

**Що набрати.**

```
/plan Я зовсім новачок. Хочу просту to-do сторінку:
додати задачу, позначити її виконаною, видалити, і щоб задачі
лишались після закриття браузера.
Тільки HTML, CSS і JavaScript — без фреймворків, нічого не встановлювати.
Запропонуй план і поясни, які файли ти створиш.
```

(Переноси рядків тут лише для зручності читання — набирай промпт одним рядком. Англійською теж
можна: це дешевше в токенах, урок 5.)

Подивись, як цей промпт зібраний з інгредієнтів уроку 12: **хто ти** (новачок), **що треба**
(чотири дії), **обмеження** (без фреймворків, нічого не встановлювати), **що повернути** (план і
список файлів).

**Що побачиш.** Claude коротко подумає (папка порожня, читати нічого) і покаже план: три файли,
що в кожному, як зберігатимуться задачі (майже напевно через `localStorage`). Під планом — меню
затвердження.

**Що перевірити.** Файлів у папці досі немає — у другому терміналі `ls` у `todo-app` порожній.
Plan mode нічого не змінює.

**Що може піти не так.**

- Claude одразу почав створювати файли → ти не в plan mode. Натисни `Esc` (зупиняє хід, урок 13),
  потім `/rewind` або просто продовж — але наступного разу дивись на рядок стану.
- План пропонує React, npm чи «встановити сервер» → ти пропустив обмеження. Напиши це прямо в
  наступному кроці.

## 19.5. Крок 4. Читаєш і правиш план

План читають так само, як вимоги до задачі: чи все, що ти просив, там є, і чи немає зайвого.

**Що перевірити в плані.**

- Чотири дії: додати, позначити, видалити, зберігати після закриття.
- Рівно три файли і жодних встановлень.
- Що буде з порожнім полем? Якщо план мовчить — це питання на кроці 7.

**Що набрати (правка).** Якщо план треба змінити, у меню затвердження обери **No, keep planning**
(лишитися в плануванні) і напиши:

```
Додай ще лічильник незавершених задач. Використай спокійний зелений колір.
```

Claude перепише план. Довгий план зручно правити у своєму текстовому редакторі: `Ctrl+G` відкриває
запропонований план там.

**Як затвердити.** Коли план тебе влаштовує, обери **Yes, manually approve edits** — ти **сам
погоджуватимеш правки**. Варіант **Yes, and use auto mode** теж затверджує план, але перемикає сесію в auto mode —
тоді Claude створюватиме файли, не питаючи тебе. Для першого проєкту він тобі не потрібен.

**Що може піти не так.** Ти випадково вибрав **Yes, and use auto mode**. Нічого страшного: auto
mode безпечний для такої задачі. Хочеш усе ж бачити кожну правку — натисни `Esc`, `Shift+Tab` один
раз (з auto це Manual), переконайся, що в рядку стану `⏸ manual mode on`, і напиши `continue`.
Claude продовжить із того місця, де зупинився.

⏸ **Зупинись і перевір себе.** Чому лічильник задач краще додати в план, а не попросити вже після
того, як усе буде готово?

> **Відповідь.** У плані це одна правка тексту, і Claude одразу закладе лічильник у структуру
> сторінки. Після готового коду це окрема зміна трьох файлів і ще одне коло перевірки. Чим раніше
> знайдена невідповідність вимогам, тим дешевше її виправити — для тестувальника це знайома ідея.

## 19.6. Крок 5. Спостерігаєш цикл

Тепер Claude працює за планом: створює `index.html`, `style.css`, `app.js`. Це агентний цикл з
уроку 8: дія → результат → наступна дія.

**Режим для навчання — Manual.** Сесія стартувала в auto mode: там окрема модель-класифікатор
перевіряє ризиковані дії замість тебе, а звичайні правки йдуть без запитів (урок 9). Поки ти
вчишся, краще бачити й погоджувати кожну правку сам. Подивись на рядок стану:

| бачиш | що робити |
|---|---|
| `⏵⏵ auto mode on` | `Shift+Tab` один раз → `⏸ manual mode on` |
| `⏸ manual mode on` | нічого, ти вже в Manual |
| `⏵⏵ accept edits on` | правки йдуть без запитів; `Shift+Tab`, поки не побачиш `manual` |
| `Shift+Tab` не перемикає (буває на Windows) | `Alt+M` |

Можна й одразу запускати сесію в Manual: `claude --permission-mode manual`.

**Що побачиш.** Перед кожним файлом — запит дозволу: який файл, що в ньому буде, і варіанти
відповіді (разовий дозвіл, дозвіл на всі правки до кінця сесії, відмова). Прочитай, що створюється,
і погодь разово. Коли звикнеш, можна перейти в accept edits (`Shift+Tab`) — правки пройдуть без
запитів, а більшість команд усе одно питатиме.

Між запитами — рядки інструментів: назва інструмента (`Write`, `Edit`, `Read`, `Bash`) і файл чи
команда. У терміналі на них не клікнеш: натисни `Ctrl+O` — відкриється перегляд історії з
детальним використанням інструментів; ще раз `Ctrl+O` — назад. У застосунку Claude і VS Code рядки
інструментів можна просто клікнути.

**Що перевірити.**

- Після кожного погодження в другому терміналі `ls` показує новий файл.
- Відкрий будь-який файл у Блокноті: там справжній код, а не опис коду.
- Наприкінці Claude підсумує, що зробив. Прочитай підсумок до кінця: там бувають припущення
  («я вирішив не перевіряти порожні задачі») і застереження.

**Що може піти не так.**

- Ти погоджуєш, не читаючи → через десять запитів так роблять усі. Зупинись і прочитай хоча б назву
  файлу й перші рядки: це твій контроль.
- Claude хоче запустити команду, якої ти не розумієш → тисни **No** і спитай: «Що робить ця
  команда і навіщо вона тут?» Відмова не ламає сесію, Claude шукатиме інший шлях.

⏸ **Зупинись і перевір себе.** Ти бачиш запит на `Bash` з варіантом «Yes, and don't ask again
for: …». Чим цей варіант відрізняється від дозволу на всі правки до кінця сесії?

> **Відповідь.** «Don't ask again» для команди зберігається надовго: у файл `.claude/settings.local.json`
> у корені проєкту, тож діятиме і в наступних сесіях (урок 9). Дозвіл на правки файлів діє лише до
> кінця поточної сесії й нікуди не записується.

## 19.7. Крок 6. Перевірка


**Що побачиш.** Пояснення: відкрити `index.html` у браузері подвійним кліком. Далі Claude
перечитує файли й називає, що перевірив. Якщо він щось виправляє — у Manual знову будуть запити.

**Як відкрити сторінку самому.** Подвійний клік на `index.html` у Провіднику (Finder) або з другого
терміналу в папці `todo-app`:

| система | команда |
|---|---|
| Windows (PowerShell) | `start index.html` |
| macOS | `open index.html` |
| Linux | `xdg-open index.html` |

**Що перевірити: твій чек-лист.** Пройди його в браузері руками:

1. Додай три задачі — вони з'являються в списку.
2. Відміть одну виконаною — вона виглядає інакше, лічильник зменшився.
3. Видали одну — зникла, лічильник правильний.
4. Онови сторінку (`F5`) — задачі на місці.
5. Закрий браузер повністю і відкрий сторінку знову — задачі на місці.
6. Спробуй додати порожню задачу і задачу з самих пробілів — що сталося?
7. Додай дуже довгу задачу (кілька рядків тексту) — чи не «поїхала» верстка?
8. Колір зелений і спокійний, як ти просив у плані.

Запиши, які пункти пройшли, а які ні. Це твій перший тестовий прогін проєкту.

**Що може піти не так.**

- Після перезапуску браузера задачі зникли → сторінку відкрито в приватному вікні, або браузер
  налаштовано очищати дані сайтів. Відкрий у звичайному вікні.
- «Я перевірив код, помилок немає» без подробиць → попроси доказ: «Які саме сценарії ти перевірив і
  як?» (урок 13). Перевірка без доказу — не перевірка.

## 19.8. Крок 7. Точне виправлення

Спершу **відтвори**. Пункт 6 чек-листа: що сталося з порожньою задачею? Можливі два результати:

- з'явився порожній рядок — це дефект, і ти щойно його відтворив;
- нічого не з'явилось — Claude вже це передбачив. Тоді дефекту немає; переходь до іншого пункту,
  що не пройшов, або все одно додай «трусіння» поля як нову поведінку.

**Що набрати** (якщо порожній рядок з'являється):

```
Коли я додаю порожню задачу, у списку з'являється порожній рядок.
Ігноруй порожній ввід і ввід із самих пробілів, а замість цього
коротко потруси поле вводу.
```

Порівняй із «виправ баг із задачами» (урок 12): тут є **симптом** (порожній рядок), **умова**
(порожній ввід і пробіли) і **очікувана поведінка** (ігнорувати й потрусити поле). Так виглядає
хороший баг-репорт — і хороший промпт.

**Що побачиш.** Claude знайде місце в `app.js`, де додається задача, і запропонує правку через
`Edit`; можливо, ще одну в `style.css` для анімації. У Manual — два запити.

**Що перевірити.** Повтори пункт 6 чек-листа: порожня задача й задача з пробілів не додаються,
поле здригається. Потім **регресія**: пункти 1–5 знову — виправлення не мало зламати решту.

**Що може піти не так.**

- Claude переписав увесь `app.js` замість одного місця → натисни `Esc` і уточни: «Зміни тільки
  перевірку вводу, решту не чіпай».
- Після двох невдалих спроб виправити те саме — не пиши третю. `/clear` і один новий, точніший
  промпт із тим, що ти дізнався (урок 13).

⏸ **Зупинись і перевір себе.** Навіщо після виправлення проходити пункти 1–5, якщо правили тільки
пункт 6?

> **Відповідь.** Зміна в коді додавання задачі може зачепити все, що з ним пов'язано: збереження,
> лічильник, відмітку. Перепрогін уже перевіреного після зміни — це регресійне тестування, і для
> коду, написаного ШІ, воно так само потрібне, як для коду людини.

## 19.9. Крок 8. Зберігаєш роботу в git

Сторінка працює — саме час зробити знімок (урок 10).

**Що набрати.**

```
Налаштуй тут git і закоміть усе з зрозумілим повідомленням.
Поясни кожну команду одним реченням.
```

**Що побачиш.** Claude запускатиме команди через інструмент `Bash`: `git init` — створити репозиторій, `git add` — додати файли до знімка,
`git commit` — зробити знімок. У Manual кожна з них питає дозволу. Команди, що лише читають
(`git status`, `git log`), дозволу не потребують.

**Що перевірити.** У своєму другому терміналі, у папці `todo-app`:

```
> git log --oneline
> git status
```

`git log --oneline` — один рядок: короткий код коміту і повідомлення. `git status` — повідомлення
на кшталт `nothing to commit, working tree clean`: усе збережено.

**Що може піти не так.**

- `Author identity unknown` / `Please tell me who you are` → git не знає, хто автор. Один раз на
  комп'ютер:

  ```
  > git config --global user.name "Olena"
  > git config --global user.email "you@example.com"
  ```

  (своє ім'я і пошту, якою користуватимешся на GitHub; для навчання годиться будь-яка). Можна
  попросити Claude зробити це — але тоді прочитай команди, перш ніж погоджувати.
- `git` не знайдено → див. розділ 19.1, встанови git, відкрий новий термінал, поверни сесію
  `claude -c` (урок 7).

## 19.12. Крок 11. Пробуєш відкат

Зараз ти навмисно зіпсуєш проєкт, щоб навчитися його рятувати.

**Що набрати.**

```

```

Погодь правки (у Manual — запити на `style.css` і, можливо, інші файли). Онови сторінку в

**Що перевірити до відкату.** У другому терміналі `git status` — `style.css` у списку змінених
(`modified`). Git бачить, що ти відійшов від останнього коміту.

**Як відкотити.** Коли поле вводу **порожнє**, натисни `Esc` двічі (або набери `/rewind`).
Відкриється список твоїх промптів. Вибери промпт «Зроби все фіолетовим» — повернення в стан

| варіант | що робить |
|---|---|
| **Restore code and conversation** | повертає і файли, і розмову до цієї точки |
| **Restore conversation** | повертає тільки розмову, файли лишаються |
| **Restore code** | повертає тільки файли, розмова лишається |
| **Summarize from here** / **Summarize up to here** | стискає частину розмови в підсумок, файли не чіпає |
| **Never mind** | нічого не робити |

Вибери **Restore code and conversation** (або **Restore code**, якщо хочеш, щоб Claude пам'ятав
невдалу спробу).

**Що перевірити після.** Онови сторінку — знову зелена. `git status` — знову `working tree clean`:
файли збігаються з останнім комітом. Це найкращий доказ, що відкат повний.

**Що може піти не так.** Колір не повернувся → Claude змінив файл командою через `Bash`, а не своїм
інструментом редагування. `/rewind` відкочує такі зміни лише у файлах, які Claude раніше в цій
розмові вже редагував своїми інструментами; файл, який змінювали тільки команди, не відстежується
(урок 10). Тоді рятує git: «Відкинь усі незакомічені зміни в `style.css`».

⏸ **Зупинись і перевір себе.** Чому `git status` після відкату — кращий доказ, ніж «сторінка знову
зелена»?

> **Відповідь.** Око бачить тільки колір. `git status` порівнює **кожен** файл з останнім
> комітом: якщо там «чисто», жодна побічна зміна (у `app.js`, у `index.html`) не лишилась.

## 19.14. Варіант-завдання: чек-лист із CSV тест-кейсів

Тепер те саме — самостійно, без покрокових підказок. Задача з життя тестувальника: у тебе є
тест-кейси в таблиці, а проходити їх хочеться по чек-листу з галочками.

**CSV** (від англ. *comma-separated values*) — простий текстовий формат таблиці: кожен рядок —
рядок таблиці, значення розділені комами. Excel і Google Sheets уміють зберігати таблицю як CSV.
Якщо в значенні є кома, його беруть у лапки.

### Підготовка

Створи папку `Documents/ai-course/checklist-app` і в ній файл `cases.csv` (у Блокноті, кодування UTF-8):

```
id,title,steps,expected
TC-01,Login with valid data,"Open login page; enter valid data; click Sign in",Dashboard is shown
TC-02,Login with empty password,"Open login page; leave password empty; click Sign in",Error under the password field
TC-03,"Search, with a comma",Type a word with a comma into search,Results contain the word
TC-04,Пошук українською,Ввести «тест» у пошук,Знайдено записи зі словом «тест»

TC-05,Logout,Click Logout,Login page is shown
```

Зверни увагу: TC-03 має кому в назві (у лапках), TC-04 — кирилицю, а перед TC-05 — порожній рядок.
Це навмисні пастки.

### Що має вміти сторінка

1. Кнопка вибору файлу: обираєш `cases.csv` — сторінка показує кожен кейс рядком: id, назва,
   очікуваний результат; кроки — під назвою або за кліком.
2. Біля кожного кейсу — галочка «пройдено» і лічильник «Пройдено X з Y».
3. Галочки зберігаються після перезапуску браузера.
4. Кнопка «Скинути» знімає всі галочки.
5. Нічого не встановлювати: HTML, CSS, JavaScript.

### Як пройти

Ті самі 12 кроків, але промпти пишеш сам. Кілька підказок:

- У промпті плану дай Claude сам файл: набери `@cases.csv` — він прочитає його вміст (урок 13).
- Назви пастки в плані явно: кома в лапках, кирилиця, порожній рядок.
- Складіть чек-лист перевірки **до** того, як Claude почне писати код, — і попроси його ж
  перевірити роботу саме за цим списком.

### Що здати (собі або наставнику)

- Папка з `index.html`, `style.css`, `app.js`, `cases.csv`, `CLAUDE.md`.
- `git log --oneline` — щонайменше два коміти.
- Твій чек-лист із позначками «пройшло / не пройшло» і що ти виправив.
- Один відкат через `/rewind` або git — опиши в одному реченні, що відкочував.

## 19.15. У роботі QA

- **Утиліта для себе.** Маленькі сторінки на кшталт CSV-чек-листа, генератора тестових даних чи
  форматувальника JSON — це те, що Claude Code робить швидко, а тобі економить години рутини.
- **Чек-лист до коду.** Ти пишеш перевірки до того, як Claude закінчить, і проганяєш їх після — так
  само, як тест-кейси до релізу. Це і є твій «pass/fail», який робить «готово» перевірюваним.
- **Відтворення перед виправленням.** На кроці 7 ти спершу відтворив дефект. Та сама звичка в
  баг-репортах: спершу кроки й фактичний результат, потім очікування.
- **Регресія після кожної правки.** Будь-яка зміна, навіть «маленька», тягне перепрогін ключових
  сценаріїв.
- **Git як журнал доказів.** Коміт після кожного робочого стану — це історія, до якої можна
  повернутись і показати, що саме змінилося між «працювало» і «зламалось».
- **Тестові дані з пастками.** Кома в лапках, кирилиця, порожній рядок у `cases.csv` — класичні
  граничні випадки, які варто класти в будь-які тестові дані.

## 19.16. Типові помилки

### Симптом → причина

| симптом | причина | що зробити |
|---|---|---|
| Claude створив усі файли без жодного запиту | сесія в auto mode | `Shift+Tab` один раз → `⏸ manual mode on` (Windows: `Alt+M`) |
| файли з'явились ще до плану | ти був не в plan mode | дивись рядок стану; або починай промпт із `/plan` |
| план з React чи npm | у промпті не було обмежень | «тільки HTML, CSS, JavaScript, нічого не встановлювати» |
| `Shift+Tab` нічого не перемикає | особливість терміналу на Windows | `Alt+M` |
| не видно, що саме зробив інструмент | у терміналі рядки не клікаються | `Ctrl+O`, ще раз `Ctrl+O` — назад |
| задачі зникають після перезапуску браузера | приватне вікно або очищення даних сайтів | звичайне вікно браузера |
| «я перевірив, помилок немає» без подробиць | ти не попросив доказу | «які сценарії і як ти перевірив?» + свій чек-лист |
| `Author identity unknown` | git не знає імені й пошти | `git config --global user.name` / `user.email` |
| після `/rewind` зміна лишилась | файл змінила Bash-команда | git: відкинути незакомічені зміни в цьому файлі |
| третя спроба виправити те саме знову невдала | контекст забитий невдалими спробами | `/clear` і один точніший промпт |
| після `/clear` Claude не знає правила «пояснюй просто» | правило було тільки в чаті | запиши його в `CLAUDE.md` |

## 19.17. Що варто запам'ятати

1. Порожня папка, `cd` у неї, `pwd` — і тільки потім `claude`.
2. Сесія стартує в auto; для навчання — Manual: `Shift+Tab` один раз (Windows: `Alt+M`).

# Розв'язки

**19.1.** Без плану Claude одразу пише код за своїм розумінням задачі; якщо він зрозумів не так, ти
дізнаєшся про це лише з готових файлів і переробка коштує дорого. План — це вимоги, які можна
прочитати й виправити за хвилину. Аналогія: тест-план погоджують до тестування, а не після; рев'ю
вимог дешевше за баг на продакшені.

**19.2.** Перше натискання: `⏸ manual mode on`. Друге: `⏵⏵ accept edits on`. Третє:
`⏸ plan mode on`. Четверте поверне в auto (якщо він доступний). Якщо в тебе сесія стартувала в
Manual (старіша версія), цикл починається з Manual, і до plan mode — два натискання. Вийди `exit`.

**19.3.** Очікувано: три файли — `index.html`, `style.css`, `app.js`. Інструменти: `Write` для
кожного нового файлу, можливо `Read` або `Edit`, якщо Claude перечитував чи правив. Запитів дозволу
в Manual — щонайменше три (по одному на файл); якщо Claude запускав команди, то більше. Якщо запитів
не було зовсім — ти був в auto або accept edits.

**19.4.** Приклади: задача з емодзі чи кирилицею зберігається й показується правильно; дві задачі з
однаковим текстом — видалення однієї не видаляє обидві; задача з кутовими дужками на кшталт
`<script>` показується як звичайний текст і нічого не ламає; сто задач — сторінка не гальмує й прокручується; відмітка
виконаної задачі теж переживає перезапуск браузера. Граничні тут: однакові задачі, HTML-символи, сто
задач.

**19.5.** Наприклад:

```
Коли я видаляю незавершену задачу, лічильник незавершених задач не змінюється
(було 3 — після видалення лишилось 3). Очікую, що він зменшиться на 1.
Виправ тільки цю логіку в app.js, потім перевір: додай 3 задачі, видали одну —
лічильник має показати 2.
```

Є симптом, кроки, очікування, межі зміни і перевірка з результатом «пройшло / не пройшло».

**19.6.** Claude опише зміну людською мовою («змінив текст у тегу `title` і заголовку в
`index.html`»). `git diff` покаже ті самі рядки: старий із `-`, новий із `+`. Відповіді мають
збігатися за змістом. Якщо Claude назвав зміни, яких у `git diff` немає (чи навпаки), — `git diff`
має рацію: це факт, а опис — переказ. Якщо `git diff` запускає Claude, дозволу він не питає:
команда лише читає.

**19.7.** **Restore code and conversation** — усе назад, ніби невдалого промпту не було: «зробив
фіолетовим, не сподобалось, хочу почати з тієї точки». **Restore code** — файли назад, а розмова
лишається: Claude пам'ятає, що фіолетовий не підійшов, і не запропонує його знову. **Restore
conversation** — файли лишаються, розмова назад: зміни тобі подобаються, але обговорення навколо
них довге й заплутане, і хочеться продовжити з чистішої точки.

**19.8.** У першому випадку — так: якщо Claude уже редагував файл своїми інструментами в цій
розмові, `/rewind` відкочує й подальші зміни Bash-командами в цьому файлі. У другому — ні:
файл, який змінювали тільки Bash-команди, не відстежується й лишається як є. Відкочувати його
доведеться через git (якщо він був закомічений) або вручну.

**19.9.** Частка розмови різко зменшилась: після `/clear` розмова майже порожня — лише питання про
проєкт і відповідь, плюс файли, які Claude прочитав, щоб відповісти. Системний промпт, інструменти й
`CLAUDE.md` лишились — вони завантажуються в кожну розмову.

**19.10.** Наприклад: «Я новачок. Хочу to-do сторінку: додати задачу, відмітити виконаною,
видалити, зберігати після закриття браузера. Тільки HTML, CSS, JavaScript, нічого не встановлювати.
Спершу запропонуй план і поясни, які файли створиш; нічого не змінюй, доки я не погоджу». Додано:
хто ти, що саме треба (чотири дії), обмеження, формат результату (план зі списком файлів) і умову
«не змінювати до погодження».

**19.11.** Ознаки успіху: після вибору `cases.csv` видно рівно п'ять кейсів (порожній рядок не
став шостим «порожнім» кейсом); TC-03 має назву `Search, with a comma` цілою, а не розірваною на дві

`git log --oneline` — щонайменше два коміти. Якщо кирилиця зламана — перевір, що `cases.csv`
