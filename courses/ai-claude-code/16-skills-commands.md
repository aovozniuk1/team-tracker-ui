# Урок 16. Команди і скіли

*Ти вже користуєшся командами — `/clear`, `/context`, `/memory`. Тепер час навчитися додавати
власні. Скіл — це файл з інструкцією для одного виду задач: Claude бачить лише його короткий опис і
відкриває повний текст тоді, коли задача справді трапилась, або коли ти кличеш його командою.
Після уроку ти розрізняєш вбудовані команди й скіли, створюєш свій перший скіл від початку до кінця
й перевіряєш, що він працює, пишеш скіл з аргументами і знаєш, коли обрати скіл, `CLAUDE.md` чи
субагента.*

## Коротко

*Картка уроку: прочитай її перед уроком і повернись до неї після.*

**Одним реченням.** Скіл — це папка з файлом `SKILL.md`: короткий опис «коли мене використовувати»
плюс інструкції; він стає командою `/назва-скіла` і завантажується тільки за потреби.

**Навіщо.** Щоб не вставляти в чат ту саму інструкцію, чек-лист чи процедуру щоразу і щоб не роздувати
`CLAUDE.md` тим, що потрібно лише іноді.

**Де.** `/` — меню команд; `/skills` — список скілів; особисті скіли — `~/.claude/skills/<назва>/SKILL.md`,
скіли проєкту — `.claude/skills/<назва>/SKILL.md`.

**Модель**

- **Команда** — керування Claude Code з рядка, що починається з `/`: `/clear`, `/model`, `/skills`.
- **Вбудована команда** — виконує фіксовану логіку самої програми (`/clear` очищає контекст).
- **Скіл** — інструкція для Claude в `SKILL.md`; запускається тобою (`/назва`) або Claude сам.
- **Вбудований (bundled) скіл** — скіл, що йде з Claude Code: `/code-review`, `/debug`, `/doctor`.
- **Frontmatter** — блок налаштувань між `---` на початку `SKILL.md` (урок 14).

**Запам'ятай**

1. Команду розпізнають лише на початку повідомлення; текст після назви — її аргументи.
2. Claude завжди бачить назву й опис скіла, а повний текст — лише коли скіл використовують.
3. Назва команди = назва папки скіла (або поле `name`); `description` каже, коли скіл доречний.
4. Однакові назви: Enterprise переважає особистий, особистий — проєктний.
5. `.claude/commands/deploy.md` і `.claude/skills/deploy/SKILL.md` — те саме: обидва дають `/deploy`.
6. Перевірка: `/skills` показує скіл, а запуск дає відповідь у форматі, який описано в скілі.

**Пастки** (симптом → причина)

- `Shell command failed for pattern` → команда всередині скіла впала (наприклад, `git` поза
  репозиторієм); скіл не запускається взагалі.
- Скіла немає в меню → нова папка з'явилась уже під час сесії; `/reload-skills` або перезапуск.
- Claude сам запустив скіл, який мав запускати тільки ти → немає `disable-model-invocation: true`.

**Як перевірити**

- `/skills` показує `summarize-changes`; після зміни файлу в git-проєкті `/summarize-changes` дає
  два-три пункти про твою зміну і список ризиків.

## 16.1. П'ять способів розширити Claude Code

«З коробки» Claude Code читає й пише файли, запускає команди й шукає в інтернеті. Навчити його
більшого можна п'ятьма механізмами, які легко сплутати:

| механізм | одним рядком | хто запускає | приклад |
|---|---|---|---|
| **команда** | вбудоване керування, що набирається через `/` | ти | `/clear`, `/model` |
| **скіл** | `SKILL.md` з інструкціями (і, за бажанням, файлами) для одного виду задач | Claude, коли доречно, або ти `/назвою` | `/summarize-changes` |
| **MCP-сервер** | конектор, що дає Claude інструменти зовнішньої системи | Claude, коли потрібен інструмент | Notion, GitHub, база даних |
| **хук** | команда, яку Claude Code сам запускає у фіксований момент | сам Claude Code, щоразу | форматувати код після кожної зміни |
| **плагін** | набір скілів, агентів, хуків і MCP-серверів, що ставиться одним пакетом | ти встановлюєш один раз | спільне налаштування команди |

У цьому уроці — команди й скіли. MCP, хуки й плагіни — в уроці 17.

## 16.2. Команди

Документація: "Type / to see the commands available to you, or type / followed by letters to
filter." — набери `/`, і з'явиться меню; допиши кілька літер — меню відфільтрується. У новіших
версіях їх називають просто **Commands** (раніше — «slash commands»).

Три правила:

1. **Тільки на початку повідомлення.** `/clear` спрацює, а `поясни /clear` — ні: це просто текст.
2. **Текст після назви — аргументи.** `/compact keep the test commands` передає команді
   інструкцію; `/model sonnet` — назву моделі.
3. **Під час відповіді — у чергу.** Якщо надіслати команду, поки Claude відповідає, вона виконається
   після завершення ходу. Деякі (`/status`, `/tasks`, `/usage`) спрацьовують одразу.

### Два види команд

- **Вбудовані команди** виконують фіксовану логіку самої програми: `/clear` очищає контекст,
  `/model` перемикає модель. Модель у цьому не бере участі.
- **Вбудовані скіли** (bundled skills) — це інструкції для Claude, які йдуть разом із Claude Code. У
  довіднику команд вони позначені **Skill**. Приклади: `/code-review` (перевірка змін на помилки),
  `/debug` (діагностика проблем Claude Code), `/doctor` (перевірка налаштувань), `/batch` (великі
  зміни частинами), `/loop` (повторювати промпт з інтервалом).

Зверни увагу на дві схожі назви: `claude doctor` у **терміналі** — перевірка встановлення без
запуску сесії; `/doctor` **у сесії** — скіл, який аналізує налаштування й пропонує виправлення,
спершу питаючи твоєї згоди.

### Команди, які ти вже знаєш

| команда | що робить | урок |
|---|---|---|
| `/help` | допомога і перелік команд | — |
| `/clear`, `/compact`, `/context` | новий контекст, стиснути, подивитись заповнення | 6 |
| `/usage` | витрати й ліміти | 5 |
| `/resume` | повернутися до попередньої розмови | 7 |
| `/permissions` | правила дозволів | 9 |
| `/rewind` | відкат до чекпоінта | 10 |
| `/code-review` | перевірка змін на помилки у свіжому субагенті | 13 |
| `/init`, `/memory` | `CLAUDE.md` і пам'ять | 14 |
| `/tasks` | фонова робота, зокрема субагенти | 15 |
| `/skills`, `/reload-skills` | список скілів; перечитати папки скілів | 16 |
| `/model`, `/effort` | модель і рівень зусиль | 18 |

⏸ **Зупинись і перевір себе.** Ти пишеш: «Будь ласка, /clear». Що станеться?

> **Відповідь.** Контекст не очиститься: команду розпізнають лише на початку повідомлення. Claude
> отримає це як звичайний текст. Правильно — повідомлення, що починається з `/clear`.

## 16.3. Що таке скіл

Документація: "Skills extend what Claude can do. Create a SKILL.md file with instructions, and
Claude adds it to its toolkit. Claude uses skills when relevant, or you can invoke one directly
with /skill-name."

Скіл — це **папка** з файлом `SKILL.md`. Файл має дві частини:

1. **Frontmatter** між `---` — насамперед `description`: що робить скіл і коли його використовувати.
2. **Інструкції** у Markdown — що робити, коли скіл запущено.

### Чому скіл «дешевий»

На старті сесії Claude бачить лише **назву й опис** кожного скіла — за ними він вирішує, чи підходить
скіл до задачі. Повний текст завантажується тільки тоді, коли скіл використовують: "Unlike CLAUDE.md
content, a skill's body loads only when it's used, so long reference material costs almost nothing
until you need it."

Аналогія: `CLAUDE.md` — пам'ятка, приклеєна на монітор, вона завжди перед очима. Скіли — папки в
шафі з підписаними корінцями: Claude бачить підписи й дістає папку, лише коли вона потрібна.

### Коли робити скіл

Документація: "when you keep pasting the same instructions, checklist, or multi-step procedure into
chat, or when a section of CLAUDE.md has grown into a procedure rather than a fact." Тобто:

- ти втретє вставляєш у чат той самий чек-лист чи шаблон;
- частина `CLAUDE.md` перетворилась із факту («тести запускає `npm test`») на процедуру («щоб
  підготувати звіт, зроби 1, 2, 3 … 12»).

Скіли Claude Code побудовані на відкритому стандарті Agent Skills, тож той самий `SKILL.md` можуть
розуміти й інші ШІ-інструменти (без розширень, специфічних для Claude Code).

⏸ **Зупинись і перевір себе.** У тебе 15 скілів по 200 рядків кожен. Скільки з цих 3000 рядків
Claude завантажить на старті сесії?

> **Відповідь.** Жодного рядка тіла: на старті Claude бачить лише назви й описи 15 скілів. Тіло
> скіла завантажується, коли його запускаєш ти або Claude вирішує, що скіл доречний.

## 16.4. Перший скіл покроково: `summarize-changes`

Це офіційний приклад з документації. Скіл підсумовує незакомічені зміни в git-репозиторії і
підсвічує ризики. Особливість: перед тим як Claude прочитає інструкцію, Claude Code сам запускає
`git diff HEAD` і вставляє результат у текст. Тож Claude працює з **реальними** змінами, а не
здогадується.

### Крок 0. Підготуй git-проєкт

Скіл запускає `git`, тому потрібні дві речі: встановлений git (урок 10) і папка-репозиторій, у якій
є **хоча б один коміт**. Без коміту `HEAD` ще не існує, і команда впаде. Візьми папку `qa-notes` з
уроків 14–15 (або будь-яку папку з кількома файлами):

```
> cd ~/Documents/ai-course/qa-notes
> git init
> git add .
> git commit -m "First commit"
```

Якщо папка вже є репозиторієм з комітами — пропусти. Якщо git відповів `Please tell me who you are`,
спершу вкажи ім'я й e-mail для комітів (урок 10), наприклад:

```
> git config --global user.name "Olena"
> git config --global user.email "you@example.com"
```

і повтори `git commit`.

### Крок 1. Створи папку скіла

Скіл буде **особистим** — доступним у всіх твоїх проєктах.

```
> mkdir ~/.claude/skills/summarize-changes          (Windows PowerShell)
> mkdir -p ~/.claude/skills/summarize-changes       (macOS, Linux)
```

PowerShell створює всі проміжні папки сам; на macOS і Linux для цього потрібен `-p`.

### Крок 2. Напиши `SKILL.md`

Відкрий новий файл у текстовому редакторі:

```
> notepad "$HOME\.claude\skills\summarize-changes\SKILL.md"      (Windows)
> nano ~/.claude/skills/summarize-changes/SKILL.md                (macOS, Linux)
```

Блокнот спитає, чи створити новий файл, — погодься. Встав текст рівно так, як у документації:

```
---
description: Summarizes uncommitted changes and flags anything risky. Use when the user asks what changed, wants a commit message, or asks to review their diff.
---

## Current changes

!`git diff HEAD`

## Instructions

Summarize the changes above in two or three bullet points, then list any risks you notice such as missing error handling, hardcoded values, or tests that need updating. If the diff is empty, say there are no uncommitted changes.
```

Збережи (`Ctrl+S`; у `nano` — `Ctrl+O`, `Enter`, потім `Ctrl+X` для виходу). Перевір, що файл
називається саме `SKILL.md`, а не `SKILL.md.txt` (урок 2): `ls ~/.claude/skills/summarize-changes`.

*Інший шлях:* попросити Claude Code створити цей файл з точно таким вмістом. Він лежить поза робочою
папкою, тож Claude може спитати дозволу (урок 9).

### Що означає кожна частина

| частина | що робить |
|---|---|
| `description` | "tells Claude when to use the skill" — каже Claude, коли скіл доречний; тут: питання «що змінилось», прохання про commit message чи огляд змін |
| назва папки `summarize-changes` | стає командою `/summarize-changes` (поле `name` у frontmatter може задати іншу) |
| `` !`git diff HEAD` `` | **динамічний контекст**: Claude Code запускає команду й підставляє її вивід замість цього рядка ще до того, як Claude побачить скіл |
| `## Instructions` | що Claude має зробити з отриманими змінами |

### Крок 3. Запусти Claude Code і перевір, що скіл є

```
> cd ~/Documents/ai-course/qa-notes
> claude
```

Набери `/skills`. У списку має бути `summarize-changes`. У цьому списку `t` сортує скіли за кількістю
токенів, а `Esc` закриває. Не тисни `Space` чи `Enter` на скілі без потреби: так перемикається
його видимість для Claude і для меню `/`.

### Крок 4. Зміни файл і випробуй скіл двома способами

Відкрий `login-tests.md` у Блокноті (TextEdit, `nano`) і зміни один рядок — наприклад, очікуваний
результат одного тест-кейсу. Збережи. Тепер у Claude Code:

**Спосіб 1 — Claude вирішує сам.** Напиши питання, що підходить під опис:

```
What did I change?
```

**Спосіб 2 — ти кличеш напряму:**

```
/summarize-changes
```

Що маєш побачити в обох випадках: два-три пункти про твою зміну в `login-tests.md` і список ризиків
(наприклад, «змінено очікуваний результат — оновіть пов'язані тест-кейси»). Якщо змін немає, скіл
каже, що незакомічених змін немає.

### Якщо не працює

| що бачиш | причина | що зробити |
|---|---|---|
| `Shell command failed for pattern ...` | `git diff HEAD` впав: папка не репозиторій або ще немає жодного коміту | крок 0: `git init`, `git add .`, `git commit` |
| `Shell command permission check failed for pattern ...` | правило дозволів (урок 9) не пустило команду | перевір правила заборони в `/permissions` |
| `/summarize-changes` немає в меню | папку скілів створено вже під час сесії, або помилка в назві файлу | `/reload-skills` або перезапуск; перевір назву `SKILL.md` |
| «What did I change?» — Claude відповів без скіла | опис не збігся з формулюванням | переформулюй ближче до опису або клич `/summarize-changes` |

Головна пастка — перший рядок таблиці. Документація: "A failed command aborts the entire skill
invocation" — якщо команда в `` !`…` `` завершилась помилкою, скіл не запускається взагалі, Claude
його не бачить.

На Windows без Git Bash такі вбудовані команди виконуються через PowerShell; `git diff HEAD`
працює однаково.

⏸ **Зупинись і перевір себе.** Ти скопіював скіл на інший комп'ютер і запустив `/summarize-changes`
у папці «Документи», яка не є git-репозиторієм. Що побачиш і чому?

> **Відповідь.** Повідомлення `Shell command failed for pattern ...`: `git diff HEAD` поза
> репозиторієм завершується помилкою, а невдала команда скасовує весь запуск скіла. Треба
> запускати його в папці-репозиторії з хоча б одним комітом.

## 16.5. Скіл з аргументами: `/bug-report`

Другий скіл — **проєктний** (лише для `qa-notes`) і з **аргументами**: те, що ти напишеш після
назви, підставиться в текст замість `$ARGUMENTS`.

Створи файл `.claude/skills/bug-report/SKILL.md` у папці `qa-notes` (самостійно або попроси Claude
створити його з цим вмістом):

```
---
description: Turns a short bug description into a full bug report in the team format.
disable-model-invocation: true
---

Turn this description into a bug report: $ARGUMENTS

Format:
- Title: one line, what is broken and where
- Severity: low, medium or high, with one sentence why
- Steps to reproduce: numbered, one action per step
- Actual result
- Expected result
- Environment: if it is not in the description, write "уточнити"

Write in Ukrainian. Do not invent details that are not in the description.
```

Якщо папки `.claude/skills/` на старті сесії не було, набери `/reload-skills` — команда перечитає
папки й скаже, скільки скілів додано. Тепер:

```
/bug-report після другого кліку на Login нічого не відбувається, Chrome
```

Claude отримає інструкцію, де `$ARGUMENTS` замінено на твій опис, і поверне баг-репорт за
форматом: заголовок, серйозність, кроки, фактичний і очікуваний результат, середовище «Chrome».

### Хто може запускати скіл

Рядок `disable-model-invocation: true` означає: Claude **не** запускає цей скіл сам, лише ти
командою. Так роблять для дій з наслідками (відправити, опублікувати, задеплоїти) або коли ти
хочеш сам вирішувати момент.

| налаштування | ти можеш запустити | Claude може запустити | що в контексті |
|---|---|---|---|
| (за замовчуванням) | так | так | опис — завжди; повний текст — при запуску |
| `disable-model-invocation: true` | так | ні | опису немає; повний текст — при запуску |
| `user-invocable: false` | ні | так | опис — завжди; повний текст — при запуску |

`user-invocable: false` — для фонових знань, які не є «дією» для людини (наприклад, як влаштована
стара система).

### Де писати назву скіла

| де | приклад | що станеться |
|---|---|---|
| на початку повідомлення | `/bug-report ...` | Claude Code запускає скіл одразу |
| посеред тексту, окремим словом | `оформи це через /bug-report` | напряму нічого не запускається: це твій дозвіл, і Claude сам вирішує за змістом, чи запускати |

Щоб просто згадати скіл без дозволу на запуск — пиши назву без `/`.

⏸ **Зупинись і перевір себе.** Навіщо скілу `bug-report` рядок `disable-model-invocation: true`, якщо
він нічого не відправляє?

> **Відповідь.** Тут це питання контролю: ти сам вирішуєш, коли текст стає баг-репортом, і Claude
> не перетворюватиме кожну згадку бага на повний звіт. Бонус: опис такого скіла не займає контекст.
> Для скілів, що щось відправляють чи публікують, цей рядок особливо важливий.

## 16.6. Як влаштований `SKILL.md`: поля і можливості

Усі поля frontmatter необов'язкові; документація рекомендує завжди писати `description`.

| поле | що робить |
|---|---|
| `name` | назва команди в меню `/`; за замовчуванням — назва папки |
| `description` | що робить скіл і коли його використовувати; за ним Claude вирішує, чи скіл доречний |
| `disable-model-invocation` | `true` — запускаєш тільки ти |
| `user-invocable` | `false` — запускає тільки Claude, у меню `/` скіла немає |
| `allowed-tools` | інструменти, які Claude може використати без запиту дозволу під час ходу, де запущено скіл |
| `argument-hint` | підказка про аргументи в автодоповненні, наприклад `[issue-number]` |

Поле з помилкою в назві Claude Code мовчки ігнорує, тож назви пиши точно, з дефісами.

### Можливості тексту скіла

- **`$ARGUMENTS`** — усе, що написано після назви. `$0`, `$1` — перший, другий аргумент окремо.
- **`` !`команда` ``** — динамічний контекст: команда виконується перед тим, як Claude побачить
  скіл, і її вивід стає частиною тексту. Працює лише на початку рядка або після пробілу.
- **Додаткові файли.** У папці скіла можуть лежати довідники, приклади, скрипти. У `SKILL.md`
  пишеш, що в якому файлі й коли його читати, — Claude відкриє їх лише за потреби. Документація
  радить тримати сам `SKILL.md` до 500 рядків.

### Як скіл живе в сесії

- Запущений скіл додається в розмову одним повідомленням і лишається там на наступні ходи. Claude
  Code не перечитує файл щоразу, тож інструкції пиши як постійні («запускай перевірку після кожної
  зміни»), а не разові.
- Після стискання розмови від запущених скілів може лишитись тільки початок. Тому найважливіше
  клади вгорі `SKILL.md`; якщо Claude перестав дотримуватися скіла — просто запусти його знову.
- Зміни в `SKILL.md` Claude Code підхоплює в поточній сесії сам. Виняток — нова верхня папка
  скілів, якої не було на старті: тоді `/reload-skills`.

Тіло скіла — теж інструкція для моделі, а не примусове правило (урок 14). Якщо крок мусить
виконуватися щоразу без винятків, йому місце в хуку (урок 17).

## 16.7. Де живуть скіли і хто перемагає

| місце | шлях | де діє |
|---|---|---|
| Enterprise | папка керованих налаштувань організації | усі користувачі на комп'ютерах, куди її розгорнули |
| особистий | `~/.claude/skills/<назва>/SKILL.md` | усі твої проєкти на цьому комп'ютері |
| проєктний | `.claude/skills/<назва>/SKILL.md` | цей репозиторій; закоміть — і отримає команда |
| плагін | `<plugin>/skills/<назва>/SKILL.md` | там, де плагін увімкнено, як `/plugin-name:skill-name` |

### Однакові назви

| однакова назва в | що спрацює |
|---|---|
| особистому і проєктному | "Enterprise over personal, and personal over project." — особистий |
| скілі й файлі `.claude/commands/` | скіл |
| твоєму скілі й вбудованому скілі чи команді | твій скіл заміняє вбудований, але не його псевдоніми |
| плагіні й будь-якому з вище | обидва: скіли плагінів мають префікс `/plugin-name:` |

Приклад до третього рядка: проєктний скіл `code-review` замінить `/code-review`, а псевдонім
`/review` і далі запускатиме вбудований. Висновок: не називай свої скіли так само, як вбудовані
команди, якщо не хочеш їх свідомо замінити.

Порівняй із субагентами (урок 15): там проєктний `.claude/agents/` переважає особистий. У скілів —
навпаки.

### Команди — це тепер скіли

Раніше власні команди писали файлами в `.claude/commands/`. Документація: "A file at
.claude/commands/deploy.md and a skill at .claude/skills/deploy/SKILL.md both create /deploy and
work the same way." Старі файли працюють і далі, але для нового обирай скіл: він підтримує
додаткові файли в папці й поля `name` і `paths`, яких немає в `.claude/commands/`.

⏸ **Зупинись і перевір себе.** У `~/.claude/skills/` і в `.claude/skills/` проєкту є скіл
`bug-report` з різним текстом. Ти набираєш `/bug-report` у цьому проєкті. Який спрацює?

> **Відповідь.** Особистий з `~/.claude/skills/`: personal over project. Якщо команда проєкту
> повинна отримати свій варіант, перейменуй особистий скіл (наприклад, `my-bug-report`).

## 16.8. Скіл, `CLAUDE.md`, правило чи субагент?

| механізм | коли завантажується | для чого |
|---|---|---|
| `CLAUDE.md` (урок 14) | завжди, на старті | короткі факти й правила, потрібні в кожній задачі |
| правило з `paths` (урок 14) | коли Claude працює з відповідними файлами | правила для частини проєкту |
| скіл | опис — завжди, текст — коли потрібен | детальні знання чи процедура для одного виду задач |
| субагент (урок 15) | окремий працівник у власному контексті | виконати шматок роботи ізольовано й повернути звіт |
| хук (урок 17) | Claude Code запускає сам, щоразу | те, що мусить статися без винятків |

Скіл і субагент поєднуються: скіл може виконуватися в субагенті (поле `context: fork`), а субагенту
можна наперед підключити скіли. Для початку тримай їх окремо.

Питання, що допомагають вибрати:

1. Це потрібно в **кожній** задачі? → `CLAUDE.md`.
2. Це потрібно лише для певних файлів? → правило з `paths`.
3. Це процедура чи шаблон для певного **виду** задач? → скіл.
4. Це великий шматок роботи з купою виводу, і потрібен лише підсумок? → субагент.
5. Це мусить відбуватися **завжди**, без винятків? → хук або дозволи.

⏸ **Зупинись і перевір себе.** У `CLAUDE.md` є розділ на 60 рядків «Як готувати щотижневий звіт
про регресію: крок 1 … крок 14». Звіт ти робиш раз на тиждень. Що з цим зробити?

> **Відповідь.** Перенести в скіл, наприклад `weekly-regression-report`. Тоді ці 60 рядків не
> займатимуть контекст у кожній сесії, а завантажуватимуться лише тоді, коли ти просиш звіт або
> кличеш `/weekly-regression-report`.

## 16.9. Безпека скілів

- **Динамічні команди виконуються на твоєму комп'ютері.** Рядок `` !`…` `` у чужому скілі запускає
  команду ще до того, як Claude щось прочитав. Перш ніж додати скіл з інтернету чи з чужого
  репозиторію, прочитай його повністю.
- **`allowed-tools` дає дозволи без запиту** на час ходу, у якому запущено скіл. Документація
  попереджає: скіл у репозиторії може надати собі широкий доступ, тож переглядай `allowed-tools`
  у скілах проєкту, перш ніж працювати з чужим репозиторієм.
- **Жодних секретів у `SKILL.md`.** Скіл — звичайний текстовий файл, а проєктний ще й потрапляє в
  git (урок 11).

[Commands](https://code.claude.com/docs/en/commands).

## 16.10. У роботі QA

- **`/bug-report`.** Короткий опис бага → баг-репорт у форматі команди: кроки, фактичний і
  очікуваний результат, «уточнити» замість вигаданих деталей.
- **`/summarize-changes` перед комітом.** Ти змінив набір тест-кейсів — скіл коротко каже, що
  змінилось, і нагадує оновити пов'язані тести.
- **Чек-лист смоук-тесту.** Скіл `smoke-checklist` з 20 пунктами перевірки після релізу замість
  щотижневого копіювання чек-листа в чат.
- **Тестові дані.** Скіл `test-data` з правилами генерації (домени example.com, вигадані телефони,
  граничні значення) і прикладом CSV у додатковому файлі.
- **Реліз-ноти для QA.** Скіл з `` !`git log --oneline -20` ``: Claude отримує останні коміти й
  групує їх у «що перевірити в регресії».

## 16.11. Типові помилки

### Симптом → причина

| симптом | причина | що зробити |
|---|---|---|
| `Shell command failed for pattern ...` | команда в `` !`…` `` впала (поза git, немає коміту) | запускай у репозиторії з комітом; перевір команду в терміналі |
| скіла немає в `/skills` чи меню `/` | нова папка після старту сесії; файл не `SKILL.md` | `/reload-skills`; перевір назву файлу й папки |
| Claude не використовує скіл сам | опис не містить слів, якими ти просиш | переписати `description` конкретно, з типовими фразами |
| Claude запускає скіл, коли не треба | опис надто широкий | звузити `description` або `disable-model-invocation: true` |
| `/bug-report` у середині фрази не спрацював одразу | команду розпізнають лише на початку повідомлення | почни повідомлення з `/bug-report` |
| поля frontmatter «не діють» | помилка в назві поля або `---` не в першому рядку | точні назви з дефісами; `---` — перший рядок файлу |
| у проєкті спрацював не той скіл | однакова назва: особистий переважає проєктний | різні назви |
| вбудований `/code-review` «зламався» | твій скіл з такою самою назвою замінив його | перейменуй свій скіл |
| Claude «забув» скіл у довгій сесії | після стискання лишився лише початок скіла | запусти скіл знову; важливе — вгорі `SKILL.md` |
| у `/skills` випадково змінилась видимість скіла | натиснуто `Space` чи `Enter` на рядку | перемкни назад тим самим; `Esc` — закрити |

## 16.12. Що варто запам'ятати

1. Команди набирають через `/`, лише на початку повідомлення; текст після назви — аргументи.
2. Вбудовані команди виконують фіксовану логіку; вбудовані скіли (`/code-review`, `/debug`,
   `/doctor`) — інструкції для Claude.
3. Скіл = папка + `SKILL.md` (frontmatter з `description` + інструкції); назва папки = назва команди.
4. Claude бачить лише назву й опис скіла; текст завантажується, коли скіл використовують.
5. `` !`команда` `` підставляє вивід команди до того, як Claude прочитає скіл; невдала команда
   скасовує весь скіл.
6. `$ARGUMENTS` — текст після назви скіла.
7. `disable-model-invocation: true` — тільки ти запускаєш; `user-invocable: false` — тільки Claude.
8. Особисті `~/.claude/skills/`, проєктні `.claude/skills/`; особистий переважає проєктний.
9. `.claude/commands/x.md` і `.claude/skills/x/SKILL.md` дають ту саму команду `/x`.
10. `/skills` — перевірити, що скіл є; `/reload-skills` — підхопити нову папку без перезапуску.

# Розв'язки

**16.1.** Вбудована команда — фіксована логіка програми, модель не задіяна: `/clear` очищає
контекст. Вбудований скіл — інструкція для Claude, що йде з Claude Code: `/code-review` дає Claude
порядок перевірки змін на помилки. Власний скіл — твоя інструкція в `SKILL.md`: `/bug-report`
перетворює опис на баг-репорт. Вбудований і власний скіли працюють однаково — як промпт для Claude.

**16.2.** а) Команда `/compact` спрацює, а `keep the test cases` — її аргумент: на що звернути увагу
в підсумку. б) Нічого не стиснеться: команда не на початку, це просто текст для Claude. в) Команда
стане в чергу й виконається після того, як Claude закінчить поточний хід.

**16.3.** `/` показує весь перелік; `/mem` лишає команди з цими літерами, серед них `/memory`. У
`/help` — довідка й перелік; які команди будуть новими, залежить від тебе (наприклад, `/btw`,
`/diff`, `/status`).

**16.4.** `git log --oneline` має показати один рядок: короткий ідентифікатор коміту і `First
commit`. Якщо бачиш `does not have any commits yet` — коміту ще немає: `git add .` і `git commit -m
"First commit"`.

**16.5.** У `/skills` у списку є `summarize-changes` (особистий скіл). Після `t` скіли
відсортовані за кількістю токенів — так видно, які найбільше займають контекст. `Esc` закриває
список. Якщо скіла немає — перевір шлях `~/.claude/skills/summarize-changes/SKILL.md` і що файл не
`SKILL.md.txt`; якщо папку створено під час сесії — `/reload-skills`.

**16.6.** Обидві відповіді мають згадати зміну саме в `login-tests.md` (який тест-кейс, що
змінилось) і дати список ризиків. На «What did I change?» Claude сам обирає скіл за описом; на
`/summarize-changes` скіл запускається напряму. Після коміту незакомічених змін немає: `git diff
HEAD` порожній, і скіл, за своєю інструкцією, скаже, що змін немає.

**16.7.** З'явиться `Shell command failed for pattern ...` з виводом git про те, що це не
репозиторій. Динамічна команда виконується **до** того, як скіл потрапить до Claude; якщо вона
впала, весь запуск скасовується — Claude не отримує ні змін, ні інструкцій.

**16.8.** Після створення файлу — `/reload-skills` (або перезапуск), бо папки `.claude/skills/`,
ймовірно, на старті не було. Звіт: заголовок про неактивну кнопку Save на сторінці Profile, кроки
(відкрити Profile, змінити телефон, спробувати натиснути Save), фактичний результат «кнопка
неактивна», очікуваний «кнопка активна, зміни зберігаються», середовище Firefox. Версії браузера,
ОС чи акаунта в описі не було — там має стояти «уточнити», а не вигадані значення.

**16.9.** Без цього рядка Claude зможе запускати скіл сам, коли вирішить, що він доречний, а опис
скіла завжди лежатиме в контексті. Погано: ти обговорюєш з Claude, чи це взагалі баг, а він уже
пише формальний баг-репорт. Зручно: ти просиш «оформи це як баг» — і Claude сам підхоплює правильний
формат без `/bug-report`.

**16.10.** Зразок:
```
description: Turns requirements from a file into manual test cases in the team format (ID, preconditions, steps, expected result). Use when the user asks to write test cases from requirements, a spec or a user story.
```
Тут сказано, що робить скіл, у якому форматі, і якими словами користувач про це просить.

**16.11.** 1 — `CLAUDE.md`: короткий факт, потрібний щоразу. 2 — скіл: довга процедура для одного
виду задач. 3 — хук (урок 17): «без винятків» Claude не гарантує. 4 — субагент: багато виводу,
потрібен підсумок. 5 — правило з `paths: - "bugs/**/*.md"` (або `bugs/CLAUDE.md`).

**16.12.** Зразок `SKILL.md`:
```
---
description: Groups recent commits into what QA must check in regression and what can be skipped.
disable-model-invocation: true
---

## Recent commits

!`git log --oneline -20`

## Instructions

Group the commits above into two sections: "Що перевірити в регресії" and "Можна не перевіряти".
One line per item, at most 15 lines in total. Write in Ukrainian.
```
Щоб працював у всіх проєктах — особиста папка `~/.claude/skills/qa-release-notes/SKILL.md`. У
`qa-notes` комітів мало, тож звіт буде коротким; запускати треба в репозиторії, інакше `git log`
впаде і скіл не запуститься.

**16.13.** Скіл — це папка, тож поруч із `SKILL.md` можна покласти довідник, і Claude читатиме його
лише за потреби; файл у `.claude/commands/` такої папки не має. Нова структура:
```
.claude/skills/smoke/
├── SKILL.md         ← інструкції + посилання на довідник
└── reference.md     ← 300 рядків довідки
```
У `SKILL.md` вкажи, що лежить у `reference.md` і коли його читати. Якщо тимчасово лишити обидва з
назвою `smoke`, спрацює скіл: при однаковій назві скіл переважає файл з `.claude/commands/`.
Старий файл потім видали, щоб не плутати колег.
