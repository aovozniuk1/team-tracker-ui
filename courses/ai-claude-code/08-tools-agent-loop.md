# Урок 8. Інструменти й агентний цикл

*Модель Claude сама нічого не відкриває й не запускає: вона лише просить Claude Code виконати дію —
прочитати файл, змінити його, запустити команду. Ці дії називаються інструментами, а повторення
«подивитися → зробити → перевірити» — агентним циклом. Після уроку ти назвеш основні вбудовані
інструменти, впізнаєш їх у вікні Claude Code, розгорнеш подробиці будь-якого кроку й розкладеш
будь-яку роботу Claude на збір контексту, дію і перевірку.*

## Коротко

*Картка уроку: прочитай її перед уроком і повернись до неї після.*

**Одним реченням.** Інструмент — це дія, яку Claude Code виконує на прохання моделі, а агентний
цикл — це повторення «зібрати контекст → діяти → перевірити», доки мету не досягнуто.

**Навіщо.** Коли розумієш, яким інструментом Claude щось зробив, ти знаєш, що саме змінилося на
диску, що можна відкотити і де шукати помилку.

**Де.** У вікні Claude Code кожен виклик інструмента — окремий рядок (наприклад, `Read` або
`Bash: npm test`). У терміналі подробиці відкриває `Ctrl+O`; у застосунку для комп'ютера і у
VS Code рядок можна клацнути.

**Модель**

- **Інструмент (tool)** — одна дія, яку Claude Code вміє виконати: прочитати, змінити, знайти, запустити.
- **Виклик інструмента** — конкретне прохання моделі: «прочитай `notes.txt`», «запусти `npm test`».
- **Результат інструмента** — що повернулося (вміст файлу, вивід команди); він додається в контекст.
- **Агентний цикл** — зібрати контекст → діяти → перевірити → повторити, поки мету не досягнуто.
- **MCP** — спосіб додати інструменти ззовні: пошту, таблиці, браузер, базу даних.

**Запам'ятай**

1. Модель не торкається твого комп'ютера; вона просить, а Claude Code виконує після перевірки дозволів.
2. `Read`, `Glob`, `Grep` читають; `Write`, `Edit` змінюють файли; `Bash` / `PowerShell` запускають команди.
3. На macOS, Linux і WSL інструментів `Glob` і `Grep` за замовчуванням немає — Claude шукає через `Bash`.
4. `Ctrl+O` у терміналі показує, що саме зробив кожен інструмент і що повернулося.
5. Без кроку «перевірити» циклу нема чим ловити помилки — завжди давай Claude спосіб перевірити себе.

**Пастки** (симптом → причина)

- Шукаєш у вікні рядок `Grep`, а бачиш `Bash: grep …` → ти на macOS/Linux/WSL, там пошук іде через `Bash`.
- Клацаєш по рядку інструмента в терміналі — нічого → у терміналі подробиці відкриває `Ctrl+O`.
- Claude сказав «готово», а нічого не працює → у циклі не було перевірки, і ти її не попросив.

**Як перевірити**

- У тестовій папці ти просиш Claude створити файл, змінити в ньому слово й знайти рядок, а потім
  через `Ctrl+O` показуєш, яким інструментом зроблено кожен крок і що він повернув.

## 8.1. Що таке інструмент

З уроку 4 ти знаєш: **модель** — це «мозок», який читає весь контекст і пише продовження, а Claude
Code — **оболонка** навколо неї. Тепер важлива деталь: модель працює на серверах Anthropic і **не має
доступу до твого комп'ютера**. Вона не може сама відкрити файл чи натиснути `Enter` у терміналі.

Що вона може — це написати в своїй відповіді спеціальне прохання: «виконай інструмент `Read` для
файлу `notes.txt`». Далі:

1. Claude Code бачить це прохання — **виклик інструмента**.
2. Перевіряє **дозволи**: чи можна це зробити без тебе, чи треба спитати (урок 9).
3. Виконує дію на твоєму комп'ютері.
4. Кладе **результат** (вміст файлу, вивід команди, повідомлення про помилку) назад у контекст.
5. Знову надсилає моделі весь контекст — і вона вирішує наступний крок.

**Інструмент** (англ. *tool*) — це одна така дія, яку Claude Code вміє виконати на прохання моделі.

Аналогія. Уяви досвідченого колегу, який допомагає тобі **по відеозв'язку**, але не бачить твого
екрана. Він каже: «Відкрий файл з логами й прочитай мені останні рядки». Ти відкриваєш і читаєш
уголос. Він думає й каже: «Тепер заміни в налаштуваннях `false` на `true`». Ти міняєш. Колега —
це модель, ти з руками на клавіатурі — Claude Code, а кожне «відкрий», «прочитай», «заміни» —
виклик інструмента. І ти маєш право сказати «ні, це я робити не буду» — це і є дозволи.

Звідси два наслідки, які пояснюють половину курсу:

- **Модель знає лише те, що повернули інструменти.** Якщо Claude не відкривав файл, він не знає,
  що там написано, — навіть якщо впевнено про це говорить (галюцинації з уроку 1).
- **Кожен результат інструмента займає місце в контексті** (урок 6). Прочитаний великий файл чи
  довгий вивід команди — це токени, які надсилаються моделі на кожному наступному кроці.

⏸ **Зупинись і перевір себе.** Хто фізично змінює файл на твоєму диску, коли Claude «виправляє
помилку в коді», — модель чи Claude Code? І що відбувається між проханням і зміною?

> **Відповідь.** Файл змінює Claude Code — програма на твоєму комп'ютері. Модель лише надсилає
> виклик інструмента (наприклад, `Edit` з тим, що на що замінити). Між проханням і зміною Claude
> Code перевіряє дозволи: залежно від режиму він або виконує дію сам, або спершу питає тебе.

## 8.2. Вбудовані інструменти

Claude Code має набір **вбудованих** інструментів — тих, що працюють одразу після встановлення.
Документація пояснює: "The built-in tools generally fall into five categories, each representing a
different kind of agency." Тобто вбудовані інструменти загалом поділяються на п'ять категорій, і
кожна відповідає своєму виду дій:

| категорія | що робить | інструменти |
|---|---|---|
| **File operations** — робота з файлами | читає, створює, змінює файли | `Read`, `Write`, `Edit` |
| **Search** — пошук | шукає файли за назвою і текст усередині файлів | `Glob`, `Grep` |
| **Execution** — виконання | запускає команди терміналу | `Bash`, `PowerShell` |
| **Web** — інтернет | шукає в інтернеті й читає сторінки | `WebSearch`, `WebFetch` |
| **Code intelligence** — розуміння коду | переходить до визначень, шукає використання | працює через окремі плагіни |

Окремо стоїть інструмент `Agent`: ним Claude запускає **субагента** — помічника з власним
контекстом (детально в уроці 15).

### Таблиця, яку варто знати напам'ять

Колонка «Дозвіл» показує, чи питає Claude Code тебе в режимі **Manual** — у режимі, де він
перепитує про все, крім читання (режими — в уроці 9). Приклади в останній колонці — ілюстрації.

| інструмент | що робить | дозвіл у Manual | приклад використання |
|---|---|---|---|
| `Read` | відкриває файл і повертає його вміст із номерами рядків | ні, в межах робочої папки | читає `package.json`, щоб зрозуміти, як запускається проєкт |
| `Glob` | знаходить файли за шаблоном назви (`**/*.csv`) | ні | знаходить усі файли з тест-кейсами |
| `Grep` | шукає текст усередині файлів | ні | знаходить усі місця, де написано `sendEmail(` |
| `Write` | створює новий файл або **повністю** перезаписує наявний | так | створює `bug-report.md` |
| `Edit` | точкова заміна: шматок тексту → інший шматок | так | замінює `==` на `===` у рядку 42 файлу `cart.js` |
| `Bash` | запускає команду в терміналі | так, крім вбудованого набору команд тільки для читання | `npm test`, `git status` |
| `PowerShell` | запускає команду PowerShell (Windows) | так | `Get-ChildItem` |
| `WebFetch` | читає вебсторінку за адресою | так, крім попередньо дозволених сайтів документації | читає документацію бібліотеки |
| `WebSearch` | шукає в інтернеті | так | шукає останню версію пакета |
| `Agent` | запускає субагента | **ні** | відправляє помічника шукати у великому проєкті |

Кілька деталей, які допоможуть читати роботу Claude:

- **`Read` читає не лише текст.** Картинки (PNG, JPEG, GIF, WebP) він повертає як зображення, яке
  Claude «бачить», і вміє читати PDF. А от файли, які вважає двійковими, наприклад `.xlsx` чи `.zip`,
  `Read` не відкриває — тоді Claude шукає інший спосіб: команду чи скрипт, що читає такий формат.
- **`Read`, `Glob` і `Grep` питають дозволу, якщо шлях поза робочою папкою.** «Без запиту» — це
  тільки про файли твого проєкту (урок 2, розділ про робочу папку).
- **`Write` перезаписує файл цілком**, а **`Edit` міняє лише шматок**. Тому для невеликої правки в
  наявному файлі Claude зазвичай бере `Edit`. `Edit` шукає точний збіг тексту: якщо шматок
  трапляється у файлі кілька разів, Claude бере довший фрагмент, щоб влучити в потрібне місце.
- **`WebFetch` повертає не саму сторінку, а витяг з неї.** Сторінку обробляє окремий виклик моделі,
  і Claude отримує результат цієї обробки. Якщо Claude каже «на сторінці про це нічого немає», це
  може означати лише те, що прохання до витягу було не про це.
- **`WebSearch` повертає лише заголовки й адреси**, а щоб прочитати сторінку, Claude далі викликає
  `WebFetch`.
- **`Agent` не питає дозволу на запуск**, але кожна дія самого субагента перевіряється за тими
  самими правилами дозволів, що й дії основного Claude.

Є й інші вбудовані інструменти: наприклад, `AskUserQuestion` ставить тобі запитання з варіантами
відповіді, а `EnterPlanMode` / `ExitPlanMode` вмикають і завершують режим плану (урок 9). Повний
перелік — у документації.

### Різниця між Windows і macOS/Linux

Це місце, де новачки часто плутаються, тож розберемо окремо.

| система | пошук файлів і тексту | запуск команд |
|---|---|---|
| **Windows** | інструменти `Glob` і `Grep` | `PowerShell` (якщо стоїть Git for Windows — ще й `Bash`) |
| **macOS, Linux, WSL** | `Glob` і `Grep` **за замовчуванням немає**; Claude шукає командами `find` і `grep` через `Bash` | `Bash` |

Тобто на Mac той самий пошук виглядатиме як рядок `Bash` з командою `grep` або `find`. Це не
помилка й не «гірший» пошук — просто інший інструмент для тієї самої дії.

### Як дізнатися свій набір

Точний набір інструментів залежить від системи, налаштувань і підключень. Найпростіше — спитати
самого Claude. Документація пропонує саме таке прохання:

```
What tools do you have access to?
```

Claude відповість звичайним текстом, переліком. Можна питати й українською: «Які інструменти тобі
доступні?»

⏸ **Зупинись і перевір себе.** Колега на MacBook каже: «У мене Claude не вміє шукати по файлах —
у списку немає `Grep`». Що ти йому відповіси?

> **Відповідь.** Вміє: на macOS, Linux і WSL інструментів `Glob` і `Grep` за замовчуванням немає,
> і Claude шукає командами `find` і `grep` через інструмент `Bash`. У вікні це видно як рядок
> `Bash` із командою `grep …` або `find …`.

## 8.3. Як виглядає виклик в інтерфейсі

Поки Claude працює, у вікні з'являються рядки — по одному на кожен виклик інструмента. Кожен рядок
каже, **який інструмент** і **з чим** (файл, команда, адреса). Під ним — коротко, що повернулося.
Схематично хід роботи може виглядати так (це схема, а не точна копія екрана — вигляд рядків
залежить від версії):

```
Read  notes.txt
Edit  notes.txt
Bash: npm test
```

Як побачити подробиці:

| де працюєш | як розгорнути подробиці кроку |
|---|---|
| **термінал** | натисни `Ctrl+O` — відкриється перегляд розмови, який показує детальне використання інструментів і їхнє виконання; ще раз `Ctrl+O` — назад |
| **застосунок для комп'ютера** (Claude Desktop) | клацни рядок інструмента |
| **VS Code** | клацни рядок інструмента |

У терміналі мишкою по рядку не клацнеш — це звичайне текстове вікно. Тому `Ctrl+O` — твій головний
спосіб подивитися, що саме прочитав файл, яку команду запустив Claude і що вона вивела.

Навіщо дивитися подробиці, якщо Claude у фінальній відповіді все одно розповість, що зробив?
Бо **підсумок пише модель**, а результат інструмента — це те, що **реально сталося**. Якщо Claude
каже «тести пройшли», а у виводі команди видно `2 failed`, правда — у виводі.

⏸ **Зупинись і перевір себе.** Ти працюєш у PowerShell, Claude показав рядок із командою, і ти
хочеш побачити її повний вивід. Що натиснути?

> **Відповідь.** `Ctrl+O` — він відкриває перегляд розмови з подробицями кожного кроку. Клацання по
> рядку працює лише в застосунку для комп'ютера і у VS Code.

## 8.4. Агентний цикл

**Агентний** означає, що Claude сам вирішує свій наступний крок, а не відповідає один раз. Документація
описує це так: "When you give Claude a task, it works through three phases: gather context, take
action, and verify results. These phases blend together." — коли ти даєш завдання, Claude проходить
три фази: збирає контекст, діє і перевіряє результат; фази переплітаються.

На практиці кожен крок — один із таких:

1. **Зібрати контекст** — прочитати файли, пошукати, запустити команду, щоб роздивитися.
2. **Діяти** — змінити файл або запустити команду.
3. **Перевірити результат** — запустити тести, зібрати проєкт, прочитати вивід.
4. **Повторити**, доки мету не досягнуто, — і тоді відповісти тобі.

```
     ┌──────────────────────────────────────────┐
     ▼                                          │
 зібрати контекст ──► діяти ──► перевірити ─────┘
                                     │
                                     ▼ мету досягнуто
                               відповідь тобі
```

Згадай слово **хід** (*turn*) з уроку 4: один хід — від твого повідомлення до відповіді Claude.
Агентний цикл крутиться **всередині одного ходу**: Claude може зробити десять кроків, а ти
отримаєш одну відповідь у кінці. Хід закінчується, коли модель відповідає тобі текстом і більше не
просить жодного інструмента.

Аналогія для тестувальника: це той самий цикл, яким ти проходиш тест-кейс. Перевіряєш передумови
(контекст), виконуєш крок (дія), порівнюєш фактичний результат з очікуваним (перевірка). Якщо не
збіглося — розбираєшся, чому, і робиш наступну спробу.

⏸ **Зупинись і перевір себе.** Ти написав «чому падає `npm test`?». Claude запустив тести, відкрив
файл з помилки, виправив рядок, запустив тести ще раз і відповів. Скільки це ходів і скільки
викликів інструментів?

> **Відповідь.** Один хід (одне твоє повідомлення — одна відповідь) і чотири виклики інструментів:
> запуск тестів, читання файлу, зміна файлу, повторний запуск тестів.

## 8.5. Цикл покроково: приклад із темною темою

Розберемо один хід повністю. **Приклад ілюстративний** — твій проєкт і кроки будуть іншими, але
логіка та сама. Промпт:

```
Add a dark-mode toggle to the settings page.
```

(«Додай перемикач темної теми на сторінку налаштувань».)

| крок | що Claude думає | дія (інструмент) | що бачить у результаті |
|---|---|---|---|
| 1 | Де сторінка налаштувань? | `Glob` `**/Settings*` | знайдено `src/pages/Settings.tsx` |
| 2 | Як тут зроблено стилі? | `Read` `Settings.tsx`, `Grep` `theme` | проєкт використовує CSS-змінні в `theme.css` |
| 3 | Додати темні кольори | `Edit` `theme.css` | темні змінні додано |
| 4 | Додати перемикач | `Edit` `Settings.tsx` | перемикач додано |
| 5 | Чи збирається проєкт? | `Bash` `npm run build` | помилка: unused import (непотрібний імпорт) |
| 6 | Виправити | `Edit` `Settings.tsx` | імпорт прибрано |
| 7 | Перевірити ще раз | `Bash` `npm run build` | збірка пройшла → відповідь тобі |

Розклади кроки за фазами:

- **Збір контексту** — кроки 1–2: Claude не знав, де сторінка й як влаштовані стилі, тож спершу

## 8.6. Перевірка — серце циклу

З прикладу видно головне правило: **якість роботи агента обмежена тим, чим він може себе
перевірити.** Модель може помилятися (урок 1), але помилка, яку повернув інструмент, — це факт, і
на нього вона реагує добре.

Що можна дати Claude як перевірку:

| що перевіряємо | що дати Claude |
|---|---|
| код | команду тестів чи збирання: «запусти `npm test` і доведи, що все зелене» |
| вебсторінку | що саме має відкриватися і працювати: «відкрий `index.html` і перевір, що порожнє завдання не додається» |
| таблицю чи CSV | контрольну цифру: «сума в колонці `price` має бути 1250» |
| текст | критерій: «не довше 200 слів, усі пункти з оригіналу на місці» |
| результат будь-якої дії | доказ: «покажи команду, яку ти запустив, і її вивід» |

Порівняй два промпти:

| слабкий | сильний |
|---|---|
| Виправ помилку в `report.py`. | У `report.py` падає підрахунок суми. Виправ і запусти `python report.py sample.csv`: має вийти `Total: 1250`. Покажи вивід. |
| Перевір, чи все гаразд із файлом. | Перевір, що в `users.csv` у кожному рядку 4 колонки і жодна адреса не повторюється. Напиши, якою командою перевіряв. |

Сильний промпт дає циклу точку перевірки й просить **доказ** — вивід команди. Доказ ти можеш
подивитися через `Ctrl+O` і не вірити підсумку на слово.

⏸ **Зупинись і перевір себе.** Перепиши промпт «зроби мені гарний README» так, щоб у Claude була
перевірка.

> **Відповідь.** Наприклад: «Напиши `README.md` для цієї папки: що в ній лежить, як відкрити
> сторінку, як запустити тести. Не довше 40 рядків. Після цього перечитай файл і перевір, що кожна
> згадана папка й команда справді існує; список перевірених назв додай у відповідь». Перевірка тут —
> обмеження обсягу й звірка згадок із реальними файлами.

## 8.7. Інструменти ззовні: MCP

Вбудовані інструменти працюють із файлами, терміналом і вебом. Але можна додати й інші — через
**MCP-сервери** та **плагіни** (детально в уроці 17). **MCP** (*Model Context Protocol*) — відкритий
стандарт, яким сторонні програми пропонують моделі свої інструменти: наприклад, читати документи з
хмарного диска, робити запит до бази даних або керувати браузером.

Для циклу вони нічим не відрізняються від вбудованих: Claude викликає інструмент, Claude Code
перевіряє дозволи, результат додається в контекст.

Дві речі варто знати вже зараз:

- **Підключені MCP-сервери майже не займають контекст, поки їх не використали.** Описи їхніх
  інструментів завантажуються на вимогу: до першого використання місце займають лише назви
  інструментів та інструкції сервера.
- **Що підключено — показує команда `/mcp`.** А загальний перелік інструментів — знайоме
  прохання `What tools do you have access to?`.

І одне застереження наперед: інструменти, які приносять у контекст вміст ззовні (вебсторінки,
листи, документи), можуть принести й чужі «інструкції», заховані в тексті. Про цей ризик — prompt
injection — буде урок 11.

⏸ **Зупинись і перевір себе.** Ти підключив MCP-сервер для таблиць. Чим виклик його інструмента
відрізняється від виклику `Read` з погляду агентного циклу?

> **Відповідь.** Нічим принципово: модель просить виклик, Claude Code перевіряє дозволи й виконує,
> результат потрапляє в контекст, і модель вирішує наступний крок. Відрізняється лише те, що саме
> робить інструмент і звідки він узявся.

## 8.8. Подивись цикл наживо

Цей розділ — коротка лабораторна робота. Вона дешева: кілька маленьких промптів у порожній папці.
Усе, що Claude тут створить, можна видалити разом із папкою.

**Крок 1. Підготуй папку.** У терміналі (урок 2):

```
> cd ~/Documents/ai-course
> mkdir tools-lab
> cd tools-lab
```

Якщо папки `ai-course` ще немає, спершу створи її в «Документах» (`mkdir ai-course`).

**Крок 2. Запусти Claude Code так, щоб він питав про кожну дію:**

```
> claude --permission-mode manual
```

`--permission-mode manual` вмикає режим, у якому Claude Code перед кожною зміною файлу й кожною
командою, крім читання, питає тебе. Так ти побачиш кожен виклик інструмента до того, як він
спрацює. Детально про режими — в уроці 9. Якщо Claude Code вперше запускається в цій папці, він
спитає, чи довіряєш ти їй (урок 3) — погодься.

**Крок 3. Створи файл.** Напиши:

```
Створи файл bugs.txt з трьома рядками: "BUG-1 login button misaligned",
"BUG-2 typo on checkout page", "BUG-3 search returns no results".
```

З'явиться запит дозволу на створення файлу. Прочитай, що саме Claude хоче записати, і вибери
**Yes** (перший варіант). У вікні з'явиться рядок інструмента `Write`.

**Крок 4. Зміни одне слово:**

```
У bugs.txt заміни "typo" на "spelling error".
```

Знову запит — погодься. Цього разу інструмент — `Edit`: він міняє лише шматок, а не переписує файл.

**Крок 5. Пошукай:**

```
У якому рядку bugs.txt згадується checkout? Відповідай номером рядка.
```

На Windows ти, найімовірніше, побачиш `Read` або `Grep`; на macOS/Linux — `Read` або `Bash` з
`grep`. Запиту дозволу, найпевніше, не буде: читання в межах робочої папки не потребує дозволу.

**Крок 6. Розгорни подробиці.** Натисни `Ctrl+O` і знайди всі три кроки: що записав `Write`, яку
заміну зробив `Edit`, що повернув пошук. Ще раз `Ctrl+O` — назад.

**Крок 7. Перевір сам.** Вийди з Claude Code (`exit`) і подивись файл у терміналі:

```
> cat bugs.txt
```

(`cat` працює і в PowerShell, і на macOS/Linux — він виводить вміст файлу.) Має бути три рядки, і в
другому — `spelling error`.

⏸ **Зупинись і перевір себе.** У кроці 3 Claude використав `Write`, а в кроці 4 — `Edit`. Чому
саме так?

> **Відповідь.** У кроці 3 файлу ще не було — `Write` створює новий файл. У кроці 4 файл уже був і
> треба було змінити одне слово — `Edit` робить точкову заміну, не переписуючи решту файлу.

## 8.9. У роботі QA

- **Логи.** «У папці `logs` знайди всі рядки з `ERROR` за сьогодні й згрупуй за текстом помилки» —
  Claude шукає (`Grep` чи `Bash`), читає потрібні шматки (`Read`) і відповідає. Через `Ctrl+O` ти
  бачиш, які саме файли він переглянув, і можеш вставити цю інформацію в баг-репорт.
- **Тест-кейси.** «Знайди всі тест-кейси, де згадується вхід у систему» — це пошук по тексту
  (`Grep`). Якщо їх 50, а Claude назвав 12, подивись подробиці пошуку: можливо, він шукав лише
  слово `login`, а в частині кейсів написано `sign in`.
- **Скриншоти.** `Read` повертає картинку як зображення, тож Claude може описати, що на скриншоті
  бага, і допомогти сформулювати фактичний результат. Великі зображення він бачить зменшеними —
  дрібні деталі краще показати окремим фрагментом.
- **Таблиці з тестовими даними.** `.xlsx` інструмент `Read` не відкриває — Claude піде іншим шляхом
  (команда, скрипт). Не дивуйся рядку `Bash` чи `PowerShell` там, де ти чекав `Read`; для простих
  даних зручніше зберегти таблицю як `.csv`.
- **Доказ замість слова.** Коли Claude каже «перевірив, працює», попроси: «покажи команду й її
  вивід». Це те саме правило, що й у твоїх баг-репортах: фактичний результат, а не враження.

## 8.10. Типові помилки

### Симптом → причина

| симптом | причина | що зробити |
|---|---|---|
| Claude описує вміст файлу, якого не відкривав | модель відповідає з припущень, а не з результату інструмента | попроси спершу прочитати файл; дивись, чи був рядок `Read` |
| «Немає `Grep`» на Mac чи Linux | на macOS, Linux і WSL `Glob`/`Grep` за замовчуванням немає | шукай рядок `Bash` з `grep` або `find` |
| клацання по рядку інструмента в терміналі нічого не дає | у терміналі немає клацання по рядках | `Ctrl+O` |
| Claude каже «готово», а проєкт не працює | у циклі не було кроку перевірки | дай команду перевірки або критерій і попроси показати вивід |
| `WebFetch` «не знайшов» на сторінці те, що там точно є | Claude отримав витяг зі сторінки, а не саму сторінку | попроси прочитати ще раз із конкретнішим проханням |
| файл несподівано переписано повністю | використано `Write`, який перезаписує файл цілком | проси точкову правку; перевіряй результат (урок 10 — як відкотити) |
| `Read` не відкрив `.xlsx` | `Read` не читає двійкові формати | дозволь Claude прочитати іншим способом або збережи як `.csv` |

## 8.11. Що варто запам'ятати

1. Модель не має доступу до комп'ютера — вона просить інструмент, Claude Code виконує після
   перевірки дозволів, результат іде в контекст.
2. П'ять категорій: файли (`Read`, `Write`, `Edit`), пошук (`Glob`, `Grep`), виконання (`Bash`,
   `PowerShell`), веб (`WebSearch`, `WebFetch`), розуміння коду (через плагіни); плюс `Agent`.
3. У Manual без дозволу працюють читання в робочій папці і `Agent`; зміни файлів, команди й веб —
   із запитом (крім команд тільки для читання і сайтів документації).
4. На macOS, Linux і WSL `Glob` і `Grep` за замовчуванням відсутні — пошук іде через `Bash`.
5. `Write` створює чи перезаписує файл цілком, `Edit` міняє шматок.
6. Подробиці кроку: `Ctrl+O` у терміналі; клацання — у застосунку для комп'ютера і VS Code.
7. Агентний цикл: зібрати контекст → діяти → перевірити → повторити; весь цикл — усередині одного ходу.
8. Без перевірки цикл не ловить помилок — давай команду, тест або критерій і проси доказ.
9. MCP додає інструменти ззовні; вони працюють у тому ж циклі; `/mcp` показує підключене.

# Розв'язки

**8.1.** Зразок: «Інструмент — це одна дія, яку Claude Code уміє виконати на прохання моделі:
прочитати файл, змінити його, знайти текст, запустити команду, прочитати сторінку. Модель працює на
серверах і бачить лише текст контексту, який їй надіслали; доступу до мого диска й терміналу в неї
немає. Тому вона пише виклик інструмента, а Claude Code на моєму комп'ютері перевіряє дозволи,
виконує дію і повертає результат у контекст. Наступний крок модель робить уже з урахуванням цього
результату».

**8.2.** Файли: `Read`, `Write`, `Edit`. Пошук: `Glob`, `Grep`. Виконання: `Bash`, `PowerShell`.
Веб: `WebSearch`, `WebFetch`. Розуміння коду: з цього списку — жоден (працює через окремі плагіни).
Не входить у п'ять категорій `Agent` — він запускає субагента.

**8.3.** Windows: `Grep` (знайти «пароль»/«password» у `test-cases`) або `Glob` для переліку файлів →
`Read` знайденого файлу → `Edit` (замінити `pasword` на `password`) → можливо, ще `Read` або `Grep`,
щоб перевірити, що помилки більше немає. На macOS замість `Glob`/`Grep` буде `Bash` з `grep` чи
`find`, решта — так само. Точний порядок може відрізнятися: це прогноз, а не правило.

**8.4.** а) Ні — читання в робочій папці. б) Так — `Read` питає для шляхів поза робочою папкою.
в) Так — створення файлу (`Write`). г) Ні — `Agent` не потребує дозволу на запуск. д) Так —
`WebSearch`. е) Ні — `ls` входить до вбудованого набору команд тільки для читання для `Bash`. (На
Windows, якщо команда піде через `PowerShell`, перевір на практиці: запит дозволу — це нормально.)

**8.5.** Очікувано: крок 3 — `Write` із запитом дозволу; крок 4 — `Edit` із запитом дозволу;
крок 5 — `Read` або пошук (`Grep` на Windows, `Bash` з `grep` на macOS/Linux) без запиту; відповідь
«рядок 2». У `Ctrl+O` видно вміст, який записав `Write`, заміну `typo` → `spelling error` в `Edit` і
результат пошуку. `cat bugs.txt` показує три рядки, другий —
`BUG-2 spelling error on checkout page`. Якщо в кроці 5 таки був запит — це нормально; головне —
ти його прочитав і зрозумів, що за дія.

**8.6.** Відповідь Claude — перелік інструментів звичайним текстом. Найчастіше там будуть `Read`,
`Write`, `Edit`, `Bash` та/або `PowerShell`, `WebFetch`, `WebSearch`, `Agent` і ще кілька службових
(наприклад, `AskUserQuestion`). На Windows у переліку є `Glob` і `Grep`; на macOS/Linux/WSL їх за
замовчуванням немає. Набір залежить від системи, версії й підключених MCP-серверів — тому твій
список може відрізнятися від списку однокурсника, і це нормально.

**8.7.** Створення трьох файлів — три виклики `Write` (з запитами дозволу в Manual). Пошук: на
Windows — `Grep` (або `PowerShell` із `Select-String`), на macOS/Linux — `Bash` з `grep`. Відповідь
має назвати рівно два файли з `ERROR` і процитувати рядки. Перевір себе в терміналі: на macOS/Linux
`grep ERROR *.log`, у PowerShell `Select-String ERROR *.log` — результат має збігтися з відповіддю
Claude.

**8.8.** 1 — збір контексту; 2 — збір контексту; 3 — дія; 4 — перевірка; 5 — дія (виправлення
того, що знайшла перевірка); 6 — перевірка; 7 — відповідь, кінець ходу. Видно класичну картину:
перша перевірка щось знайшла, і цикл пішов на друге коло.

**8.9.** Наприклад: «Додай у `index.html` форму зворотного зв'язку: поля "Ім'я", "Email",
"Повідомлення" і кнопка "Надіслати". Порожню форму надіслати не можна — під полем з'являється
повідомлення. Нічого не встановлюй, лише HTML, CSS і JavaScript. Після змін перечитай файл і
перелічи, як перевірити кожну вимогу в браузері; скажи, яку з них ти перевірив сам і як». Тут є
конкретні вимоги (критерії), обмеження і запит на перевірку з поясненням.

**8.10.** Запуск субагента — це ще не дія над твоїми файлами: субагент лише отримує завдання.
Документація каже, що запуск не викликає запиту дозволу, а кожен виклик інструмента самого
субагента перевіряється за твоїми правилами дозволів. Тобто якщо субагент захоче змінити файл чи
запустити команду, діють ті самі правила, що й для основного Claude.

**8.11.** `WebFetch` повертає Claude не саму сторінку, а витяг, зроблений окремим викликом моделі за
певним проханням. Якщо прохання було про інше, потрібне місце в витяг могло не потрапити. Що
робити: попросити прочитати сторінку ще раз із конкретним запитанням («Знайди на сторінці розділ
про обмеження для нових клієнтів і процитуй його дослівно») і звірити з тим, що бачиш у браузері.

**8.12.** Типовий хід: `Write` `prices.csv` (дія) → команда підрахунку через `Bash` чи `PowerShell`
(перевірка) → можливо, `Read` `prices.csv` для ручної звірки (збір контексту / перевірка) →
відповідь із командою, виводом і порівнянням. Викликів зазвичай 2–4. Сума з команди має збігтися із
сумою, яку ти сам порахуєш по рядках файлу. Якщо Claude не показав команду й вивід — попроси; без
доказу цю частину вважай неперевіреною.

**8.13.** Зразок для задачі «у всіх тест-кейсах заповнене поле Expected result»: збір контексту —
знайти всі файли тест-кейсів (`Glob` чи `find`), прочитати один-два, щоб зрозуміти формат; дія —
пройти всі файли й зібрати ті, де поле порожнє; перевірка — порахувати загальну кількість кейсів і
кількість знайдених, вибірково відкрити 2–3 «порожні» кейси й підтвердити. Промпт: «…Виведи
таблицю: файл, назва кейсу, проблема. Наприкінці напиши, скільки кейсів переглянуто всього, і
покажи, якою командою чи пошуком ти це рахував».
