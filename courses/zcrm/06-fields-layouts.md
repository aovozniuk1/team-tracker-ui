# Урок 6. Поля й макети сторінок (layouts)

*Після цього уроку ти знаєш, що дають стандартні модулі й що в них можна змінювати, обираєш тип
кастомного поля під вимогу, будуєш окремий layout і робиш поля обов'язковими, унікальними та
прихованими для профілю. Для QA це щоденна робота: кожна властивість поля — окремий вимір
тестування, а layout визначає, що людина бачить і що мусить заповнити.*

---

## 6.1. Стандартні модулі й базова кастомізація

Дані в Zoho CRM розкладені по **модулях**: кожен модуль — окремий тип сутності (ліди, угоди,
продукти), у модулі — **записи**, у записі — значення **полів**, а показує поля **layout** (макет
сторінки).

Стандартні модулі за довідкою Zoho: **Leads**, **Accounts**, **Contacts**, **Deals**,
**Campaigns**, **Forecasts**, **Cases**, **Solutions**, **Products**, **Price Books**, **Quotes**,
**Invoices**, **Vendors**, **Purchase Orders**, **Sales Orders**, **Tasks**, **Calls**,
**Meetings**, а також **Reports**, **Dashboards**, **Documents**. У тріалі модуль угод показується
як **Deals** (`Potentials` — стара назва в API й адресах).

Кожен стандартний модуль приходить зі своїми полями і стандартним layout. Що з ними можна робити:

- **прибирати** непотрібні поля з layout — приклад з довідки: поле `X (Twitter)` у лідах, якщо ніхто
  ним не користується;
- **додавати** кастомні поля;
- змінювати значення списків, обов'язковість, дозволи, порядок і секції;
- **не можна** видалити стандартний модуль;
- **не можна** прибрати, перейменувати чи зняти обов'язковість з частини полів, які Zoho вважає
  системно обов'язковими: довідка наводить **Last Name** у лідах і **Subject** у задачах. У списку
  стандартних полів довідка позначає обов'язковими ще, зокрема, **Company** у лідах, **Deal Name**,
  **Closing Date** і **Stage** в угодах, **Product Name** у продуктах.

Якщо стандартних модулів замало, створюють **кастомні модулі**: **Setup → Customization → Modules
and Fields** → **Create New Module** → **Organization Modules** (або **Team Modules** — модулі, якими
керує сама команда). Кількість кастомних модулів обмежена редакцією: за довідкою — 10 у Standard,
25 у Professional, 200 в Enterprise, 500 в Ultimate (кастомні й командні разом).

Усі налаштування полів і layouts живуть в одному місці: **Setup → Customization → Modules and
Fields** → модуль. Швидкий шлях з бічної панелі: наведи курсор на модуль → **⋯** → **+ Fields**.
Відкривається редактор layout (у довідці — layout editor або module builder):

- ліворуч лоток **New Fields** — типи полів, які перетягують у секції праворуч, і елемент нової
  секції;
- праворуч — секції з полями; у кожного поля є значок налаштувань (**Settings**) з діями
  **Mark as required**, **Edit Properties**, **Set Permission** тощо, а прибрати поле з layout можна
  через його меню (у довідці — пункт **Remove Field**);
- розділ **Unused Fields** — поля, прибрані з цього layout;
- лічильник **Custom Fields Left** — скільки кастомних полів ще дозволяє редакція;
- **Preview** — подивитися layout очима певного профілю;
- **Save Layout** — зберегти.

## 6.2. Поля і типи полів

Поле — одна властивість запису: сума угоди, дата закриття, email. **Тип поля** визначає, що в ньому
можна зберегти, як CRM перевіряє введене, які умови доступні у фільтрах і правилах. Тип обирають
один раз: **після створення тип поля змінити не можна** (перейменувати можна). Помилився з типом —
створюєш нове поле і переносиш дані.

Основні типи за довідкою Zoho:

| тип (як у довідці) | для чого | обмеження з довідки |
|---|---|---|
| Single Line (Text) | короткий текст, код, номер договору | до 255 символів |
| Multi-line: Plain Text Small | опис, коментар | до 2000 символів; може бути обов'язковим; підтримує шифрування |
| Multi-line: Plain Text Large | довгий опис | до 32000 символів; не працює у фільтрах і критеріях |
| Multi-line: Rich Text | форматований текст | до 50000 символів з HTML-тегами; не може бути обов'язковим |
| Integer | ціле число | до 9 цифр |
| Long Integer | довге ціле | до 18 цифр |
| Decimal | дробове число | до 16 цифр разом з дробовою частиною |
| Currency | гроші | до 16 цифр; знаки після коми й округлення задаються |
| Percent | відсоток | — |
| Date, Date/Time | дата, дата й час | показуються у форматі користувача |
| Email, Phone, URL | контактні дані, посилання | — |
| Pick List | одне значення зі списку | значення задаються в полі |
| Multi-select Pick List | кілька значень зі списку | — |
| Checkbox | так / ні | — |
| Auto Number | автоматичний номер | префікс, стартове число, суфікс |
| Lookup | посилання на запис іншого модуля | створює related list на іншому боці |
| Multi-select Lookup | посилання на кілька записів | — |

Є й спеціальні типи: **User** (вибір користувача CRM), **File Upload**, **Image Upload**,
**Formula** (обчислюване поле), **Rollup Summary** (підсумок по пов'язаних записах). Для цього уроку
вони не потрібні, але знай, що вони існують і мають власні обмеження.

У самому продукті частина типів називається інакше, ніж у довідці, — шукай їх у лотку **New Fields**
під такими назвами: Integer — **Number**, Multi-line — **Multi-Line**, Multi-select Pick List —
**Multi-Select**, Auto Number — **Auto-Number**. **Single Line**, **Long Integer**, **Currency**,
**Pick List** називаються так само.

Що ще варто знати про поля:

- **Довжину** можна змінювати пізніше для Currency, Text, Integer, Decimal, Phone, Long Integer, URL.
- **Прибрати поле з layout** — не видалити. Прибране поле переходить у **Unused Fields** цього
  layout; повернеш його перетягуванням — повернуться й дані. Видалити поле назавжди можна лише з
  **Unused Fields**, і тоді дані зникають безповоротно. Поля в **Unused Fields** все одно
  рахуються в ліміт.
- **Also create for.** Створюючи поле в лідах, CRM пропонує одразу створити таке саме в
  **Accounts**, **Contacts**, **Deals** — зручно, коли значення має пройти через конвертацію ліда.
- **Властивості поля** — окремі осі тестування: обов'язковість, унікальність, дозволи на
  профілі, підказка (tooltip), шифрування (для Plain Text Small), залежні списки (**Map Dependency
  Fields**: значення дочірнього списку залежать від батьківського).
- **Ліміти.** Кастомних полів не буває в безкоштовній редакції, а загальна кількість і кількість
  полів кожного типу залежать від редакції.

## 6.3. Layout: форма над полями

Layout (page layout) — це «форма» над полями модуля: які поля показати, у яких секціях, у якому
порядку, в одну чи дві колонки, що обов'язкове, які значення списків доступні. За замовчуванням у
модуля один layout — **Standard**.

Навіщо кілька layouts в одному модулі? Приклад з довідки: компанія продає телефони і ремонтує їх.
Продаж і ремонт — різні процеси з різними полями і стадіями, але це все угоди. Замість двох модулів
роблять два layouts модуля **Deals**: `Mobile Sales` і `Mobile Service`.

Що вирішує layout, а що — модуль:

| властивість | де живе | що це означає для тестів |
|---|---|---|
| склад полів, секції, порядок, колонки | layout | перевіряй кожен layout окремо |
| обов'язковість (**Mark as required**) | layout | поле може бути обов'язковим в одному layout і необов'язковим в іншому |
| значення Pick List | layout | у різних layouts список може бути різним |
| інші властивості поля (**Edit Properties**) | модуль | продукт попереджає: `All changes made here except marking the fields as 'Required' will reflect in all layouts.` Одна з FAQ довідки стверджує протилежне — перевір, що каже вікно властивостей у тріалі |
| форма **Quick Create** і **Detail View** | layout | окремі поверхні для тестів |
| дозволи на поле (**Set Permission**) | модуль | діють у всіх layouts (довідка: field permissions are not layout-specific) |
| унікальність | поле модуля | у списку полів модуля позначається як Unique |
| системна обов'язковість (**Last Name** тощо) | модуль | не змінюється |

**Хто яким layout користується.** Після **Save Layout** CRM просить обрати профілі, яким layout
доступний (**Layout Permission**). Профіль може мати кілька layouts, але один з них — за
замовчуванням; призначення і вибір за замовчуванням робляться кнопкою **Layout Assignments** (у
довідці — Layout Assignment або Layout and Type Assignment). Поки в модулі лише один активний
layout, ця дія недоступна.

**Системне поле Layout.** Коли в модулі з'являється другий layout, CRM додає поле **Layout** — у ньому
записано, через який layout створено запис. За цим полем будують подання, правила призначення,
звіти.

**Як запис потрапляє в layout** (за довідкою):

- у формі створення людина обирає layout;
- при імпорті layout обирають на початку імпорту;
- записи з вебформ ідуть у layout, обраний у налаштуваннях вебформи;
- записи через API — у layout, переданий у запиті; якщо не передано — у стандартний;
- коли в модулі вперше створюють другий layout, усі наявні записи лишаються в **Standard**.

**Важлива для QA деталь.** Довідка прямо каже: власник запису відкриває і редагує свій запис навіть
тоді, коли layout цього запису йому не призначено. Тобто **Layout Permission — це про вибір форми
при створенні, а не межа безпеки.** Щоб приховати дані, потрібні дозволи на поля або доступ до
записів.

Деактивувати чи видалити layout можна лише з перенесенням його записів в інший layout — CRM про
це попросить. Створювати нові layouts можна в редакції Enterprise і вище; у тріалі
**Create New Layout** доступна одразу.

## 6.4. Дозволи на поля

Дозвіл на поле задається для кожного профілю, рівнів три: повний доступ, лише читання і приховане
поле. У вікні **Set Permission** вони називаються **Read and Write**,
**Read Only** і **Don't Show**. Обов'язкове поле сховати не можна, продукт має на це окремі
повідомлення, наприклад:
`Required fields cannot be marked as 'Hidden'. Please check the field properties.`

Де налаштовується:

- у редакторі layout: **Settings** поля → **Set Permission** → вікно **Set Permission** з рядком на
  кожен профіль → **Save**, потім **Save Layout**;
- або зі списку полів модуля: **Fields** → **Field Permissions**.

Три факти з довідки, які напряму б'ють по тестах:

1. дозволи на поле **не залежать від layout**: сховав поле для профілю — воно сховане в усіх
   layouts модуля;
2. дозволи на поля є в Professional і вище;
3. **Set Permission** відкривається і працює навіть коли в CRM один користувач — він просто показує
   рядок на кожен наявний профіль, а профілів завжди щонайменше два (`Administrator`, `Standard`).

«Приховане» має бути прихованим скрізь, де людина може побачити значення: форма створення і
редагування, сторінка запису, колонки списку, фільтри й критерії подань, пошук, звіти, експорт.
Кожна з цих поверхонь — окремий тест.

## 6.5. Унікальні поля

Унікальне поле — поле, значення якого не може повторюватися в записах модуля: email, номер паспорта,
код продукту. У Zoho це властивість **Do not allow duplicate values**.

Правила з довідки Zoho:

- унікальними можуть бути лише поля типів Text, Email, Phone, Integer, Long Integer, URL;
- у модулі — до двох унікальних полів; у **Leads**, **Contacts** і кастомних модулях — Email плюс
  два поля; у **Products** — **Product Code** плюс два поля;
- у **Tasks**, **Calls**, **Meetings** унікальних полів не буває;
- порівняння **не чутливе до регістру**: `ABC` і `abc` — дубль;
- після позначення поля унікальним CRM потрібен час на індексацію: якщо одразу створити дубль, CRM
  може його пропустити. Зачекай кілька хвилин, перш ніж тестувати;
- унікальність діє для записів, створених вручну, через імпорт, API і конвертацію
  (ліди, квоти, замовлення);
- **не діє** для записів з міграції CRM, синхронізації з Outlook і Google, відновлення з Recycle
  Bin і для Sheet View;
- функція є лише в платних редакціях.

Як позначити:

- **стандартне поле:** **Settings** поля → **Do not allow duplicate values**;
- **кастомне поле:** **Settings** → **Edit Properties** → у вікні **Field Properties** прапорець
  **Do not allow duplicate values** → **Done** → **Save Layout**.

Після цього в списку полів модуля в колонці типу даних поле позначене як Unique.

Для QA з цих правил виходить готовий набір тестів: точний дубль, дубль в іншому регістрі, дубль
одразу після позначення, дубль через імпорт, дубль через відновлення з кошика. Останні два канали
Zoho сам називає непідтримуваними — дубль там не дефект, а відома межа, яку варто записати в звіт.

## 6.6. Покроково: A8 — керований layout для введення даних

Завдання A8 з документа: у модулі пісочниці (sandbox) створити layout `QA Training` (або layout
окремого тестового модуля) і зробити в ньому щонайменше 2 обов'язкові поля, 1 унікальне і 1 поле,
приховане для обмеженого профілю; здати структурований набір тестів, що перевіряє поведінку
обов'язкових, унікального і прихованого полів для профілів користувачів.

Модуль беремо **Products**: продукт — проста сутність з одним обов'язковим системним полем
(**Product Name**), і в ньому є природні кандидати на властивості з таблиці нижче.

| вимога | поле | тип | звідки |
|---|---|---|---|
| обов'язкове 1 | **Unit Price** | Currency | стандартне |
| обов'язкове 2 | `Warranty Months` | Number (ціле число) | кастомне |
| унікальне | `Supplier SKU` | Single Line (Text) | кастомне |
| приховане для `Junior Sales Restricted` | `Internal Cost` | Currency | кастомне |

Кожна властивість — на своєму полі. Так кожну поведінку можна перевірити окремо, і провал одного
тесту не маскує інший.

### Крок 0. Середовище і передумови

Пісочниця — копія налаштувань production на момент її створення. Що з'явилось у production пізніше
(користувачі, ролі, профілі), у пісочниці автоматично не з'являється, а **оновити (Rebuild)
пісочницю в тріалі не можна** — так пише довідка.

Тобі потрібні:

- обмежений профіль `Junior Sales Restricted`: клон `Standard`, у якому знято видалення лідів,
  експорт лідів і доступ до **Campaigns**, а **Products** доступний;
- користувач з цим профілем — User C;
- для порівняння — User B з профілем `Standard`.

Перевір у пісочниці три речі, саме в такому порядку:

1. **User C і User B мають доступ до пісочниці.** У production: **Setup → Data Administration →
   Sandbox** → твоя пісочниця → значок угорі праворуч → **Edit** → у вікні **Edit Sandbox** додай
   User C і User B до тих, хто має доступ. За довідкою, користувач отримує лист з адресою пісочниці.
   Доступ — першим, бо за довідкою, поки в CRM один користувач, нові профілі не створюються, а
   **Set Permission** недоступний; у пісочниці, де є лише ти, очікуй того самого.
2. **Профіль є в пісочниці.** Увійди в неї: **Setup → Data Administration → Sandbox** → **Go to
   Sandbox** (пісочницю видно за яскравою помаранчевою смугою з її назвою, адреса — на
   `crmsandbox.zoho.eu`). У пісочниці **Setup → Security Control → Profiles**. Немає
   `Junior Sales Restricted` — створи його тут так само: клон `Standard` з тими самими знятими
   дозволами.
3. **У пісочниці в User C правильний профіль.** У пісочниці **Setup → General → Users** → User C →
   **Profile** `Junior Sales Restricted`. Не припускай, що профіль «приїхав» з production:
   перевір.

Якщо хоч одну передумову в пісочниці виконати не вдається, роби A8 у production-організації
тріалу. Це відступ від документа, який просить пісочницю (як альтернативу він допускає лише
layout окремого тестового модуля), тож напиши в шапці набору тестів середовище і причину.
Перевірка прихованого поля під адміністратором замість User C — не альтернатива: вона нічого не
доводить.

### Крок 1. Layout `QA Training`

1. **Setup → Customization → Modules and Fields** → **Products**.
2. **Create New Layout**. У вікні створення назви layout `QA Training` і обери клонування зі
   **Standard**.

**Що побачиш:** редактор layout з тими самими полями і секціями, що в **Standard**.

### Крок 2. Кастомні поля

Перетягни з лотка **New Fields** у секцію з інформацією про продукт такі типи полів (**Number** —
ціле число, у довідці цей тип називається Integer):

| тип | **Field Label** | що задати у властивостях |
|---|---|---|
| **Single Line** | `Supplier SKU` | довжина за замовчуванням |
| **Number** | `Warranty Months` | — |
| **Currency** | `Internal Cost` | **Decimal Places** `2`, округлення за замовчуванням |

Після кожного поля у вікні властивостей натисни **Done**.

**Що побачиш:** нові поля в секції, лічильник **Custom Fields Left** зменшився на три.

### Крок 3. Обов'язкові поля

1. **Unit Price** → **Settings** → **Mark as required**.
2. `Warranty Months` → **Settings** → **Mark as required**.

**Що побачиш:** поля позначені як обов'язкові в цьому layout. У layout **Standard** нічого не
змінилось — обов'язковість живе в layout.

## 6.7. Як це тестувати

### Виміри

Кожен тест A8 — це точка в чотирьох вимірах:

- **властивість:** обов'язковість, унікальність, прихованість;
- **профіль:** `Junior Sales Restricted`, `Standard`, `Administrator`;
- **layout:** `QA Training` проти **Standard**;
- **канал:** форма створення, редагування, Quick Create, клонування запису, імпорт, масове
  оновлення, API.

Повний перебір не потрібен. Потрібні ті точки, де налаштування може «протекти».

### Обов'язкові поля

- порожнє **Unit Price** → запис не зберігається;
- порожнє `Warranty Months` → не зберігається;
- обидва заповнені → зберігається;
- `0` у `Warranty Months` — це значення, а не порожнеча: має зберегтися (якщо бізнесу потрібно
  «більше нуля» — це вже правило валідації);
- текстове поле з самих пробілів — чи вважає CRM це заповненим? Хороший дослідницький тест;
- редагування: стерти **Unit Price** в наявному записі → не зберігається;
- **Standard** layout: порожнє **Unit Price** → зберігається, бо обов'язковість — властивість
  `QA Training`. Це не дефект, а доказ, що обов'язковість живе в layout.

### Унікальне поле

- `SKU-001` у першому продукті → зберігається;
- `SKU-001` у другому → блокується; запиши повідомлення дослівно;
- `sku-001` → теж блокується (порівняння без урахування регістру);
- `SKU-002` → зберігається;
- редагування другого продукту на `SKU-001` → блокується;
- `SKU-001 ` з пробілом у кінці — дослідницький тест: запиши, що зробить CRM;
- додатково: перетягни `Supplier SKU` у layout **Standard** (нове поле, найімовірніше, чекає в
  його **Unused Fields**; якщо його там немає — запиши, де ти його знайшов) і створи там продукт з
  `SKU-001` — очікуємо блокування, бо унікальність стосується записів модуля, а не layout. Інший
  результат — знахідка.

### Приховане поле

Тестовий продукт для цих перевірок створює адміністратор: заповнює `Internal Cost` і ставить
власником (**Product Owner**) User C. Власник важливий: якщо продукт належить адміністратору, а
модуль закритий налаштуванням `Private`, User C не відкриє запис зовсім, і тест «поля не видно»
нічого не доведе.

Під User C (`Junior Sales Restricted`):

- форми створення і редагування `QA Training`: поля `Internal Cost` немає;
- сторінка цього продукту: поля і значення не видно;
- список **Products**: колонки `Internal Cost` немає і додати її не можна;
- фільтр або умова подання: поля немає серед доступних;
- експорт продуктів (якщо профіль дозволяє експорт цього модуля): поля немає у файлі;
- **цілісність даних:** User C змінює інше поле цього продукту і зберігає — під адміністратором
  `Internal Cost` має лишитися незмінним.

Під User B (`Standard`) і адміністратором поле видно і його можна редагувати.

### Докази і середовище

- у шапці набору: середовище (пісочниця або production), дата, модуль, layout, профілі й
  користувачі;
- на знімку видно, хто залогінений і який layout у формі;
- тексти повідомлень CRM — дослівно, як на екрані.

### Якщо колись переноситимеш це в production

При розгортанні змін з пісочниці в production познач у наборі змін і layout, і всі його поля.
Розгортання самого layout (без його кастомного поля) може пройти перевірку залежностей зі статусом
`Qualified`, а поле в production так і не з'явиться; скасувати розгортання не можна. Після будь-якого
розгортання перевір результат у production очима.

## 6.8. Типові помилки

**1. Одне поле на всі властивості.** Зробив `Supplier SKU` одночасно обов'язковим і унікальним — і
тест «не зберігається» не каже, яка саме властивість спрацювала. А сховати обов'язкове поле CRM і
не дасть.

**2. «Сховав», прибравши з layout.** Поле в **Unused Fields** зникає для всіх профілів, а не лише для
обмеженого, а в інших layouts, де воно є, лишається видимим. Для одного профілю — тільки
**Set Permission**.

**3. Обов'язковість не в тому layout.** **Mark as required** поставлено в **Standard**, а тестуєш
`QA Training` — або навпаки.

**4. Тест унікальності одразу після налаштування.** CRM ще не проіндексувала поле, дубль проходить,
і з'являється хибний дефект. Зачекай кілька хвилин.

**5. Унікальність на полі не того типу.** Pick List, Date, Currency унікальними не бувають — опції
просто не буде.

**6. Прихованість перевірена лише у формі.** Поле зникло з форми, але його видно в колонці списку
чи у звіті.

**7. Тест під адміністратором або в Preview.** Адміністратор бачить поле, Preview — лише імітація.
Доказ — вхід під User C.

**8. Профіль у пісочниці «такий самий, як у production».** Пісочниця — знімок на момент
створення; у тріалі її не оновиш. Профіль і користувача в пісочниці перевіряй окремо.

**9. Невдалий тип поля.** Створив `Warranty Months` як Single Line — тепер туди можна ввести `abc`, а
тип не змінити. Вибирай тип до створення.

**10. Видалив поле з Unused Fields, щоб «почистити».** Разом з полем зникли його дані в усіх
записах, назавжди.

### Симптом → причина

| симптом | найімовірніша причина |
|---|---|
| немає **Create New Layout** | редакція без кількох layouts або немає дозволу на кастомізацію модулів |
| немає **Set Permission** у налаштуваннях поля | редакція без дозволів на поля (потрібен Professional і вище) |
| немає **Do not allow duplicate values** | тип поля не підтримує унікальність, у модулі вже максимум унікальних полів, або це модуль активностей |
| дубль `SKU-001` зберігся | поле ще не проіндексоване; дубль створено через Sheet View чи відновлено з Recycle Bin; прапорець не збережено (**Save Layout**) |
| `sku-001` зберігся при наявному `SKU-001` | поле не унікальне — перевір список полів (позначка Unique) |
| **Unit Price** не обов'язкове | запис створюється в **Standard**, а не в `QA Training` |
| User C не може обрати `QA Training` при створенні | layout не призначено профілю `Junior Sales Restricted` |
| User C бачить `Internal Cost` | у пісочниці в User C інший профіль; дозвіл поставлено не тому профілю; не натиснуто **Save** у вікні дозволів |
| `Internal Cost` зник і в User B | поле прибрано з layout замість дозволу на поле, або приховано і для `Standard` |
| поле видно у формі, але не в іншому layout | поле є лише в одному layout; в іншому воно в **Unused Fields** |
| після розгортання з пісочниці layout без поля | у наборі змін позначено layout без його полів |

## 6.9. Що варто запам'ятати

1. Стандартні модулі можна налаштовувати, але не видаляти; частину системно обов'язкових полів
   змінити не можна.
2. Тип поля обирають один раз — змінити його не можна.
3. Прибране з layout поле живе в **Unused Fields** з даними; видалене звідти — зникає назавжди.
4. Layout вирішує склад форми, обов'язковість і значення списків; дозволи на поля — ні.
5. Дозволи на поля діють у всіх layouts модуля.
6. **Layout Permission** — про вибір форми, а не про безпеку: власник редагує свій запис і без
   доступу до його layout.
7. Унікальність: лише певні типи, без урахування регістру, з паузою на індексацію, не для всіх
   каналів.
8. Одна властивість — одне поле — один набір тестів.
9. Прихованість перевіряй на кожній поверхні: форма, сторінка, список, фільтр, звіт, експорт.
10. Пісочниця — знімок; у тріалі її не оновити, тож профілі й користувачів там перевіряй окремо.
