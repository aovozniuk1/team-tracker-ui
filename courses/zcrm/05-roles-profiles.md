# Урок 5. Користувачі, ролі та профілі

*Після цього уроку ти додаєш тестових користувачів у тріал Zoho One, будуєш ієрархію ролей і
доводиш, хто чиї записи бачить, а ще робиш обмежений профіль і перевіряєш, що обмеження справді
тримають, а адміністратора не зачіпають. Для QA це фундамент: той самий екран у різних людей
виглядає по-різному, і чимала частина «багів» у CRM — це налаштування доступу.*

---

## 5.1. Три питання доступу

Коли користувач відкриває CRM, система відповідає на три окремі питання:

| питання | що на нього відповідає | де це налаштовується |
|---|---|---|
| хто ти? | **користувач** (user): обліковий запис, ім'я, email, стан | Zoho One Admin Panel і **Setup → General → Users** |
| чиї записи ти бачиш? | **роль** (role) в ієрархії + налаштування спільного доступу модуля | **Setup → Security Control → Roles and Sharing** |
| що ти можеш робити? | **профіль** (profile): модулі, дії, налаштування | **Setup → Security Control → Profiles** |

Коротке правило, яке варто вивчити напам'ять: **профіль — що можна робити, роль — чиї записи
видно.**

Приклад. User B і User C мають однаковий профіль `Standard`: обоє можуть створювати, змінювати й
видаляти ліди. Але User B стоїть в ієрархії вище, тому бачить і свої ліди, і ліди User C. User C
бачить лише свої. Дозволи однакові — видимість різна.

Кожному користувачу CRM призначають одну роль і один профіль. Кілька ролей одній людині дати не
можна.

Два винятки треба знати з першого дня, бо саме вони ламають перевірки:

- користувач із профілем **Administrator** бачить усі записи незалежно від своєї ролі;
- роль впливає на видимість лише тоді, коли модуль закритий налаштуванням спільного доступу
  `Private` (розділ 5.4). Якщо модуль «публічний», чужі записи бачать усі, і на видимість ієрархія
  вже не впливає.

Є ще рівень полів: профіль може бачити поле, лише читати його або не бачити зовсім. Це дозволи на
поля, вони налаштовуються в модулі, а не в профілі, і для завдань цього уроку не потрібні.

## 5.2. Користувачі в тріалі Zoho One

Твій тріал — це організація Zoho One, а не окремий CRM. Користувачі належать організації: їх
створюють в адмін-панелі Zoho One, а CRM отримує їх як своїх. Звідси три наслідки:

- CRM у тріалі стартує з одним користувачем — тобою, адміністратором;
- кнопка **+ New User** у **Setup → General → Users** користувача не створює: вона лише відкриває
  в новій вкладці адмін-панель Zoho One — сторінку **Applications → CRM** з панеллю **Assign CRM to
  User(s)** (браузер може цю вкладку заблокувати);
- користувачів додають у **Admin Panel → User Management → Users → Add User**.

Форма **Add User** у тріалі має поля **First name** (обов'язкове), **Last name**, **Email**
(обов'язкове) і прапорець **Send Notification Mail**. У вікні видно, скільки ліцензій лишилось,
наприклад `Licenses left: Zoho One - 9`. Довідка Zoho One описує ще необов'язкові блоки (дані про
компанію, мову, часовий пояс) і вибір ліцензії для користувача.

Що відбувається після **Add** (так описує довідка Zoho One):

- на вказану адресу йде запрошення, воно дійсне 7 днів;
- поки людина не прийняла запрошення, вона в списку зі станом `Pending`; надіслати запрошення
  повторно можна до трьох разів;
- якщо в людини ще нема облікового запису Zoho, під час прийняття вона реєструється і задає
  пароль.

Далі перевір, що новому користувачу призначено CRM: він має з'явитися у **Setup → General → Users**
твого CRM. Якщо його там нема — CRM треба призначити в адмін-панелі. Довідка Zoho One робить це так:
розділ застосунків (**Applications**), застосунок CRM, меню **⋯** → **Assign Users** → вкладка
**Individual** → обрати людину → **Assign**.

Роль і профіль призначаються вже в самому CRM: **Setup → General → Users** → клік на ім'я
користувача → значок редагування → у формі редагування обери **Role** і **Profile** → **Save**.
Не покладайся на те, що CRM поставить «правильні» значення сам: для завдань вони мають бути саме
такими, як ти задав.

Кілька практичних речей, які зекономлять вечір:

- **Temp Mail.** Документ дозволяє одноразові скриньки. Важливіше інше: скринька має жити, поки ти
  проходиш курс, бо через неї ти приймаєш запрошення і відновлюєш пароль. Адреса, що зникає за
  годину, не годиться.
- **Окреме вікно на кожного користувача.** Адміністратор лишається в основному вікні браузера,
  User B і User C — у приватних вікнах або окремих профілях браузера. Інакше дуже легко перевірити
  «як User C», насправді сидячи під адміністратором.
- **EU.** Тріал у європейському дата-центрі: усі входять через `accounts.zoho.eu`, CRM відкривається
  на `crm.zoho.eu`.
- **Ролі й профілі не чекають на User B і User C.** У тріалі кнопка **New Role** і
  форма **New Profile** працюють одразу, навіть коли в CRM є лише адміністратор — можеш будувати
  ієрархію ролей і клонувати профілі до того, як з'являться інші люди. Але саму видимість записів
  (A6) без User B і User C не перевіриш, тож користувачів усе одно варто замовити першими — це
  найдовший крок (запрошення, лист, пароль).

## 5.3. Ролі: ієрархія і видимість записів

Роль — це місце людини в оргструктурі. Кожна роль підпорядкована іншій (поле **Reports To**), і з
ролей складається дерево. З дерева випливає доступ до записів:

- вищий бачить записи нижчих у своїй гілці: `Sales Manager` бачить записи `Sales Representative`;
- нижчий записів вищого не бачить;
- колеги з однаковою роллю за замовчуванням записів одне одного не бачать; це змінює прапорець
  **Share Data with Peers** у налаштуваннях ролі;
- роль `CEO` має доступ до всієї бази;
- менеджер бачить записи підлеглих лише в тих модулях, де його профіль дає право на перегляд
  (**View**), і змінює їх лише там, де профіль дає **Edit**.

«Записи користувача» — це записи, де він власник: поле **Lead Owner** у лідах, **Deal Owner** в
угодах тощо. Змінив власника — змінилось, хто цей запис бачить. Тому в кожному тесті на видимість
перевіряй власника, а не автора запису.

За замовчуванням у CRM є дві ролі: `CEO` і `Manager`. Для завдання тобі потрібна така ієрархія:

```
CEO                           <- адміністратор тріалу (перевір його роль)
├── Manager                   (стандартна роль, не чіпаємо)
└── Sales Manager             <- User B
    └── Sales Representative  <- User C
```

Зверни увагу: `Manager` і `Sales Manager` — різні ролі. Якщо помилково підпорядкувати
`Sales Representative` ролі `Manager`, User B не побачить записів User C, і тест «впаде» через
налаштування, а не через продукт.

**Hierarchy Preference.** Zoho вміє будувати ієрархію двома способами: за ролями (**Role
Hierarchy**) або за тим, хто кому звітує серед користувачів (**Reporting Hierarchy**). Перемикач —
у **Setup → General → Company Settings → Hierarchy Preference**. Завдання перевіряє саме ролі, тож
там має стояти **Role Hierarchy**. У режимі Reporting Hierarchy прапорця **Share Data with Peers** у
ролі немає. Роль у кожного користувача потрібна за будь-якого режиму.

**Створення ролі** (так описує довідка Zoho):

1. **Setup → Security Control → Roles and Sharing**.
2. **New Role**.
3. **Role Name** — назва; дві ролі з однаковою назвою не створюй.
4. **Reports To** — безпосередньо вища роль. Не обрав — роль стане під `CEO`.
5. **Share Data with Peers** — за потреби.
6. **Description** — опис.
7. **Save**.

Роль можна перейменувати, перевісити під іншу роль і змінити прапорець колег. Видалити роль можна
лише разом із перенесенням її підлеглих ролей і користувачів в іншу роль (**Transfer and Delete**).
Тобто ролі легко виправити, а видалення — це вже перебудова дерева.

## 5.4. Data Sharing Settings: коли ієрархія взагалі працює

Перш ніж застосувати ієрархію, CRM дивиться на базовий рівень доступу до модуля — **Default
Access** у налаштуваннях спільного доступу організації. Для кожного модуля він свій:

| **Default Access** модуля | що бачать і роблять інші користувачі з чужими записами | чи діє ієрархія ролей |
|---|---|---|
| `Private` | чужий запис бачать лише власник і ті, хто вище за роллю | так |
| `Public Read Only` | усі бачать; змінювати чужі записи інші не можуть | для перегляду — ні: бачать усі |
| `Public Read/Write` | усі бачать і змінюють, але не видаляють | ні |
| `Public Read/Write/Delete` | усі бачать, змінюють і видаляють | ні |

За замовчуванням модулі стоять на `Private` — у тріалі саме так і стоїть для **Leads**, без жодних
змін. Але перед тестом завжди дивись самостійно, бо будь-хто міг це змінити:

**Setup → Security Control → Roles and Sharing → Data Sharing Settings** → вкладка **Default
Organization Permissions** → потрібний модуль → **Default Access**.

Там же є вкладка **Sharing Rules**: правила, які відкривають записи певних ролей чи груп іншим
ролям або групам. Правила можуть лише **розширити** доступ, звузити базовий рівень вони не можуть.
Цікава деталь: записи, відкриті правилом підлеглому, керівник цього підлеглого за замовчуванням не
бачить — для цього в правилі є прапорець **Superiors Allowed**.

Для QA головне: **значення Default Access модуля — обов'язкова передумова будь-якого тесту на
видимість.** Без нього результат не можна інтерпретувати: «User C бачить ліди адміністратора» при
`Private` — дефект, при `Public Read Only` — норма.

Якщо змінюєш Default Access, запиши попереднє значення. Ця зміна діє на всіх користувачів
організації одразу.

## 5.5. Профілі: що можна робити

Профіль — набір дозволів: до яких модулів людина має доступ, які дії в них виконує, які
налаштування бачить. Профіль призначають користувачу, а один профіль може мати багато людей.

Стандартних профілів два:

- **Administrator** — доступ до всього. Довідка: змінювати в ньому можна лише базові дозволи
  модулів і кілька дозволів розширень.
- **Standard** — щоденна робота без адміністративних налаштувань. Змінювати його майже не можна.

Тому робочий прийом один: **клонуєш стандартний профіль і міняєш дозволи в копії.** Клон забирає
всі дозволи оригіналу, далі ти їх звужуєш або розширюєш.

Як улаштована сторінка профілю (за довідкою Zoho):

| розділ | що всередині (приклади) |
|---|---|
| **Module Permissions** | **Basic**: доступ до кожного модуля і дії **View**, **Create**, **Edit**, **Delete** (галочки у випадному списку біля модуля); **Import/Export**: **Import Records**, **Export** по модулях; **Send Email**; **Tools**: **Mass Update**, **Mass Delete**, **Change Owner**, **Mass Transfer**, **Convert**, **Share**, **Lock** тощо; **Others** |
| **Setup Permissions** | адміністративні дозволи (**User Management**, **Modules Customization**), шаблони, автоматизація (**Manage Automation**), вебформи, адміністрування даних, Zia |
| **Extension Permissions** | інтеграції (Zoho, Google, мобільний застосунок тощо) |
| **Developer Permissions** | **Zoho CRM API Access** та інше для розробників |

Чотири властивості профілів, про які найчастіше забувають:

1. **Зміни діють одразу.** Кнопки Save на сторінці профілю немає: перемкнув дозвіл — він уже діє
   для всіх користувачів цього профілю. У тріалі це зручно, на живій системі — небезпечно.
2. **Розширені дозволи залежать від базових.** **Mass Delete** можна дати лише в модулях, де є
   **Delete**; **Export** — лише де є **View**; масова пошта — лише де є звичайна. Довідка
   попереджає: якщо вимкнути розширений дозвіл, а потім базовий, то повторне ввімкнення базового
   розширений не поверне — його треба ввімкнути окремо.
3. **Дозвіл на модуль ≠ дозвіл на дані з модуля.** Наприклад, звіти мають власні дозволи (у тому
   числі експорт звітів). Зняв **Export** у модулі — це ще не означає, що людина не зможе вивантажити
   ті самі дані через звіт. Це типова дірка, яку тестувальник має помітити.
4. **Профіль не можна видалити «просто так».** Якщо в профілі є користувачі, CRM попросить
   перенести їх в інший профіль.

Порівняння, яке варто пам'ятати:

| | роль | профіль |
|---|---|---|
| відповідає на питання | чиї записи видно | що можна робити |
| будова | дерево (Reports To) | плоский список дозволів |
| стандартні | `CEO`, `Manager` | `Administrator`, `Standard` |
| скільки в користувача | одна | один |
| залежить від Default Access модуля | так | ні |
| типовий дефект конфігурації | роль не під тим керівником | знятий не той дозвіл або не в тому модулі |

## 5.6. Покроково: A6 — мінімальна ієрархія і перевірка видимості

Завдання A6 з документа: створити ролі `Sales Manager` і `Sales Representative` (представник під
менеджером), створити двох тестових користувачів і призначити їм ролі, перевірити, що видимість
записів відповідає опису ієрархії в Zoho, і здати матрицю «User → Can see whose records?» з
доказами.

### Крок 1. Перевір режим ієрархії

**Setup → General → Company Settings → Hierarchy Preference** → має бути **Role Hierarchy**.

### Крок 2. Користувачі

Якщо User B і User C ще нема:

1. У Zoho One відкрий **Admin Panel → User Management → Users → Add User**.
2. User B: **First name** `User`, **Last name** `B`, **Email** — робоча скринька (твоя тестова або
   Temp Mail). Залиш **Send Notification Mail** увімкненим, щоб прийшло запрошення. **Add**.
3. Так само User C.
4. Відкрий кожну скриньку, прийми запрошення, задай пароль.

**Що побачиш:** у списку користувачів Zoho One обидва стоять як `Pending`, доки запрошення не
прийнято; після прийняття — як звичайні користувачі. У CRM, у **Setup → General → Users**,
з'являються User B і User C.

Якщо в CRM їх нема, признач їм CRM в адмін-панелі (5.2).

### Крок 3. Ролі

1. **Setup → Security Control → Roles and Sharing** → **New Role**.
2. **Role Name** `Sales Manager`, **Reports To** `CEO`, **Share Data with Peers** не чіпай,
   **Description** `A6: manager level`. **Save**.
3. Ще раз **New Role**: **Role Name** `Sales Representative`, **Reports To** `Sales Manager`,
   **Description** `A6: rep level`. **Save**.

**Що побачиш:** у дереві ролей `Sales Manager` стоїть під `CEO`, а `Sales Representative` — під
`Sales Manager`.

### Крок 4. Призначення

**Setup → General → Users**:

| користувач | **Role** | **Profile** |
|---|---|---|
| адміністратор (ти) | `CEO` — перевір, нічого не міняй | `Administrator` |
| User B | `Sales Manager` | `Standard` |
| User C | `Sales Representative` | `Standard` |

Для кожного: клік на ім'я → значок редагування → **Role**, **Profile** → **Save**.

### Крок 5. Передумова видимості

**Setup → Security Control → Roles and Sharing → Data Sharing Settings** → **Default Organization
Permissions** → **Leads**. Має бути `Private`. Якщо стоїть інше — запиши поточне значення,
постав `Private` і збережи.

### Крок 6. Тестові записи

Під адміністратором створи три ліди (**Leads** → **Create Lead**). Обов'язкові поля ліда —
**Last Name** і **Company**.

| **Last Name** | **Company** | **Lead Owner** |
|---|---|---|
| `A6-Admin` | `A6 Visibility Test` | ти (адміністратор) |
| `A6-UserB` | `A6 Visibility Test` | User B |
| `A6-UserC` | `A6 Visibility Test` | User C |

**Що побачиш:** у кожному записі поле **Lead Owner** показує потрібну людину. Перевір це ще раз
на сторінці запису: помилка у власнику зіпсує всю матрицю.

З кожного запису скопіюй адресу з рядка браузера — вона знадобиться для перевірки прямого доступу.

### Крок 7. Перевірка під кожним користувачем

Для адміністратора, User B і User C по черзі (кожен — у своєму вікні):

1. Увійди як цей користувач.
2. **Leads** → подання **All Leads** (стандартне подання «усі ліди, які мені доступні»).
3. Знайди записи з префіксом `A6` (пошуком або фільтром у списку).
4. Зроби знімок екрана так, щоб було видно, **хто** залогінений (ім'я або аватар угорі) і
   **які** `A6`-записи в списку.
5. Встав у рядок браузера адресу запису, якого цей користувач бачити не повинен (для User B — ліда
   `A6-Admin`, для User C — лідів `A6-Admin` і `A6-UserB`). Зафіксуй, що показує CRM, дослівно.

**Що побачиш:** User B бачить `A6-UserB` і `A6-UserC`, але не `A6-Admin`. User C бачить лише

задачі 5.9. Суть перевірок:

- **Сховано або вимкнено:** у User C недоступні видалення свого ліда й експорт у списку лідів, у
  навігації немає модуля **Campaigns**. Масове видалення лідів теж має стати недоступним: воно
  можливе лише там, де є **Delete**. Запиши, як саме це виглядає: дії немає зовсім чи вона
  неактивна.
- **Відмовляє коректно:** відкрий під User C пряму адресу запису кампанії (скопіюй її під
  адміністратором). Друга перевірка — «застаріла сторінка»: на сторінці ліда, яку User C відкрив ще
  з профілем `Standard` (крок 3), спробуй видалити лід, не оновлюючи сторінку. Правильна поведінка:
  дія не виконується, дані цілі, людина бачить зрозуміле повідомлення. Якщо на тій сторінці дії
  видалення вже немає — запиши й це. Точні тексти повідомлень запиши дослівно.
- **Не зачепили інших:** адміністратор бачить експорт, видалення і **Campaigns**; User B з профілем
  `Standard` видаляє свій лід — отже, клон не змінив оригінал.

## 5.8. Як це тестувати

### Головне правило: доступ перевіряють під тим, кого обмежують

Адміністратор бачить усі записи незалежно від ролі й має всі дозволи. Будь-яка перевірка
доступу, виконана під адміністратором, не доводить нічого. Тому для кожного тесту в передумовах
пиши **під ким** він виконується, а на знімку має бути видно ім'я залогіненого користувача.

### Що записувати в передумови

Результат тесту на доступ залежить від п'яти речей. Якщо хоч одна не записана — тест не можна
відтворити:

1. режим ієрархії (**Role Hierarchy** чи **Reporting Hierarchy**);
2. **Default Access** модуля;
3. роль і профіль користувача, під яким виконуєш тест;
4. власник тестового запису;
5. прапорець **Share Data with Peers** у ролях, якщо в ролі кілька людей.

### Що може зламатися

- роль підпорядкована не тій ролі (типово — `Manager` замість `Sales Manager`);
- модуль «публічний», і ієрархія не діє;
- дозвіл знято не в тому модулі або не в тому профілі (у `Standard` замість клону);
- розширений дозвіл лишився, хоча базовий знято, або навпаки не повернувся після повторного
  ввімкнення базового;
- дію сховано в одному місці інтерфейсу, але вона доступна в іншому (список, сторінка запису,
  масові дії, звіти, пряма адреса);
- кнопка лишилась на сторінці, відкритій до зміни дозволу, і сервер дію виконує.

## 5.9. Типові помилки

**1. Перевірка під адміністратором.** Адміністратор бачить усе, тому «усе працює». Кожну перевірку
доступу виконуй під тим, кого обмежуєш.

**2. «Публічний» модуль.** При `Public Read/Write/Delete` чи `Public Read/Write` ієрархія не
застосовується, і матриця A6 вийде «усі бачать усіх».

**3. Не та вища роль.** `Sales Representative` підпорядкували стандартній `Manager`, а не
`Sales Manager`. User B не бачить записів User C.

**4. Змінюєш `Standard` замість клону.** Стандартні профілі майже не редагуються, а якщо щось і
зміниться — зачепить усіх користувачів `Standard`.

**5. Прибрав модуль, потрібний далі.** Без **Deals** обмежений користувач не зможе працювати з
угодами, і будь-який наступний тест «не можу» стане неінформативним.

**6. Сприйняв залежність дозволів за дефект.** **Mass Delete** зник разом з **Delete** — так і має
бути. Інший випадок: ти вимкнув **Mass Delete**, потім **Delete**, а потім знову ввімкнув **Delete** —
**Mass Delete** сам не повернеться. За довідкою це теж очікувано: його вмикають окремо.

**7. Одне вікно на всіх.** Вийшов з одного користувача, увійшов іншим, забув — і тестуєш не того.
Тримай окреме вікно на кожного.

**8. Не той власник запису.** Лід створив адміністратор, але поле **Lead Owner** лишилось на ньому
самому — і User C «не бачить свого» запису.

**9. Очікуєш, що менеджер бачить записи вищих.** Ієрархія працює лише вниз: `Sales Manager` не
бачить записів `CEO`.

**10. Зникла скринька.** Одноразова адреса протермінувалась до прийняття запрошення — користувач
лишився `Pending`, а відновити пароль нема куди.

### Симптом → причина

| симптом | найімовірніша причина |
|---|---|
| нову роль чи профіль не вдається зберегти, назва підкреслена червоним | назва містить символ, якого Zoho не приймає (наприклад круглі дужки) — прибери його |
| **+ New User** у CRM відкриває іншу вкладку або нічого не робить | в організації Zoho One користувачів додають в **Admin Panel**; вкладку міг заблокувати браузер |
| User B / User C нема в **Setup → General → Users** | не прийнято запрошення або користувачу не призначено CRM |
| користувач у Zoho One має стан `Pending` | запрошення не прийняте; перевір скриньку або надішли ще раз |
| User C бачить ліди адміністратора | **Default Access** для **Leads** не `Private`; або User C має профіль `Administrator` |
| User B не бачить лідів User C | `Sales Representative` підпорядковано не `Sales Manager`; або **Lead Owner** цих лідів не User C |
| User B бачить ліди адміністратора | модуль «публічний»; або User B дали роль `CEO` чи профіль `Administrator` |
| двоє з однією роллю бачать записи одне одного | у ролі ввімкнено **Share Data with Peers** |
| прапорця **Share Data with Peers** у ролі немає | обрано **Reporting Hierarchy** або в CRM лише один користувач |
| знятий дозвіл «не діє» | змінено не той профіль; користувачу призначено інший профіль; сторінку відкрито до зміни |
| дозвіл знято в клоні, а обмеження з'явилось і в User B | змінено `Standard`, а не клон |
| **Mass Delete** зник | знято **Delete** у цьому модулі — очікувана залежність |
| після повернення **Delete** не повернувся **Mass Delete** | **Mass Delete** вимкнули ще до **Delete**; такий розширений дозвіл сам не вмикається — увімкни окремо |
| на «застарілій сторінці» лід видалився | дозвіл перевіряється лише в інтерфейсі — дефект безпеки, описуй з часом і знімками |
| дані лідів усе одно вивантажуються | експорт через звіт має окремий дозвіл у розділі звітів |

## 5.10. Що варто запам'ятати

1. Профіль — що можна робити; роль — чиї записи видно; **Default Access** — чи діє ієрархія взагалі.
2. У тріалі Zoho One користувачів додають в **Admin Panel → User Management → Users → Add User**, а
   роль і профіль задають у **Setup → General → Users**.
3. Роль і профіль можна будувати вже з одним користувачем; лише видимість записів (A6) доводить
   лише другий і третій.
4. Ієрархія працює вниз: вищий бачить нижчих, нижчий вищих — ні, колеги — лише з
   **Share Data with Peers**.
5. Ієрархія застосовується лише при `Private`; при публічних рівнях її не видно.
6. Адміністратор бачить усе — тести доступу під ним нічого не доводять.
7. Стандартні профілі не редагують — їх клонують.
8. Дозволи профілю діють одразу після перемикання, для всіх людей з цим профілем.
9. Розширені дозволи залежать від базових; розширений дозвіл, який ти вимкнув, не повернеться сам
   після повторного ввімкнення базового.
10. Сховати дію в одному місці не означає заборонити її: перевіряй пряму адресу, застарілу
    сторінку, масові дії та звіти.

спробуй видалити лід без оновлення сторінки; (3) адміністратора зміни не зачепили. Запиши
дослівно всі повідомлення, які показала CRM.

**5.9.** *(A7, здача)* Склади короткий чекліст регресії дозволів — щонайменше 20 перевірок — для

# Розв'язки

**5.1.**
(а) Профіль: модуль вимкнено в **Module Permissions → Basic**.
(б) Роль: ієрархія працює вниз, User B вище за User C і нижче за `CEO`.
(в) **Default Access**: модуль **Leads** «публічний», ієрархія не застосовується.
(г) Профіль: у модулі **Leads** немає дії **Delete**.
(ґ) Виняток для адміністратора: у людини профіль `Administrator`, а він бачить усе незалежно від
ролі. (Друга можлива причина — Sharing Rule, що відкриває їй чужі записи; саме тому правила теж
треба дивитись.)

**5.2.** Очікувані стани: у Zoho One після **Add** — `Pending`, після прийняття запрошення — активний
користувач. У CRM користувач з'являється в **Setup → General → Users**; довідка CRM описує стани
`Unconfirmed` → `Active` (згодом можливі `Inactive` і `Deleted`). Якщо користувача в CRM немає,
перевір призначення застосунку в **Admin Panel** (розділ застосунків → CRM → **⋯** → **Assign
Users**). Точні підписи станів у своєму тріалі запиши такими, як бачиш.

**5.3.** Фінальна конфігурація:

```
Hierarchy Preference: Role Hierarchy
CEO                          <- адміністратор
├── Manager
└── Sales Manager            <- User B, profile Standard
    └── Sales Representative <- User C, profile Standard
```

Ролі створюються в **Setup → Security Control → Roles and Sharing → New Role** з полями **Role
Name**, **Reports To**, **Description**, **Save**. Призначення — **Setup → General → Users** →
користувач → редагування → **Role**, **Profile** → **Save**.

**5.4.**

`Private` (ієрархія діє):

| хто дивиться | `A6-Admin` | `A6-UserB` | `A6-UserC` |
|---|---|---|---|
| адміністратор | так | так | так |
| User B | ні | так | так |
| User C | ні | ні | так |

Змінити `A6-UserB` можуть User B (власник) і адміністратор; User C — ні.

`Public Read Only`: усі троє бачать усі три ліди. Змінити `A6-UserB` можуть власник і адміністратор;
User C лише переглядає.

`Public Read/Write/Delete`: усі бачать усе; змінити (і видалити) `A6-UserB` може кожен, у чийому
профілі є **Edit** (і **Delete**) для лідів. Ієрархія ролей тут непомітна — саме тому для A6 потрібен
`Private`.

**5.5.** Очікувана матриця — як у кроці 8 розділу 5.6. Приклад шапки документа:

```
A6. Implement a minimal hierarchy and verify visibility
Environment: Zoho CRM (Zoho One trial, EU), production org
Preconditions: Role Hierarchy; Leads Default Access = Private (was: <value>)
Users: admin (CEO / Administrator), User B (Sales Manager / Standard),
       User C (Sales Representative / Standard)
Test data: A6-Admin, A6-UserB, A6-UserC (Company: A6 Visibility Test)
Executed: <date, time>
```

| User (role / profile) | Admin's records | User B's records | User C's records | Evidence |
|---|---|---|---|---|
| Admin (CEO / Administrator) | Yes | Yes | Yes | IMG-01 |
| User B (Sales Manager / Standard) | No (direct URL: *message*) | Yes | Yes | IMG-02, IMG-03 |
| User C (Sales Representative / Standard) | No (direct URL: *message*) | No (direct URL: *message*) | Yes | IMG-04, IMG-05 |

Під матрицею — одне речення висновку: «Visibility matches Zoho's role-hierarchy rules: superiors see
subordinates' records, not vice versa; the Administrator profile sees all records.»

**5.6.**
Помилка 1: `Sales Representative` підпорядкована ролі `Manager`, а не `Sales Manager`. User B і
User C опинились у різних гілках, тож User B не бачить записів User C. Виправлення: **Reports To**
`Sales Manager`.
Помилка 2: у ліда `A6-UserC` власник — адміністратор, хоча створив його User C. Видимість рахується
за власником, тож цей лід «належить» адміністратору, і його не бачать ні User B, ні сам User C.
Виправлення: **Lead Owner** `User C`.
Що бачить User B:
- лише після виправлення 1 — ліди, власник яких User C, але не `A6-UserC`: той досі належить
  адміністратору;
- лише після виправлення 2 — нічого з лідів User C: гілки ролей досі різні;
- після обох — `A6-UserB` і `A6-UserC`.

   адресу сторінки експорту, якщо вона є, — та переконайся, що всюди однаково.
Лише після цього можна казати «не можуть вивантажити ліди»; до того — «не бачать кнопки експорту в
