# Урок 15. Погодження в дії: тестові потоки A17 і здача

*Після уроку ти проганяєш усі дев'ять тестових потоків завдання A17 від імені трьох людей —
власника запису, погоджувача й адміністратора — і впізнаєш на екрані блокування, погодження,
відхилення, takeover і повторну подачу. Для QA головне тут довести не «кнопка працює», а «запис
пройшов рівно той маршрут, який налаштовано, і рівно через тих людей», і здати це доказами, які
ніхто не попросить переробити.*

---

## 15.1. Що має бути готове до першого прогону

Кожен тестовий потік спирається на три речі: користувачів, активні процеси й чисті тестові дані.
Бракує однієї — потік впаде не з вини продукту, і ти шукатимеш «баг», якого нема.

### Три людини — три окремі сесії

| хто | що робить у тестах |
|---|---|
| адміністратор (твій обліковий запис, профіль Administrator) | другий етап погодження в сценарії B, rule admin у сценарії C |
| User B | погоджувач у всіх трьох процесах |
| User C | власник записів: створює й редагує їх, отримує лист про відхилення, подає повторно |

Тріал CRM стартує з одним користувачем — тобою. User B і User C додаються не в CRM, а в Zoho One:

1. **Admin Panel → User Management → Users → Add User**. Форма просить **First name**, **Last
   name**, **Email**; прапорець **Send Notification Mail** надсилає людині запрошення. Кнопка
   **+ New User** у CRM (**Setup → General → Users**) відкриває не цю форму, а сторінку адмін-панелі
   **Applications → CRM** з панеллю **Assign CRM to User(s)**.
2. Переконайся, що обом призначено CRM.
3. У CRM, **Setup → General → Users**, задай кожному Role і Profile.

Скриньки мають бути справжні й доступні тобі: User B отримує лист, коли запис чекає його рішення,
а User C — лист про відхилення, без якого потік A-2 не довести. Підійде й тимчасова пошта, якщо
вона проживе, доки ти тестуєш.

Профіль User C має дозволяти створювати Deals, Leads і Contacts та редагувати Contacts. Якщо
раніше ти дав йому обмежений профіль, потік впаде на створенні запису, а не на погодженні.
Погоджувачу особливий профіль не потрібен: за довідкою Zoho, погоджувачем може бути будь-який
користувач CRM незалежно від профілю, і він може погодити запис навіть без доступу до самого запису.
Але правити запис, що чекає (потік C-1), погоджувач може лише в межах свого профілю, тож профіль
User B має дозволяти редагувати Contacts.

Щоб не виходити й не входити щоразу, тримай три окремі сесії: три браузери або три профілі
браузера (приватне вікно — теж окрема сесія). Входь на `crm.zoho.eu`: тріал живе в дата-центрі EU.

### Три активні процеси

Потоки перевіряють ось таку конфігурацію. Перед прогоном відкрий **Setup → Process Management →
Approval Processes**, переконайся, що всі три процеси активні, і звір кожен з таблицею.
Розбіжність тут дасть FAIL, який насправді помилка налаштування.

| | A | B | C |
|---|---|---|---|
| **Approval Process Name** | `High-Value Deal Review` | `Cold Call Lead Validation` | `Cross-Border Contact Edit Review` |
| **Module** | Deals | Leads | Contacts |
| **Send for Approval on** | Create or Edit Record | Create Record | Edit Record |
| **Approval Criteria** (Rule 1) | Amount `>` `10000` | Lead Source is `Cold Call` | Mailing Address - Country / Region isn't `United States` |
| **Approval Stages** | один етап: User B | етап 1: User B; етап 2: адміністратор; **Overall approval flow**: All stages are approved (Everyone) → Sequential | один етап: User B |
| **Action on Final Approval** | Update fields: Stage = `Needs Analysis` | Update fields: Lead Status = `Contacted` | — |
| **Action on Rejection** | Email Notifications → Owner (**To → Deal → Owner**) | Update fields: Lead Status = `Not Contacted` | — |
| **Record Modification Settings** | Allow approvers to edit pending approval records — не позначено | за замовчуванням | позначено, Selected Fields → лише Mailing Address - Country / Region |
| **Assign Admins** | не задано | не задано | адміністратор; Allow rule admins to edit pending approval records → All Fields |

За замовчуванням, за довідкою Zoho, погоджувачі не можуть правити запис, що чекає рішення, а
власник може правити всі поля відхиленого запису (**Allow users to edit rejected records**, All
Fields).

### Тестові дані, що справді щось доводять

Final Action змінює поле — отже, до погодження поле мусить мати інше значення, інакше тест нічого
не покаже:

- угоди створюй зі **Stage** `Qualification`, а не `Needs Analysis`, у pipeline **Standard** (після A12
  `Needs Analysis` є лише в ньому — в іншому pipeline фінальна дія Stage не змінить);
- ліди створюй з **Lead Status** `Attempted to Contact`, а не `Contacted` чи `Not Contacted`.

Давай записам імена, з яких видно потік: `A1-Approve-15000`, `B2-RejectStage1`, `C3-Resubmit`.
У черзі погоджувача, у листах і на скриншотах ти одразу бачиш, що де.

Суми вводь без знака долара. Документ пише `$15,000`, але критерій порівнює число у валюті
організації (у тріалі поле умови показувало префікс UAH). Тож у **Amount** — `15000`.

Якщо на Deals, Leads чи Contacts працює інша автоматизація (workflow rules, blueprint), вона може
змінити ті самі поля. Хто саме змінив поле, показує Timeline запису — зазирни туди, перш ніж
писати «Final Action спрацював».

### Де живуть погодження

- **Workqueue** у лівій навігації → розділ **My Jobs** → **Approvals**. Поруч у My Jobs —
  **Blueprint** і **Review Process**. Окремої вкладки Approvals і модуля My Jobs у тріалі нема,
  хоча довідка Zoho досі так пише.
- Глобальний пошук знаходить пункт `Approvals waiting for you`.
- Сторінка самого запису: статус погодження, список погоджувачів і кнопки **Respond**,
  **Takeover**, **Resubmit** — залежно від того, хто ти і в якому стані запис.

> Очікуй на екрані: банер очікування (`Waiting for your response:
> 0/N`), **Approve/Reject** прямо з рядка черги **Workqueue → My Jobs → Approvals**, **Takeover**
> (з банера картки запису), **Resubmit** і його тост, лист про відхилення (а факт відправки завжди
> видно і в Timeline). Кнопка **Respond** на сторінці самого запису не відкриває видиму панель —
> якщо на екрані назва чи поведінка інша, у **Actual Result** пиши те, що бачиш.

## 15.2. Життя запису на погодженні

```
запис збережено (створено чи відредаговано — як задано в Send for Approval on)
   │
   ├─ не відповідає Approval Criteria ──► звичайне збереження, погодження нема
   │
   └─ відповідає ──► заблоковано, чекає етапу 1
                        │
                        ├─ Reject ──► відхилено: розблоковано, Action on Rejection;
                        │             власник може правити поля й натиснути Resubmit
                        │
                        └─ Approve ──► є ще етап? ── так ──► чекає етапу 2 ── …
                                          │
                                          └─ ні ──► погоджено: розблоковано,
                                                    Action on Final Approval
```

**Подача.** Процес дивиться на запис у момент, заданий у **Send for Approval on**: при створенні,
при редагуванні або в обох випадках. Записи, створені чи змінені до активації процесу, заднім
числом на погодження не йдуть. І навпаки: у процесі з Edit Record або Create or Edit Record уже
погоджений запис після нового редагування, що відповідає критерію, іде на погодження знову.

**Блокування.** Запис, що чекає рішення, позначений значком замка (у списку модуля) і банером
**`Waiting for your response: 0/N`** на сторінці запису (N — кількість етапів правила); **Edit**,
**Delete** і (у лідів) **Convert** недоступні. Погоджувач отримує лист,
що запис чекає на нього.

**Рішення погоджувача.** З черги **Workqueue → My Jobs → Approvals** або зі сторінки запису
(**Respond**) погоджувач обирає **Approve**, **Reject** або **Delegate**. Кожна дія відкриває вікно
з необов'язковим коментарем; коментар можна зберегти ще й як Note у записі, а власник отримує його
листом. Після рішення замість кнопок стоїть позначка Approved чи Rejected: змінити рішення вже не
можна, запис зникає з черги.

**Кілька етапів.** З **Sequential** запис після погодження етапу 1 лишається заблокованим і
переходить до етапу 2; погоджувач етапу 2 до цього моменту не має його серед своїх. **Action on
Final Approval** виконується лише після останнього етапу.

**Відхилення.** Запис розблоковується, попередні погодження анулюються, виконується **Action on
Rejection**. Власник може поправити поля (за замовчуванням — будь-які) і натиснути **Resubmit** на
сторінці запису; ця кнопка доступна 180 днів після відхилення, а **View Reason** показує причину.
Як поводиться відхилення на одному з кількох етапів, задає налаштування процесу: довідка перелічує
варіанти «відхилити всі попередні етапи», «лише поточний» і «дати погоджувачу обрати етап».

**Повторна подача.** Клік на **Resubmit** одразу показує тост **"This record has been resubmitted
for approval."** (підтверджень не питає) — запис спершу перевіряють
на критерій того процесу, яким його відхилили; не підходить — на всі інші правила; не підходить
нікуди — розблоковують.

**Адміністратор.** Користувач з профілем Administrator бачить усі записи, що чекають погодження,
включно з чужими, і може їх погодити чи відхилити. **Takeover** (перехоплення рішення) — дія на
сторінці запису. Якщо в правилі задано rule admins, перехопити можуть лише вони; якщо ні — будь-
який адміністратор.

**Автопогодження.** Запис погоджується сам, якщо погоджувач деактивований або якщо обрана роль чи
група не має користувачів (так перелічує FAQ довідки Zoho). «Погодилось миттєво, хоча ніхто не
натискав» — перевір спершу це. Є ще одна причина, довідкою не описана:
якщо наступний послідовний етап технічно резолвиться в **того самого** користувача, який щойно
погодив попередній етап (наприклад, тип погоджувача другого етапу — Record Owner, а власник запису
той самий адміністратор), Zoho одразу авто-погоджує й цей етап (Timeline показує подію
**"Auto-approved"** без імені виконавця одразу після ручного погодження). Тобто послідовність
етапів у сценарії B не можна перевірити двома різними діями одного облікового запису — потрібні
справді різні User B і Administrator; інакше друге погодження станеться саме собою, і тест нічого
не доведе.

**Зміни процесу.** Зміна правила не зачіпає записи, що вже чекають рішення. Деактивований процес
не подає нові записи, але вже подані лишаються чекати. Видалений процес розблоковує очікуючі
записи, і дії на погодження чи відхилення для них не виконуються.

**Recall.** Довідка описує ще відкликання запису власником (**Recall**), але цю функцію підтримка
Zoho вмикає на запит — у тріалі на неї не розраховуй.

| хто | де бачить запис на погодженні | що може |
|---|---|---|
| User C, власник | у своїх списках — із замком; на сторінці — статус і список погоджувачів | поки запис чекає — нічого; після відхилення — правити поля й **Resubmit** |
| User B, погоджувач | **Workqueue → My Jobs → Approvals**; лист про новий запис | **Approve**, **Reject**, **Delegate**; у сценарії C — правити Mailing Address - Country / Region до рішення |
| адміністратор | усі очікуючі погодження, свої й чужі | погодити чи відхилити будь-який запис; **Takeover** — за правилом вище |

У довідці свої погодження лежать у представленні `My Approvals`, а чужі відкриває посилання `View
records that are awaiting approval by other users`. Як саме це розкладено в Workqueue — дивись, що
покаже екран.

## 15.3. Покроково: сценарій A — High-Value Deal Review

### A-1. Погодити угоду понад 10 000

1. **User C** → **Deals** → нова угода з назвою `A1-Approve-15000`: **Amount** `15000`, **Stage**
   `Qualification`, **Pipeline** — Standard (після A12 лише в ньому є `Needs Analysis`), решта
   обов'язкових полів — як вимагає форма. Збережи.
   **Що побачиш:** угоду збережено й заблоковано: замок, `Waiting for your response: 0/1`, недоступні
   **Edit** і **Delete**. Скриншот `A-1-RecordLocked.png`.
2. **User B** → **Workqueue → My Jobs → Approvals**.
   **Що побачиш:** рядок `A1-Approve-15000 | Deals | <твій користувач> | Today | High-Value Deal Review |
   Approve / Delegate / Reject` (три посилання-дії прямо в рядку списку); у скриньці User B — лист
   про подачу. Скриншот `A-1-PendingForUserB.png`.
3. Натисни посилання **Approve** у рядку → відкриється вікно **"Approve Deal? / Comments / [ ] Add
   my comments as a note in the Deal."** → впиши `Approved for review stage.` → **Approve**.
   **Що побачиш:** дії в рядку заміняються позначкою **Approved**, запис лишається видимим у списку
   (фільтр за замовчуванням — «All», не лише очікувані), але діяти з ним уже нема чого.
4. Відкрий угоду (під User C чи адміністратором).
   **Що побачиш:** **Stage** = `Needs Analysis`, замка нема. Скриншот `A-1-StageNeedsAnalysis.png`.

### A-2. Відхилити угоду понад 10 000

1. **User C** створює `A2-Reject-20000`: **Amount** `20000`, **Stage** `Qualification`.
2. **User B** → **Workqueue → My Jobs → Approvals** → посилання **Reject** у рядку → вікно
   **"Reject Deal? / Comments / Cancel / Reject"** (та сама форма, що й у Approve, без окремого
   поля причини — воно є лише в review process, не в approval process) → впиши, наприклад,
   `Discount terms are not justified.` → **Reject**. Скриншот `A-2-Rejected.png`.
3. **User C** → скринька (або дзвіночок сповіщень у CRM).
   **Що побачиш:** лист, налаштований в **Action on Rejection → Email Notifications** для власника
   угоди (**Owner**). Окремо від нього може прийти системний лист з коментарем погоджувача — розрізняй їх за
   темою. Скриншот `A-2-RejectionEmail.png`. Якщо доступу до самої скриньки нема, у записі на
   вкладці **Timeline** з'являється запис за фактом відправки — **"Email Sent to ⟨власник⟩ using
   Email Notification ⟨назва сповіщення⟩ via Approval Process ⟨назва процесу⟩"** — цього досить,
   щоб довести, що сповіщення пішло, навіть без листа на руках.
4. **User C** відкриває угоду.
   **Що побачиш:** замка нема, банер `Record Rejected: 0/1`, посилання **Resubmit** і **View
   Reason.**, **Edit** доступний; **Stage** лишився
   `Qualification` — на відхилення сценарій A полів не змінює. Скриншот `A-2-RecordUnlocked.png`.

### A-3. Негатив: сума нижче порогу

1. **User C** створює `A3-Below-5000`: **Amount** `5000`.
   **Що побачиш:** звичайне збереження — ні замка, ні банера `Waiting for your response`; у черзі User B нічого
   нового. Скриншот `A-3-NoApproval.png`.

Межа варта двох додаткових записів — `10000` і `10001`: саме на межі найчастіше живуть помилки.

## 15.4. Покроково: сценарій B — Cold Call Lead Validation

### B-1. Два етапи по черзі

Цей потік треба записати на відео: увімкни запис екрана до кроку 1 і не зупиняй до кроку 6. Кроки
нижче працюють, лише якщо User B і Administrator — справді різні акаунти: якщо обидва етапи
резолвяться в одного й того ж користувача, Zoho авто-погоджує другий етап одразу за першим (без
окремої дії адміністратора) — див. «Автопогодження» вище.

1. **User C** → **Leads** → новий лід: **Last Name** `B1-Sequential`, **Lead Source** `Cold Call`,
   **Lead Status** `Attempted to Contact`, решта обов'язкових полів. Збережи.
   **Що побачиш:** лід заблоковано, `Waiting for your response: 0/2`. Скриншот `B-1-RecordLocked.png`.
2. **Адміністратор** → **Workqueue → My Jobs → Approvals** — ще **до** рішення User B.
   **Що побачиш:** серед записів, що чекають саме тебе, `B1-Sequential` нема; як адміністратор ти
   побачиш його лише серед чужих погоджень. Скриншот `B-1-NotYetForAdmin.png`.
3. **User B** → **Workqueue → My Jobs → Approvals** → `B1-Sequential` → **Approve**.
   **Що побачиш:** у черзі User B запис погоджено, але сам лід досі заблокований, а **Lead Status**
   досі `Attempted to Contact` — фінальна дія ще не виконувалась. Скриншот `B-1-Stage1Approved.png`.
4. **Адміністратор** → **Workqueue → My Jobs → Approvals**.
   **Що побачиш:** тепер `B1-Sequential` чекає тебе — це другий етап. Скриншот
   `B-1-Stage2Pending.png`.
5. **Approve**.
6. Відкрий лід.
   **Що побачиш:** замка нема, **Lead Status** = `Contacted`. Скриншот `B-1-LeadStatusContacted.png`.

### B-2. Відхилення на першому етапі

1. **User C** створює `B2-RejectStage1`: **Lead Source** `Cold Call`, **Lead Status** `Attempted to
   Contact`.
2. **User B** → **Workqueue → My Jobs → Approvals** → запис → **Reject**.
   **Що побачиш:** лід розблоковано, **Lead Status** = `Not Contacted`; у черзі адміністратора він
   так і не з'явився. Скриншот `B-2-RejectedNotContacted.png`.

### B-3. Негатив: інше джерело

1. **User C** створює `B3-WebDownload` з **Lead Source** `Web Download`.
   **Що побачиш:** звичайне збереження без замка; у User B нічого нового. Скриншот
   `B-3-NoApproval.png`.

## 15.6. Як це тестувати

### Що доводить завдання

Підсумковий чекліст документа — це вимоги. Під кожну має бути конкретний доказ:

| пункт чекліста | чим доведено |
|---|---|
| усі три процеси створені й активні | скриншот списку **Approval Processes** |
| позитивні потоки виконані | A-1, B-1, C-1 |
| негативні потоки виконані | A-3, B-3 |
| лист про відхилення в сценарії A | A-2, крок 3 |
| послідовність етапів у сценарії B | B-1, кроки 2–4, і відео |

### Де ламається погодження

- **Межа критерію.** `10000` проти `10001`: оператор `>` чи `>=` — різниця в одиницю суми.
- **Тип події.** Лід, змінений на `Cold Call` після створення, і контакт, створений одразу з
  `Germany`, погодження не отримують — так налаштовано. Якщо бізнес чекав іншого, це знахідка про
  вимоги, а не про продукт.
- **Порядок етапів.** До рішення User B запис не має бути в черзі адміністратора як «його».
- **Момент фінальної дії.** Після етапу 1 поле не змінюється; змінилося — фінальну дію поставили
  на етап (**Action on Approval**), а не у **Final Actions**.
- **Дії на відхилення.** Лист саме власнику (A), `Not Contacted` (B).
- **Selected Fields.** Позитив (Mailing Address - Country / Region редагується) без негативу (інші поля — ні) нічого
  не доводить: так само виглядало б і All Fields.
- **Rule admins.** Перехопити в сценарії C може лише адміністратор правила.
- **Повторне блокування.** Погоджена угода з сумою понад поріг після будь-якого редагування знову
  йде на погодження (процес на Create or Edit Record). Для бізнесу це може бути несподіванкою —
  покажи це окремим кейсом.

### Тестуй не від адміністратора

Адміністратор бачить і може погодити все. Якщо весь прогон іти під ним, маршрутизація «запис
пішов до User B» не перевірена взагалі: адміністратор погодив би й запис, який помилково пішов
не туди. Кожен крок роби від імені тієї людини, яку називає документ, а адміністратора бери лише
там, де він сам є учасником.

## 15.7. Типові помилки

**1. Весь прогон під адміністратором.** Він погодить будь-що, тож маршрутизацію така перевірка не
доводить.

**2. Початкове значення дорівнює фінальному.** Угода, створена одразу з `Needs Analysis`, «пройде»
A-1 навіть без фінальної дії.

**3. Пошук вкладки Approvals.** Її нема, як і модуля My Jobs: черга — у **Workqueue → My Jobs**.

**4. Очікування фінальної дії після етапу 1.** У сценарії B **Lead Status** змінюється лише після
останнього етапу.

**5. Зміна ліда на `Cold Call` як позитивний тест.** Процес B реагує тільки на створення; такий лід
на погодження не піде, і FAIL тут буде хибним.

**6. Контакт одразу з `Germany`.** Процес C реагує тільки на редагування.

**7. Selected Fields лише позитивом.** Без скриншота, що інші поля заблоковані, пункт чекліста не
доведено.

**8. Takeover шукають лише в черзі.** Довідка описує цю дію на сторінці запису; і коли rule admins
задано, вона є лише в них.

**9. Недоступна скринька User C.** Лист про відхилення тоді не довести, і A-2 лишиться BLOCKED.

**10. Скриншоти без імен і часу.** Через тиждень ніхто, включно з тобою, не скаже, який з п'яти
«заблокованих лідів» належить якому потоку.

### Симптом → причина

| симптом | найімовірніша причина |
|---|---|
| угоду з **Amount** `15000` збережено без замка | процес неактивний, критерій не той (`<`, інше поле) або не той модуль |
| запис погодився сам, ніхто не натискав | погоджувач деактивований або роль/група без користувачів |
| у **Workqueue → My Jobs → Approvals** User B порожньо, хоча запис заблоковано | запис чекає іншого погоджувача або іншого етапу; на сторінці запису видно, кого саме |
| адміністратор бачить лід B до рішення User B | він дивиться чужі погодження — для адміністратора це нормально; перевір свою чергу |
| **Lead Status** змінився одразу після рішення User B | дію поставили на етап, а не у **Final Actions** |
| **Stage** угоди не змінився після погодження | дія на погодження не налаштована; угода в pipeline без стадії `Needs Analysis` (після A12 — бери **Standard**); або поле змінила інша автоматизація — дивись Timeline |
| лід з `Cold Call` не пішов на погодження | його змінили на `Cold Call` після створення, а процес на Create Record |
| контакт з `Germany` не пішов на погодження | його створили з `Germany`, а процес на Edit Record |
| User B може правити всі поля контакту | у **Record Modification Settings** обрано All Fields замість Selected Fields |
| User B не може змінити Mailing Address - Country / Region в записі, що чекає | не позначено **Allow approvers to edit pending approval records**, у **Selected Fields** нема Mailing Address - Country / Region або профіль User B не дозволяє редагувати Contacts |
| **Takeover** нема в адміністратора | у правилі задано rule admins, і він не серед них |
| **Resubmit** нема на відхиленому записі | ти не власник запису або минуло понад 180 днів |
| після **Resubmit** запис одразу розблоковано | він уже не відповідає жодному критерію (наприклад, країну повернули на `United States`) |
| лист про відхилення не прийшов | скринька User C недоступна чи в спамі, або лист у **Action on Rejection** адресований не власнику угоди (**To → Deal → Owner**) |
| посилання на папку просить увійти | доступ за посиланням не ввімкнено |

## 15.8. Що варто запам'ятати

1. Погодження в тріалі — **Workqueue → My Jobs → Approvals**; вкладки Approvals і модуля My Jobs
   нема.
2. Запис, що чекає рішення, заблокований: замок, банером `Waiting for your response: 0/N`, без **Edit**, **Delete**
   і (у лідів) **Convert**.
3. **Send for Approval on** вирішує, чи піде запис на погодження при створенні, редагуванні чи
   обох.
4. **Sequential**: етап 2 бачить запис як свій лише після етапу 1; **Final Actions** — після
   останнього етапу.
5. Відхилення розблоковує запис; **Resubmit** — 180 днів; повторна подача спершу дивиться на
   критерій того самого процесу.
6. Адміністратор бачить і може погодити все, тож маршрути доводь від імені погоджувачів.
7. **Takeover** — на сторінці запису; з rule admins — лише для них.
8. Selected Fields доводять позитив плюс негатив.
9. Кожен кейс, що перевіряє поле, починай з іншого значення, ніж поставить фінальна дія.
10. Докази: ім'я за шаблоном, час у **Actual Result**, відео для B, публічне посилання на папку.
