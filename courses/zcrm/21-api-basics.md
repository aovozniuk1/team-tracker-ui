# Урок 21. API Zoho CRM v8: REST, OAuth 2.0, ліміти і Postman

*Після уроку ти читаєш будь-який запит до Zoho CRM API — метод, адресу, заголовки, тіло, —
розумієш, як працюють токени OAuth 2.0 і скоупи, рахуєш кредити сесії тестування, знаходиш
витрату в API Dashboard і знаєш, що перевіряти у відповіді. Для QA це фундамент: API-тести швидші
за UI, бачать те, чого не видно на екрані, і ловлять помилки інтеграцій, через які записи
потрапляють у CRM.*

## Коротко

*Картка уроку: прочитай її перед уроком і повернись до неї після.*

**Одним реченням.** REST API — спосіб, яким програми через HTTP і JSON створюють, читають, змінюють і видаляють дані CRM без інтерфейсу.

**Навіщо.** Частина записів приходить з інтеграцій, і їхні помилки не видно в UI; API-тести швидші й перевіряють логіку окремо від екранів.

**Де.** Документація `https://www.zoho.com/crm/developer/docs/api/v8/`; у тріалі **Setup → Developer Hub → APIs and SDKs → CRM API** (**Dashboard**, **API names**).

**Модель**

- **Grant token** — одноразовий код згоди на скоупи; живе хвилини, обмінюється на токени.
- **Access token** — ключ у кожному запиті (`Zoho-oauthtoken`); діє одну годину.
- **Refresh token** — отримує нові access token; не спливає, доки його не відкличуть.
- **Scope** — що дозволено токену: `служба.назва.операція`, наприклад `ZohoCRM.modules.ALL`.
- **Кредит** — одиниця витрати API; добовий ліміт — ковзні 24 години (тріал — 60 000).

**Запам'ятай**

1. Запит = метод + URL + заголовки + тіло; записи в тілі — завжди в масиві `data`.
2. У шляху й JSON — лише API-імена (`Leads`, `Last_Name`), а не підписи з інтерфейсу.
3. HTTP-код один на весь запит, `status` — у кожного запису; 207 означає частковий успіх.
4. Весь ланцюжок — один дата-центр: у нас `api-console.zoho.eu`, `accounts.zoho.eu`, `www.zohoapis.eu`.
5. Кожну зміну підтверджуй окремим GET: «success» ще не доводить, що дані збереглися.

**Пастки** (симптом → причина)

- 401 на запит, що вчора працював → access token прожив годину; онови його через refresh token.
- 401 `OAUTH_SCOPE_MISMATCH` → токену бракує скоупу (для пошуку — ще `ZohoSearch.securesearch.READ`); лікує лише новий grant token.
- 400 `REQUIRED_PARAM_MISSING` на GET списку → у v8 не передано обов'язковий параметр `fields`.

**Як перевірити**

- POST ліда → код, `data[0].status` = `success`, є `details.id`; потім GET за id — значення поле за полем.
- POST без `Last_Name` → 400 `MANDATORY_NOT_FOUND` з `message`, запис не створено.

## 21.1. Що таке API і навіщо він CRM

**API** (Application Programming Interface) — набір правил, за якими одна програма розмовляє з
іншою. Замість кліків і форм — структурований запит на сервер і структурована відповідь. Через API
Zoho CRM зовнішні програми — сайти, мобільні застосунки, сховища даних, інструменти тестування на
кшталт Postman — створюють, читають, змінюють і видаляють дані CRM, не відкриваючи інтерфейс.
Класичний приклад: людина заповнює форму на сайті компанії, сайт викликає API, і за секунди в CRM
з'являється лід.

Для QA з цього випливає важливе: частина записів у справжній CRM приходить не з UI, а з інтеграцій.
Помилку інтеграції не видно на екрані, доки вона не зіпсує дані. І навпаки, через API можна
перевірити бізнес-логіку окремо від того, як намальований інтерфейс.

Zoho CRM має **REST API** (Representational State Transfer) — найпоширеніший вид веб-API. REST
працює поверх HTTP, того самого протоколу, яким браузер завантажує сторінки, а дані передає у
форматі **JSON**. Поточна версія API — **v8**. Документація:
`https://www.zoho.com/crm/developer/docs/api/v8/`, повний перелік ендпоінтів —
`https://www.zoho.com/crm/developer/docs/api/v8/api-references.html`.
Посилання на документацію лишаються на `.com`, навіть коли твій тріал у європейському дата-центрі.

Сторінки, на які посилається завдання (усі — під `https://www.zoho.com/crm/developer/docs/api/v8/`):

| тема | сторінка |
|---|---|

| реєстрація клієнта | `register-client.html` |
| grant token для Self Client | `auth-request.html` |
| отримання access і refresh token | `access-refresh.html` |
| строки дії токенів і обмеження | `token-validity.html` |
| перелік скоупів | `scopes.html` |
| ліміти й кредити, калькулятор кредитів | `api-limits.html` |
| API Dashboard | `dashboards.html` |
| коди статусу й помилок | `status-codes.html` |
| конвертація ліда | `convert-lead.html` |
| Postman-колекція Zoho | `api-collection.html` |
| COQL | `COQL-Overview.html` |
| Bulk Read | `bulk-read/overview.html` |

## 21.2. Як влаштовані запит і відповідь

Запит складається з чотирьох частин.

**1. Метод (HTTP method)** — що ти хочеш зробити.

| метод | зміст | приклад у Zoho CRM v8 |
|---|---|---|
| GET | отримати дані | `GET /crm/v8/Leads/{record_id}` — один лід |
| POST | створити або виконати дію | `POST /crm/v8/Leads` — нові ліди; `POST /crm/v8/Leads/{record_id}/actions/convert` — конвертація |
| PUT | змінити наявне | `PUT /crm/v8/Leads/{record_id}` — оновити лід |
| DELETE | видалити | `DELETE /crm/v8/Leads?ids={record_id}` |

Не вгадуй метод за змістом операції. Запит COQL «отримує» записи, але надсилається методом POST —
ти «постиш» запит; додавання і зняття тегів — теж POST. Метод завжди звіряй з документацією
ендпоінта.

**2. URL (endpoint)** — адреса ресурсу. База, версія і шлях разом визначають операцію:

```
https://www.zohoapis.eu | /crm/v8 | /Leads | /4150868000001944196
API domain (EU)         | версія  | модуль | ID запису
```

(У справжній адресі частини йдуть підряд: `https://www.zohoapis.eu/crm/v8/Leads/4150868000001944196`.)

Наш тріал живе в європейському дата-центрі, тому API domain — `https://www.zohoapis.eu`. Приклади в
документації Zoho написані для США (`https://www.zohoapis.com`) — доменну частину в них замінюєш.
Для sandbox домен інший: за документацією, `sandbox.zohoapis.eu`.

У шляху і в JSON використовуються **API-імена**, а не підписи з інтерфейсу: модуль `Leads`, поля
`Last_Name`, `Lead_Source`, `Lead_Status`. Підпис «Last Name» з пробілом API не зрозуміє. Модуль
угод в інтерфейсі й API зветься **Deals**; назва Potentials — стара. API-імена шукай у **Setup →
Developer Hub → APIs and SDKs → CRM API**, вкладка **API names**: клацни модуль, і відкриється
список його полів (**Filter By:** модуль, `Fields`, `All Layouts`) з колонками **Field Label**,
**API Name**, **Data Type** і **Custom Field**. Друге джерело — метадані полів через API.

**3. Заголовки (headers)** — службові дані запиту. Для Zoho CRM головні два:

- `Authorization: Zoho-oauthtoken <access_token>` — токен доступу. Такий префікс стоїть у кожному
   прикладі документації CRM API v8. Сторінка про access і refresh token на початку згадує й
   передачу токена як `Bearer`, а у відповіді з токеном `token_type` дорівнює `Bearer`, але далі
   та сама сторінка вимагає `Zoho-oauthtoken {access_token}` — тримайся його;
- `Content-Type: application/json` — формат тіла для POST і PUT з JSON.

**4. Тіло (body)** — дані для POST і PUT. Записи завжди загорнуті в масив `data`, навіть якщо
запис один:

```json
{
  "data": [
    { "Last_Name": "Mueller", "Company": "Deutsche Tech GmbH", "Email": "h.mueller@deutschetech.example" }
  ]
}
```

За один виклик insert, update чи upsert — до 100 записів.

### Відповідь

Відповідь має **HTTP-код** і **тіло**. Коди за документацією v8:

| код | значення |
|---|---|
| 200 OK | запит успішний |
| 201 Created | запис додано (`record added`) |
| 202 Accepted | запит прийнято, обробка ще триває |
| 204 No Content | даних для відповіді немає |
| 207 Multi-Status | частковий успіх: частина записів пройшла, частина ні |
| 304 Not Modified | ресурс не змінювався після часу в If-Modified-Since |
| 400 Bad Request | некоректний запит або дані (сюди ж INVALID_DATA, MANDATORY_NOT_FOUND тощо) |
| 401 | помилка авторизації |
| 403 Forbidden | немає прав на операцію |
| 404 Not Found | невірний запит |
| 405 Method Not Allowed | метод для цієї адреси не дозволено |
| 413 / 415 | файл завеликий / тип файлу не підтримується |
| 429 Too Many Requests | вичерпано добові кредити або ліміт одночасних запитів |
| 500 Internal Server Error | несподівана помилка сервера |

Тіло для записів має масив `data` (кожен елемент — один запис) і, для списків, об'єкт `info` з
пагінацією: `page`, `per_page`, `count`, `more_records` та інші ключі. Відповідь на створення, зміну
чи видалення містить для **кожного** запису свій `code`, `details`, `message` і `status`. Ось
успішне створення, скорочено за прикладом з документації:

```json
{
  "data": [
    {
      "code": "SUCCESS",
      "details": {
        "Created_Time": "2022-03-13T01:47:05+05:30",
        "id": "3652397000007549434"
      },
      "message": "record added",
      "status": "success"
    }
  ]
}
```

Три наслідки для тестування:

- **HTTP-код один на весь запит, а статус — у кожного запису.** Якщо з трьох лідів один не
   створився, документація обіцяє 207 Multi-Status, а подробиці — в елементі масиву. Перевіряти
   треба кожен елемент.
- **Помилка теж має структуру:** машинний `code` (наприклад, `MANDATORY_NOT_FOUND`), людський
   `message`, часто — `details` з уточненням. На сторінці кожного ендпоінта є розділ Possible Errors:
   коди, HTTP-статуси і як виправити.
- **Метадані виглядають інакше.** Список модулів приходить у масиві `modules`, поля — у `fields`,
   дані організації — в `org`, теги — в `tags`. «Масив data і об'єкт info» — правило для записів, а
   не для всього API.

## 21.3. OAuth 2.0: як програма доводить право на дані

Перш ніж читати дані CRM, програма має довести, хто вона і що їй дозволено. Zoho CRM використовує
**OAuth 2.0** — галузевий стандарт делегованого доступу. Чому не просто логін і пароль (документація
v8):

- клієнту не треба знати пароль користувача чи зберігати його;
- доступ делегований: лише до того, що дозволив користувач;
- користувач може відкликати доступ будь-коли;
- токени спливають: якщо клієнта зламали, дані під загрозою лише доки дійсний токен.

**Терміни.**

| термін | що це |
|---|---|
| Client | програма, яка звертається до API від імені користувача (у нас — твої запити в Postman) |
| Client ID / Client Secret | «логін і пароль» клієнта; видаються при реєстрації клієнта в API Console |
| Grant token (authorization code) | короткоживучий одноразовий код, що підтверджує згоду користувача на скоупи |
| Access token | ключ, який іде в кожному запиті; дійсний одну годину |
| Refresh token | довгоживучий ключ для отримання нових access token; не спливає, доки його не відкличуть |
| Scope | що саме дозволено токену |

**Потік для нашого випадку:**

```
1. Реєструєш клієнта в API Console (https://api-console.zoho.eu)        → Client ID + Client Secret
2. Генеруєш grant token зі скоупами (Self Client → Generate Code)        → code, одноразовий
3. POST https://accounts.zoho.eu/oauth/v2/token, grant_type=authorization_code
                                                                         → access_token + refresh_token
4. Кожен запит до API: Authorization: Zoho-oauthtoken <access_token>
5. Через годину: POST https://accounts.zoho.eu/oauth/v2/token, grant_type=refresh_token
                                                                         → новий access_token
```

**Типи клієнтів** (документація): Client-based (у браузері), Server-based (веб-застосунок для
багатьох акаунтів), Mobile-based, Non-browser Mobile (пристрої без браузера; у консолі картка
зветься **Non-browser Applications**) і **Self Client** — клієнт без redirect URL і без
веб-інтерфейсу, для бекенд-задач, коли застосунок і акаунт Zoho в руках однієї людини. Для ручного
тестування API саме він.

**Правила дійсності токенів** (сторінка Token Validity документації v8):

| токен | строк | обмеження |
|---|---|---|
| grant token | за замовчуванням 3 хвилини; для Self Client можна обрати довший строк у випадному списку **Code expiry duration** (3, 5, 7 або 10 minutes) | одноразовий; до 10 grant tokens за 10 хвилин на один Client ID, далі `access_denied` |
| access token | 1 година | до 15 активних на один refresh token (16-й робить недійсним найстаріший); з одного refresh token — до 10 нових за 10 хвилин, далі `Access Denied` |
| refresh token | не спливає, доки користувач його не відкличе | до 20 на користувача: 21-й робить недійсним найперший |

Ще три правила, які рятують від годин налагодження:

- **Дата-центр — один на весь ланцюжок.** Клієнт, grant token і обмін на токени мають бути в тому
   самому дата-центрі. Згенерував код в `api-console.zoho.eu`, а міняєш на `accounts.zoho.com` —
   отримаєш `invalid_client`. Для EU: консоль `https://api-console.zoho.eu`, акаунти
   `https://accounts.zoho.eu`, API `https://www.zohoapis.eu`.
- **Токени прив'язані до організації і середовища.** Токени для продакшн-організації не працюють для
   sandbox і навпаки; для Self Client при генерації коду обираєш організацію явно.
- **Refresh token можна відкликати:** `POST {accounts_URL}/oauth/v2/token/revoke?token={refresh_token}`.

**Безпека.** Access token — ключ до даних CRM. Документація прямо забороняє показувати його на
форумах, у публічних репозиторіях чи клієнтському коді. Для тестувальника це означає: токени і
Client Secret не потрапляють ні на скриншоти, ні в експортовані файли, ні в чат.

## 21.4. Скоупи: рівно стільки прав, скільки треба

Скоуп має формат `служба.назва.операція`: у `ZohoCRM.modules.ALL` служба — `ZohoCRM`, назва —
`modules`, операція — `ALL`. Операції: `ALL`, `CREATE`, `READ`, `UPDATE`, `DELETE` (ALL — усе).

- **Груповий скоуп** дає доступ до всіх модулів: `ZohoCRM.modules.ALL`, `ZohoCRM.modules.READ`.
- **Окремий скоуп** — лише до одного модуля: `ZohoCRM.modules.leads.READ`,
   `ZohoCRM.modules.deals.ALL`.
- **Кілька скоупів** пишуться через кому без пробілів: `ZohoCRM.modules.READ,ZohoCRM.settings.READ`.

Родини скоупів у документації: `users`, `org`, `settings` (з підвидами на кшталт `settings.fields`,
`settings.modules`, `settings.tags`, `settings.related_lists`), `modules` (з підвидами за модулями,
зокрема `modules.notes`), `bulk` (`ALL`, `READ`, `CREATE`), `notifications`, `coql` (`READ`).

Принцип найменших привілеїв: інтеграція сайту, яка лише створює ліди, не повинна вміти видаляти
угоди. Для навчального набору з багатьох різних операцій беруть ширші скоупи, але логіка «яка
операція — який скоуп» має бути в голові:

| операція | скоуп за документацією v8 |
|---|---|
| дані організації (`GET /org`) | `ZohoCRM.org.READ` або `.ALL` |
| список модулів, метадані полів | `ZohoCRM.settings.ALL` або `settings.modules` / `settings.fields` |
| записи: створити, читати, змінити, видалити; теги на записах; нотатки; конвертація | `ZohoCRM.modules.ALL` або скоупи окремих модулів (для нотаток тоді ще `ZohoCRM.modules.notes...`) |
| створити тег (`/settings/tags`) | `ZohoCRM.settings.ALL` або `settings.tags` |
| COQL | `ZohoCRM.coql.READ` **і** доступ до модулів (`ZohoCRM.modules...`) |
| Bulk Read | `ZohoCRM.bulk.read` і доступ до модуля |
| Search Records | доступ до модуля **і** `ZohoSearch.securesearch.READ` |

Останній рядок варто запам'ятати: пошук вимагає скоупу іншої служби — `ZohoSearch`. Бракує
скоупу — API відповідає помилкою `OAUTH_SCOPE_MISMATCH` (HTTP 401), і лікується це лише новим grant
token з потрібним скоупом.

## 21.5. Ліміти і кредити

Zoho CRM рахує використання API в **кредитах**. Кожен виклик списує кредити; більшість — один,
важкі операції — більше. Витяг з таблиці документації v8:

| виклик | кредити |
|---|---|
| більшість викликів (отримати записи, метадані, пошук, «усі інші API») | 1 |
| Insert / Update / Upsert | 1 за кожні 10 записів (до 100 записів у виклику) |
| Get Records з параметром cvid | 3 |
| Convert Lead | 5 |
| COQL-запит | LIMIT 1–200 — 1; 201–1000 — 2; 1001–2000 — 3 |
| Send Mail | 20 |
| Bulk Read Initialize (створення завдання експорту) | 50 |
| Mass Convert Leads | 200 |
| Bulk Write Initialize | 500 |

**Добовий ліміт** рахується в ковзному вікні 24 години від моменту виклику і залежить від
редакції та кількості ліцензій. Для Enterprise / Zoho One: 50 000 + 1 000 за кожну ліцензію
користувача + докуплені кредити, максимум 5 000 000. Тріал має ті самі ліміти, що й відповідна
платна редакція. У нашому тріалі API Dashboard показує добовий ліміт 60 000 — за формулою це
відповідає 10 ліцензіям.

Коли використано 50% і більше добового ліміту, у відповідях з'являється заголовок
`X-API-CREDITS-REMAINING` з залишком. Кредити витрачають і integration tasks у функціях Deluge.

**Одночасність (concurrency).** Крім кредитів, обмежено кількість викликів, що виконуються
одночасно в межах організації і застосунку: для Enterprise / Zoho One — 20. Для важких API (Convert
Lead, COQL, insert/update/upsert понад 10 записів, Get Records з cvid або sort_by, Send Mail,
Composite API, пошук з функції) діє ще **sub-concurrency** — 10. Перевищив — `TOO_MANY_REQUESTS`
(HTTP 429). Поминутного ліміту немає: скільки завгодно викликів на хвилину, якщо одночасних не
забагато.

Що це означає для тестувальника: один Bulk Read коштує як 50 звичайних запитів, а скрипт, що
зациклився, спалює кредити тисячами. Витрату планують і перевіряють.

## 21.7. Що таке API-тестування і що перевіряти

**API-тестування** перевіряє поведінку програмного інтерфейсу напряму, без UI. UI-тест перевіряє те,
що бачить і натискає людина; API-тест — логіку, обробку даних, безпеку і надійність на рівні
сервісу. Навіщо воно:

- ловить проблеми раніше, ще до готового інтерфейсу;
- швидше: виклик API — мілісекунди, дія в UI — секунди;
- перевіряє бізнес-логіку незалежно від вигляду екранів;
- перевіряє інтеграції (сайт → CRM);
- покриває те, що в UI не зробити: зламаний JSON, прострочений токен, одночасні запити.

**Що перевіряти в кожному запиті:**

1. **Функціональна коректність.** API робить те, що обіцяє документація: POST створив лід — GET його
   повертає; DELETE видалив — GET більше не знаходить.
2. **Коди статусу.** Для кожного сценарію свій правильний код: створення — 201 за таблицею кодів
   (або 200, якщо так відповідає ендпоінт — фіксуй фактичний), неавторизований запит — 401, а не 200.
3. **Структура відповіді.** Відповідає документованій: є очікувані ключі, типи правильні (рядок,
   число, boolean, масив). ID записів у прикладах документації — рядки.
4. **Цілісність даних.** Значення у відповіді дорівнюють надісланим поле за полем. Створив лід з
   Last_Name `Mueller` — GET повертає `Mueller`. Оновив одне поле — решта не змінилися. Стеж за
   picklist: у метаданих кожне значення має `display_value` і `actual_value`, і вони можуть
   відрізнятися (у прикладі документації: `Shut Down` і `ShutDown`).
5. **Обробка помилок.** Порожнє тіло, пропущене обов'язкове поле, прострочений токен, неіснуючий
   запис — у відповіді зрозумілий машинний `code` і людський `message`.
6. **Негативне тестування.** Навмисно погані дані: зламаний JSON, перевищена довжина поля (за
   документацією — `INVALID_DATA`), неправильні типи, операція без прав (`NO_PERMISSION`, 403), без
   скоупу (`OAUTH_SCOPE_MISMATCH`, 401).

І одна особливість Zoho, про яку часто забувають: записи, створені чи змінені через API, **запускають
автоматизацію**. За документацією insert виконує пов'язані workflow, якщо не передати `"trigger":
[]`, а оновлені записи за замовчуванням потрапляють у review process (довідка про Review Process
каже, що рев'ю — лише для нових записів, урок 16; перевір окремим тестом). Правила, процеси і Blueprint,
налаштовані в тріалі раніше, реагуватимуть і на твої тестові записи — це треба враховувати, коли
результат здається дивним.

## 21.8. Postman і колекція Zoho

**Postman** — десктопний застосунок для ручного тестування API. Що в ньому знадобиться:

| можливість | навіщо |
|---|---|
| запит: метод, URL, вкладки Params, Authorization, Headers, Body | зібрати будь-який виклик |
| **Collection** з папками | упорядкувати запити: одна папка — одне завдання |
| **Environment** і змінні `{{назва}}` | тримати домени, токени й ID поза запитами і міняти їх в одному місці |
| авторизація на рівні колекції | задати токен один раз — запити колекції його успадковують |
| скрипти після відповіді | зберегти ID з відповіді в змінну, автоматично перевірити статус і поля |
| Save Response | зберегти відповідь (наприклад, файл експорту) на диск |
| Postman Console | побачити, що насправді пішло на сервер |

**Офіційна колекція Zoho.** Zoho публікує Postman-колекцію CRM API (документація: сторінка
api-collection). У Postman шукаєш `Zoho Developers`, відкриваєш workspace **Zoho CRM Developers**,
колекцію **Zoho CRM REST APIs** і робиш **Create a fork**. Далі налаштовуєш environment зі змінними
`client-id`, `client-secret`, `redirect-uri`, `authorization-code`, `access-token`, `refresh-token`,
`accounts-url`, `api-domain`, `expiry-time`; після запиту на генерацію токенів колекція сама
заповнює `access-token`, `refresh-token` і `expiry-time`. Запити розкладено по папках за версіями
API. Колекція — зручний довідник готових запитів, але документацію вона не замінює.

## 21.9. Ключові поняття Zoho CRM API для QA

**Модулі й ендпоінти.** Кожен модуль має свій ендпоінт: `/crm/v8/Leads`, `/crm/v8/Deals`.
Метадані — під `/crm/v8/settings/...`: `/settings/modules`, `/settings/fields?module=Leads`,
`/settings/tags?module=Deals`. У v8 при отриманні **списку** записів параметр `fields` обов'язковий
(до 50 API-імен через кому); без нього — `REQUIRED_PARAM_MISSING`. На сторінці — до 200 записів
(`per_page`), параметром `page` без `page_token` — до 2000 записів.

**COQL (CRM Object Query Language)** — SQL-подібні запити SELECT до CRM. Надсилаються
`POST /crm/v8/coql` з тілом `{"select_query": "..."}`. Що варто знати (документація v8):

- використовуються API-імена модулів і полів; `select Last_Name, Company from Leads where ...`;
- JOIN — через lookup-поле і крапку: `Account_Name.Account_Name` у Contacts дає назву акаунта;
- агрегати `SUM`, `AVG`, `COUNT`, `MIN`, `MAX`; назви агрегатних функцій чутливі до регістру; якщо в
   SELECT є агрегат і звичайне поле — потрібен `GROUP BY`;
- `LIMIT` за замовчуванням 200, максимум 2000, синтаксис `limit offset, limit`;
- у `WHERE` до 25 умов; три і більше — з дужками: `((A and B) and C)`;
- багаторядкові поля (зокрема `Description`) в умовах використовувати не можна;
- відповідь — `data` і `info` з `count` та `more_records`; помилки — `SYNTAX_ERROR`, `INVALID_QUERY`
   (невідоме поле, непідтримуваний тип, неправильний оператор), `LIMIT_EXCEEDED`.

**Search чи COQL.** Search Records шукає в одному модулі за `criteria`, `email`, `phone` або `word`.
Нюанси з документації: `equals` у пошуку поводиться як «містить» (Company:equals:ABC знайде і `ABC`, і
`ABC Inc`), крім picklist; `word` — щонайменше два символи; одразу після створення запису пошук може
повернути 204 через затримку індексації, а COQL такої затримки не має.

**Bulk API** — асинхронні операції з великими обсягами. **Bulk Read** експортує записи модуля у
файл, **Bulk Write** імпортує з файлу. Bulk Read іде в три кроки:

```
POST /crm/bulk/v8/read                → завдання створено, state = ADDED, отримуєш job id
GET  /crm/bulk/v8/read/{job_id}       → state: ADDED → QUEUED → IN PROGRESS → COMPLETED; result.download_url
GET  /crm/bulk/v8/read/{job_id}/result → ZIP-архів із CSV (колонку id додано автоматично)
```

Зверни увагу на шлях: `/crm/bulk/v8/`, а не `/crm/v8/`. Одне завдання — до 200 000 записів;
створення завдання коштує 50 кредитів; завантажувати результат можна не частіше 10 разів на хвилину.

**Upsert** — «вставити або оновити»: `POST /crm/v8/{module}/upsert`. Якщо запис із таким самим
значенням поля перевірки дублікатів уже є — він оновлюється, якщо ні — створюється новий. Системні
поля перевірки: Leads і Contacts — `Email`, Accounts — `Account_Name`, Deals — `Deal_Name`. Порядок
перевірки задає масив `duplicate_check_fields`. У відповіді кожного запису є `action` (`insert` або
`update`) і `duplicate_field`. Для інтеграцій це головний захист від дублікатів.

## 21.10. Як це тестувати: план API-сесії

**До сесії.**

- середовище: домени EU, змінні, дійсний access token, потрібні скоупи;
- бюджет кредитів: скільки коштує план (особливо Bulk Read, конвертація, великі COQL);
- тестові дані: впізнавані назви й адреси (`*.example`), план прибирання;
- знімок API Dashboard «до».

**Під час сесії.**

- один запит — один чекліст: метод, URL, авторизація, тіло → код, структура, `status` кожного
   запису, ID, значення поле за полем;
- кожну зміну підтверджуй окремим GET: відповідь «success» ще не доводить, що дані збереглися;
- ID з відповідей — у змінні, а не вручну в URL;
- запит і відповідь — у доказах (без токенів).

**Після сесії.** Знімок Dashboard «після», прибирання тестових записів, таблиця результатів.

## 21.11. Типові помилки

**1. Домен не того дата-центру.** Приклад з документації скопійовано з `www.zohoapis.com`, а тріал
в EU.

**2. Токен без префікса.** У заголовку лише сам токен, без `Zoho-oauthtoken` перед ним (часто так
буває в полі Value авторизації колекції). Документація CRM API v8 вимагає
`Authorization: Zoho-oauthtoken <token>`.

**3. Підписи замість API-імен.** `"Last Name"` чи `"Lead Status"` у JSON — API їх не знає. Потрібні
`Last_Name`, `Lead_Status`.

**4. Тіло без масиву `data`.** Навіть один запис загортається в `{"data": [ ... ]}`.

**5. Список без `fields`.** У v8 отримання списку записів без параметра `fields` — помилка.

**6. Довіра до HTTP-коду.** 200 чи 201 на пакет із трьох записів не означає, що створено три.
Дивись `status` кожного елемента.

**7. Повторне використання grant token.** Він одноразовий і живе хвилини; друга спроба — `invalid_code`.

**8. Забутий скоуп.** Пошук без `ZohoSearch.securesearch.READ`, COQL без `ZohoCRM.coql.READ` — 401
`OAUTH_SCOPE_MISMATCH`.

**9. Кредити «зникли».** Bulk Read за 50 кредитів кожен, цикл у скрипті, COQL з великим LIMIT.

**10. Токен на скриншоті чи в експорті.** Це витік ключа до даних; такий токен треба відкликати.

### Симптом → причина

| симптом | найімовірніша причина |
|---|---|
| `invalid_client` при обміні коду на токени | неправильні Client ID / Secret або різні дата-центри (консоль .eu, обмін на .com) |
| `invalid_code` | grant token прострочений, уже використаний; або при оновленні — хибний чи відкликаний refresh token |
| `Access Denied` з текстом про надто часті запити | понад 10 access token з одного refresh token за 10 хвилин |
| `access_denied` при генерації коду | понад 10 grant token за 10 хвилин на один Client ID |
| 401 на будь-який запит, що вчора працював | access token прожив годину — онови його |
| 401 `OAUTH_SCOPE_MISMATCH` | токену бракує скоупу для цього ендпоінта |
| 400 `REQUIRED_PARAM_MISSING` на GET списку | немає параметра `fields` |
| 400 `INVALID_MODULE` | помилка в API-імені модуля (`Lead` замість `Leads`) |
| 400 `MANDATORY_NOT_FOUND` | бракує обов'язкового поля (для Leads системно обов'язковий `Last_Name`) |
| 400 `INVALID_DATA` | неправильний тип, задовге значення, невірний ID |
| 207 на пакетний запис | частина записів не пройшла — дивись елементи `data` |
| 204 на пошук щойно створеного запису | затримка індексації пошуку; перевір пізніше або через COQL |
| 429 `TOO_MANY_REQUESTS` | вичерпано кредити або забагато одночасних важких запитів |
| Dashboard не показує щойно зроблених викликів | статистика оновлюється із затримкою 15 хвилин |

## 21.12. Що варто запам'ятати

1. REST API Zoho CRM: HTTP + JSON, поточна версія v8; для нашого тріалу — домени `.eu`.
2. Запит = метод + URL + заголовки + тіло; у JSON і шляхах — лише API-імена.
3. Заголовок авторизації — `Zoho-oauthtoken <access_token>`; записи в тілі — у масиві `data`.
4. HTTP-код один на запит, статус — у кожного запису; 207 — частковий успіх.
5. OAuth 2.0: Client ID/Secret → одноразовий grant token → access (1 година) + refresh (до
   відкликання).
6. Токени прив'язані до дата-центру, організації і середовища.
7. Скоуп = служба.назва.операція; пошук вимагає `ZohoSearch.securesearch.READ`.
8. Кредити: більшість викликів — 1, Convert Lead — 5, Bulk Read — 50; ліміт — ковзні 24 години; у
   тріалі 60 000.
9. API Dashboard: **Setup → Developer Hub → APIs and SDKs → CRM API**; статистика із затримкою 15
   хвилин.
10. Кожну зміну підтверджуй окремим GET; перевіряй код, структуру, статуси, значення.
11. Записи з API запускають автоматизацію CRM.
12. Токени і секрети не потрапляють на скриншоти і в експортовані файли.

# Розв'язки

**21.1.** Метод — PUT (оновлення). API domain — `https://www.zohoapis.eu` (EU). Версія — `v8`. Модуль —
`Leads`. ID — `4150868000001944196`. Заголовки: `Authorization: Zoho-oauthtoken ...` (токен
доступу) і `Content-Type: application/json` (формат тіла). Тіло: масив `data` з одним об'єктом, що
змінює `Lead_Status` на `Contacted`. Для США змінюється лише домен: `https://www.zohoapis.com`;
токени теж мали б бути отримані через `accounts.zoho.com`.

**21.2.**

| # | очікуваний код | що ще перевірити |
|---|---|---|
| 1 | 201 (таблиця кодів: record added); якщо прийде 200 — зафіксуй фактичний | у кожного з трьох елементів `status` = `success` і є `details.id`; GET підтверджує дані |
| 2 | 207 Multi-Status | два елементи з `success`, один з помилкою `MANDATORY_NOT_FOUND`; порядок відповіді = порядок вхідних записів |
| 3 | 204 No Content (або порожній результат) | помилки немає — «не знайдено» не є збоєм |
| 4 | 401 | зрозумілий `code` і `message`; після оновлення токена запит проходить |
| 5 | 403 (`NO_PERMISSION`) | запис не видалено — перевір GET |
| 6 | 429 | після відновлення ліміту запити проходять |
| 7 | за документацією — 400 `INVALID_MODULE` («The module name given is invalid»); зафіксуй фактичний код (для невірної адреси документація описує ще `INVALID_URL_PATTERN`, 404) | не очікуй 404 «за звичкою»: код визначає документація ендпоінта, а не загальна інтуїція |

**21.3.** Grant token видає API Console (для Self Client — вкладка Generate Code) після згоди на
скоупи; він одноразовий і живе хвилини (за замовчуванням 3; для Self Client у **Code expiry
duration** можна обрати до 10);
використовується один раз — для обміну на токени. Access token і refresh token видає Zoho Accounts
(`/oauth/v2/token`) в обмін на grant token. Access token живе годину і йде в заголовку кожного
запиту. Refresh token не спливає, доки його не відкличуть; ним отримують нові access token. Через
61 хвилину запити почнуть отримувати 401 — треба оновити access token запитом з
`grant_type=refresh_token`. Refresh token на скриншоті — витік: відклич його (`POST
https://accounts.zoho.eu/oauth/v2/token/revoke?token=...`), видали скриншот, згенеруй нові токени.

**21.4.** а) `ZohoCRM.modules.leads.READ`; б) `ZohoCRM.modules.deals.CREATE,ZohoCRM.modules.deals.UPDATE`;
в) `ZohoCRM.coql.READ,ZohoCRM.modules.deals.READ`; г) `ZohoCRM.settings.fields.READ`;
д) `ZohoCRM.modules.leads.READ,ZohoSearch.securesearch.READ`; е) `ZohoCRM.settings.tags.CREATE`.

**21.5.** 10 × 1 = 10; 3 ліди — 1; 30 лідів — 3 (1 кредит за кожні 10 записів); конвертація — 5;
чотири COQL з `limit 10` — 4; COQL з `limit 500` — 2; Bulk Read — 50. Разом **75** кредитів, це
0,125% від 60 000. Помилковий цикл із 1000 GET — ще 1000 кредитів: небагато для ліміту, але в
Dashboard це помітний сплеск, а важкі виклики в циклі (Bulk Read) витратили б 50 000 — майже весь
добовий ліміт.

**21.6.** Вкладки: Dashboard і API names (Help — посилання праворуч, над вкладками — перемикач
CRM API / SDKs). Віджети: API Credits Usage, Configure Notification, Total API Credits Consumed,
Integration Task Credits, Versions, Access Points, Credits By Module, Credits By
Applications/Functions, Prolific API Users, API Usage Pattern. Total API Credits Consumed показує
«витрачено / 60000». У вікні API Usage Notification Configuration у трьох полях Credits Threshold
percentage for notification заміни 100, 90, 80 на 60, 80, 95, залиш Notification Type — Email (за
бажанням додай In Product) і натисни **Save**. Скриншоти: Dashboard цілком і вікно сповіщень після
збереження.

**21.7.** `First_Name`, `Last_Name`, `Company`, `Email`, `Phone`, `Lead_Source`, `Lead_Status`,
`Description`, `Annual_Revenue`. Для створення ліда в тілі можуть бути всі ці ключі; системно
обов'язковий лише `Last_Name`, решта — за потребою і за правилами твого макета.

**21.8.** Очікування — помилка авторизації, найімовірніше 401 (за таблицею кодів 401 — помилка
авторизації); точний `code` у тілі запиши сам — саме для цього тест. Корисність: так ти бачиш, як
API реагує на запит без токена, і маєш еталон для негативного тесту «інтеграція без авторизації не
отримує даних». Заодно перевіряєш, що Postman і мережа працюють, ще до роботи з токенами.

**21.9.**
   1. Домен `.com` для тріалу в EU — запит піде в інший дата-центр, а за документацією кожен
      дата-центр тримає дані лише своїх користувачів; очікуй помилку авторизації. Потрібен
      `https://www.zohoapis.eu`.
   2. Немає `fields` — у v8 для списку записів це обов'язковий параметр: `REQUIRED_PARAM_MISSING`.
   3. Немає префікса: документація CRM API v8 вимагає `Authorization: Zoho-oauthtoken 1000.xxxx`.
      Очікуй помилку авторизації (401) і запиши фактичний `code`.
   4. Дві помилки: підпис `Last Name` замість API-імені `Last_Name` і тіло без масиву `data`.
      Правильно: `{"data": [{"Last_Name": "Mueller", "Company": "Deutsche Tech GmbH"}]}`.
   5. `Lead` — невірне API-ім'я модуля; потрібно `Leads` (за документацією — `INVALID_MODULE`).
   6. `Description` — багаторядкове поле, у критеріях COQL його використовувати не можна.
   7. `word` коротший за два символи — `INVALID_DATA` (пошук вимагає щонайменше двох символів).

**21.10.** Створено два ліди: перший і третій — у них `status` = `success` і є ID. Другий вхідний
запис не пройшов: відповідь зберігає порядок вхідних записів, і другий елемент має `status` =
`error` з кодом `MANDATORY_NOT_FOUND` — у другого запису бракувало обов'язкового поля (для Leads —
`Last_Name`). Якщо тест очікував три створені ліди — Fail. У звіті: HTTP 207, два ID, помилка
другого запису з кодом і повідомленням, які дані надсилались; окремо — чи це дефект даних тесту
(забули поле) чи продукту (поле було, а API його не прийняв).

**21.11.** Приклад набору:

| TC ID | Request data | Expected Result |
|---|---|---|
| API-LEAD-01 | один лід лише з `Last_Name` | 201/200; `status` = `success`; ID є; GET повертає значення |
| API-LEAD-02 | без `Last_Name` | 400 `MANDATORY_NOT_FOUND`; запис не створено |
| API-LEAD-03 | три ліди, один без `Last_Name` | 207; два `success`, один помилка; порядок збережено |
| API-LEAD-04 | `Email` = `not-an-email` | помилка з `code` і `message` (фактичний код зафіксуй); запис не створено |
| API-LEAD-05 | `Last_Name` довжиною 256 символів | помилка `INVALID_DATA` (довжина понад ліміт) |
| API-LEAD-06 | 101 запис в одному запиті | помилка ліміту (до 100 записів); нічого не створено або фактичну поведінку описано |
| API-LEAD-07 | коректний лід без заголовка Authorization | 401; запис не створено |
| API-LEAD-08 | токен без скоупу модулів | 401 `OAUTH_SCOPE_MISMATCH` |
| API-LEAD-09 | лід, що відповідає критеріям наявного workflow | запис створено, і workflow спрацював (видно в CRM) |
| API-LEAD-10 | той самий лід із `"trigger": []` | запис створено, workflow не спрацював |

**21.12.** а) Search Records з `email=` — пошук в одному модулі за email (або COQL з `where Email =
'...'`). б) COQL з `COUNT` і `GROUP BY Stage` — агрегати в одному виклику. в) Bulk Read — сотні
тисяч записів асинхронно, одним файлом, до 200 000 за завдання. г) COQL з JOIN через lookup:
`select Last_Name, Account_Name.Account_Name from Contacts ...`. д) COQL або Get Records за ID —
пошук може повернути 204 через затримку індексації, а COQL такої затримки не має.

**21.13.** Тест 1 (equals як «містить»): створи ліди з Company `Nova` і `Nova Labs`, виконай
`GET /crm/v8/Leads/search?criteria=(Company:equals:Nova)`. За документацією повернуться обидва. Тест
2 (індексація): створи лід з унікальним email і одразу виконай `search?email=...`; зафіксуй, чи
прийшов 204; повтори через хвилину; паралельно зроби COQL-запит за тим самим email — він має
знайти запис одразу. Для автотестів це важливо: перевірка «знайдено рівно один запис» через Search
може давати хибні збої (зайві збіги) і нестабільність (204 одразу після створення). Точну перевірку
роблять через Get Records за ID або COQL, а пошук тестують з урахуванням цих правил.
