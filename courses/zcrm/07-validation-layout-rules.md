# Урок 7. Правила layout і правила валідації

*Після цього уроку ти налаштовуєш правило layout, яке змінює форму на льоту, і правило валідації,
яке не пускає в CRM неправильне значення, і знаєш, через які канали обидва правила обходяться.
Для QA тут головне: «у формі працює» ще не означає «в даних чисто». А ще ти зробиш шаблон
дефекту саме для помилок конфігурації — такий, щоб розробник відтворив їх з першого разу.*

---

## 7.1. Три рівні контролю введення

Керувати тим, що людина вводить, у Zoho CRM можна на трьох рівнях:

| рівень | що робить | коли спрацьовує | де налаштовується |
|---|---|---|---|
| властивості поля | тип, обов'язковість, унікальність, дозволи | завжди, статично | редактор layout, **Settings** поля |
| **правило layout** (layout rule) | змінює форму залежно від введених значень: показує, ховає, робить обов'язковим або лише для читання, підставляє значення | поки людина працює з формою | **Layout Rules** модуля |
| **правило валідації** (validation rule) | перевіряє значення і блокує збереження або попереджає | при збереженні (або кнопкою перевірки поля) | **Validation Rules** модуля |

Різниця на прикладі продукту:

- «поле `Service Duration` видно лише для послуг» — це про **форму**: правило layout;
- «**Unit Price** не може бути від'ємною» — це про **значення**: правило валідації;
- «**Unit Price** обов'язкова завжди» — це властивість поля в layout.

Документ описує їх так: правила layout задають залежності й умовно показують або роблять
обов'язковими поля залежно від введеного; правила валідації не пускають у CRM невалідні дані,
перевіряючи обмеження на полях і показуючи помилки.

Обидва типи правил **прив'язані до layout**. Правило, створене для layout `QA Training`, не діє на
записи в **Standard**. Це найчастіша причина «правило не працює».

## 7.2. Правила layout: будова

Правило layout складається з:

- **основного поля** (primary field) — поля, від значення якого все залежить, наприклад
  `Product Type`;
- **умови** — наприклад, `Product Type` is `Service`;
- однієї або кількох **дій**, які виконуються, коли умова справджується.

В одному правилі може бути кілька умов, а в умови — гілки з додатковими критеріями.

### Дії

За довідкою Zoho дії поділяються на дії з полями та інші:

| дія | що робить |
|---|---|
| **Show Fields** | показує поля лише тоді, коли умова справджується; в інших випадках вони сховані |
| **Set Mandatory Fields** | робить поля обов'язковими лише за умови |
| **Show Picklist Values** | звужує список значень за умови (значення, не згадані в дії, показуються завжди) |
| **Set Read Only Fields** | блокує редагування полів за умови |
| **Set Field Value** | підставляє значення; людина може його змінити, і система не поверне його сама |
| **Recommend Field Value** | пропонує значення підказкою; відхилена підказка лишається значком біля поля |
| **Show Message** | показує повідомлення біля поля |
| **Show Sections** / **Show Subforms** / **Show Related Lists** | показує секції, підформи, пов'язані списки за умови |
| **Show Buttons** / **Show Links** | показує кастомні кнопки, корисні посилання |
| **Verify Fields** | просить підтвердити важливі поля перед збереженням |

Для завдання потрібна **Show Fields**. Зверни увагу на логіку: ти не пишеш «інакше сховай». Поле,
згадане в **Show Fields**, сховане завжди, коли умова не справджується. «If Service — show, else
hide» — це одна дія.

### Де правило діє, а де — ні

Правила layout працюють на сторінках **створення**, **редагування** і **перегляду** запису. Довідка
перелічує ще кілька місць:

- у формі **Quick Create** виконуються лише **Show Fields** і **Set Mandatory Fields**;
- якщо поле, від якого залежить правило, змінюють прямо на сторінці запису, обов'язкові за правилом
  поля CRM запитує у спливному вікні;
- перетягування в Kanban теж перевіряє правила;
- правила працюють і при погодженні записів;
- у формі переходу процесу (Blueprint) виконується лише **Set Mandatory Fields**.

І головне для QA — де правило **не** працює:

- записи з **імпорту**, **вебформ** і сторінки **конвертації ліда** правил layout не проходять;
- через **API** виконується лише **Set Mandatory Fields**;
- **workflow**-оновлення поля, імпорт і API пишуть значення в обхід правила;
- основне поле правила з дією **Set Mandatory Fields** недоступне для масового оновлення;
- основні поля правил не можна змінювати макросом;
- **Set Read Only Fields** блокує поле лише на сторінках, де працюють правила: масове оновлення,
  імпорт, API й інтеграції можуть його змінити.

### Обмеження

- основним полем не може бути поле власника запису;
- правила не працюють з полями типів Auto Number, Lookup, User Lookup, Formula, File Upload,
  Multi Line;
- одне поле не можна для однієї умови поставити і в **Set Mandatory Fields**, і в
  **Set Read Only Fields**;
- ліміти: до 10 правил на layout, до 25 основних умов, до 5 гілок на умову, до 5 критеріїв на гілку,
  до 40 дій на гілку.

### Профілі й попередній перегляд

- Правило можна обмежити профілями: наприклад, поле лише для читання для одного профілю і
  редаговане для решти. Якщо профілі не обирати, правило, очікувано, діє для всіх (довідка цього
  прямо не пише; підтвердить тест під User C).
- Після збереження правило можна переглянути прямо на сторінці налаштування (**Interactive
  Preview** у довідці): обираєш умову — бачиш, що вона ховає, показує чи робить обов'язковим; можна
  перемикати профіль. Це зручно для налагодження, але, як і будь-який попередній перегляд, не
  замінює перевірки під реальним користувачем.

## 7.3. Правила валідації: будова

Правило валідації перевіряє **одне поле** — основне (primary field) — і працює в межах **одного
layout**. Для одного поля в різних layouts можуть бути різні правила.

Частини правила за довідкою Zoho:

- **Primary condition** — умова на основне поле, наприклад `Unit Price` `<` `0`. До 10 основних
  умов у правилі.
- **Execute rule** — як читати умову. Можна описати **погане** значення і показати помилку, коли
  умова справджується (у довідці — **When criteria is met**), або описати **добре** значення і
  показати помилку, коли умова не справджується.
- **Secondary condition** — до яких записів застосовувати: до всіх або лише до тих, що відповідають
  іншим полям (наприклад, лише для певного регіону). До 5 вторинних умов на основну, до 5 критеріїв
  у кожній. На кожну вторинну умову — власне повідомлення.
- **Validation type** — **Based on Criteria** (візуальний конструктор) або через функцію (для
  складної логіки).
- **Validate on** — **Save Only** (перевірка при збереженні; при цьому спрацьовують усі правила
  валідації цього layout) або **Field Verify and Save** (біля поля з'являється кнопка перевірки, і
  перевірка повторюється при збереженні).
- **Validation preference** — **Stop with error** (не дає зберегти) або **Allow by alert**
  (попереджає і зберігає після підтвердження). Довідка попереджає: **Allow by alert** вмикається
  поступово і може бути ще не доступний у твоїй організації. Цей вибір є лише для **Save Only**.
- **Error location** — **On primary field** (біля поля) або **Top of page** (угорі форми). Є лише
  для **Stop with error**.

### Де правило діє

За довідкою: створення, швидке створення, редагування, швидке редагування (на сторінці), конвертація
(одинична й масова), Kanban, копіювання налаштувань і пісочниця.

### Як правило обходять

Довідка чесно перелічує канали, де **оновлення поля має пріоритет над правилом** — значення
приймається без перевірки:

| канал | що відбувається |
|---|---|
| імпорт | значення з файлу записується |
| workflow | оновлення поля дією workflow записується |
| процес погодження | оновлення при погодженні чи відхиленні записується |
| Blueprint | оновлення в розділі після переходу записується; поки запис у процесі, перевірка процесу для того самого поля переважає правило валідації |
| API | оновлення через API записується |
| масове оновлення | основного поля правила немає серед полів масового оновлення |
| вебформа | запис, що порушує правило, іде на ручне погодження |

Окремо про **вторинні поля**: їх можна змінювати масовим оновленням, імпортом, API і workflow без
жодної перевірки. Якщо правило каже «знижка не більше 15% для України», а хтось масово поміняв
регіон — знижки, що вже були, правилу вже не відповідають, і CRM це не зупинить.

### Два застереження з довідки

1. У відповідях на часті питання довідка пише, що правило валідації **не виконується, якщо поле
   для будь-якого профілю стоїть лише для читання**. Перевіряй дозволи на поле, коли правило
   «мовчить».
2. Там само сказано, що кастомні поля валідувати не можна, хоча основна стаття такого обмеження не
   згадує. Тому для першого правила ми беремо стандартне поле. Якщо в списку полів вікна створення
   правила є твоє кастомне поле — перевір, чи правило справді спрацьовує.

Правила не підтримуються для полів типів Multi-select Lookup, Multi-select Pick List,
Multi-user, Formula, Auto Number, Image Upload і Multi-line.

## 7.4. Покроково: A9, частина 1 — правило валідації

Завдання A9 з документа: створити одне правило валідації (наприклад, заборонити від'ємну знижку
або вимагати мінімальний формат) і перевірити поведінку помилки; створити одне правило layout
(наприклад, «якщо Product Type = Service, показати поля Service Duration, інакше сховати») і
перевірити динамічні зміни інтерфейсу; здати шаблон звіту про дефект, пристосований до дефектів
конфігурації (модуль, layout, профіль, кроки, очікуване / фактичне, докази).

Працюємо в модулі **Products**, у layout `QA Training`. Якщо такого layout немає, створи його:
**Setup → Customization → Modules and Fields** → **Products** → **Create New Layout** → назва
`QA Training`, клон зі **Standard** → **Save Layout** → доступ профілям `Administrator`, `Standard`
і обмеженому профілю, під яким тестуєш (наприклад, `Junior Sales Restricted`, призначений User C).

«Заборонити від'ємну знижку» з документа — приклад. У **Products** стандартного поля знижки немає,
тож ідею «не може бути від'ємним» застосуємо до стандартного поля **Unit Price** (гроші,
Currency).

### Крок 1. Відкрити правила валідації

**Setup → Customization → Modules and Fields** → **Products** → вкладка **Validation Rules** →
**Create New Validation Rule**. Інший шлях — у бічній панелі наведи курсор на **Products** → **⋯** →
**Validation Rules**.

### Крок 2. Вікно створення

У вікні **Create Validation Rule**:

| параметр | значення |
|---|---|
| layout | `QA Training` |
| поле | **Unit Price** |
| **Validation type** | **Based on Criteria** |
| **Validate on** | **Save Only** |

**Next**.

### Крок 3. Умова і повідомлення

1. Основна умова: **Unit Price** `<` `0` → **Done**. Біля суми стоїть префікс валюти `UAH`,
   як і в інших конструкторах умов цього тріалу.
2. **Execute rule**: **When criteria is met** — ми описали погане значення.
3. Повідомлення: `Unit Price cannot be negative.`
4. Вторинну умову не чіпай: правило для всіх записів.
5. Якщо є вибір: **Stop with error**, **On primary field**.
6. **Save** угорі праворуч.

**Що побачиш:** правило в списку **Validation Rules** модуля **Products** з увімкненим перемикачем
**Status**.

### Крок 4. Швидка перевірка

Під адміністратором: **Products** → створення в `QA Training` → **Product Name** `A9-VR-01`,
`Warranty Months` `12` (якщо таке обов'язкове поле є в layout), **Unit Price** `-1` → **Save**.

**Що побачиш:** запис не зберігається, біля **Unit Price** з'являється `Unit Price cannot be
negative.` Заміни на `0` — зберігається.

Повний набір тестів — у розділі 7.6.

**Відкотити легко:** правило вимикається перемикачем **Status** (підтвердження **Deactivate now**)
і видаляється значком кошика (**Yes, Delete**).

## 7.5. Покроково: A9, частина 2 — правило layout

### Крок 1. Поля

У layout `QA Training` модуля **Products** додай з лотка **New Fields** три кастомні поля
(**Number** — ціле число, у довідці цей тип називається Integer):

| **Field Label** | тип | значення |
|---|---|---|
| `Product Type` | **Pick List** | `Goods`, `Service` |
| `Service Duration` | **Number** | — |
| `Service Duration Unit` | **Pick List** | `Days`, `Months` |

Значення списку додаються у вікні властивостей Pick List (довідка: значком «плюс» біля значення).
**Save Layout**.

### Крок 2. Нове правило

**Setup → Customization → Modules and Fields** → **Products** → вкладка **Layout Rules** (поруч із
**Layouts** і **Validation Rules**, на рівні модуля, а не всередині редактора layout) → **New
Layout Rule**. Список на цій вкладці показує правила всіх layouts модуля разом, з фільтром
**All Layouts** і колонкою **Layout Name**.

У вікні **New Layout Rule** поле **Choose layout** за замовчуванням показує **Standard** — онови
на `QA Training`, інакше правило прив'яжеться не до того layout:

| параметр | значення |
|---|---|
| назва | `Show service duration` |
| опис | `A9: service fields only for services` |
| основне поле | `Product Type` |
| умова | `Product Type` is `Service` |

**Next**.

### Крок 3. Дія

1. На сторінці правила умова вже заповнена → **Trigger an action**.
2. Обери **Show Fields**.
3. У правій панелі **Create Action** обери `Service Duration` і `Service Duration Unit`.
4. Збережи дію і правило.

Профілі не обмежуй — правило має діяти для всіх.

**Що побачиш:** правило в списку правил layout `QA Training`. Перевір його в попередньому перегляді
на сторінці налаштування: для умови `Service` обидва поля показуються.

### Крок 4. Швидка перевірка

**Products** → створення в `QA Training`:

1. `Product Type` порожній — полів `Service Duration` і `Service Duration Unit` не видно.
2. Обери `Service` — обидва поля з'являються.
3. Обери `Goods` — зникають.

**Що побачиш:** поля з'являються і зникають одразу, без збереження. Що відбувається зі значенням,
уже введеним у `Service Duration`, коли поле знову ховається, — саме це перевіряє один з
найцікавіших тестів розділу 7.6.

## 7.6. Як це тестувати

### Правило валідації: класи і межі

Число ділиться на класи: від'ємні (помилка), нуль і додатні (норма). Тести ставлять на межі і в
середину класів:

| значення **Unit Price** | очікувано |
|---|---|
| `-100` | помилка `Unit Price cannot be negative.` |
| `-0.01` | помилка (найменше від'ємне для двох знаків після коми) |
| `0` | зберігається (межа: нуль не від'ємний) |
| `0.01` | зберігається |
| `100` | зберігається |
| порожньо | якщо **Unit Price** у `QA Training` обов'язкова — помилка обов'язкового поля, а не правила валідації; якщо ні — дослідницький тест: запиши, чи вважає правило порожнє значення від'ємним |

### Правило валідації: канали і контекст

- **редагування:** наявний продукт змінити на `-5` → не зберігається;
- **зміна прямо на сторінці запису** (швидке редагування) → не зберігається;
- **інший layout:** у **Standard** `-5` → **зберігається**, бо правило створене для `QA Training`.
  Це очікувано, але саме так у реальних проєктах «протікають» погані дані;
- **інший профіль:** під User C (`Junior Sales Restricted`) і User B (`Standard`) правило діє
  так само;
- **масове оновлення:** **Unit Price** не має бути серед полів масового оновлення;
- **імпорт / API / workflow:** за довідкою, значення запишеться в обхід правила. Перевіряти це в
  межах A9 не обов'язково, але в звіті треба прямо написати, що правило захищає лише ручне введення,
  і запропонувати контроль: наприклад, подання продуктів з умовою **Unit Price** `<` `0`, яке мусить
  бути порожнім.

### Правило layout: стани і переходи між ними

Форма має три стани `Product Type`: порожньо, `Goods`, `Service`. Тести покривають і стани, і
переходи:

| тест | очікувано |
|---|---|
| створення, `Product Type` порожній | поля сервісу сховані |
| порожньо → `Service` | поля з'являються |
| `Service` → `Goods` | поля ховаються |
| `Goods` → `Service` | поля з'являються знову |
| `Service`, введено `12` `Months`, потім `Goods`, **Save** | дослідницький тест: чи збереглись значення прихованих полів? Сторінка запису їх не покаже — правило ховає поля і для адміністратора. Додай `Service Duration` і `Service Duration Unit` колонками в список продуктів (правила layout діють на сторінках створення, редагування і перегляду запису) і подивись значення там |
| перегляд запису з `Service` | поля видно |
| перегляд запису з `Goods` | полів не видно |
| редагування: `Goods` → `Service` | поля з'являються |
| під User C | поведінка та сама (правило без обмеження профілів) |

Результат «прихованого, але збереженого значення» — не очевидний і для бізнесу важливий: звіт по
тривалості сервісу може порахувати тривалість у товару. Хоч би що показав тест, запиши це
дослівно.

### Правило layout: що правило не гарантує

Правило layout — про форму, а не про дані. Імпорт, вебформи, конвертація ліда, workflow і API його
не проходять. Тому «поле `Service Duration` заповнене лише для послуг» правило layout не гарантує:
товар з тривалістю можна завантажити імпортом.

### Шаблон дефекту конфігурації

Дефект конфігурації відрізняється від дефекту коду: код правильний, а налаштування — ні (або
навпаки, налаштування правильне, а продукт поводиться не так, як описано). Щоб його відтворили,
звіт має описувати не лише кроки, а й **що саме налаштовано і де**. Мінімальний набір полів з
документа: модуль, layout, профіль, кроки, очікуване / фактичне, докази. Решта полів — те, без чого
дефект конфігурації не відтворити.

| поле шаблону | що писати | навіщо |
|---|---|---|
| ID, Title | коротко: об'єкт + поведінка | пошук і дублікати |
| Environment | production чи пісочниця, організація, дата й час | пісочниця — знімок, налаштування там можуть відрізнятися |
| Module | модуль | — |
| Layout | layout, у якому створювався або редагувався запис | правила прив'язані до layout |
| Profile / Role / User | під ким відтворено | поведінка залежить від профілю і ролі |
| Configuration object | тип (validation rule, layout rule, field property, permission), назва, стан (активне?) | що саме налаштовано |
| Configuration snapshot | знімок екрана налаштування: умова, дія, повідомлення | розробник бачить налаштування, не заходячи в систему |
| Channel | створення, редагування, швидке редагування, Quick Create, імпорт, API, масове оновлення | багато правил діють лише в частині каналів |
| Preconditions / Test data | запис, значення полів | — |
| Steps | нумеровані кроки | — |
| Expected result + source | що мало статися і на чому базується очікування: вимога, документ, стаття довідки | відділяє дефект від неправильного очікування |
| Actual result | що сталося, тексти повідомлень дослівно | — |
| Evidence | знімки з видимим користувачем і layout, відео для динамічних змін | — |
| Frequency | завжди / іноді / один раз | — |
| Severity | вплив на дані й процес | — |
| Classification | помилка налаштування / дефект продукту / задокументоване обмеження / середовище | визначає, хто виправляє |

## 7.7. Типові помилки

**1. Правило не в тому layout.** Правило створене для `QA Training`, а тестуєш у **Standard** — «не
працює». Обидва типи правил прив'язані до layout.

**2. Інвертована умова.** Написав умову як «добре значення» (`Unit Price` `>=` `0`) і поставив
**When criteria is met** — тепер помилку отримують усі нормальні ціни.

**3. «Інакше сховай» окремою дією.** Для **Show Fields** окрема дія «сховати» не потрібна: поля
сховані завжди, поки умова не справджується.

**4. Поле непідтримуваного типу.** Правило layout на Lookup чи Multi Line, правило валідації на
Multi-select Pick List — поля немає у списку або правило не спрацює.

**5. Тестування лише у формі.** Правило перевірене руками, а імпорт і workflow пишуть у поле в
обхід. У звіті про це ні слова.

**6. Поле лише для читання для якогось профілю.** За довідкою, правило валідації тоді не
виконується. Шукаєш дефект у правилі, а причина — у дозволах поля.

**7. Порожнє поле як тест валідації.** Порожня обов'язкова **Unit Price** дає помилку
обов'язковості, а не правила. Це різні механізми й різні тести.

**8. Не записав тексти повідомлень.** «Показалась помилка» — не результат. Результат — дослівний
текст, місце і те, що запис не зберігся.

**9. Шаблон дефекту без налаштування.** Кроки є, а знімка правила немає — розробник не знає, що
саме налаштовано, і відтворює на іншому layout.

### Симптом → причина

| симптом | найімовірніша причина |
|---|---|
| від'ємна ціна зберігається | запис у іншому layout; правило вимкнене (**Status**); умова інвертована; поле лише для читання для якогось профілю |
| помилку отримує навіть `100` | умова описує добре значення, а **Execute rule** — «коли справджується» |
| повідомлення вгорі форми, а не біля поля | **Error location** — **Top of page** |
| немає вибору **Allow by alert** | функція ще не ввімкнена в організації або обрано **Field Verify and Save** |
| поля немає у списку при створенні правила валідації | тип поля не підтримується; поле не з цього layout |
| **Unit Price** немає серед полів масового оновлення | це основне поле правила валідації — так задумано |
| імпортований продукт з від'ємною ціною | імпорт має пріоритет над правилом — задокументована межа |
| поля сервісу не з'являються при `Service` | правило в іншому layout; умова на інше значення; поля не додано в дію; поля не в layout |
| поля сервісу видно завжди | поля не в дії **Show Fields**, а просто в layout; правило вимкнене |
| основного поля немає у списку для правила layout | тип поля не підтримується або це поле власника |
| правило layout працює у формі, але в імпортованих записах поля заповнені «не для того» | імпорт правил layout не проходить |
| у Quick Create частина дій не працює | там виконуються лише **Show Fields** і **Set Mandatory Fields** |

## 7.8. Що варто запам'ятати

1. Правило layout — про форму, правило валідації — про значення.
2. Обидва правила прив'язані до layout; в іншому layout вони не діють.
3. **Show Fields** ховає поля завжди, поки умова не справджується; окремого «інакше сховай» не треба.
4. Правила layout не проходять імпорт, вебформи й конвертацію ліда; через API працює лише
   **Set Mandatory Fields**.
5. Правило валідації: основне поле, основні умови, вторинні умови з власними повідомленнями.
6. **Execute rule** визначає, що описує умова: погане значення чи добре.
7. Імпорт, workflow, погодження, Blueprint і API записують значення в обхід правила валідації.
8. Ручний тест правила не гарантує чистих даних; пропонуй контроль (подання з поганими значеннями).
9. Дефект конфігурації без знімка налаштування і без layout, профілю та каналу не відтворити.
