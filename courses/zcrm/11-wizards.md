# Урок 11. Wizards: довга форма як кілька екранів

*Після уроку ти ділиш довгу форму створення акаунта на три екрани, додаєш умовні правила між
екранами і чернетки, а потім перевіряєш усе це як QA: від звичайного проходження до навмисно
зламаної схеми, яку Zoho має відмовитися зберегти. Wizard — це форма, тож і дефекти тут «формені»:
поле не з'явилось, поле не заблокувалось, запис зберігся не туди.*

---

## 11.1. Що таке wizard і навіщо він

**Wizard** ділить довгу форму створення запису на послідовність невеликих екранів. Замість однієї
сторінки на п'ятдесят полів користувач бачить кілька екранів і кнопки, що ведуть від одного до
іншого, аж до кнопки збереження.

Навіщо це бізнесу:

- **менше перевантаження** — на екрані тільки те, що потрібно зараз;
- **точніші дані** — покроковий шлях зменшує пропущені й помилкові поля;
- **чернетки** — частково заповнену форму можна зберегти і повернутися пізніше; це критично для
  довгих заявок, коли людині треба піти по дані;
- **динамічна логіка** — умовні правила показують, роблять обов'язковими чи блокують поля на
  наступних екранах залежно від того, що введено раніше.

Коли wizard доречний: дані треба збирати в певному порядку (спершу загальне, потім фінанси, потім
юридичне); кроків багато; користувачі часто зупиняються посеред заповнення. Приклади: онбординг
корпоративного клієнта, вступ до університету, страхова заява.

Де живе: **Setup → Customization → Wizards** → **Create Wizard**. Створювати, редагувати й видаляти
wizards може користувач з дозволом **Modules Customization**. Wizard працює в стандартних і власних
модулях; серед підтримуваних — Leads, Contacts, Accounts, Deals, Cases, Campaigns, власні й
командні модулі.

Чого wizard **не** робить:

- не створює записи через вебформи, імпорт чи API — тільки ручне створення в CRM;
- не створює поля: він розкладає по екранах поля вже наявного layout;
- не керує процесом після створення запису — це робота blueprint.

Поруч стоять два схожі інструменти. **Layout rules** показують і роблять обов'язковими поля на
звичайній формі; у wizard свої **conditional rules**, тож layout rules там не потрібні, а от
**validation rules** працюють і в wizard. **Kiosk Studio** — ширший конструктор інтерфейсних
сценаріїв: віджет, який ставлять на Home, у список, на сторінку запису, і який не лише вводить дані,
а й шукає записи, оновлює кілька модулів, запускає дії. Wizard же сфокусований на одному: зручно і
правильно створити запис.

## 11.2. З чого складається wizard

Wizard будується поверх layout: створюючи його, ти обираєш модуль і layout (до чотирьох), і всі
поля, розділи та subforms цього layout з'являються у вкладці **Fields** дизайнера.

**Екран** (screen) має **Screen name** і **Segment Title**. Перший екран — домашній (з іконкою
будиночка); зробити домашнім інший екран можна з меню екрана.

**Fields.** Поля перетягуєш з вкладки **Fields** на екран. Обов'язкові поля — системні й ті, що
зробили обов'язковими в layout, — показані там окремим списком, щоб їх не загубити. Там само
вмикається фото запису і порядок переходу між полями клавішею Tab.

**Components:**

| компонент | для чого | ліміт на екран |
|---|---|---|
| Text | інструкція, попередження, скрипт розмови; підтримує merge fields | до 5 |
| Widget | обмін даними з віджетом | 1 |
| Query | пошук запису за полем і дії за результатом | 1 |
| Section | групує поля; умовне правило може показати чи сховати весь розділ | до 10 |

**Кнопки.** До 10 на екран, додаються через **+ Button** → **Button** або **Custom Button**. У
звичайної кнопки:

- **Button Name**;
- призначення: або **веде на екран** (перетягни курсор від кнопки на полотно — з'явиться новий
  екран; або клікни **Link to screen** над кнопкою), або **зберігає запис** — прапорець **Use this
  button to save the record**. Від кнопки збереження далі екранів не буває: це кінець шляху;
- вкладка **Visibility**: **Always show**, **Hide** або **Disable**, для двох останніх — **Set
  criteria** (наприклад, Next вимкнений, поки не заповнено email);
- вкладка **Style** — форма і колір;
- вкладка **Action** — дії на клік: email-сповіщення, webhook, власні дії;
- для кнопки збереження — підсумковий екран перед збереженням і повідомлення-підтвердження.

**Custom Button** викликає функцію, URL чи вебвкладку. Вона може зберігати запис, але не може вести
на екран. Для custom button дій на кшталт email чи webhook немає: її поведінку визначає функція.

Зайвий зв'язок між екранами видаляють правим кліком по лінії → **Delete Path**. Кнопки дизайнера:
**Save Wizard** — зберегти, **Discard Changes** — викинути всі зміни, **Permissions** — які
профілі бачать wizard.

## 11.3. Правила схеми: шлях без петель і повторів

Wizard — це граф: екрани — вузли, кнопки — ребра. Zoho зберігає лише коректний граф:

- кожен екран досяжний, і з кожного є вихід: кнопка на інший екран або кнопка збереження;
- кожна кнопка або веде на екран, або зберігає запис;
- на шляху немає петель — жоден шлях не повертається на екран, де вже був;
- одне поле не зустрічається двічі на одному шляху (на різних гілках — можна);
- усі обов'язкові поля розставлені по екранах, а кнопка збереження стоїть після них.

Якщо щось не так, **Save Wizard** покаже помилку:

| помилка | що означає |
|---|---|
| Orphan screens | екран не з'єднаний з іншими |
| Save button not valid | кнопка збереження стоїть раніше, ніж усі системні обов'язкові поля |
| Invalid buttons | кнопка не зберігає запис і не веде на екран |
| No option to save the record | з екрана немає кнопки збереження |
| Looping is not allowed | шлях починається і закінчується на одному екрані, наприклад 1 → 2 → 3 → 1; у тріалі дизайнер ловить це ще раніше — не дає домалювати таке з'єднання й одразу пише "Sorry, the connection will create a loop in the path", тож до Save Wizard справа зазвичай не доходить |
| Save button missing | у wizard немає кнопки збереження |
| Empty wizard | немає жодного екрана |
| Duplicate name | wizard з такою назвою вже є |
| Mandatory Fields missing | на екранах бракує обов'язкових полів |
| Node has no save or transition | з екрана немає ні збереження, ні переходу |
| Field [field name] is repeated | поле трапляється двічі на одному шляху |

Zoho частину цього лагодить сам: сирітські екрани можна видалити просто з повідомлення (разом з ними
зникають умовні правила, що спиралися на їхні поля), невалідні кнопки він пропонує видалити, а
для «немає збереження» — створити кнопку збереження.

## 11.4. Conditional rules

Умовне правило — це умова плюс дії. Налаштовується на конкретному екрані: посилання **Set up
conditional rule** → **+Create Conditional Rule** → вікно **Conditional Rule**:

1. **Коли застосовувати**: **Create and Edit**, **Create** або **Edit**. Так правило не
   перераховується там, де не треба (скажімо, при кожному редагуванні запису).
2. **Умова**: поле, оператор, значення. У списку полів є поля і цього екрана, і інших — отже,
   екран 2 може реагувати на те, що введено на екрані 1. Але **дії застосовуються тільки до
   екрана, на якому стоїть правило.**
3. **Дії:**

   | дія | що робить |
   |---|---|
   | Show fields | показує поля, коли умова виконана; що поза умовою вони приховані, очікує завдання, але довідка прямо цього не пише — перевір тестом з іншим значенням |
   | Set Mandatory Fields | робить поля обов'язковими |
   | Set Value | ставить значення (крім системних обов'язкових полів) |
   | Set Lock | блокує поле від редагування; можна дозволити редагування окремим профілям |
   | Show subform, text component, widget | показує subform, текст або віджет |

Кілька тонкощів з довідки, які варто знати до тесту:

- значення, поставлене правилом, важливіше за введене вручну;
- поле обов'язкове і водночас заблоковане, а значення немає — запис не збережеш;
- заблоковане поле не оновить і інше правило через Set Value (крім профілів, яким дозволено
  редагувати заблоковане);
- conditional rules важливіші за залежності picklist-полів (map dependency).

Ліміти залежать від редакції. Наприклад, в Enterprise — 10 правил на екран, 15 полів у Show fields
і в Set Mandatory Fields на правило, 10 заблокованих полів; в Ultimate — 20, 25 і 20.

## 11.5. Чернетки

Чернетка (draft) — частково заповнений запис, який ще не став записом модуля. Що про неї треба
знати:

- **де шукати**: у списку модуля іконка **More** → **Drafts**; вкладка Drafts з'являється
  автоматично, щойно хтось зберіг першу чернетку; у ній можна фільтрувати чернетки за критеріями;
- **як зберегти**: чернетку зберігають з екрана wizard. У мобільному застосунку довідка показує
  **Save as draft** у правому верхньому куті; для вебу вона місця кнопки не описує, хоча в
  інтерфейсі CRM є і напис «Save as draft», і повідомлення «Your record is being saved as draft» —
  де саме ця дія у вебі, перевір у тріалі. Мобільна довідка пише, що для чернетки досить заповнити
  обов'язкові поля, тобто без них чернетку не зберегти; завдання очікує того самого у вебі;
- **дії кнопок**: дії, налаштовані на кнопках екранів до моменту збереження чернетки, виконуються;
  чернетка зберігається і тоді, коли користувач натискає кнопку з дією (email, webhook, функція);
- **завершення**: відкриваєш чернетку, дозаповнюєш, зберігаєш — запис з'являється в списку модуля і
  зникає з Drafts;
- **обмеження**: чернетка живе без терміну, в approval не йде (це ще не запис), видно її в
  audit log;
- **небезпека**: деактивація wizard видаляє всі його чернетки, видалення wizard — теж, і це не
  відкотити. Спершу збери докази, потім вимикай.

## 11.6. Як користувач працює з wizard

**Створення запису.** У модулі натискаєш створення запису і в списку layouts обираєш свій wizard
(довідка описує перемикач layout на сторінці створення). Далі — екрани й кнопки.

**Wizard за замовчуванням.** Якщо профілю треба одразу відкривати wizard: **Setup → Customization →
Modules and Fields** → модуль → **More** → **Layouts** → **Layout and Type Assignment** → для
layout обрати тип (Regular layout або Wizard layout) і позначити layout за замовчуванням. Інші
layouts користувач усе одно може обрати вручну.

**Доступ.** Хто бачить wizard, задає **Permissions**. Але дозвіл на layout сильніший: без
доступу до layout wizard не відкриється, навіть якщо профілю дозволено wizard.

**Редагування.** Запис, створений через wizard, редагується в тому ж wizard layout. Тому правила з
тригером **Create and Edit** працюють і при редагуванні.

**Звітність.** У звіті можна відібрати записи, створені через wizard (у розширеному фільтрі звіту є
відповідна опція) — зручно для перевірки, що тестові записи створено саме так.

## 11.7. Покроково: будуємо wizard A14

Сценарій — онбординг корпоративного клієнта. Стандартну форму Accounts треба розбити на wizard з
трьох екранів, щоб зменшити помилки вводу і дати продавцям зберігати незавершені заявки чернетками.

**Перед стартом** відкрий layout Accounts і подивись, які поля в ньому обов'язкові. За
замовчуванням це **Account Name**. Якщо ти раніше зробив обов'язковим щось ще, wizard вимагатиме й
ці поля (помилка Mandatory Fields missing) — або постав їх на екран, або зніми обов'язковість.

1. **Setup → Customization → Wizards** → **Create Wizard**. На сторінці створення: **Wizard Name** —
   завдання його не задає, візьми назву сценарію, `Corporate Account Onboarding`; **Module** —
   Accounts; layout — твій layout Accounts; тип — **Blank**. **Next**.

   **Що побачиш:** дизайнер з порожнім полотном. Подвійний клік по полотну створює екран.
2. **Screen 1.**

   | параметр | значення |
   |---|---|
   | Screen name | `General Information` |
   | Segment Title | `Account Basics` |
   | поля | **Account Name** (системне обов'язкове), **Phone**, **Account Type** |
   | кнопка 1 | `Proceed to Financials` → веде на Screen 2 |

   Другої кнопки на цьому екрані не додавай: чернетку зберігає вбудована кнопка **Save as draft**,
   яку wizard показує сам (див. пункт 6 і розділ нижче) — окрему кнопку для цього створювати не
   треба і не можна (кнопка вміє тільки вести на екран або зберігати повноцінний запис).

3. **Screen 2.** Перетягни курсор від `Proceed to Financials` на полотно — з'явиться новий екран.

   | параметр | значення |
   |---|---|
   | Screen name | `Financial & Industry Details` |
   | Segment Title | `Business Demographics` |
   | компонент | Text угорі екрана: `Please verify all financial data against public records before proceeding.` |
   | поля | **Industry**, **Annual Revenue**, **Website** |
   | кнопка 1 | `Proceed to Location` → веде на Screen 3 |

4. **Conditional rules на Screen 2** (обидва — **Create and Edit**):

   | правило | умова | дії |
   |---|---|---|
   | Rule A (Dynamic Display) | **Account Type** (з Screen 1) = `Partner` | Show fields: **Website**; Set Mandatory Fields: **Website** |
   | Rule B (Data Integrity) | **Industry** = `Government/Military` | Set Lock: **Annual Revenue**; профілям-виняткам редагування не дозволяй |

   Значення беруться з picklist-ів тріалу: в Account Type є `Partner`, а в Industry —
   `Government/Military` (просто «Government» там немає).
5. **Screen 3.** Від `Proceed to Location` — новий екран.

   | параметр | значення |
   |---|---|
   | Screen name | `Location Details` |
   | Segment Title | `Headquarters Address` |
   | поля | **Billing Address** (складене поле: Country/Region, Flat/House No./Building/Apartment Name, Street Address, City, State/Province — у тріалі окремих полів Billing Street/City/State в переліку полів wizard немає, є тільки ціле **Billing Address**) |
   | кнопка 1 | `Submit Account`, прапорець **Use this button to save the record** |

6. **Save Wizard.** Жодне поле не повторюється між екранами, петель немає — wizard має зберегтися.
   Zoho відкриє діалог **`<назва wizard>` - Permission**: "Select whichever profile(s) can use this
   wizard to create records" — обери профілі (за замовчуванням уже стоїть твій, Administrator) →
   **Save**. Кнопка нагорі дизайнера, що відкриває цей діалог повторно, називається **Permissions**
   (не "Manage Permission" — так документ називає саму дію, а не підпис кнопки).

   **Що побачиш:** wizard у списку **Setup → Customization → Wizards**. Список фільтрується за
   статусом (активні й неактивні) — переконайся, що твій wizard активний.

**Чернетка — вбудована кнопка, а не та, що будуєш ти.** У дизайнері в кнопки лише два призначення:
вести на екран або зберігати запис — окремої дії «зберегти чернеткою» немає, і додавати для неї
кнопку не треба. У тріалі, під час проходження wizard, поряд з **Cancel** у
правому верхньому куті кожного екрана, завжди є кнопка **Save as draft** — вона там від початку,
незалежно від того, що намалював дизайнер. Клік по ній зберігає введене й переносить на список
**Drafts** цього модуля (заголовок сторінки — **Drafts**, з фільтром **Criteria** і лічильником
**Total Records**); запису при цьому в основному списку модуля немає. Тому в кроці 1 жодної другої
кнопки на Screen 1 не додавай.

## 11.8. Покроково: тестування за таблицею завдання

Коли wizard збережено, перейди в модуль Accounts як користувач: створення запису → у списку
layouts обери `Corporate Account Onboarding`.

**1. Позитивний, наскрізний.** Screen 1: `Account Name` = `ACME Onboarding 01`, Phone, Account Type
= `Customer` → **Proceed to Financials** → Screen 2: Industry, Annual Revenue (Website прихований) →
**Proceed to Location** → Screen 3: адреса → **Submit Account**.

**Що побачиш:** новий акаунт у списку Accounts; на сторінці запису всі введені значення.

**2. Чернетка.** Screen 1: `Account Name` = `ACME Draft 01`, Phone → натисни **Save as draft** (вона
стоїть поряд із **Cancel** у правому верхньому куті екрана, з'являється сама, без участі дизайнера).

**Що побачиш:** wizard закривається, відкривається список **Drafts** цього модуля з твоїм записом;
у звичайному списку Accounts цього запису немає. Скриншот списку
Drafts — частина здачі. Потім відкрий чернетку, заверши і збережи: запис переходить у список і
зникає з Drafts.

**3. Rule A.** Screen 1: Account Type = `Partner` → Screen 2.

**Що побачиш:** поле **Website** з'явилось і обов'язкове. Залиш його порожнім і натисни **Proceed to
Location** — помилка обов'язкового поля, далі не пускає. Запиши текст помилки.

**4. Rule B.** На Screen 2 обери Industry = `Government/Military`.

**Що побачиш:** **Annual Revenue** заблоковане: ввести з клавіатури нічого не можна.

**5. Негативний, Account Name.** Screen 1: Account Name порожнє → **Proceed to Financials**; потім
спроба зберегти чернетку з порожнім Account Name.

**6. Помилка конфігурації: петля.** Тестується в дизайнері. Додай на Screen 3 нову кнопку,

списку кнопок екрана → червоний хрестик) і збережи wizard знову.

Rule A і Rule B запиши на коротке відео — це окремий пункт здачі.

## 11.9. Як це тестувати

**Що може зламатися.** Правило стоїть не на тому екрані й не діє. Умова на `Government` замість
`Government/Military` — правило ніколи не спрацює. Тригер правила **Create** замість **Create and
Edit** — при редагуванні поле вже не блокується. Кнопка «чернетки» насправді зберігає запис.
Обов'язкове поле з layout не розставлене — wizard не зберігається. Wizard вимкнули, і чернетки
зникли разом з доказами.

**Карта перевірок понад таблицю завдання:**

## 11.10. Типові помилки

1. **Шукати, як створити поле в дизайнері.** Wizard бере поля з layout; нове поле спершу додай у
   layout.
2. **Поставити Rule A на Screen 1.** Дії правила діють тільки на своєму екрані; Website — на
   Screen 2, отже і правило там.
3. **Умова `Government`.** У тріалі значення — `Government/Military`.
4. **Тригер правила Create замість Create and Edit.** При редагуванні правило вже не працює.
5. **Будувати в дизайнері окрему кнопку «для чернетки».** Не треба: чернетку зберігає вбудована
   **Save as draft** поряд із **Cancel**, вона є завжди, сама по собі.
6. **Лишити кнопку без призначення.** Save Wizard відповідає Invalid buttons.
7. **Повторити поле на іншому екрані «для зручності».** На одному шляху це помилка
   `Field ... is repeated`.
8. **Забути про обов'язкові поля layout.** Wizard не зберігається з Mandatory Fields missing.
9. **Тестувати петлю через кнопку Submit Account.** Від кнопки збереження екранів не буває; для
   петлі потрібна окрема кнопка.
10. **Вимкнути wizard до скриншотів чернеток.** Деактивація видаляє всі чернетки.
11. **Шукати чернетку в списку Accounts.** Вона в **More → Drafts**, а не серед записів.

### Симптом → причина

| симптом | найімовірніша причина |
|---|---|

| Save Wizard: `Field [field name] is repeated` | поле стоїть на двох екранах одного шляху |
| Save Wizard: `Mandatory Fields missing` | обов'язкове поле layout не розставлене по екранах |
| Save Wizard: `Orphan screens` | екран не з'єднаний з іншими |
| Save Wizard: `Save button not valid` | кнопка збереження стоїть раніше, ніж усі системні обов'язкові поля |

| Website видно навіть для Customer | у правилі Set Mandatory без Show fields, а поле стоїть на екрані як звичайне |

| чернеток немає в More → Drafts | чернетку не збережено або wizard деактивували |

## 11.11. Що варто запам'ятати

1. Wizard ділить форму створення запису на екрани; поля бере з layout, нових не створює.
2. Кожна кнопка або веде на екран, або зберігає запис; від кнопки збереження екранів немає.
3. Wizard зберігається лише без петель, повторів полів на шляху, сирітських екранів і з усіма
   обов'язковими полями.
4. Conditional rule: тригер (Create and Edit / Create / Edit) + умова (з будь-якого екрана) + дії
   (тільки на своєму екрані).
5. Show fields показує поле за умовою і ховає його, поки умова не виконана; Set Lock блокує,
   з винятками для профілів.
6. Чернетку зберігає вбудована кнопка **Save as draft**, яка сама стоїть поряд із **Cancel** на
   кожному екрані готового wizard — дизайнер її не малює; знайти чернетку можна в **More → Drafts**
   модуля. Обов'язкові поля потрібні і для неї.
7. Деактивація чи видалення wizard знищує його чернетки.
8. Validation rules працюють і в wizard; layout rules там замінюють conditional rules.
9. Wizard працює тільки для ручного створення: вебформи, імпорт і API його оминають.
10. Розбіжність вимоги і продукту — теж результат тестування: її документують як аномалію.

**11.12.** Чекліст: Writer-документ з шістьма сценаріями таблиці завдання (кроки, дані, очікуване,
фактичне, статус) і додатковими кейсами; документ аномалій — точні тексти помилок і все неочікуване
з твого тріалу; відео Rule A і Rule B; скриншоти списку
Drafts з чернеткою. Wizard не вимикай і не видаляй, поки рецензент (ментор, тренер чи тімлід) не
прийняв здачу: чернетки зникнуть разом з ним. Усе — у WorkDrive, назва документів = назва завдання,
рецензенту — публічне посилання.
